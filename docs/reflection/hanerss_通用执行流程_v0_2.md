# Hanerss 通用执行流程

## 1. 文档定位

本文件把 Hanerss Skill Framework v0.1 中的注册表、矩阵坐标、工程模式、业务节点与技能模板，转换为一套可落地的通用运行流程。

本文件不重新定义认知基座、拓扑基座与工程模式基座，也不把某个具体业务流程写死到框架中。它只规定：

1. 一个已注册的工程模式或技能，怎样被编译为可执行工作流；
2. 一次任务怎样形成稳定、可追踪、可验收、可停止、可恢复的运行实例；
3. 感知、记忆、推理、行动、反思、协作、治理怎样在同一条运行链路中协同；
4. 链式、路由、并行、编排、循环、层级怎样作为执行拓扑被统一管理；
5. 执行流程怎样在没有可观测性探针时独立运行；
6. 执行流程怎样在接入工作流可观测性探针后，获得补全数据、风险信号与放行建议。

本文件对应的是“执行控制面”。关联的《Hanerss 工作流可观测性探针》对应的是“观测与证据补全面”。两者可以独立部署，也可以通过统一事件与引用标识交互运行。

## 2. 核心原则

### 2.1 注册表是源数据，运行实例是派生数据

认知、拓扑、工程模式、业务节点、技能、评估用例与治理规则仍然由各自注册表维护。

运行时不得把一次任务中的临时判断直接写回注册表。一次运行只能产生：

- 运行实例；
- 节点实例；
- 中间工件；
- 证据引用；
- 动作记录；
- 验收结果；
- 反思记录；
- 变更提案；
- 回滚与交接记录。

只有经过独立验证与治理流程后，运行结果才可能升级为新的工程模式、技能版本、经验或治理规则。

### 2.2 定义可以演进，引用必须稳定

框架中的基础对象以稳定 ID 被引用。执行时使用“定义 ID + 定义版本 + 运行实例 ID”三元组，避免定义更新后无法重放历史运行。

示例：

```text
技能定义：SKILL_0007@0.3.0
工作流运行：RUN_20260812_000042
节点实例：RUN_20260812_000042::WFNODE_0003::ATTEMPT_02
```

### 2.3 契约先于执行

模型输出的自然语言计划不能直接成为执行许可。进入执行前，至少要固定：

- 原始目标；
- 成功标准；
- 输入与上下文边界；
- 允许使用的工具；
- 允许改变的对象；
- 验收方式；
- 停止条件；
- 恢复方式；
- 人工接管条件。

### 2.4 叙事态与机械态分离

叙事态保存目标、进度、解释、摘要和模型认为已经发生的事情。

机械态保存业务对象 ID、版本、状态、参数绑定、外部回执、数据库事实、文件指纹、测试结果和权限记录。

必须遵守以下边界：

```text
叙事态可以描述机械态。
叙事态可以提出机械态变更建议。
叙事态不能直接覆盖机械态。
机械态只能通过受约束的业务接口、工具接口或事务接口改变。
```

### 2.5 输出、轨迹与环境终态分开验收

一次运行至少有三个不同对象：

1. 最终输出：智能体最后交付的文本、文件、代码或结构化结果；
2. 执行轨迹：任务实际经过的节点、工具、参数、决策、失败、重试和审批；
3. 环境终态：数据库、文件系统、远程服务、业务对象或代码仓库最终发生的真实变化。

“输出声称成功”不等于“轨迹合规”，也不等于“环境终态成功”。

### 2.6 发现问题、修改对象与决定放行是三种权限

检查器可以指出偏差，但不能因为发现问题就自动获得修改权限。

修订器可以生成新版本，但新版本不能继承旧版本的审批结果。

策略闸负责决定通过、拒绝、继续、回滚或转人工，不能由被审对象自行放行。

### 2.7 反思必须引入新的结果信号

在输入、工具和事实源完全没有变化时，仅让同一个模型再读一遍、再批评一遍或重新采样，不构成可靠的工程反思。

反思至少要获得一种新信号：

- 数据库事实；
- 外部回执；
- 测试结果；
- 业务规则；
- 受控回放结果；
- 针对性干预结果；
- 人工审核；
- 其他可复核证据。

### 2.8 先定义停止与恢复，再允许循环

任何循环、自动修复或长程执行都必须在开始前固定：

- 最大轮次；
- 最大时长；
- 最大费用；
- 无进展判定；
- 风险升级条件；
- 可回滚基线；
- 回滚验证；
- 人工接管入口。

### 2.9 风险决定证据厚度

内容润色、信息检索、代码修改、业务写入、支付与权限变更不能共享同一套放行线。

改变越持久、越不可逆、越接近真实业务状态，所需的外部证据、独立验收、人工确认与恢复证明越严格。

### 2.10 未知不是成功，也不是零

缺少结果、证据失效、引用断裂、探针不可用或终态无法读取时，必须显式标记为“未知”或“未验证”，不能自动折算为成功。

### 2.11 改进声明必须绑定基线、改变与结果

“修订后分数更高”本身不能证明反思有效。任何改进声明都必须同时绑定：

- 改变前冻结的目标、被审对象、环境快照与验收器版本；
- 本轮实际改变的对象、范围、参数与指纹；
- 改变后使用可比较口径得到的结果信号；
- 对原有通过项、硬约束与高风险不变量的回归检查；
- 可能影响结果的环境漂移、并发改变与其他混杂因素。

若多个变量同时变化、验证口径发生改变或环境基线不可比，可以记录“结果改善”，但归因状态只能标为“暂不可归因”。只有受控回放、单变量干预、对照运行或其他足够的因果证据，才允许把改善归因到某个具体改变。

## 3. 与 Hanerss 基座的关系

### 3.1 从框架资产到运行实例

```text
认知注册表
    +
拓扑注册表
    +
工程模式注册表
    +
矩阵坐标
    +
业务节点
    +
技能定义
    +
评估与治理规则
    ↓ 编译
工作流定义
    ↓ 实例化
工作流运行
    ↓ 产生
事件、工件、证据、动作、回执、检查点、反思与终态
```

### 3.2 基座对象的运行时作用

| 框架对象 | 运行时作用 | 是否直接执行 |
|---|---|---|
| 认知项 | 声明节点需要的能力域 | 否 |
| 拓扑项 | 声明节点之间的组织与控制结构 | 否 |
| 工程模式 | 提供可复用的问题—约束—流程—验收结构 | 否 |
| 矩阵坐标 | 表明工程模式位于哪些认知与拓扑交织点 | 否 |
| 业务节点 | 把真实业务流程切成可引用节点 | 否 |
| 技能 | 对工程模式进行执行化包装 | 是，需实例化 |
| 评估用例 | 提供运行时或离线验收规则 | 是，作为检查器运行 |
| 治理规则 | 限定权限、版本、风险、人工与审计要求 | 是，作为策略闸运行 |

### 3.3 不新增第四基座

执行流程与可观测性探针不是新的一级基座。

它们属于运行时挂载资产，可同时引用：

```text
认知项
拓扑项
矩阵坐标
工程模式
业务节点
技能
评估用例
治理规则
```

这样既保持 Hanerss v0.1 的三大基座稳定，又允许后续持续扩展执行与观测能力。

## 5. 四个运行状态面

原始材料强调叙事态与机械态必须分离。为便于执行化，本文件在不改变该边界的前提下，增加证据面与控制面。

### 5.1 叙事面

保存：

- 用户目标的自然语言描述；
- 当前计划摘要；
- 已完成与待完成事项；
- 风险说明；
- 交接摘要；
- 模型解释；
- 面向用户的最终说明。

叙事面用于帮助模型保持任务方向，但不能单独证明业务事实。

### 5.2 机械面

保存：

- 业务对象 ID 与版本；
- 数据库状态；
- 文件与代码指纹；
- 参数绑定；
- 工具调用结果；
- 外部回执；
- 事务状态；
- 权限状态；
- 测试状态；
- 回滚状态。

机械面是环境实际发生了什么的记录。

### 5.3 证据面

保存：

- 证据来源；
- 证据版本；
- 获取时间；
- 有效时间；
- 证据内容摘要；
- 完整性指纹；
- 与结论、节点、动作的引用关系；
- 冲突与失效状态。

证据面不得被修订器原地覆盖。新证据必须形成新版本并保留来源链。

### 5.4 控制面

保存：

- 当前工作流状态；
- 节点状态；
- 风险等级；
- 权限范围；
- 预算；
- 策略闸结果；
- 停止原因；
- 恢复指针；
- 人工责任人；
- 探针交互状态。

只有执行器、策略闸和治理组件可以改变控制面。

### 5.5 长程任务必须持续保留三条线

**目标线：**每次重规划、修订、反思与恢复后，都重新检查当前动作是否仍服务于原始目标与成功标准，而不是只处理最近出现的局部报错。

**证据线：**每个关键判断都能追溯到具体数据库记录、测试、规则、回执或人工意见，并保存所使用的版本、时间和适用范围。

**恢复线：**每次可能改变机械态的动作，都能指出失败后回到哪个基线、怎样回、怎样验证已经恢复，以及无法安全恢复时交给谁。

三条线缺少任何一条，长程工作流都容易把临时叙述、局部修补或偶然成功固化成后续事实。

## 6. 通用契约体系

### 6.1 目标契约

目标契约固定任务为什么存在，以及什么才算完成。

```yaml
contract_type: goal
contract_id: CONTRACT_GOAL_XXXX
contract_version: 0.2.0
subject_ref: TASK_...
original_goal: 原始目标
success_criteria:
  - 可验证成功标准
non_goals:
  - 明确不做的事项
required_outcomes:
  - 必须出现的环境终态
acceptable_partial_outcomes:
  - 可接受的部分完成
forbidden_outcomes:
  - 不允许出现的结果
owner: 责任主体
```

目标契约一旦进入执行状态，不允许由执行节点静默改写。需要改变目标时，必须生成新的目标版本并记录授权来源。

### 6.2 输入与上下文契约

```yaml
contract_type: context
required_inputs:
  - 输入名称
optional_inputs:
  - 输入名称
source_constraints:
  - 允许来源
freshness_requirements:
  - 时效要求
completeness_requirements:
  - 完整性要求
sensitive_fields:
  - 敏感字段
missing_input_policy: 阻断|降级|转人工|继续但标记未知
```

### 6.3 计划与拓扑契约

```yaml
contract_type: execution_plan
selected_topology_refs:
  - TOP_...
node_graph_ref: 图结构版本
entry_nodes:
  - WFNODE_...
exit_nodes:
  - WFNODE_...
dependency_rules:
  - 依赖规则
parallelism_limit: 数值
retry_budget: 数值
loop_budget: 数值
critical_path_refs:
  - WFNODE_...
replan_policy: 禁止|局部重排|全局重编译|人工批准
```

### 6.4 节点段间契约

每个节点必须明确“上一段交什么、下一段凭什么签收”。

```yaml
contract_type: node
node_ref: WFNODE_XXXX@版本
responsibility: 单一职责
input_contract:
  required_artifact_types: []
  required_evidence_refs: []
  required_state: []
preconditions: []
action_scope: []
output_contract:
  artifact_type: 类型
  required_fields: []
  mechanical_state_changes: []
acceptance_ref: VALIDATOR_XXXX@版本
failure_policy: 重试|局部重排|补偿|回滚|转人工
```

节点不得仅凭“上一步说已经完成”接收输入。必须检查工件版本、字段、证据和必要机械状态。

### 6.5 工具与动作契约

```yaml
contract_type: action
action_id: ACTION_...
tool_ref: 工具定义及版本
permission_scope: 权限范围
parameter_schema_ref: 参数结构
bound_parameters_hash: 参数指纹
preconditions: []
expected_postconditions: []
idempotency_key: 幂等键或空
side_effect_level: 无|可逆|可补偿|不可逆
confirmation_policy: 无需|策略确认|人工确认
receipt_required: true
compensation_ref: RECOVERY_...或空
```

未生成动作 ID、参数指纹和权限判定的工具调用，不得进入正式执行轨迹。

### 6.6 工件契约

```yaml
contract_type: artifact
artifact_type: 类型
schema_ref: 结构版本
producer_ref: 节点或技能
source_refs: []
required_fields: []
quality_rules: []
versioning_policy: 每次修订产生新版本
acceptance_required: true
```

修订稿必须生成新工件版本，不能原地覆盖已经被评审的版本。

### 6.7 验收器治理契约

运行时验收回答“这次结果是否通过”，治理契约回答“这把尺子是否仍可信”。

```yaml
validator_ref: VALIDATOR_XXXX@版本
owner: 维护者
validator_type: 代码与环境检查|模型评分|人工审核|组合
calibration: 校准说明
regression_suite_ref: 回归用例
valid_from: 时间
expires_at: 时间或空
applicable_risk_levels: []
known_blind_spots: []
manual_sampling_policy: 人工抽检规则
```

### 6.8 反思契约

反思开始前必须回答六个问题：

1. 反思谁：被审对象与具体版本；
2. 回到哪里：原始目标与成功标准；
3. 拿什么对照：证据、规则、测试、指标或人工判断及其版本；
4. 允许改变什么：当前工件、能力路由、经验上下文或系统状态；
5. 改完怎样验收：独立复验方式与结果信号；
6. 何时停止、回到哪：通过、预算耗尽、无进展、风险升高、人工接管与恢复基线。

六问是语义入口。进入自动执行前，还必须把触发原因、基线、路由、信号独立性、改变预算、回归范围和终态写成机器可检查字段。反思契约不是一段提示词，也不能在每轮失败后被执行器自行放宽。

```yaml
contract_type: reflection
```

#### 反思准入规则

只有同时满足以下条件，`eligibility.state` 才能为 `eligible`：

1. 触发信号指向已冻结的被审版本，而不是模糊地指向“当前结果”；
2. 原始目标、验收口径和改变前基线可取回；
3. 至少有一个新增结果信号，或已有获权且可执行的取证计划；
4. 允许改变范围、禁止改变范围与责任主体明确；
5. 改变后存在可独立执行的复验；
6. 循环预算、停止条件与适合当前风险的恢复或交接路径已经固定。

缺少新信号时进入“补证据”而不是“再想一次”；没有可授权改变时结束于评估或人工裁决；没有可靠复验时不得进入自动改变。

## 7. 风险等级与执行剖面

风险等级用于决定需要多少证据、多少守卫、是否必须接入探针以及是否需要人工批准。

| 等级 | 典型改变 | 可逆性 | 默认要求 |
|---|---|---|---|
| R0 | 仅生成草稿，不写外部系统 | 完全可逆 | 基础输入检查、工件版本、最终自检 |
| R1 | 读取外部数据或生成分析 | 不改变外部状态 | 来源、版本、时效、证据引用 |
| R2 | 修改本地文件、分支代码或可回滚配置 | 可回滚 | 检查点、差异审查、测试、回滚验证 |
| R3 | 修改重要业务状态、发送通知、创建正式记录 | 可补偿但有成本 | 权限、前置确认、回执、终态对账、独立验收 |
| R4 | 支付、权限、生产发布、不可逆或高责任动作 | 难以恢复 | 多重证据、人工批准、强制探针、事务或补偿、完整审计 |

风险等级不是固定业务标签，应由“改变对象、持续时间、影响范围、可逆性、责任要求”共同决定。

## 8. 通用执行生命周期

### 8.1 阶段零：加载与编译

#### 输入

- 认知注册表；
- 拓扑注册表；
- 工程模式注册表；
- 业务节点注册表；
- 技能定义；
- 评估用例；
- 治理规则。

#### 处理

1. 校验引用 ID 是否存在；
2. 固定各定义版本；
3. 解析矩阵坐标；
4. 编译节点图；
5. 检查必需契约；
6. 生成工作流定义指纹；
7. 生成可执行清单与禁止清单。

#### 输出

- 已编译工作流；
- 定义版本锁；
- 节点图；
- 验收器清单；
- 策略闸清单；
- 探针挂载策略；
- 编译报告。

#### 阻断条件

- 引用断裂；
- 版本冲突；
- 必需契约缺失；
- 循环没有停止条件；
- 高风险动作没有恢复或人工策略；
- 节点有输出但无验收规则。

---

### 8.2 阶段一：任务接收与目标固定

#### 处理

1. 保存原始请求，不覆盖原文；
2. 生成任务 ID 与运行 ID；
3. 抽取目标、成功标准、限制、期限与交付格式；
4. 区分明确事实、模型推断和缺失信息；
5. 生成目标契约；
6. 冻结目标契约版本。

#### 输出

- 原始任务记录；
- 目标契约；
- 初始叙事态；
- 未决问题清单；
- 初始风险候选。

#### 阻断条件

- 目标自相矛盾且不能安全降级；
- 成功标准完全不可验证；
- 请求要求越过既有治理边界；
- 必需输入缺失且场景不允许继续。

---

### 8.3 阶段二：风险、权限与改变边界判定

#### 处理

1. 列出可能改变的对象；
2. 判断改变持续时间与可逆性；
3. 绑定工具权限与数据权限；
4. 分配风险等级；
5. 确认人工审批点；
6. 确认是否强制接入工作流可观测性探针；
7. 生成禁止动作清单。

#### 输出

- 风险等级；
- 权限范围；
- 允许改变对象；
- 需确认动作；
- 恢复要求；
- 探针要求。

#### 关键规则

发现偏差的组件不自动获得修改权限。读取机械态的权限不自动包含写入机械态的权限。

---

### 8.4 阶段三：上下文与证据获取

#### 处理

1. 根据输入契约收集必要上下文；
2. 优先获取权威机械事实；
3. 保存来源、版本、时间与指纹；
4. 标记证据冲突、过期与缺失；
5. 区分用于生成的上下文和用于验收的独立证据；
6. 形成证据清单与盲区清单。

#### 输出

- 上下文包；
- 证据包；
- 来源图；
- 缺口清单；
- 冲突清单；
- 时效状态。

#### 阻断条件

- 高风险结论只有叙事证据；
- 权威事实不可访问；
- 验收证据与生成证据完全同源且无独立检查；
- 关键证据已失效。

---

### 8.5 阶段四：规划与拓扑选择

#### 处理

1. 将任务拆为职责单一的业务节点；
2. 为每个节点绑定认知项；
3. 选择一个或多个拓扑；
4. 固定段间契约；
5. 标记关键路径与副作用节点；
6. 设置重试、局部重排、循环和并行预算；
7. 插入验收节点、检查点与人工节点；
8. 生成计划版本。

#### 输出

- 节点图；
- 拓扑引用；
- 计划契约；
- 节点契约；
- 预算与停止条件；
- 检查点计划。

#### 规划原则

- 链式用于严格段间交付；
- 路由用于根据证据选择能力或路径；
- 并行用于可隔离的独立子任务；
- 编排用于有依赖关系的多节点工作流；
- 循环用于存在外部红灯和明确停止线的迭代；
- 层级用于授权明确的委派与汇总。

---

### 8.6 阶段五：执行前检查

执行前必须完成以下检查：

```text
目标契约已冻结
输入契约满足或已记录降级
权限范围已绑定
工具与参数结构已校验
高风险动作已取得所需确认
节点图无未声明依赖
循环已设置停止与恢复
必要检查点已创建
验收器版本有效
探针要求已满足或已按策略降级
```

执行前检查失败时，不得通过“让模型再想一次”绕过。

---

### 8.7 阶段六：节点执行

每个节点按统一顺序执行：

```text
接收输入
→ 验证段间契约
→ 读取必要机械态与证据
→ 绑定动作参数
→ 执行前守卫
→ 调用工具或生成工件
→ 获取外部回执
→ 验证后置条件
→ 生成工件版本
→ 运行节点验收
→ 写入检查点或失败记录
```

节点状态机：

```text
pending
→ ready
→ running
→ validating
→ succeeded | failed | blocked | rolled_back | handed_off
```

#### 重试规则

只有在以下条件满足时才允许自动重试：

- 失败属于可重试类型；
- 剩余预算足够；
- 动作幂等，或补偿已经完成；
- 输入、工具、证据或策略至少有一项发生有效变化；
- 没有命中无进展指纹；
- 风险没有升级到需要人工接管。

---

### 8.8 阶段七：中间工件验收与检查点

#### 中间工件验收

下一节点不能只因为上一节点返回“成功”就签收。至少检查：

- 工件类型；
- 工件版本；
- 必需字段；
- 来源引用；
- 证据完整性；
- 机械状态；
- 验收器结果；
- 是否存在未关闭的严重问题。

#### 检查点

检查点应包含：

- 可恢复机械状态；
- 相关文件与配置指纹；
- 已完成节点；
- 未完成节点；
- 未决副作用；
- 外部回执；
- 恢复命令或补偿引用；
- 检查点有效性验证结果。

---

### 8.9 阶段八：结果对账

任务到达候选终点后，必须分别检查：

#### 最终输出

- 是否符合交付格式；
- 是否覆盖目标要求；
- 是否引用正确工件与证据；
- 是否明确未知、限制和部分完成。

#### 执行轨迹

- 是否经过规定审批；
- 是否越过权限；
- 是否出现未声明工具；
- 是否发生重复副作用；
- 是否保留失败、异议与回滚记录。

#### 环境终态

- 目标业务对象是否达到期望状态；
- 数据库、文件、代码、远程服务是否留下真实成功记录；
- 外部回执是否与本地叙述一致；
- 是否存在部分完成、补偿中或未知状态。

#### 对账粒度

对账不能只检查汇总数字。两条明细错误可能相互抵消，使总数和总额看起来完全正确。风险要求较高时，必须同时检查：

- 汇总级一致性；
- 逐对象、逐记录或逐字段一致性；
- 异常对象清单；
- 状态变更与冲正记录；
- 汇总规则是否覆盖全部合法状态。

汇总通过但逐对象未检查时，只能标记“汇总已验证”，不能标记“业务终态完全正确”。

结果对账的状态不得只使用“成功/失败”二值，应至少支持：

```text
已验证完成
已验证部分完成
已完成但未验证
未完成
已回滚
补偿中
等待人工
结果未知
```

---

### 8.10 阶段九：反思与受约束改变

反思不是每次任务都必须执行的固定尾节点。只有反思契约通过准入检查，并获得新结果信号或已授权取证计划时，才进入本阶段。已经通过全部必要验收、没有新信号、没有允许改变对象，或只能重复同源自评时，应直接结束、补证据或转人工，不能制造一轮形式化反思。

#### 反思触发与路由

先把触发信号分类，再选择处理路径：

| 裁定或触发类型 | 默认路径 | 关键约束 |
|---|---|---|
| 格式、完整性、表达质量偏差 | 生成评审 | 预先固定判据，通常最多 1—2 次修订 |
| 判断型质量差距且无确定性检查 | 跨模型或人工评审 | 评审者与生成者的独立性必须披露 |
| 测试、Schema、业务不变量等可确定裁定的失败 | 自愈循环 | 外部验证器、最小修改、回归护栏、硬轮次上限 |
| 证据缺失、过期或冲突 | 补证据或人工分诊 | 在证据充分前不得通过修改结果“消除”未知 |
| 超权限、高风险或不可逆问题 | 策略闸与人工接管 | 不允许执行器自行缩小风险描述或扩大权限 |
| 跨运行重复出现的同类问题 | 经验回放 | 分层聚合，保留样本范围与记录缺口 |
| 同类问题被同一解法反复稳定解决 | 候选技能生命周期 | 先影子/试运行与有限流量，不直接获得正式路由 |
| 全部必要检查已通过且无新偏差 | 不进入反思 | 直接进入交付或归档 |

无法分类的裁定默认进入人工分诊，不允许猜测路由。

#### 反思状态机

```text
candidate
→ eligibility_checked
→ admitted | needs_evidence | not_applicable | blocked | human_required

admitted
→ baseline_frozen
→ deviation_confirmed
→ attribution_hypothesized（可选）
→ change_proposed
→ change_authorized | change_rejected
→ change_applied
→ revalidation_finished
→ accepted | continue | rolled_back | handed_off | aborted
```

每次状态转换必须记录转换前状态、转换后状态、守卫条件、依据事件、执行者、权限与时间。终态必须有停止原因；不得在缺少 `revalidation_finished` 的情况下进入 `accepted`。

#### 单轮闭环

```text
冻结被审对象、目标、基线与验收口径
→ 读取本轮新增结果信号
→ 确认偏差及其影响范围
→ 形成可证伪归因假设（可选）
→ 选择最小充分改变并预测结果变化
→ 由策略闸检查权限、风险与验证器完整性
→ 通过正常接口原子应用或在隔离环境应用改变
→ 使用冻结口径和独立结果信号复验
→ 检查原有通过项、硬约束与副作用回归
→ 记录结果增量、信息增量、成本与剩余未知
→ 接受、继续、回滚或转人工
```

下一轮必须消费上一轮的真实结果。只改写解释、重复相同输入、重复同一失败指纹或再次提出等价补丁，均不得建立新的有效轮次。

独立信号数量必须由本轮有效新信号的唯一证据绑定重算，不能接受调用方自报数量；同一证据绑定只能被一个轮次消费。当前被审对象也是跨轮持久状态：新轮次必须从上一轮实际产生的对象版本开始，历史版本不得重新包装成“新改变”。

轮次观察包必须与完整事件流交叉校验。对象版本、偏差、提案、授权、实际应用、复验、归因晋升、学习决定和停止原因任一项与对应事件不一致时，即使重新计算观察包哈希，也应拒绝闭环。

#### 偏差与归因分离

发现“报告写 800，账本实际 798”足以拒绝报告，但不能仅凭这个差异断言根因是旧快照、映射错误或数据延迟。

归因证据不足时，应输出：

```text
已确认偏差
影响范围：已确认部分与未知部分
根因状态：未归因或仅有假设
控制决定：允许阻断放行
禁止行为：不得把假设写成已确认根因
```

归因假设必须包含“若假设成立，什么可观测结果应发生；若不成立，什么结果会反驳它”。相关性只能支持调查优先级，不能自动支持根因声明。

归因状态必须按“假设 → 相关性证据 → 受控回放 → 干预验证”逐级晋升。每次晋升必须产生公开事件、绑定与目标等级匹配的新增证据，并累计保留先前证据；不得重复消费同一证据，也不得在关闭轮次时直接替换假设或越级自报强归因。

归因证据还必须绑定契约预先批准的证据权威。受控回放与干预验证只有在复验状态为通过、必选与回归检查均通过且比较可比时才能保留；调用方不能仅通过给普通绑定改名来制造“干预证据”。

#### 改进有效性判定

一轮反思只有同时满足以下条件，才可标记为“已验证改善”：

1. 改变前后绑定同一目标版本，或目标变更已单独获权并明确不可直接比较；
2. 关键验收口径保持冻结；若验收器发生变更，必须由循环外主体独立评审，旧结果与新结果分开报告；
3. 至少一个目标相关结果指标达到预设改善阈值；
4. 原有通过项、硬约束和高风险不变量没有发生不可接受回归；
5. 改变指纹与结果指纹完整，环境漂移和并发改变得到披露；
6. 复验使用满足契约独立性要求的结果信号。

基线必须在契约中预先绑定指标 ID、指标值及测量证据。若验证器改变，封存契约时一般改变授权器与验证器改变授权器必须已经分离；新比较只能标记为“独立重建”，并绑定改变前对象、标准、环境、验证器与回归集合、指标与基线值、重建证据及精确审批。仅自报“已独立重建”不构成可比性。

若结果变好但存在多项并发改变、样本不可比或环境漂移，应记录“观察到改善，归因未确认”。若只通过删除测试、放宽规则、改变评分提示或缩小分母获得通过，应判定为验证器投机，而不是改善。

`rolled_back` 必须由恢复事件链证明，不能只写结果文本。合法回滚必须依次记录回滚开始、精确消费契约回滚绑定、回滚应用及其回执、恢复到本轮改变前对象、用必选验证器独立验证恢复结果，并在观察包中同时保留失败版本和恢复版本。

### 8.11 阶段十：提交、交付与责任转移

通过最终策略闸后：

1. 冻结最终工件版本；
2. 记录验收器与策略闸版本；
3. 提交允许的机械状态变化；
4. 生成用户交付说明；
5. 生成内部运行摘要；
6. 对未完成项生成交接契约；
7. 对高风险动作保留完整回执与审批链；
8. 将运行状态更新为终态。

### 8.12 阶段十一：归档、回放与候选学习

归档内容：

- 原始目标；
- 定义版本锁；
- 节点图；
- 完整事件；
- 工件与证据；
- 动作与回执；
- 验收与策略闸；
- 反思与变更；
- 检查点与恢复证明；
- 交接记录；
- 最终环境终态。

一次成功运行只能形成“候选经验”或“候选技能”，不能自动获得正式路由资格。

## 9. 六类拓扑的执行适配

### 9.1 链式

#### 适用

- 输入输出关系明确；
- 上一步工件必须由下一步严格签收；
- 错误传播需要在段间阻断。

#### 必需控制

- 每段独立输入输出契约；
- 工件版本冻结；
- 段间验收；
- 首个失败定位；
- 下游禁止消费未验收工件。

#### 失败处理

默认只重做失败段及其下游，不重做已验收且输入未变化的上游段。

---

### 9.2 路由

#### 适用

- 不同请求需要不同技能、模型、工具或风险路径；
- 路径选择依赖输入特征、证据和治理规则。

#### 必需控制

- 保存候选路径；
- 保存选路依据；
- 保存首选、回退与重路由原因；
- 路由结果必须绑定技能版本；
- 路由失败不能被误记为模型缓存未命中。

#### 失败处理

允许回退到已声明路径，不允许临时调用未注册能力。

---

### 9.3 并行

#### 适用

- 子任务相互独立；
- 可以隔离输入与副作用；
- 需要降低总时延或进行多视角检查。

#### 必需控制

- 明确扇出集合；
- 限制并发；
- 每个分支独立事件与工件；
- 禁止多个分支竞争同一不可幂等副作用；
- 汇合节点必须处理缺失、冲突与重复结果。

#### 失败处理

根据汇合契约决定：全部成功、法定数量成功、关键分支成功或任何失败即阻断。

---

### 9.4 编排

#### 适用

- 多节点存在依赖、条件、分支与检查点；
- 需要对长任务进行计划、重排与局部恢复。

#### 必需控制

- 节点图版本；
- 依赖满足证明；
- 关键路径；
- 计划漂移记录；
- 局部重排边界；
- 检查点与恢复。

#### 失败处理

优先重排失败子图，不重复支付已经完成且仍有效的节点成本。

---

### 9.5 循环

#### 适用

- 存在可测量的外部红灯；
- 每轮可以产生新证据或新状态；
- 结果可以重新验收。

#### 必需控制

- 原始目标锚点；
- 每轮状态指纹；
- 每轮进展量；
- 最大轮次、时间和费用；
- 无进展检测；
- 风险升级；
- 基线恢复。

#### 禁止

同一输入、同一证据、同一失败签名和同一补丁连续重复，不得继续伪装为有效反思。

---

### 9.6 层级

#### 适用

- 主智能体向子智能体、专业角色或人工委派任务；
- 需要分层汇总与责任边界。

#### 必需控制

- 委派目标；
- 子任务成功标准；
- 最大授权范围；
- 可用工具；
- 返回工件与证据；
- 交接验收；
- 汇总者不得捏造子任务未返回的事实。

#### 权限规则

子层权限不得默认继承父层全部权限。委派只能缩小或显式赋予权限，不能隐式扩大。

## 10. 七类认知能力在执行流程中的挂载

| 认知项 | 主要职责 | 典型输入 | 必须产出 | 关键控制 |
|---|---|---|---|---|
| 感知 | 获取当前环境、文档、数据与工具结果 | 外部来源、机械态、用户输入 | 版本化观察与证据引用 | 来源、时效、完整性、冲突 |
| 记忆 | 保存与召回任务相关历史 | 运行轨迹、工件、经验 | 带来源的记忆条目与使用记录 | 写入条件、召回条件、实际使用与结果反馈 |
| 推理 | 形成计划、判断、假设与选择 | 目标、证据、约束 | 决策候选、理由、未知与假设 | 事实和假设分离、不得越权执行 |
| 行动 | 通过工具改变外部状态 | 动作契约、参数、权限 | 回执、机械终态、工件 | 前置守卫、后置检查、幂等、补偿 |
| 反思 | 将结果与基准比较并推动受约束改变 | 输出、轨迹、终态、外部证据 | 偏差、变更提案、复验结果 | 新结果信号、独立验收、停止与恢复 |
| 协作 | 在节点、智能体与人工之间转移责任 | 子任务、工件、状态 | 交接契约、接收确认 | 权限不扩张、摘要不替代机械事实 |
| 治理 | 决定什么能做、谁批准、如何审计 | 风险、权限、规则、检查结果 | 策略闸决策、审批与审计记录 | 版本、有效期、人工责任、不可绕过 |

## 11. 反思的四种改变对象

反思模式由“结果反馈最终改变了什么对象”决定，不由模型调用次数决定。

四种模式不是从低级到高级的单线成熟度阶梯。经验可能只作为建议进入上下文，而一个进入正式路由的技能可能直接调用高风险工具；持续范围、改变直接性和治理风险需要分别判断。

| 模式 | 改变对象 | 常用拓扑 | 持续范围 | 主要风险 |
|---|---|---|---|---|
| 生成评审 | 当前工件版本 | 链式 | 单次版本 | 错误放行 |
| 技能包 | 可复用能力的路由资格 | 路由 | 跨任务 | 未验证能力获得正式流量 |
| 经验回放 | 后续任务的经验上下文 | 层级 | 跨任务 | 偶然经验被长期放大 |
| 自愈循环 | 代码、配置或运行状态 | 循环 | 系统级 | 破坏状态、循环失控 |

模式选择遵循“被什么信号裁定、准备改变什么对象、改变持续多久”三个维度：

| 判断问题 | 选择规则 |
|---|---|
| 外部验证器能否确定裁定？ | 能则可考虑自愈循环；不能则使用生成评审或人工判断 |
| 改变是否只作用于当前工件？ | 是则优先生成评审，不应直接升级为长期经验或技能 |
| 结论是否需要跨任务复用？ | 先进入经验回放并验证真实复用收益，再考虑长期化 |
| 解法是否在可比任务上反复稳定有效？ | 满足复现、回归和治理条件后，才进入候选技能生命周期 |
| 改变是否触及高风险机械态？ | 无论采用何种模式，均提高证据、审批、隔离与恢复要求 |

### 11.1 生成评审

```text
冻结被审工件
→ 批评者依据证据提出问题
→ 策略闸决定是否拒绝
→ 修订器生成新版本
→ 新版本重新接受完整审查
```

批评者不能自己决定放行，修订稿不能继承旧版本的通过状态。

根据可验证性选择反馈来源：

| 反馈变体 | 适用范围 | 默认可信度边界 |
|---|---|---|
| 同模型自评 | 格式、风格、显式清单与低风险完整性检查 | 与生成器共享盲区，不用于关键事实正确性放行 |
| 角色或模型分离评审 | 语义、判断与开放式质量问题 | 提高视角独立性，但仍需校准并披露非确定性 |
| 工具接地评审 | 代码、数据、结构、可检索事实与业务不变量 | 优先用于正确性关键对象，并保留工具版本与原始结果 |
| 人工专业评审 | 高责任、模糊边界、价值冲突与不可逆决策 | 绑定审核者权限、意见、异议与有效期 |

生成评审默认最多进行 1—2 次批评—修订。仍未通过时，应升级到自愈循环、补证据或人工接管，不得把短链悄悄延长为无界循环。

### 11.2 技能包

```text
成功轨迹
→ 候选技能
→ 试运行状态
→ 外部验证
→ 有限流量
→ 真实复用结果写回
→ 正式、降级、撤销或归档
```

一次成功只能证明“值得试验”，不能直接证明“值得进入正式路由”。

技能生命周期至少包含：

```text
候选
→ 离线回放
→ 影子运行
→ 有限流量
→ 正式路由
→ 降级、撤销或归档
```

每次晋升都必须绑定任务分层、样本量、对照基线、成功与风险指标、回滚条件和责任人。技能版本更新后，旧版本的验证结果不得自动继承；效果只在其适用任务分布和有效时间内成立。

### 11.3 经验回放

```text
失败或成功轨迹
→ 候选经验
→ 带来源存储
→ 后续任务召回
→ 记录是否被实际使用
→ 对比真实结果
→ 保留、降权、失效或升级
```

一次任务同时注入多条经验时，不得把整体成功平均归功于全部经验。

经验回放按作用粒度分层：

| 层级 | 默认触发 | 输入 | 产物 |
|---|---|---|---|
| 动作级 | 单次执行、修复或失败后 | 步骤账本、失败签名、复验结果 | 逐步修正与候选经验 |
| 任务级 | 里程碑或任务关闭时 | 动作级经验、交接、返工与成本 | 检查清单、任务模板提案 |
| 版本级 | 发布、事故或规则周期边界 | 任务聚合、事故时间线、策略闸结果 | 规则、阈值或治理变更提案 |

上层回放应消费经验证的下层产物，并同时披露记录完整性。经验进入后续上下文前要经过相关性、时效、冲突与适用范围过滤，不能把全部历史一次性回灌。

### 11.4 自愈循环

```text
外部红灯
→ 诊断
→ 补丁提案
→ 权限与差异审查
→ 原子应用
→ 独立测试
→ 通过、继续、回滚或转人工
```

目标是恢复原始目标约束下的系统正确性，不是只让最后一个测试表面转绿。

自愈循环只适用于验证器可裁定的失败，并强制以下规则：

- 验证器及通过标准在循环开始前冻结，由循环外责任主体维护；
- 每轮解析失败签名，只实施针对该签名的最小充分改变；
- 禁止删除失败用例、放宽 Schema、降低阈值或修改评分提示来制造通过；
- 每轮完整运行目标相关检查和已通过项回归护栏，而不是只重跑最后一个失败项；
- 修复优先在沙箱、分支或隔离副本中执行，只有复验通过的版本才可向外晋级；
- 达到重复指纹、无进展、预算或风险停止线时，携带全部尝试历史转人工。

### 11.5 与评估、记忆的边界

**评估**可以停在分数、标签、问题清单或裁决，它是反思的信号入口。**反思**还必须继续回答：这个判断准备改变什么、改变是否获得授权、改变以后怎样独立复验、何时停止与怎样恢复。

**记忆**负责保存过去的轨迹、经验与失败。保存并不代表已经学会。只有当某条经验被后续任务召回、实际使用，并通过真实结果证明有益时，才可能被保留、升级为规则或候选技能。

因此：

```text
评估不自动等于反思闭环
保存不自动等于有效学习
候选经验不自动等于正式规则
一次成功不自动等于正式技能资格
```

## 12. 停止与恢复

### 12.1 通用停止条件

任一条件满足时，执行器应停止当前自动路径：

- 成功标准已通过独立验收；
- 最大轮次、时长或费用耗尽；
- 连续多轮没有可测量进展；
- 失败签名与修复指纹重复；
- 风险等级上升；
- 权限不足；
- 关键证据缺失、过期或冲突；
- 外部系统状态未知；
- 无法保证原子性或补偿；
- 验收器失效；
- 人工审批被拒绝；
- 已达到契约规定的人工接管点。

### 12.2 无进展判定

每轮使用同一口径生成进展向量，至少比较：

- 失败签名是否变化；
- 通过的验收项是否增加；
- 未解决偏差是否减少；
- 环境终态是否更接近目标；
- 新证据是否排除了假设、缩小未知或改变了路由；
- 补丁或变更指纹是否发生实质变化；
- 原有通过项、风险与副作用是否恶化；
- 本轮消耗的时长、费用、模型调用与工具调用。

应区分两类进展：

- **结果进展：**目标差距缩小、失败减少或终态改善；
- **信息进展：**新证据有效排除假设、缩小未知或使下一步路由更确定。

继续循环至少需要一种进展，且不得出现阻断级回归。仅有证据数量增加、解释文本变长、分数在噪声范围内波动，或补丁文本不同但语义等价，都不算进展。只有信息进展而长期没有结果进展时，仍必须受独立的信息轮次预算约束。

### 12.3 恢复方式

| 方式 | 适用场景 | 证明要求 |
|---|---|---|
| 回滚 | 文件、代码、配置、事务可恢复 | 指纹、版本、测试与终态均回到基线 |
| 补偿 | 外部动作无法直接撤销但有反向业务动作 | 补偿回执、残余影响、人工确认 |
| 隔离 | 状态不确定或存在污染风险 | 隔离范围、禁止下游消费、责任人 |
| 检查点恢复 | 长程工作流局部失败 | 恢复点有效、已完成节点仍然成立 |
| 重建 | 可由权威源确定性重建 | 重建来源、版本与完整性检查 |
| 转人工 | 自动处理风险过高或证据不足 | 原始目标、当前状态、尝试记录、停止原因齐全 |

### 12.4 基线恢复证明

不能只记录“已执行回滚命令”。必须证明：

- 代码、文件或配置指纹回到基线；
- 数据库状态符合基线或补偿目标；
- 临时资源已清理；
- 未决副作用已关闭；
- 回滚后的验收器通过；
- 残余风险已记录。

## 13. 独立运行模式

执行流程在没有工作流可观测性探针时也必须能够完成基本控制。

### 13.1 最低能力

- 生成并冻结契约；
- 按节点图执行；
- 写入不可变事件；
- 保存工件、证据、动作与回执；
- 运行本地验收器；
- 维护检查点；
- 执行停止与恢复；
- 生成最终运行摘要。

### 13.2 独立运行输出

```text
运行清单
事件日志
节点状态
工件清单
证据清单
动作与回执
验收结果
最终环境终态
反思与恢复记录
未知与盲区清单
```

### 13.3 独立运行限制

执行器可以记录自己知道的数据，但不应假装知道未观测到的终态。

探针缺失时，以下字段可标记为未知：

- 跨系统结果对账；
- 证据覆盖率；
- 轨迹与终态分歧；
- 验收器健康；
- 历史基线偏差；
- 跨运行技能与经验收益。

### 13.4 探针不可用时的策略

| 风险等级 | 默认策略 |
|---|---|
| R0 | 允许独立运行，记录探针缺失 |
| R1 | 允许降级，关键结论标记未完全验证 |
| R2 | 允许在本地检查与回滚完整时运行 |
| R3 | 根据治理规则阻断或转人工 |
| R4 | 默认阻断，不允许静默降级 |

## 14. 与工作流可观测性探针交互运行

### 14.1 角色边界

执行器负责：

- 运行节点；
- 改变允许的机械状态；
- 保存原始事件；
- 执行策略闸决策；
- 回滚与交接。

探针负责：

- 读取事件、状态与证据；
- 检查数据完整性；
- 补全可获取但未写入的运行数据；
- 计算信号与指标；
- 识别偏差、风险与无进展；
- 发出证据请求、告警和放行建议。

探针默认不直接修改机械态，也不直接执行回滚。任何控制动作都必须由策略闸转换为执行器可执行的决策。

### 14.2 交互过程

```text
执行器创建运行
→ 发出运行与契约事件
→ 探针绑定运行
→ 探针检查必需数据与证据
→ 执行器运行节点并持续发出事件
→ 探针关联输出、轨迹与环境终态
→ 探针发现缺口时发出证据请求
→ 执行器按权限返回快照或回执
→ 探针生成补全记录、指标与风险信号
→ 策略闸结合契约决定继续、阻断、回滚或转人工
→ 执行器执行控制决定
```

### 14.3 交互引用键

双方必须共同使用：

```text
run_id
node_instance_id
attempt_id
action_id
artifact_id
evidence_id
checkpoint_id
reflection_id
reflection_round_id
correlation_id
schema_version
```

没有共同引用键的数据只能作为孤立观察，不得直接用于高风险放行。

### 14.4 数据补全规则

探针对执行数据的补全必须满足：

- 不覆盖原始事件；
- 生成独立补全记录；
- 标明补全来源、时间、版本与置信状态；
- 通过 `enriches_event_id` 或 `enriches_object_id` 连接原对象；
- 发生冲突时同时保留原值与补充值；
- 无法验证时标记未知，不得推测填充。

### 15.3 事件写入规则

- 原始事件追加写，不原地修改；
- 更正通过新事件表达；
- 事件顺序不等于业务因果，必须同时保存因果引用；
- 外部系统时间与本地时间应分开记录；
- 大对象只保存引用与指纹；
- 敏感数据按治理规则脱敏，但不能破坏关联能力；
- 失败、异议、拒绝与未知必须和成功事件一样被保留。

## 19. 典型场景执行剖面

### 19.1 内容生成与文档任务

#### 推荐拓扑

- 链式：提纲、草稿、评审、修订、终审；
- 路由：按文档类型选择技能；
- 并行：事实检查、结构检查、语言检查。

#### 主要改变对象

当前工件版本。

#### 必需证据

用户材料、指定来源、格式要求、版本记录。

#### 停止条件

- 工件通过验收；
- 关键事实无法核验；
- 修订没有减少已知问题；
- 用户要求与来源材料冲突且不能安全处理。

---

### 19.2 检索、研究与分析任务

#### 推荐拓扑

- 路由：选择不同信息源与分析路径；
- 并行：多来源独立检索；
- 编排：收集、归一、比较、结论、复核。

#### 主要风险

来源不完整、时效失效、事实与推断混淆、证据不能支持结论。

#### 必需终态

不是“生成了答案”，而是“关键结论均能连接到有效证据，缺口被明确标出”。

---

### 19.3 代码修改与持续集成任务

#### 推荐拓扑

- 编排：定位、修改、测试、审查、提交；
- 循环：测试红灯驱动的受控修复；
- 并行：独立测试与静态检查。

#### 必需控制

- 修改前基线；
- 补丁指纹；
- 测试版本；
- 变更范围；
- 最大修复轮次；
- 回滚证明。

#### 禁止

只让最后一个失败测试转绿，而不重新运行原始目标相关的完整验收。

---

### 19.4 企业业务写入任务

#### 推荐拓扑

- 编排：审批、校验、执行、回执、对账；
- 链式：严格段间签收；
- 治理挂载：权限与人工确认。

#### 必需控制

- 业务对象 ID；
- 参数绑定；
- 权限范围；
- 幂等键；
- 外部回执；
- 数据库终态；
- 补偿策略；
- 结果对账。

#### 成功定义

必须以机械终态和外部回执为准，不能以智能体的完成说明为准。

---

### 19.5 多智能体协作任务

#### 推荐拓扑

- 层级：主任务委派；
- 并行：独立子任务；
- 编排：汇总与冲突处理。

#### 必需控制

- 每个子任务的目标与权限；
- 子任务工件与证据；
- 交接契约；
- 汇总规则；
- 子层权限不得隐式扩大；
- 主智能体不得把未返回信息写成已确认事实。

---

### 19.6 自愈与长期运行任务

#### 推荐拓扑

- 循环：诊断、变更、验证；
- 编排：基线、补丁、测试、发布、恢复；
- 层级：诊断者、修复者、审查者、策略闸分离。

#### 强制要求

- 外部红灯；
- 反思契约；
- 最大预算；
- 无进展检测；
- 独立验收；
- 回滚栈；
- 人工接管。

## 20. 执行流程验收清单

### 20.1 框架一致性

- [ ] 认知、拓扑与工程模式仍由注册表维护；
- [ ] 工作流没有把矩阵视图当作唯一源数据；
- [ ] 所有引用使用稳定 ID 与版本；
- [ ] 执行流程没有新增不受治理的一级基座；
- [ ] 技能是工程模式的执行化产物，而不是反向覆盖基座。

### 20.2 契约完整性

- [ ] 原始目标与成功标准已固定；
- [ ] 输入、上下文与证据边界已固定；
- [ ] 每个节点有输入、输出与验收；
- [ ] 每个副作用动作有权限与后置条件；
- [ ] 循环有停止、无进展与恢复；
- [ ] 高风险动作有人工或策略批准；
- [ ] 反思六问均有答案。

### 20.3 状态与证据

- [ ] 叙事态与机械态分离；
- [ ] 最终输出、执行轨迹与环境终态分别检查；
- [ ] 证据带来源、版本、时间与指纹；
- [ ] 未知状态没有被当作成功；
- [ ] 修订稿生成新版本；
- [ ] 异议、失败、拒绝与回滚被保留。

### 20.4 安全与恢复

- [ ] 发现问题、修改对象与决定放行权限分离；
- [ ] 工具调用绑定动作 ID 与参数指纹；
- [ ] 重试满足幂等或补偿要求；
- [ ] 基线真实可恢复；
- [ ] 回滚后有独立验证；
- [ ] 人工交接包含原始目标、当前状态、证据和停止原因。

### 20.5 探针交互

- [ ] 执行器可在无探针时独立运行；
- [ ] 风险等级明确探针是否必需；
- [ ] 原始事件不可被探针覆盖；
- [ ] 数据补全有独立记录与来源；
- [ ] 探针建议必须经过策略闸才产生控制动作；
- [ ] 双方共享运行、节点、动作、工件与证据关联键。

### 20.6 反思闭环

- [ ] 反思触发信号指向具体被审版本，且准入状态可复核；
- [ ] 缺陷类型已经分类，未分类裁定进入人工分诊；
- [ ] 改变前目标、工件、机械态与验收口径已经冻结；
- [ ] 每轮新增结果信号与上一轮结果不同且可追溯；
- [ ] 实际改变未超出授权范围，并保留改变指纹；
- [ ] 验收器未在循环内被削弱；验收器变更经过独立审批；
- [ ] 改变后完成独立复验和原有通过项回归检查；
- [ ] “观察到改善”与“已确认归因”被分别表达；
- [ ] 无进展、预算、风险与重复指纹停止条件真实生效；
- [ ] 反思以接受、回滚、拒绝、转人工或中止等明确终态结束。

## 22. 总结

Hanerss 通用执行流程将框架中的静态资产转换为一条受契约约束的运行链路：

```text
固定目标
→ 判断风险与权限
→ 获取上下文和证据
→ 选择拓扑并编译节点图
→ 执行前检查
→ 分段执行与验收
→ 对账输出、轨迹与环境终态
→ 在新结果信号下进行反思
→ 受权改变并独立复验
→ 通过、继续、回滚或转人工
→ 归档与候选学习
```

这条流程的核心不是让智能体“多想几次”，而是让每一次行动都能回答：

- 它为什么做；
- 它依据什么做；
- 这一轮反思为什么具备准入资格；
- 相比上一轮新增了什么可复核信号；
- 它允许改变什么；
- 它实际改变了什么；
- 改变前后是否使用可比较的目标、基线与验收口径；
- 谁以什么独立性验证了结果；
- 改善是否伴随回归、混杂因素或验证器投机；
- 失败时怎样停止；
- 怎样证明已经恢复；
- 哪些事实仍然未知。

执行流程可以独立运行并保留完整事实记录；接入工作流可观测性探针后，则可以进一步补全跨系统终态、证据覆盖、轨迹分歧、循环进展、验证器健康与跨运行收益等数据。
