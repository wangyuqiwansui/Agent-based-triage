# 层级委派：工作流可观测性探针

> 目标：独立读取工作流的目标、责任、工件、裁决和运行证据，发现覆盖与执行问题，补全可核验的数据，向执行流程返回有来源、版本和适用边界的报告或补全提案。
>
> 本文不是一张静态指标清单，而是一套“接收观测任务 → 采集证据 → 核验口径 → 运行探针 → 分类缺口 → 受控补全 → 交回结果”的执行规格。没有主流程在线，也能对给定快照或历史记录独立运行。

## 一、依据、范围与设计边界

本文以用户粘贴的黄佳第32讲《层级委派：把大目标拆成可验收的责任》〔来源一〕和 `hanerss_skill_framework_v0_1.md`〔来源二〕为依据。

原文直接提供的观测重点是：责任是否真正拆开、执行者返回与父目标完成的区别、结构化工件与来源、两道闸门，以及上下文、工具、预算、失败和递归边界。原文演示包含三项责任、覆盖由一项变为三项、重复由两项变为零的对照现象。

原文没有提供完整的探针引擎、统计口径、补全协议或生产阈值。本文的探针目录、指标定义、证据分级、消息协议、反馈控制和配置均为设计扩展，不宣称原文或框架已经实现。也不将原文演示数字当成真实模型的统计性能。

框架 v0.1 只预留基座和技能模板。本文件是后续技能化草案；元数据标识是建议值，登记前查重、登记后冻结，不新增“可观测性”一级认知或拓扑基座。〔来源二：第2—5、8、18、20节〕

## 二、定位、挂载与权限

### 2.1 观察对象与自身结构分开

| 维度 | 定义 |
|---|---|
| 被观察的工程模式 | 层级委派，主要坐标为 `COG_COLLABORATION__TOP_HIERARCHY` |
| 探针主要能力 | 感知：读取和识别事件；反思：重建、诊断与比对；治理：核查权限与版本边界 |
| 探针自身结构 | 默认链式：采集到报告；交互补全开启后可采用有次数上限的循环 |
| 元数据拓扑含义 | `TOP_CHAIN`、`TOP_LOOP`描述探针自身流程，不把被观察对象的层级关系混作探针自身拓扑 |
| 建议归档 | 框架既有的 `04_skills/draft/`；与模式、评估用例和治理规则通过注册表引用关联 |
| 复用范围 | 默认配置观察层级委派；通过字段映射可观察链式、路由、并行等流程，不适用的责任或组合指标明确标记不适用 |

其他拓扑的观测不得硬套“必须有多个子执行者”。例如单步骤工作流可以只检查输入、工件、裁决和数据缺口；没有父子责任结构时，不计算层级委派专属指标。

### 2.2 允许做与禁止做

| 允许做 | 必须禁止 |
|---|---|
| 读取获准的目标快照、事件、工件、裁决与运行时记录 | 超出读取范围搜索数据或继承主管全部凭据 |
| 去重、关联、计算派生值，记录来源和算法版本 | 用估算值替代缺失事件却标记为实测 |
| 从既有可信记录恢复漏掉的关联和字段 | 用当前页面或当前状态伪装历史时刻已知的事实 |
| 对照规则独立复核，指出与正式裁决的差异 | 覆盖正式闸门结论或直接把父目标改成成功 |
| 提交有证据的补全提案和局部重派建议 | 自行增加业务任务、修改权限、执行发布或付款等动作 |
| 按最小权限保存观测报告及脱敏证据引用 | 默认收集完整子会话、敏感正文或隐藏思维过程 |

探针有自己的运行状态和报告写入权，不拥有业务状态写入权。它独立运行，不等于脱离输入、证据和授权也能得出完整结论。

## 三、三种运行方式与最小输入

### 3.1 运行方式

| 模式 | 启动入口 | 探针可以做什么 | 业务流程是否必须在线 |
|---|---|---|---|
| 独立检查 | 用户或审计任务提交快照、工件包、日志或历史记录 | 检查材料、自行计算、按授权只读补查、输出报告和提案 | 否 |
| 旁路观测 | 订阅运行事件或读取阶段快照 | 生成阶段报告和告警，不自动阻断或修改业务 | 是，或可读取持续更新的记录 |
| 交互补全 | 执行流程发送明确的观测请求 | 按指定范围补证、提交提案、等待采纳回执并核对重验 | 是 |

独立检查时，即使无法获得父目标，也可以完成工件结构检查或日志质量检查，但“目标覆盖率、父目标是否完成”等结论必须标记未知，不能从已有结果推断全部任务需求。

### 3.2 观测请求输入

| 字段 | 必需性 | 说明 |
|---|---|---|
| 观测任务编号、运行模式、观测目的 | 必需 | 明确是运行诊断、历史复盘、证据补全还是规则复核 |
| 被观察对象或输入材料引用 | 必需 | 至少存在一份实际可读取材料；只有口头描述时注明仅能做描述性分析 |
| 运行、目标、计划、对象版本 | 能获取时必需 | 无法获取时保留未知，限制跨对象关联与提案采纳 |
| 责任基线和场景规则 | 覆盖与组合检查必需 | 来自目标契约或已批准清单，不能来自执行者自报标签的集合 |
| 观测窗口与截止点 | 必需 | 明确当前进度、某次修复，还是已经封口的完整运行 |
| 数据源权限与读取方式 | 补查时必需 | 只能使用已批准的适配器和范围 |
| 探针配置、规则版本、阈值版本 | 必需 | 用于复算；缺少阈值时只报告原始值和契约违例 |
| 补全字段白名单、时间与调用预算 | 补全时必需 | 未开启补全则只诊断，不主动发起读取链 |

### 3.3 输出契约

每次运行至少返回：观测范围、输入基线、检查完成状态、指标结果、证据目录、已确认问题、未知项、缺口分类、补全提案、建议动作、运行消耗及读取失败清单。

“探针运行完成”表示完成了获准的检查，不表示被观察业务通过。报告可以同时是“探针已完成、业务覆盖未知、补全未获授权”。

## 四、证据模型与数据质量规则

### 4.1 证据目录

| 证据类别 | 通常提供什么 | 不能单独证明什么 |
|---|---|---|
| 父目标与责任基线 | 应交付的责任、范围、验收口径与版本 | 责任已经执行 |
| 运行时派工与状态记录 | 谁被派发、何时启动、处于什么执行状态 | 工件内容合格、父目标通过 |
| 工件存储与输入快照 | 提交了什么、内容和输入版本是什么 | 工件自报的责任一定属实 |
| 工件闸与组合闸记录 | 按何规则得出何裁决，基线与证据是什么 | 规则本身覆盖了所有开放问题 |
| 工具授权与调用回执 | 调用了什么、身份和范围、实际返回结果 | 一次拒绝事件代表没有发生任何其他越权 |
| 来源内容与定位 | 结论能否追溯到具体资料 | 来源一定真实、结论一定正确或始终有效 |
| 子执行者摘要 | 执行者声称完成了什么、还有哪些问题 | 权威执行状态和独立验收结论 |

遇到冲突时，先核对是否同一对象、版本和时点，再按字段的权威维护方核对。运行时记录适合确认执行状态，不能自动覆盖业务原始输入；业务原始输入适合确认输入事实，不能自动覆盖授权服务的权限裁决。冲突未解决时并列保留，不静默挑选有利值。

### 4.2 每条观测结果附带的信息

```yaml
结果编号: 观测结果示例一
指标编号: 指标二
指标名称: 有效履约覆盖率
范围:
  运行编号: 简报运行一
  父目标编号: 简报目标一
  目标版本: 1
  计划版本: 1
  基线快照编号: 快照一
  观察阶段: 当前快照
计算:
  数值: null
  单位: 比例
  已确认分子: 2
  已确认分母: 3
  未知责任数: 1
  已确认下界: 0.666667
  可能上界: 1.0
  未知原因: 第三项工件的验收记录无法取得
证据性质: 有条件重建
证据引用: [责任基线一, 工件裁决一, 工件裁决二]
计算规则版本: "0.1.0"
阈值配置版本: null
产生时间: "2026-09-09T14:00:00+09:00"
限制说明: 该区间只针对已确认责任清单，不证明范围穷尽
```

这个示例表达“可以确认两项通过，第三项无法判断”，不等于“第三项确实未完成”。如果权威快照完整且明确第三项尚未交付，则覆盖值是三分之二，第三项属于业务未完成，不应标记为纯数据未知。

### 4.3 证据性质

| 标记 | 含义 | 使用限制 |
|---|---|---|
| 直接观测 | 从当前授权的权威记录读取到原始事实 | 仍需保留对象、时点、版本和来源 |
| 计算派生 | 基于完整可核验输入按确定规则计算 | 保留算法版本和所有必要输入 |
| 有条件重建 | 从旁证或历史残留记录重建，带明确假设 | 不伪装成原始日志；关键验收是否可用由规则决定 |
| 待验证线索 | 搜索命中、模型解释或未经确认的映射 | 不能作为关键字段自动回填的依据 |
| 未知 | 必要输入不可得、冲突未解决或时间无法对齐 | 数值为空并给原因，不填零 |
| 不适用 | 当前任务不存在该对象或规则 | 提供场景配置依据，不当作通过率的一部分 |

### 4.4 去重、时序、抽样与缺失

事件按“运行编号＋事件编号”去重。相同编号不同载荷必须隔离。重复消息不是新尝试；重试产生新尝试编号，但不会生成新的父目标责任。

同一生产者的序号可以辅助识别缺段；没有封口清单或可信预期事件范围，不能宣称“日志完整率为百分之百”。事件迟到时生成报告新版本，保留旧报告的观测截止点。

单进程耗时优先使用同一执行环境提供的单调时钟差值；跨进程耗时须确认时钟口径或使用共同接收端的可比较时间。只有开始事件时，可以在条件成立时报告已运行时长下界，不能虚构结束时刻。并行子任务时长相加不等于父目标端到端耗时。

授权、闸门、目标提交和副作用回执等关键证据应由运行时保证可核对记录；探针离线不应导致这些记录停写。高频明细可以按配置抽样，但采样比例、漏采和保留范围必须进入报告。抽样结果不能被宣称为全量“零越权”或“全量主键已覆盖”。

## 五、探针执行流程

```text
接收观测请求或离线材料
  → 确认权限、目的、窗口与版本
  → 建立证据目录并采集最小数据
  → 去重、关联、核验时序和完整性
  → 选择适用探针
  → 计算指标与独立复核
  → 区分业务缺口、证据缺口和观测盲区
  → 按权限进行有限补查
  → 生成报告或补全提案
  → 独立交付，或等待采纳回执
  → 必要时重算并关闭缺口
```

### 观测一：确定检查范围

读取请求目的、输入引用、当前目标版本、观察窗口和授权。区分“检查当时是否正确”和“现在为后续执行补充资料”；两种目的不能混在一起。

输入为空时返回“无可观测材料”。没有目标基线时，允许继续材料级检查，但禁用目标覆盖判断。输出观测计划和不可检查项。

### 观测二：建立证据目录

优先使用已有目标快照、任务清单、工件、闸门和运行时记录，按最小权限取数。每个引用登记来源、对象版本、获取时间、适用时间、完整性及访问状态。敏感材料只保留必要摘要和受控引用。

读取失败与没有数据分别记录。无权限读取不等于对象不存在，也不等于业务没有执行。

### 观测三：形成可复算快照

对事件去重，绑定运行、责任、任务、尝试和工件；检查缺号、冲突、过期和无法关联的记录。生成观测快照编号，冻结本次计算的输入集合。

不能仅凭近似名称或文本相似度自动把两个对象视为同一责任。此类匹配只能输出待验证线索。

### 观测四：运行适用探针

根据场景配置启用下节探针，按第七节口径计算。先检查分母和证据是否存在，再算数值；先检查正式裁决对应的基线，再比较探针复核结果。

输出逐项检查状态。探针发现正式裁决疑似不正确时，形成复核发现和证据，不直接覆盖原裁决。

### 观测五：对缺口分类

识别可恢复的记录缺口、可确定计算的派生缺口、缺少原始事实的业务缺口、权限受限、来源冲突、历史不可重建或规则本身未定义等情况。

同一责任可以同时存在业务问题和观测缺口，分别记录。不能为了只输出一个标签，把两个问题合并成模糊的“失败”。

### 观测六：有限补查与提案生成

只对已批准字段和数据源执行补查。能够从可信来源恢复的字段附上证据与有效期；只能推测的字段不填入正式值。需要新的研究、重新测试或重新处理输入时，返回业务补做建议。

读取次数、来源数量、总耗时与重试次数均受探针预算约束。补查失败不允许反复生成同一请求形成无限循环。

### 观测七：交付报告与回执核对

独立运行时交付报告和未应用提案，任务结束。交互运行时等待执行流程的采纳回执，核对实际生成的新对象版本及必要的重验结果。

“提案已发送”“字段已写入”和“关键缺口已关闭”分别记录。只有必要的业务重验通过后，才能把关键缺口关闭。

## 六、可按需组合的探针目录

各探针均需在检查前核验所列输入。下表的“发现”是观测结果，不是自动执行指令。

| 探针 | 必需输入 | 核心检查 | 输出发现与补全边界 | 接收责任人 |
|---|---|---|---|---|
| 探针一：目标基线 | 目标、原始要求、责任清单、规则 | 是否有稳定责任人；清单是否来自目标；范围完备性如何确认 | 可补基线引用，不能自行删除必需责任或宣称开放范围穷尽 | 父目标责任人 |
| 探针二：委派契约 | 责任基线、计划、任务契约 | 责任覆盖、未声明重叠、边界、输入、交付、工具、预算和版本是否明确 | 报告无主责任、模糊交付和越界授权；不自动重写计划 | 父目标责任人与运行时 |
| 探针三：完成状态 | 权威任务快照、返回记录、工件与组合裁决 | 执行者返回、工件通过、父目标通过是否被混淆 | 定位局部完成与整体完成的断点；状态无法核实时标未知 | 执行流程 |
| 探针四：工件与证据 | 工件、任务契约、输入及来源、工件闸 | 结构、归属、版本、证据定位与结论支撑；是否仅依赖自报 | 可提出补充来源或输入映射；改动正式工件须授权生成新版本 | 工件验收器 |
| 探针五：组合验收 | 责任基线、有效候选集、组合规则与裁决 | 缺失责任、候选超额、重复主键、口径冲突和全局约束 | 返回缺口与冲突清单；不能自动宣布父目标完成 | 组合验收器 |
| 探针六：执行隔离 | 权限配置、授权和调用回执、工作区与父子关系 | 最小上下文、工具与数据范围、委派深度、并发及敏感内容暴露 | 区分被拦截的尝试和已发生的违规；无运行时证据不能证明隔离成立 | 核心运行时与治理负责人 |
| 探针七：失败与恢复 | 尝试历史、重派记录、工件复用、检查点 | 局部失败是否扩大、累计预算是否清零、旧结果是否污染新计划 | 说明不必要重做、丢失工件、重复外部动作风险；不自行发起恢复 | 执行流程 |
| 探针八：时延与预算 | 可比较时间、预算预留、结算与在途记录 | 主管排队、工件等待验收、重试放大、总预算占用 | 补充可计算消耗与耗时；未知费用不当零，不能自行追加预算 | 运行时及流程负责人 |
| 探针九：观测质量 | 事件清单、生产者封口、采样与读取记录 | 去重、漏段、迟到、时钟、关联缺失、报告输入是否可复算 | 先报告数据可靠程度；可恢复既有记录，不制造原始事件 | 可观测性维护方 |
| 探针十：补全闭环 | 请求、提案、采纳回执、新版本、重验结果 | 白名单、基线有效性、重复请求、采纳及重验是否真正闭合 | 输出未关闭缺口、越界提案与补全消耗；不把“已发送”当“已完成” | 探针与执行流程各自负责人 |

默认优先检查目标基线、委派契约、完成状态、工件与组合验收；涉及外部工具、共享状态或生产动作时增加隔离与恢复检查。性能和成本探针不能替代前述正确性检查。

## 七、指标口径：先定义可计算性，再定义数值

### 7.1 共同口径

同一质量指标必须绑定运行编号、目标版本、计划版本、规则版本、观测截止点和样本范围。不同版本的责任清单不得混在一个分母里。预算与总消耗是累计指标，应单独汇总整次运行的全部计划和尝试，不能通过切换计划版本把已消耗资源清零。

术语统一：候选池是工件闸通过、归属与版本适用但尚未完成最终选择的工件集合；提交集合是执行流程按明示规则选出、实际送入组合闸的集合，也称组合候选集。有效履约覆盖按提交集合计算，候选超额在选择前计算。没有提交集合时，只能报告候选层覆盖或待选择状态，不把它冒充正式履约覆盖。

设必需责任集合为“责任集”，冻结输入主键集合为“输入集”。一项责任只有在真实交付经过核验、版本适用且满足该责任基数规则时，才记为有效履约。工件自报的责任标签只用于寻找待核验关系，不能直接充当履约证据。

比率分母为零时输出不适用及原因；分母未知时输出未知。分母已知、部分分子无法判断时，不输出一个伪精确比率；可以给出已确认下界和可能上界，并明确未知对象数。若存在必需责任之外的开放范围未知，这类区间也只对已确认清单成立。

跨运行汇总同时给出样本数、未知数、场景与版本分组；比率优先按分子分母合并计算，不直接平均不同规模任务的百分比。未完成运行的耗时单列为进行中或下界，不能只展示已成功运行而隐去失败、超时和取消样本。

### 7.2 责任与组合指标

| 编号与指标 | 计算口径 | 数据来源 | 重要限制 |
|---|---|---|---|
| 指标一：计划责任覆盖率 | 已有有效委派安排的不同必需责任数 ÷ 必需责任总数 | 责任基线、已批准计划、完整任务契约 | 有安排不代表已完成；需排除只写角色、没有交付约定的无效任务 |
| 指标二：有效履约覆盖率 | 满足工件验收、版本和责任基数的不同必需责任数 ÷ 必需责任总数 | 责任基线、工件与有效裁决、提交集合 | 是责任级结果，不按卡片数计算；关键未知不能计入通过 |
| 指标三：候选超额覆盖数 | 对每项责任，累计“去重后的当前有效候选数－事先允许的候选数”的正数部分 | 候选池、尝试替代关系、冗余配置 | 在最终选择前统计；同一消息重投不增加，已被替代尝试不重复计；不等同于所有超额都毫无价值 |
| 指标四：提交集合非法重复键数 | 对提交组合闸的实际记录按唯一键计数，累计超过允许基数的部分 | 提交集合内容、唯一键与基数规则 | 候选超额不必然成为最终重复；两个指标必须分开 |
| 指标五：输入主键覆盖率 | 输入集中有合格输出的不同主键数 ÷ 输入集主键总数 | 冻结输入集、输出记录、裁决 | 仅用于主键分片；额外主键和重复主键另报，不能只看比例 |
| 指标六：执行者返回率 | 已有结构化终态回报的逻辑任务数 ÷ 当前计划已派发逻辑任务数 | 派工清单、任务快照、成功或失败工件 | 失败工件也算已回报；此指标不证明执行成功或父目标通过 |
| 指标七：工件首验通过率 | 首次业务工件通过工件闸的逻辑任务数 ÷ 已发生首次业务工件提交的逻辑任务数 | 首次交付、首次闸门裁决 | 首次裁决待定须列未知；执行前失败另报，不能把该指标当端到端成功率 |
| 指标八：证据链完整率 | 已具备可核验完整来源链的必需证据项数 ÷ 契约要求的证据项数 | 工件证据清单、输入与来源快照 | 完整来源链不等于来源必然真实或结论必然正确，语义支撑还需单独核验 |
| 指标九：局部全返回但整体未通过次数 | 当前全部任务已回报，且组合裁决明确不通过的父目标快照数 | 任务快照、组合裁决 | 同一未变更问题只计一次，按问题编号去重；裁决未知单列，不混入不通过 |
| 指标十：父目标误报完成次数 | 已声明完成，但经完整证据确认不满足当时必需验收条件的提交次数 | 完成提交、当时基线、工件和裁决 | 仅因查不到日志不能直接定性；证据不全应报告疑似误报 |
| 指标十一：未解决组合冲突数 | 当前候选集或综合产物中已确认、尚无有效裁决的不同冲突数 | 冲突记录、工件内容、裁决 | 未执行完整冲突检查时不能因为没有记录就报零 |
| 指标十二：范围完备性评审状态 | 已确认、待评审、未定义或不适用 | 清单来源、独立评审或批准记录 | 属于状态指标；不能由覆盖率高低推导 |

这里的“当前有效候选”指归属和版本已经确认、未被替代且在候选层可使用的工件；它不表示已经通过父目标组合验收。双人独立复核等有意冗余，需在允许候选数与独立性规则中明确体现。

### 7.3 执行、资源与观测质量指标

| 编号与指标 | 计算口径 | 数据来源 | 重要限制 |
|---|---|---|---|
| 指标十三：重试放大倍数 | 实际已启动尝试数 ÷ 至少启动过一次的不同逻辑任务数 | 运行时尝试记录 | 无重试时为一；同一消息重投不算启动；新增业务责任不是重试 |
| 指标十四：合格工件复用率 | 修复后仍被合法复用的原工件数 ÷ 修复前经兼容性确认可复用的工件数 | 修复计划、版本依赖、接纳记录 | 无修复或无可复用对象时不适用；不能复用旧证据来追求高值 |
| 指标十五：父目标端到端时长 | 有效终态提交时刻－目标开始执行时刻 | 统一或可比较的运行时时间 | 进行中报告下界；成功、失败、取消分别统计；不累加并行子任务耗时 |
| 指标十六：工件等待验收时长 | 对每份工件，首次进入待验收至开始验收的时间差 | 工件登记和验收开始记录 | 反映排队，不等于验收计算耗时；缺少开始验收事件时未知 |
| 指标十七：预算占用率 | 已确认消耗与在途预留之和 ÷ 已批准总预算 | 运行时预留与结算账本 | 结果不明调用的预留不得提前释放；按同一单位分别计算 |
| 指标十八：隔离违规与拦截次数 | 分别计已确认越权实际发生数、未授权请求被拒绝数、无法核实数 | 授权服务、工具网关和实际调用回执 | 拦截不等于违规已发生；没有全量证据时不能宣称零违规 |
| 指标十九：事件可核对完整率 | 在可信封口范围内收到的不同事件数 ÷ 生产者确认的应有事件数 | 生产者事件清单、封口记录、采集事件 | 没有可信分母时未知；抽样链不能冒充全量完整率 |
| 指标二十：字段补全采纳率 | 已有终态回执的字段提案中，被采纳字段数 ÷ 终态字段提案总数 | 提案与逐字段采纳回执 | 部分采纳逐字段算；等待回执单列；采纳不等于业务问题已解决 |
| 指标二十一：关键补全闭环时长 | 从缺口正式登记到必要重验通过且关闭的时间差 | 缺口、采纳回执、新版本与重验记录 | 没有重验通过不能结束计时；未闭合项单列，不能删除 |
| 指标二十二：必需观测字段未知率 | 当前无法确定的必需观测字段单元数 ÷ 配置要求的字段单元总数 | 观测字段基线、证据目录 | 字段单元以对象、字段、版本去重；不适用字段不进分母 |

时延分位值至少附样本数与观察窗口；样本很少时展示原始样本或范围，不用精细分位数制造稳定性错觉。成本缺失时可以报告已确认消耗和未结算项，但不能把它们合成一个声称完整的总费用。

### 7.4 告警规则与阈值来源

契约型检查优先于统计阈值。缺失必需责任、已确认越权、非法重复主键、错误版本提交等，按对应业务契约报告问题；不能让良好的平均时延或总体得分抵消。

重试、等待、成本等性能指标的阈值来自场景预算、服务要求或经批准的历史基线，必须记录制定者、版本与生效时间。没有依据时只报告数值、变化及样本范围，不编造“通用优秀线”。

探针发现严重问题时可以发出高优先级事件；是否暂停、取消或阻断，由运行时预先配置的治理规则决定。没有这种规则时，探针输出不自动获得控制权。

## 八、把“数据补全”拆成可执行的处理类型

### 8.1 缺口分类

| 类型 | 示例 | 探针能做什么 | 不能做什么 |
|---|---|---|---|
| 既有记录未关联 | 运行记录缺工件编号，但回执含同一任务的工件地址 | 核验身份与版本后提出关联补全 | 仅凭内容相似就认定属于该任务 |
| 原始事件可恢复 | 中央记录缺结束事件，执行实例保留原始回执 | 读取可信原件并注明恢复时间、原发生时间和来源 | 用补查时间冒充原发生时间 |
| 派生字段未计算 | 有可靠开始与结束时间，尚无耗时 | 按固定规则计算到观测扩展区 | 在时钟不可比较时仍给精确耗时 |
| 正式工件证据缺失 | 结论缺来源定位，既有资料库可能保留出处 | 获准只读查找，提出新版本补证方案 | 未读来源内容就因为找到链接而标记证据通过 |
| 业务责任未完成 | 没有状态管理或交接研究 | 返回缺失责任和局部重派建议 | 自动生成“已经完成”的记录 |
| 原始业务事实缺失 | 输入中没有待核对金额或实验结果 | 返回补充输入或重新执行建议 | 编造金额、测试结果或业务事实 |
| 历史无法重建 | 只知道任务当前结束，原始结束时间已经丢失 | 报告可确认状态、时间边界和未知项 | 把当前状态当作当时状态的证明 |
| 来源冲突 | 两份同版本清单对责任范围描述不同 | 并列保留，提交权威方裁决 | 自动选择能提高覆盖率的一份 |
| 权限受限 | 无权读取某个原始工件 | 记录访问受限及其影响，返回授权需求 | 借助另一身份绕过权限 |
| 验收规则未定义 | 只说“深入研究”，没有交付判定 | 返回规则缺口给父目标责任人 | 自定低门槛并将任务验收通过 |

### 8.2 补全字段白名单

| 字段层级 | 可以提出的补全 | 应由谁实际保存 | 是否影响业务验收 |
|---|---|---|---|
| 观测扩展区 | 可信事件关联、数据质量标记、计算耗时、派生统计、证据目录引用 | 探针或专用观测存储 | 默认不影响；被规则用作关键证据时另行评估 |
| 正式工件的证据元数据 | 来源定位、输入映射、快照引用等已经核实的内容 | 执行流程的授权工件写入组件 | 影响；生成新版本并重新验收 |
| 正式业务内容 | 结论、金额、处理结果、代码或事实字段 | 原责任执行者或有授权的业务组件 | 不是普通观测补全；按业务修复流程处理 |
| 目标与治理配置 | 责任范围、通过条件、权限、预算、完成状态 | 原目标与治理责任方 | 禁止探针直接回填 |

### 8.3 补全的完整过程

对每个缺口先登记对象、字段、影响、权威来源和截止时间，再判断是否具备合法补查能力。能够恢复时，产生证据及带基线约束的提案；无法恢复时保留未知，明确需要业务补做、授权或人工裁决。

执行流程采纳提案后，探针只核对采纳结果是否与提案一致、目标对象是否生成正确版本、必要闸门是否已重验。不能因为“找到了一条来源”就关闭缺口，也不能因为执行流程拒绝采纳就把原始数据改成建议值。

补全涉及历史事实时，同时记录“事实适用时间、来源版本、读取时间和补全时间”。新取得的资料可以支持后续重新验收，但不能反向证明先前验收当时拥有该资料。

## 九、与执行流程交互的共享数据契约
### 共享契约版本与对象归属

共享契约版本：`0.1.0`。本节在两份文档中完整保留，任何一份单独使用时都不依赖另一份文件才能解析消息。

| 数据对象 | 权威维护方 | 另一方的使用方式 |
|---|---|---|
| 父目标、责任清单、委派计划、运行状态、正式工件版本、闸门裁决 | 执行流程及其授权写入组件 | 探针只读，不覆盖原记录 |
| 工具授权、预算预留与结算、执行者身份、取消与恢复凭据 | 核心运行时及资源服务 | 执行流程和探针按权限读取 |
| 观测扩展区、指标结果、证据缺口、补全提案 | 探针 | 执行流程校验后引用或采纳 |
| 补全采纳回执、重新验收结果 | 执行流程 | 探针据此关闭或重开缺口 |

执行流程拥有业务状态写权限，不代表主管模型可以绕过运行时约束；探针生成报告，不代表它获得业务裁决权。

### 统一消息信封

```yaml
契约版本: "0.1.0"
消息编号: 消息示例一
消息类型: 观测请求
发送方: 执行流程
运行编号: 运行示例一
父目标编号: 目标示例一
目标版本: 1
计划版本: 1
基线快照编号: 快照示例一
基线状态修订号: 7
责任编号: null
任务编号: null
契约版本号: null
尝试编号: null
关联请求编号: null
产生时间: "2026-09-09T14:00:00+09:00"
截止时间: "2026-09-09T14:00:30+09:00"
数据体: {}
```

信封中的“契约版本”指通信协议版本；“契约版本号”指某项委派任务的业务契约版本，二者不能混用。消息编号必须唯一；重复投递同一消息时复用原编号。目标版本和计划版本描述业务口径，基线状态修订号描述同一口径下的运行状态，不得互相替代。仅与局部对象有关的字段可以为空；未知字段必须明确为空并说明原因，不得猜测补齐。上述时间仅为格式示例，不是建议的超时阈值。

| 消息类型 | 方向 | 数据体最小内容 | 是否允许直接改变业务状态 |
|---|---|---|---|
| 观测请求 | 执行流程→探针 | 观测范围、需补字段、规则版本、读取权限引用、预算、是否阻断及阻断依据 | 否 |
| 观测快照 | 执行流程→探针 | 目标与责任快照引用、工件清单、闸门记录、事件区间、数据完整性声明 | 否 |
| 观测报告 | 探针→执行流程 | 指标值及口径、证据引用、未知项、缺口、建议、报告版本 | 否 |
| 补全提案 | 探针→执行流程 | 补丁编号、目标对象、字段路径、基线值指纹、建议值、证据、有效期、影响范围 | 否 |
| 采纳回执 | 执行流程→探针 | 补丁编号、采纳状态、原因、新对象版本、受影响闸门、重验结果引用 | 只有执行流程按权限采纳后才允许 |

采纳状态限定为：`已采纳、部分采纳、已拒绝、已过期、已被替代`。部分采纳必须逐字段记录结果。需要重验但尚未完成时，回执明确标注“重验待完成”，不能据此关闭关键缺口。

### 最小事件信封

```yaml
事件编号: 事件示例一
事件类型: 工件闸已裁决
运行编号: 运行示例一
父目标编号: 目标示例一
目标版本: 1
计划版本: 1
责任编号: 责任示例一
任务编号: 任务示例一
契约版本号: 1
尝试编号: 1
执行者实例编号: 实例示例一
生产者编号: 运行时示例一
生产者序号: 18
发生时间: "2026-09-09T14:00:05+09:00"
接收时间: "2026-09-09T14:00:06+09:00"
对象引用: 工件示例一
对象版本: 1
对象指纹: 由运行时计算
因果事件编号: 事件示例零
来源类别: 运行时记录

```

字段是否必填由事件类型决定。没有子任务的事件不强制填写任务和尝试编号。生产者序号只用于本生产者内部排序，不能当成跨进程全局时间。事件去重键为“运行编号＋事件编号”；事件载荷冲突时隔离处理，不能静默保留任意一份。

### 补全提案的处理规则

补全提案按以下顺序处理：校验发送方和权限 → 消息去重 → 校验目标与计划版本 → 校验对象指纹与有效期 → 校验字段白名单 → 复核证据 → 判断影响 → 生成新记录或新工件版本 → 必要时重新验收 → 返回采纳回执。

非关键状态发生变化时，不必机械拒绝整个报告，但必须检查提案所依赖的字段是否变化。目标、责任契约、证据对象或闸门规则发生变化时，旧提案不得直接采纳，应重建基线并重算。

| 提案影响 | 合法处理 |
|---|---|
| 仅补充观测耗时、事件关联或派生统计，不改变业务事实与验收依据 | 写入带来源的观测扩展区；保留原始事件；不必重跑业务闸门 |
| 补充正式工件的来源、输入映射或用于验收的数据 | 由授权组件生成新工件版本；重跑工件闸和受影响的组合闸 |
| 改变责任范围、验收条件、预算或工具权限 | 提交变更申请；由原治理流程批准并产生新版本，探针不得直接实施 |
| 发现责任实际上没有完成 | 生成业务缺口或重派建议；由执行流程派工，不得用观测字段伪装完成 |

探针不得改写父目标完成状态、正式闸门结论、已结算费用、原始事件时间或授权范围。补全不是覆盖历史，也不是自动授权。

### 超时、停机与闭环终止

非关键观测超时：执行流程继续运行，输出明确标注观测缺口。业务验收所必需的证据缺失：保持待补充或转人工，不得默认通过；执行流程可以使用自身合法取证渠道，不要求某个特定探针必须在线。

同一缺口的去重键为“运行编号＋目标版本＋计划版本＋对象编号＋字段路径＋规则版本”。同一时刻最多一个补全请求在途，重试、读源次数和总耗时受独立预算限制。建议不自动触发派工，报告生成事件不自动触发下一轮同类观测。

缺口只能在证据补齐且必要的重验通过后关闭；预算耗尽、请求被拒绝、任务终止、目标升级或证据无法恢复时，以对应终止原因结束本轮补全，保留未解决状态。

## 十、挂载点与联动控制

### 10.1 推荐挂载点

| 执行阶段 | 优先运行的探针 | 补全价值 | 是否直接控制执行 |
|---|---|---|---|
| 父目标和责任基线冻结后 | 目标基线、委派契约 | 找到责任来源、无主项和范围完备性缺口 | 否，交由执行流程处理 |
| 派工前或权限配置变化后 | 执行隔离、时延与预算 | 核对授权和资源边界；补齐缺失配置证据 | 否，硬限制由运行时执行 |
| 收到子执行者工件后 | 完成状态、工件与证据 | 关联尝试、工件和来源；避免把返回当成功 | 否 |
| 候选集合形成、组合闸前后 | 组合验收、完成状态 | 定位覆盖、重复、冲突和版本差异 | 否，正式裁决仍由闸门产生 |
| 局部失败、重试或恢复时 | 失败与恢复、时延与预算 | 补齐失败范围、可复用结果和累计消耗 | 否 |
| 父目标提交及补全回执后 | 完成状态、补全闭环 | 核验提交基线、关键缺口是否真正关闭 | 否 |
| 独立定时检查或离线复盘 | 观测质量及适用业务探针 | 发现迟到事件、失联引用、历史记录缺口 | 否 |

挂载点是可选调用入口，不要求把每个探针变成主工作流中的阻塞节点。事件订阅、阶段快照和显式请求都可以使用，前提是满足相同版本与权限契约。

### 10.2 阻断依据来自业务，不来自探针存在与否

如果某项数据仅用于性能统计，探针失败不阻断交付。若某项证据是业务验收的必要条件，执行流程必须取得合法证据或保持待补充；它可以自行读取，也可以请求探针，不依赖某个特定探针在线。

规则明确要求“发布前必须完成独立复核”时，复核结果属于正式验收条件。此时缺失该结果会阻断发布，但不能由探针擅自新增这条规则，也不能把普通监控报告冒充独立复核。

### 10.3 防止反馈循环

一次观测只处理指定基线、范围和字段。报告、指标刷新和日志补写默认不再次触发同一观测请求；只有新的业务事件、证据到达或显式复核要求才能开启下一轮。

每个缺口维护请求次数、在途状态、累计读源消耗、下次允许重试时间和终止原因。父目标取消或升级后取消旧基线请求；无法确认停止的外部读取不得假装已经终止，但旧结果不能写入新业务版本。

## 十一、独立运行模板与输出示例

### 11.1 只读独立检查模板

以下阈值只是示例配置，不是通用推荐。材料引用应替换为实际可读取的对象。

```yaml
观测任务编号: 独立检查一
运行模式: 独立检查
观测目的: 检查责任覆盖、候选超额和局部完成是否被当成整体完成
输入:
  材料引用: [目标与责任快照一, 任务记录一, 工件包一, 闸门记录一]
  运行编号: 简报运行一
  目标版本: 1
  计划版本: 1
  观察阶段: 已封口快照
  快照编号: 快照一
探针配置:
  启用探针: [目标基线, 委派契约, 完成状态, 工件与证据, 组合验收, 观测质量]
  规则版本: "0.1.0"
  缺失值策略: 明确未知
  自动业务写入: false
  只读补查: false
  最大观测时限秒: 60
输出:
  报告格式: 中文结构化报告
  输出证据目录: true
  输出补全提案: true
  应用补全提案: false
```

此时探针完全可以不调用执行流程。它只能检查输入中真实存在的材料；不存在的引用或工具应列为读取失败，不能假装已经查到。

### 11.2 原文演示口径与生产探针口径分开

| 项目 | 模糊委派 | 责任委派 |
|---|---:|---:|
| 原文资料卡责任字段覆盖 | 三项中的一项 | 三项中的三项 |
| 原文重复数量 | 二 | 零 |
| 原文组合结果接收 | 否 | 是 |

这张表复述来源一的演示，不是本文执行了课程仓库。原文演示使用责任字段计数，生产系统不能仅凭字段自报就认定有效履约。

为说明本文口径，构造一个额外的确定性样例：预期责任共三项；三份工件经过可信的工件验收后，都被确认只履行责任一；允许候选数为一；执行流程已经按明示规则从中选择一份作为当前提交工件，另外两项责任确认尚未交付。该样例可代表对旧系统或故障记录的独立复盘，不表示本规范会允许缺项计划通过派工检查。

```yaml
探针执行状态: 已完成
观测结论:
  必需责任数: 3
  当前已确认有效履约责任数: 1
  有效履约覆盖率: 0.333333
  候选超额覆盖数: 2
  提交集合非法重复键数: 0
  缺失责任: [状态管理, 跨边界交接]
  组合验收复核: 不通过
  完成状态写入: 未执行
数据边界:
  工件验收及候选选择: 由该样例的可信输入显式给定
  真实模型研究表现: 未测试
  真实来源内容正确性: 不由这组计数证明
补全判断:
  类型: 业务责任未完成
  可以补充: 缺口与责任关联记录
  不可以补充: 两项责任的已完成状态
建议动作:
  由执行流程处理: 对缺失责任局部派工并重新验收
```

候选超额为二而最终重复为零并不矛盾：前者发生在选择前，后者是实际提交集合的结果。即使去重成功，缺失责任依然存在。

### 11.3 证据不全时的输出

已确认两项责任通过，但第三项工件是否通过无法读取时，应输出“覆盖未知，已确认下界为三分之二，可能上界为一”，并列出证据缺口。

如果主流程明确记录第三项没有执行，则是“已确认覆盖为三分之二，业务缺一项”。如果连总责任数都未知，则不能给三分之二或任何覆盖区间，只能报告已有工件数量和分母缺失。

## 十二、交互补全示例

### 12.1 工件证据补全提案

执行流程提交观测请求，指出某份工件缺少来源定位，并授予对既有资料库的只读权限。探针读取后核验来源与结论的对应关系，再返回提案。下面仅展示消息数据体；实际发送应使用共享消息信封。

```yaml
补丁编号: 补丁一
目标对象:
  工件编号: 状态工件一
  工件版本: 1
  字段路径: 证据.来源定位
基线值指纹: 由实际对象计算
建议值:
  来源对象: 输入快照中的状态说明一
  来源版本: 1
  内容定位: 状态隔离说明段
证据:
  证据性质: 直接观测
  输入快照引用: 输入快照一
  读取记录引用: 只读调用回执一
  支撑关系核验引用: 独立核验记录一
有效期说明: 目标、任务契约、来源和工件版本保持一致期间
预期影响: 补充正式工件的验收依据
建议处理:
  写入方: 执行流程授权的工件写入组件
  新工件版本: 2
  必需重验: [工件闸, 受影响的组合闸]
自动写回: false
```

执行流程仍要检查身份、权限、指纹、来源和有效性。如果工件已经更新，旧提案应拒绝、替代或重新基线化，不允许直接覆盖。采纳后工件版本是否为二由权威写入方确认，探针不能预先把建议版本当成事实。

### 12.2 补全回执不能越过重验

字段已经写入但工件闸仍未通过时，探针记录“提案已采纳、关键缺口未关闭”。工件闸通过而组合闸发现跨工件矛盾时，也不能宣布补全闭环成功；应保留证据缺口已修复、组合冲突仍未解决这两个独立状态。

一次补全可能解决数据缺口而未解决业务问题。报告应分别列出字段修复结果、工件验收结果、组合验收结果和父目标状态，不压缩成单个“成功”。

## 十三、场景配置与复用方式

| 场景 | 必需观测对象 | 专用口径 | 不应套用的假设 |
|---|---|---|---|
| 研究简报 | 主题责任、结论、来源、综合产物 | 主题覆盖、来源链、结论支撑与未解决冲突 | 来源多等于覆盖全；清单全等于开放范围穷尽 |
| 输入分片处理 | 输入主键清单、分片映射、输出逐条记录 | 主键覆盖、非法重复、额外主键、例外处置 | 文件数相等就代表输入记录完整 |
| 多人代码修改 | 工作区、变更、依赖、局部及集成测试 | 变更范围、冲突、复用、测试与合并结果 | 每个分支测试通过就代表合并后正确 |
| 事故调查 | 事件时钟、证据链、假设、影响范围 | 时间一致性、证据缺口、因果冲突 | 日志时间自然可比；缺少日志等于事件未发生 |
| 权限敏感处理 | 授权引用、最小输入、调用回执、批准记录 | 实际越权与拦截分离、全量主键核对、最终动作许可 | 只看工具菜单就能证明没有越权 |
| 普通链式或路由流程 | 步骤输入输出、分支规则、状态和裁决 | 工件、版本、证据、耗时与数据缺口 | 必须存在主管与多个子执行者 |

接入新场景时，只需声明数据源映射、责任或步骤口径、唯一键、工件结构、验收规则和补全白名单。源数据不支持的指标禁用或标为未知，不为了保持统一面板而编造适用性。

## 十四、探针自身的失败处理与验收用例

### 14.1 自身运行状态

探针状态可以使用：待输入、采集中、核验中、补查中、待回执、已完成、部分完成、失败、已终止。它们与被观察父目标的状态独立，不能互相复制。

部分数据源失败时输出已完成检查、未完成检查与影响范围；关键材料完全不可读时返回失败或待输入，而不是一份所有值为零的健康报告。写报告失败也要保留运行失败信息，避免业务侧把没有报告误当没有问题。

### 14.2 验收与回归用例

以下是实现应满足的预期，不是已执行真实系统的证明。

| 编号 | 场景 | 预期结果 |
|---|---|---|
| 探针验收一 | 无主流程在线，仅有完整离线快照 | 能输出独立报告和未应用提案，不要求调用执行流程 |
| 探针验收二 | 只有三张工件，没有责任基线 | 可统计工件数；责任覆盖率未知 |
| 探针验收三 | 三项责任，可信核验与选择后仅一项履约 | 有效履约覆盖为三分之一；缺少两项业务责任 |
| 探针验收四 | 三份当前候选同属一责任，允许一份；最终只选一份 | 候选超额为二，提交集合重复为零，不混淆两者 |
| 探针验收五 | 约定每项责任需两份独立复核，确有两份 | 不记为超额；仍核验独立性与冲突处理 |
| 探针验收六 | 三项责任，两项已确认通过，一项裁决不可读 | 覆盖值未知；可报告下界三分之二、上界一和未知原因 |
| 探针验收七 | 同一事件重投三次 | 只记一次，不增加尝试和候选数量 |
| 探针验收八 | 同一事件编号出现不同内容 | 隔离并报告冲突，不任意择一 |
| 探针验收九 | 工件责任标签正确，但来源不支撑结论 | 不以标签计有效履约；报告语义核验问题 |
| 探针验收十 | 只有开始事件且时钟不可比较 | 不伪造结束时间或精确耗时 |
| 探针验收十一 | 日志经过抽样，没有可信总事件数 | 事件完整率未知，不能报告全量零违规 |
| 探针验收十二 | 缺少结束事件，但可信实例回执可恢复 | 标明历史恢复来源，不覆盖原始事件 |
| 探针验收十三 | 原始业务数据没有任何可信来源 | 返回业务补做或输入缺口，不自行生成正式值 |
| 探针验收十四 | 新资料仅在原任务之后出现 | 标记当前补充证据，不能证明原任务当时已获证 |
| 探针验收十五 | 补全提案目标版本已过期 | 不应用，返回过期或重新生成提案 |
| 探针验收十六 | 提案要求改父目标完成状态 | 拒绝越权字段，保留诊断和拒绝原因 |
| 探针验收十七 | 提案已采纳，关键组合重验未通过 | 字段采纳可计入，关键缺口不能关闭 |
| 探针验收十八 | 所有执行者已回报，组合闸不通过 | 返回率可以为一，但父目标仍未通过 |
| 探针验收十九 | 正式完成状态存在，验收日志不可读 | 报疑似误报或未知；不武断确认违规 |
| 探针验收二十 | 同一缺口被多次刷新或报告触发 | 去重且受预算约束，不形成自激循环 |
| 探针验收二十一 | 探针离线，运行时仍有合法验收能力 | 非关键观测不阻塞；关键证据仍依业务规则处理 |
| 探针验收二十二 | 把其他计划版本的责任集用于当前统计 | 拒绝混算，按版本分组重建分母 |

## 十五、可直接用于技能配置的探针指令

你的职责是观察工作流、核验数据并提交受控补全，不是替业务执行或宣布完成。
