# 层级委派：执行流程

> 目标：把一个父目标转成边界清楚、能够交付、能够验收的子责任；保留稳定的总责任人，通过工件闸和组合闸确认父目标完成。
>
> 本文可以单独作为工作流或技能的执行规格，也可以与《32_层级委派_工作流可观测性探针.md》联动。探针不是执行流程的必需依赖，不代替派工、授权或验收。

## 一、依据、范围与设计边界

本文的来源只有两份：用户提供的黄佳第32讲《层级委派：把大目标拆成可验收的责任》〔来源一〕，以及 `hanerss_skill_framework_v0_1.md`〔来源二〕。文末给出对应章节。

| 内容 | 来源性质 | 本文处理 |
|---|---|---|
| 稳定责任人、动态拆分、隔离执行、中心化综合 | 原文核心机制 | 保留为执行主线 |
| 委派任务、结构化工件、工件闸与组合闸 | 原文工程结构 | 扩展成明确的输入、输出与状态转移 |
| 单项失败局部重派、限制递归、执行者可替换 | 原文原则 | 增补版本校验、重试边界与适配器要求 |
| 注册表为源数据、矩阵为视图、技能为执行化产物 | 框架原则 | 沿用已有基座、标识规则与草稿目录 |
| 消息契约、并发提交、补全提案、幂等、字段白名单 | 本文设计扩展 | 为独立运行和交互运行补充，不宣称原文或框架已实现 |

框架 v0.1 明确只建立基座，尚不填充具体工程模式或技能实现。本文属于其“后续填充入口”的一份模式执行草案，不修改基座定义，也不声称已经登记或部署。正文不验证原文提及的框架现状，不依赖其中任何特定产品。

元数据中的模式与技能标识均为建议值；登记前应对现有注册表查重，登记后保持稳定。`draft` 是资产生命周期状态，不是某次任务的执行状态。

## 二、框架挂载与模块责任

### 2.1 挂载位置

| 项目 | 定义 |

| 主要拓扑 | 层级，引用 `TOP_HIERARCHY` |

| 技能产物 | 本文对应的执行技能；配套探针是可复用的观测技能 |
| 建议归档 | 框架既有的 `04_skills/draft/`；模式说明可挂入 `03_patterns/draft/` |
| 注册方式 | 先登记模式与技能，再由引用生成矩阵视图；不得只在矩阵中写入孤立内容 |

执行过程可以并发运行子任务，但并发只是调度策略；本模式的核心仍是父子责任关系，而不是同时启动多少个执行者。〔来源一：核心机制；来源二：第4—8、16、18节〕

### 2.2 谁负责什么

| 组件 | 必须承担的责任 | 不应承担的责任 |
|---|---|---|
| 父目标责任人 | 保留总目标，确认拆分，处理缺口，批准变更，对整体交付负责 | 以“所有子调用已结束”替代父目标验收 |
| 核心运行时 | 身份、工具权限、资源限制、任务状态持久化、取消、幂等和提交控制 | 依赖模型承诺来实现权限隔离 |
| 子执行者 | 在授权范围内完成局部责任，形成工件，报告失败与不确定性 | 擅自扩展责任、发布整体结论、自行增加下级任务 |
| 工件验收器 | 按责任契约验收单项工件，生成有依据的裁决 | 仅凭工件自报“已完成”放行 |
| 组合验收器 | 对候选工件集合和最终交付物检查覆盖、冲突与全局约束 | 把单项通过数量当成整体正确性的证明 |
| 可观测性探针 | 读取证据、发现数据缺口、提供补全提案与诊断 | 直接改写上述组件的权威状态 |

这些是逻辑角色，可以由确定性程序、工作流引擎、模型和人工共同实现，不要求每个角色都对应一个独立智能体。可编码规则由程序执行；语义核验可以引入独立评审，但不能让提交者仅凭自己的声明完成验收。

## 三、适用条件与不变约束

### 3.1 何时进入本流程

有一个需要统一验收的父目标，且能够识别至少两个可区分的责任单元，或者需要跨权限、上下文、执行环境分开处理时，进入层级委派。

输入过短、一个执行者足够、责任无法区分，或者多个执行者必须持续共享未结构化的临场决策时，应输出“本模式不适用”及原因，转给更简单的执行流程。不能为了使用本模式强行增加主管和子执行者。〔来源一：适用场景〕

### 3.2 无论场景如何变化都必须保持

1. 父目标始终有一个明确的当前责任人；责任人转移必须留下交接记录。
2. 先明确验收对象和责任边界，再选择执行者；不能先列角色再寻找交付物。
3. 子执行者只能得到完成责任所需的上下文、工具、预算和输出位置。
4. 执行者返回、工件通过、父目标通过是三个不同事件。
5. 工件必须与原始责任契约、输入和目标版本建立可追溯关系。
6. 未知的关键证据不能当成通过；非关键观测缺失也不能被误判为业务失败。
7. 局部补做只影响相关责任；复用旧工件必须再次确认版本与依赖仍有效。
8. 探针只能提供观测和受控补全，正式验收及业务状态变更仍属于执行流程。

## 四、独立运行需要的输入与产物

### 4.1 输入契约

| 输入 | 必需性 | 最低要求 | 缺失处理 |
|---|---|---|---|
| 父目标 | 必需 | 目标编号、预期交付、明确责任人 | 无法识别时不派工 |
| 验收依据 | 必需 | 用户要求、业务清单或可确认的初始验收规则 | 先形成草案并确认；不能直接宣布拆分完整 |
| 输入资料 | 按场景必需 | 不可变引用或内容指纹，说明范围、时间和可使用权限 | 标记待补充，不虚构资料 |
| 场景配置 | 必需 | 分解方式、唯一键、依赖、工件结构、组合约束 | 先生成配置草案，批准后冻结 |
| 执行能力 | 必需 | 可用执行者、工具适配器、权限范围及实际可达性 | 无相应能力则返回受限状态 |
| 资源约束 | 必需 | 总预算、单任务额度、截止时间、并发和委派深度限制 | 采用已批准的运行配置；没有配置则不无限执行 |
| 保存能力 | 必需 | 任务状态、工件版本、闸门裁决的可恢复存储 | 不能持久化时只能试运行，不宣称具备可靠恢复能力 |
| 探针结果 | 可选 | 与当前基线兼容的报告或补全提案 | 缺失时按本流程自行验收 |

### 4.2 必须交回的产物

最终输出应包含父目标状态、冻结后的责任计划、有效工件清单、工件闸与组合闸记录、未解决缺口、资源与版本摘要、最终交付物引用、后续动作边界。

不能只交回一段综合文本。即使失败，也必须能回答：哪里未完成、现有结果还能否复用、失败属于证据不足还是业务不合格、下一步需要谁决定。

## 五、业务对象与版本契约

本节是执行流程自身的数据模型，不依赖探针。这里的中文字段是建议的业务契约；接入实际运行时可以做字段映射，但不能改变字段语义。

### 5.1 父目标与责任基线

| 对象 | 最小字段 |
|---|---|
| 父目标 | 运行编号、父目标编号、目标版本、责任人、交付说明、范围内事项、范围外事项、输入引用、全局约束、截止时间 |
| 责任基线 | 基线编号、目标版本、必需责任清单、可选责任清单、原始要求映射、清单来源、完备性确认方式、审批记录 |
| 责任单元 | 责任编号、可验收问题、边界、交付对象、验收规则、证据要求、基数规则、唯一键、依赖责任 |
| 委派计划 | 计划版本、责任到任务的映射、执行顺序、并发策略、预算分配、修复与终止策略 |

责任基线来自父目标和外部要求，不能从“当前已经返回的工件”反向生成，否则缺失责任会从分母和验收条件中一起消失。

对开放研究，责任清单只能代表“已确认范围内的覆盖要求”。若缺乏可信的外部完备性清单，应记录“范围完备性待独立评审”，不能把枚举项全部完成包装成对开放世界问题的穷尽。

### 5.2 责任与任务不是同一个对象

“责任”描述最终必须交付什么；“任务”是为该责任安排的一次委托；“尝试”是该任务的一次实际执行。换人、重试和补做不应无条件增加父目标的责任数量。

每个必需责任默认只有一个交付责任人。需要双人独立复核、候选对比或冗余执行时，必须在契约中明确：需要几份独立结果、独立性如何确认、冲突由谁裁决、最终接收哪一份或怎样合并。不能把有意复核全部算作重复劳动。

### 5.3 委派任务契约

| 字段组 | 内容与限制 |
|---|---|
| 身份与版本 | 任务编号、责任编号、父目标编号、目标版本、计划版本、契约版本号、执行者实例编号、尝试编号 |
| 局部目标 | 要回答的问题、必须完成的检查项、明确不做的事情 |
| 输入范围 | 输入引用、输入指纹、必要背景、依赖工件版本；不默认继承父会话全部内容 |
| 交付约定 | 工件结构、保存位置、结论与证据对应方式、失败工件结构 |
| 工具与权限 | 可见工具、服务端授权引用、数据范围、读写边界、敏感动作审批条件 |
| 资源边界 | 单次额度、累计额度、执行截止时间、最大尝试数、允许的最大委派深度 |
| 验收与回报 | 工件闸规则、回报地址、心跳或状态查询方式、取消凭据 |

删掉一项任务后应能说明最终交付少了什么；若它是有意复核，则应能说明少了哪项独立核验。无法回答时，退回拆分环节。〔来源一：责任划分〕

### 5.4 正式工件契约

| 字段组 | 内容与限制 |
|---|---|
| 工件标识 | 工件编号、工件版本、工件类型、内容指纹、存储引用 |
| 对应关系 | 运行、父目标、目标版本、计划版本、责任、任务、契约、尝试编号 |
| 生产者 | 执行者实例及运行时确认的身份，不只接受模型填报的名称 |
| 业务内容 | 结论、完成项、未完成项、不确定性、适用范围；每个重要结论对应证据 |
| 证据 | 来源引用、来源版本或快照、获取时间、输入指纹、必要的定位信息 |
| 执行摘要 | 状态、错误、已发生副作用、消耗记录引用、完整执行记录引用 |

主管默认接收压缩工件与可展开引用，不接收整段子会话。完整记录留在权限受控的存储中；记录工具调用和可核验的决策摘要，不要求读取或保存模型的隐藏思维过程。〔来源一：结果工件化；最后一句为本文治理约束〕

失败工件仍必须包括身份、版本、失败阶段、已完成部分、可复用工件、是否可能已产生外部副作用和可否重试。失败不是无输出。

### 5.5 闸门裁决契约

裁决至少包含：裁决编号、闸门类型、目标与计划版本、被审对象及版本、输入集合指纹、规则版本、逐条结果、证据引用、裁决者、裁决时间、允许的后续动作。

逐条结果限定为：`通过、不通过、未知、不适用`。不适用必须有场景规则或经授权的豁免理由；不能用于隐藏未完成项。必需规则出现不通过或未知时，不能生成通过裁决。

## 六、执行节点

```text
接收父目标
  → 建立责任基线
  → 生成并校验委派计划
  → 隔离派工
  → 接收结果工件
  → 工件闸
  → 选择有效工件集合
  → 组合闸与综合产物核验
  → 提交父目标验收结果
  → 归档交付

工件闸或组合闸未通过
  → 分类缺口
  → 补证 / 局部重派 / 修订计划 / 人工处理
  → 回到受影响节点
```

### 执行一：接收目标并判断适用性

**输入：** 用户任务、范围约束和能力清单。

**动作：** 识别交付对象、总责任人、截止时间与敏感动作；判断是否有真实可拆的责任。分清“生成可发布内容”和“实际对外发布”是否都是目标的一部分。

**输出：** 父目标草案、适用性结论、缺失输入清单。缺少关键输入时停在待补充，不伪造执行者或工具。

**事件：** 父目标已接收、适用性已判断。

### 执行二：建立责任基线

**输入：** 父目标草案及其原始要求。

**动作：** 把目标拆成可验收的最小责任，逐项映射回原始要求；列出必需与可选项、依赖、基数与全局约束。采用输入主键分片时，先冻结预期主键集合；按主题拆分时，先确认主题范围与口径。

**输出：** 责任基线、验收规则、范围完备性说明。开放范围未确认时转独立评审或人工确认。

**事件：** 责任基线已建立、目标基线已冻结。

### 执行三：生成并校验委派计划

**输入：** 冻结责任基线、执行者与权限配置。

**动作：** 生成任务契约，执行“删掉任务会少什么”的检查；检查责任遗漏、未经声明的重叠、依赖循环、预算超分配和权限越界。依赖尚未满足的任务只能进入等待队列，不得读取未验收的半成品冒充稳定输入。

**输出：** 已批准的计划版本、每项任务契约、资源预留。无法满足约束时输出计划不成立，不启动局部任务来掩盖缺口。

**事件：** 委派计划已冻结、任务契约已生成、预算已预留。

### 执行四：在边界内派工

**输入：** 已批准的任务契约。

**动作：** 创建独立会话或工作区，提供最小输入、工具白名单和服务端授权；分配独立预算，登记尝试编号。默认不允许子执行者继续创建下级任务；确需递归时，先批准子责任树并保留父级验收责任。

**输出：** 已启动任务及可查询的执行实例。权限、输入或能力不匹配时不启动。

**事件：** 任务已派发、尝试已开始、权限检查已拒绝、工具调用已开始或结束。

### 执行五：接收并固定结果

**输入：** 子执行者提交的成功或失败工件。

**动作：** 检查身份、任务关系、当前尝试及版本；按消息编号去重；保存不可变工件。已取消尝试、失效目标版本或未登记生产者提交的结果进入隔离区，不直接加入候选集合。

**输出：** 待验收工件，或拒收与隔离记录。此时只能标记“执行者已返回”，不能标记父目标成功。

**事件：** 执行者已返回、工件已登记、迟到结果已隔离。

### 执行六：执行工件闸

**输入：** 待验收工件、原始任务契约和可信输入。

**动作：** 依次检查结构、身份、版本、责任对应、证据可定位性与内容支撑关系，再执行场景专用规则。字段齐全只是结构检查通过，不代表结论正确。

**输出：** 通过工件、待补证工件或不通过工件及明确理由。补证会改变正式工件时生成新版本，不直接修改已经裁决的旧版本。

**事件：** 工件闸已裁决。

### 执行七：组建有效工件集合

**输入：** 工件闸通过的候选工件。

**动作：** 按责任、唯一键与基数规则选择当前有效版本；排除重复投递、已被替代尝试及过期依赖。多份独立结果存在冲突时，进入明示的裁决流程，不由主管随意选“看起来更好”的一份。

**输出：** 带成员清单与集合指纹的组合候选集，以及未被选入的工件和原因。

**事件：** 候选集合已冻结、重复候选已识别、冲突已登记。

原文演示把资料卡直接交给组合闸并拒绝重复。本文增加的版本选择环节只解决生产中的重试、替换与冗余治理，不抹掉已经发生的重复劳动，也不能用去重后的集合掩盖责任缺失。

### 执行八：执行组合闸并核验综合产物

**输入：** 组合候选集、责任基线和全局约束。

**动作：** 检查必需责任覆盖、唯一性或约定基数、跨工件口径、冲突、依赖版本和全局资源约束。形成综合产物后，再检查它是否忠实保留工件证据，是否出现无来源的新结论或删掉必要限制条件。

**输出：** 绑定候选集合指纹及综合产物版本的组合裁决。语义尚不明确时输出未知并升级评审，不把一段流畅总结当成验收依据。

**事件：** 组合闸已裁决、综合产物已核验。

### 执行九：定位缺口并局部修复

**输入：** 任一道闸门的非通过结果。

**动作：** 把缺口分成证据缺失、业务未完成、错误结论、跨工件冲突、范围或版本变化、权限问题及外部执行结果不明。仅对相关责任补证、重派或重审；保留仍有效的已通过工件。

**输出：** 有预算和终止条件的修复计划，或者待审批、失败、终止决定。探针可以参与补证，但不直接发起业务重派。

**事件：** 缺口已登记、补全已请求、责任已重派、目标或计划已升级。

### 执行十：原子提交父目标验收结果

**输入：** 两道闸门均通过的当前版本产物。

**动作：** 提交前再次核对目标版本、计划版本、状态修订号、候选集合指纹及规则版本。只有仍与裁决基线一致时，才能把父目标状态提交为已验收；不一致则重验受影响部分。

**输出：** 唯一的正式验收结果和结果版本。采用比较后写入或等价事务机制，防止旧组合裁决覆盖新计划。

**事件：** 父目标已验收，或提交基线已失效。

### 执行十一：归档并交付

**输入：** 验收结果及已批准的交付要求。

**动作：** 保存目标、任务、工件、裁决与版本关系，输出最终交付包。需要外部动作时使用独立授权和幂等键，并记录真实回执。

**输出：** 交付包及其交付状态。默认情况下，“内容验收通过”不等于“已经发布、付款或部署”。如果父目标本身包含外部执行，该动作必须作为必需责任纳入基线；只有其回执通过验收，父目标才允许完成。

**事件：** 结果已归档、交付动作已回执、外部结果待核对。

## 七、两道闸门的具体判定

### 7.1 工件闸：这个责任单元能不能接收

| 检查项 | 必须核验的内容 | 不能接受的替代判断 |
|---|---|---|
| 结构 | 约定字段、数据类型、必要引用 | 能解析成对象就算业务正确 |
| 归属 | 责任与任务契约、生产者身份、尝试关系 | 工件自己填写了正确责任名称 |
| 版本 | 目标、契约、输入、依赖与工件版本 | 来源相似便视为可复用 |
| 证据 | 能定位到支撑该结论的内容，时间和范围适用 | 仅有一个可打开的链接 |
| 局部语义 | 实际回答了所分配的问题，必要检查均完成 | 文本足够长或措辞足够自信 |
| 业务约束 | 输入主键、金额、测试结果等按场景规则核对 | 让执行者自行保证没有遗漏 |
| 边界 | 未越权、未夹带无授权动作、外部副作用状态明确 | 新会话天然意味着权限隔离 |

工件可以通过结构检查而未通过语义检查。来源内容不能获取、关键规则没有执行结果、权限凭据不可确认时，对应检查为未知，不自动判成事实错误，也不自动放行。

### 7.2 组合闸：所有工件能不能共同完成父目标

| 检查项 | 判定依据 |
|---|---|
| 必需责任齐全 | 对责任基线中的每一项，都存在与当前版本兼容、工件闸通过且满足基数规则的有效交付 |
| 无非法重复 | 按责任或输入主键识别未经允许的重复；一份文件可以包含多个主键，不能只按文件数验收 |
| 口径相容 | 时间范围、单位、对象范围、定义、接口版本与必要假设一致 |
| 无未解决冲突 | 对相互矛盾的结论或数据有裁决结果；简单拼接不算解决 |
| 全局约束成立 | 例如全部输入主键覆盖、总量守恒、总预算、集成测试和敏感动作审批 |
| 综合没有失真 | 最终产物没有丢掉必要条件，没有生成无法追溯的新结论 |
| 裁决基线有效 | 候选集、目标、计划、规则与最终提交时的版本一致 |

父目标通过条件是所有必需检查均通过，而不是一个加权总分达到阈值。即使大部分责任很好，也不能用它们的得分抵消一个关键责任缺失。

需要人工豁免时，应先生成带批准依据的目标或规则变更，再按新版本验收；不得在原规则下把不通过直接改为通过。诊断性覆盖率等统计放在探针文档中，执行闸门不依赖探针返回一个百分比来放行。

## 八、运行状态与版本规则

### 8.1 三类状态分别维护

| 状态对象 | 建议状态 | 特别限制 |
|---|---|---|
| 父目标 | 待建模、待派工、执行中、验收中、修复中、待补充、待审批、已验收、失败、已终止 | 只有当前有效组合裁决才能进入已验收 |
| 执行尝试 | 待启动、执行中、已返回、失败、超时、取消请求中、已取消、结果待核对 | 已返回只说明收到工件；取消请求不代表外部执行已经停止 |
| 工件 | 待验收、已通过、待补证、未通过、已隔离、已被替代 | 执行尝试成功不自动改变工件验收状态 |

责任完成状态由当前有效的已通过工件及基数规则推导，不由最后一次子调用状态推导。修复是父目标的非终态；失败和已终止必须说明是否允许新运行继承有效工件。

### 8.2 版本变化如何处理

| 变化 | 应产生的记录 | 对既有结果的影响 |
|---|---|---|
| 目标范围、必需责任或验收口径改变 | 新目标版本及责任基线 | 评估所有受影响工件；不受影响项也要有明确兼容性记录 |
| 执行者、调度或任务映射改变 | 新计划版本；必要时新任务契约版本 | 旧尝试结果不能直接写入新计划，可经兼容性核验重新接纳 |
| 同一任务重试 | 新尝试编号，保留原失败记录 | 不新增父目标责任，不重置累计消耗 |
| 正式工件内容或验收来源改变 | 新工件版本与指纹 | 原裁决不覆盖新版本；重跑受影响闸门 |
| 只补观测数据 | 新观测记录或报告版本 | 不修改原工件；没有验收影响时不要求重跑业务 |

主管发生替换时，通过运行时的单一写入权或等价机制保证同一父目标只有一个有效提交者。恢复者必须读取持久化目标、计划、尝试和裁决，不能仅凭新会话中的简述恢复执行。

## 九、失败、预算、恢复与外部执行者

### 9.1 缺口分类与处理

| 情况 | 分类 | 处理 |
|---|---|---|
| 已知工件存在，但日志没有关联到该工件 | 观测证据缺失 | 在权限内查找可信记录，补关联，不重新做业务 |
| 工件来源无法定位，但结论需要该来源才能验收 | 验收证据缺失 | 补证或重做对应研究；补证后重验 |
| 根本没有人承担状态管理等必需责任 | 业务责任缺失 | 修订计划并派工，不能靠生成指标补齐 |
| 工件回答了错误问题 | 业务不合格 | 退回或重派，保留错误工件和原因 |
| 两个已通过工件在全局口径上冲突 | 组合不合格 | 创建有责任人的裁决任务；不得直接拼接 |
| 执行者超时，但外部动作可能已完成 | 执行结果不明 | 先核对外部回执及幂等键，未确认前不盲目重试 |
| 工具权限不足 | 授权受限 | 合法降级或申请授权；探针与执行者均不能扩大自身权限 |
| 超过累计预算或最终截止时间 | 资源终止条件 | 停止新增工作，尝试取消在途任务并归档部分结果 |

### 9.2 预算与重试

预算同时约束父目标总量和每项任务累计量。父级已确认消耗与在途预留之和不能超过批准额度；在途预留包含尚未结算和结果不明的调用，不能因为收到超时事件就释放。

重试必须使用新尝试编号，沿用同一责任编号，消耗计入该责任和父目标。最大尝试数包含首次尝试。主管综合、评审与必要的补全也有自己的预算，不能只给子任务设限而让主管无限循环。

资源单位必须显式声明。调用次数、词元数、费用和时间不能直接相加；不同供应方费用只有在有可信计费数据和统一口径后才能合计。

### 9.3 隔离与恢复

工具白名单与最小上下文保留原文隔离原则；本文额外要求资源服务在调用时核验身份、授权范围和有效期。隐藏工具不能替代服务端拒绝未授权请求。共享写入场景采用独立工作区、版本化合并和全局验证；缺少这些能力时改为串行或不采用本模式。

恢复过程先加载最近有效检查点，核对仍在运行或结果不明的尝试，再继续缺失责任。已接收工件不因主管重启而丢弃，也不因缓存存在而跳过版本核验。

### 9.4 替换外部执行者时不变与必验的部分

| 保持不变 | 必须重新验证 |
|---|---|
| 父目标、责任边界、输入引用、工件结构、验收规则、目标版本、失败报告要求 | 身份和权限映射、工具范围、会话隔离、工作区隔离、回调认证、超时与取消语义、预算计量、重复交付、存储可访问性、实际副作用 |

适配器至少支持提交任务、查询状态、获取工件和取消请求，或明确声明不支持的能力。缺少可靠取消能力时，应限制可授权动作和资源暴露，不能假装已经停止外部执行。

## 十、不同场景如何复用

通用流程、两道闸门、版本与权限边界不变；仅替换责任分解方式、工件结构、唯一键与验收规则。

| 场景 | 责任拆分 | 典型工件 | 工件闸 | 组合闸 |
|---|---|---|---|---|
| 开放研究与简报 | 按已确认主题、地区或对象 | 结论与证据卡 | 问题匹配、来源支撑、范围与时间 | 必需主题齐全、口径一致、无未裁决冲突；开放范围另行评审 |
| 合同、简历、工单批处理 | 按冻结输入主键或不重叠分片 | 每个主键的处理结果及例外 | 输入对应、字段正确、局部规则成立 | 预期主键集合完整覆盖、无非法重复、例外有处置 |
| 代码修改 | 按模块、接口或独立工作区 | 变更工件、测试记录、依赖说明 | 局部测试、范围与权限 | 合并冲突、接口一致、集成测试及全局限制 |
| 线上事故分析 | 时间线、代码变更、设施、影响 | 证据时间线和原因假设 | 时间来源、证据对应、事实与假设分开 | 时间线一致、关键空白明确、跨域因果冲突已评审 |
| 权限敏感的批次核对 | 按部门、数据域或职责分离 | 脱敏批次和校验记录 | 主键、输入指纹、局部总量及授权 | 全量覆盖、全局重复与总量、最终动作审批 |

批处理的“每个输入主键恰好一次”和研究的“至少两份独立复核”是不同规则，必须由场景配置决定，不统一写死为“每个责任只能有一张卡”。敏感场景这里只给出工程控制示例，不提供具体业务或法律规则。

## 十一、不接探针时的最小启动模板

以下是配置示例，不是所有场景的推荐阈值。输入引用需由调用环境提供真实对象。

```yaml
运行模式: 独立执行
父目标:
  父目标编号: 简报目标一
  目标版本: 1
  责任人: 主管一
  交付说明: 形成一份覆盖组织拓扑、状态管理、跨边界交接的简报
  输入引用: [已授权资料集合一]
  必需责任:
    - 责任编号: 责任一
      名称: 组织拓扑
      问题: 谁协调团队，任务如何分发
      基数规则: 恰好一份有效交付
    - 责任编号: 责任二
      名称: 状态管理
      问题: 上下文和状态如何隔离与保存
      基数规则: 恰好一份有效交付
    - 责任编号: 责任三
      名称: 跨边界交接
      问题: 结果如何跨执行者或系统交接
      基数规则: 恰好一份有效交付
场景配置:
  分解方式: 主题责任
  工件类型: 结论与证据卡
  工件必需字段: [责任编号, 结论, 来源引用, 来源定位, 输入指纹]
  组合规则: [必需责任齐全, 无非法重复, 无未裁决冲突, 综合结论可追溯]
执行配置:
  工具策略: 仅使用输入授权的读取能力
  对外发布: 不允许
  最大并发: 3
  最大委派深度: 1
  每任务最大尝试数: 2
  父目标总时限秒: 300
  预算单位: 调用次数
  父目标调用上限: 30
  每责任累计调用上限: 8
  主管与验收累计调用上限: 6
探针配置:
  启用: false
```

执行流程先核验责任基线和权限，再生成完整任务契约。即使关闭探针，仍保存运行时必需的状态、工件与闸门记录，仍自行完成两道闸门。关闭探针不等于关闭权限控制、预算控制或安全审计。

该模板提供的是可由工作流引擎或技能执行器解释的规范；没有实际工具绑定、存储和验收实现时，只能生成计划或报告能力缺口，不能宣称任务已经执行。

## 十二、与探针交互的共享数据契约
### 共享契约版本与对象归属

共享契约版本：`0.1.0`。本节在两份文档中完整保留，任何一份单独使用时都不依赖另一份文件才能解析消息。

| 数据对象 | 权威维护方 | 另一方的使用方式 |
|---|---|---|
| 父目标、责任清单、委派计划、运行状态、正式工件版本、闸门裁决 | 执行流程及其授权写入组件 | 探针只读，不覆盖原记录 |
| 工具授权、预算预留与结算、执行者身份、取消与恢复凭据 | 核心运行时及资源服务 | 执行流程和探针按权限读取 |
| 观测扩展区、指标结果、证据缺口、补全提案 | 探针 | 执行流程校验后引用或采纳 |
| 补全采纳回执、重新验收结果 | 执行流程 | 探针据此关闭或重开缺口 |

执行流程拥有业务状态写权限，不代表主管模型可以绕过运行时约束；探针生成报告，不代表它获得业务裁决权。

### 统一消息信封

```yaml
契约版本: "0.1.0"
消息编号: 消息示例一
消息类型: 观测请求
发送方: 执行流程
运行编号: 运行示例一
父目标编号: 目标示例一
目标版本: 1
计划版本: 1
基线快照编号: 快照示例一
基线状态修订号: 7
责任编号: null
任务编号: null
契约版本号: null
尝试编号: null
关联请求编号: null
产生时间: "2026-09-09T14:00:00+09:00"
截止时间: "2026-09-09T14:00:30+09:00"
数据体: {}
```

信封中的“契约版本”指通信协议版本；“契约版本号”指某项委派任务的业务契约版本，二者不能混用。消息编号必须唯一；重复投递同一消息时复用原编号。目标版本和计划版本描述业务口径，基线状态修订号描述同一口径下的运行状态，不得互相替代。仅与局部对象有关的字段可以为空；未知字段必须明确为空并说明原因，不得猜测补齐。上述时间仅为格式示例，不是建议的超时阈值。

| 消息类型 | 方向 | 数据体最小内容 | 是否允许直接改变业务状态 |
|---|---|---|---|
| 观测请求 | 执行流程→探针 | 观测范围、需补字段、规则版本、读取权限引用、预算、是否阻断及阻断依据 | 否 |
| 观测快照 | 执行流程→探针 | 目标与责任快照引用、工件清单、闸门记录、事件区间、数据完整性声明 | 否 |
| 观测报告 | 探针→执行流程 | 指标值及口径、证据引用、未知项、缺口、建议、报告版本 | 否 |
| 补全提案 | 探针→执行流程 | 补丁编号、目标对象、字段路径、基线值指纹、建议值、证据、有效期、影响范围 | 否 |
| 采纳回执 | 执行流程→探针 | 补丁编号、采纳状态、原因、新对象版本、受影响闸门、重验结果引用 | 只有执行流程按权限采纳后才允许 |

采纳状态限定为：`已采纳、部分采纳、已拒绝、已过期、已被替代`。部分采纳必须逐字段记录结果。需要重验但尚未完成时，回执明确标注“重验待完成”，不能据此关闭关键缺口。

### 最小事件信封

### 补全提案的处理规则

补全提案按以下顺序处理：校验发送方和权限 → 消息去重 → 校验目标与计划版本 → 校验对象指纹与有效期 → 校验字段白名单 → 复核证据 → 判断影响 → 生成新记录或新工件版本 → 必要时重新验收 → 返回采纳回执。

非关键状态发生变化时，不必机械拒绝整个报告，但必须检查提案所依赖的字段是否变化。目标、责任契约、证据对象或闸门规则发生变化时，旧提案不得直接采纳，应重建基线并重算。

| 提案影响 | 合法处理 |
|---|---|
| 仅补充观测耗时、事件关联或派生统计，不改变业务事实与验收依据 | 写入带来源的观测扩展区；保留原始事件；不必重跑业务闸门 |
| 补充正式工件的来源、输入映射或用于验收的数据 | 由授权组件生成新工件版本；重跑工件闸和受影响的组合闸 |
| 改变责任范围、验收条件、预算或工具权限 | 提交变更申请；由原治理流程批准并产生新版本，探针不得直接实施 |
| 发现责任实际上没有完成 | 生成业务缺口或重派建议；由执行流程派工，不得用观测字段伪装完成 |

探针不得改写父目标完成状态、正式闸门结论、已结算费用、原始事件时间或授权范围。补全不是覆盖历史，也不是自动授权。

### 超时、停机与闭环终止

非关键观测超时：执行流程继续运行，输出明确标注观测缺口。业务验收所必需的证据缺失：保持待补充或转人工，不得默认通过；执行流程可以使用自身合法取证渠道，不要求某个特定探针必须在线。

同一缺口的去重键为“运行编号＋目标版本＋计划版本＋对象编号＋字段路径＋规则版本”。同一时刻最多一个补全请求在途，重试、读源次数和总耗时受独立预算限制。建议不自动触发派工，报告生成事件不自动触发下一轮同类观测。

缺口只能在证据补齐且必要的重验通过后关闭；预算耗尽、请求被拒绝、任务终止、目标升级或证据无法恢复时，以对应终止原因结束本轮补全，保留未解决状态。

## 十三、交互运行的典型过程

### 13.1 只补观测记录，不改变业务结果

工件闸已经按可信输入通过，但主运行记录缺少执行结束时间。探针从同一执行实例的可信事件中恢复时间，并提交到观测扩展区。执行流程验证实例和事件后采纳；工件内容与验收依据没有变化，不重跑业务。

原始事件仍保持原样。若只能在稍后查询到“当前已经结束”，不能把查询时刻伪造为原始结束时刻；只能记录状态观测及时间边界。

### 13.2 补充验收证据，需要重新过闸

一张状态管理工件有结论，但缺少来源定位。探针在获准读取的既有工件库中找到可验证出处，提出补全。授权组件形成新工件版本，工件闸重新核验结论与来源，组合闸针对更新集合重验；全部通过后才能关闭此缺口。

若找到的来源是任务完成后才产生的新版本，必须标记“当前补充证据”，不能声称原任务当时已具备该证据。

### 13.3 发现业务缺口，只能返回派工流程

三个执行者都返回了组织拓扑材料，状态管理和跨边界交接没有有效交付。探针可以指出缺少两项责任及其证据，但不能生成两条“已完成”记录。主管应修订计划或局部重派，再按正常流程形成工件与验收结果。

### 13.4 探针不可用

执行流程没有探针仍能判断责任是否完成。缺少非关键性能统计时照常交付并披露缺口；缺少来源、授权或全量主键核验等必需验收证据时，使用自身合法取证能力补齐，或者保持待补充。不能因为探针离线而普遍放宽规则，也不能把所有工作无条件阻塞。

## 十四、验收与回归用例

以下用例是本文设计的验收要求，不是已运行课程仓库或真实业务系统的结果。

| 编号 | 输入或故障 | 必须得到的结果 |
|---|---|---|
| 执行验收一 | 三张合格工件实际都对应同一必需责任 | 不能通过组合闸；保留另外两项责任缺口及重复候选记录 |
| 执行验收二 | 三项不同必需责任各有一份有效工件，全部约束通过 | 允许提交父目标已验收 |
| 执行验收三 | 三项责任名齐全，但一项来源无法支撑结论 | 对应工件不通过或未知，不能被计为已履约 |
| 执行验收四 | 工件属于旧目标版本 | 隔离，或经明确兼容性证明及重验后生成当前接纳记录 |
| 执行验收五 | 同一消息重复投递 | 只登记一次，不增加候选数或消耗计数 |

| 执行验收十 | 探针补充来源字段 | 新工件版本，重跑两道受影响闸门 |
