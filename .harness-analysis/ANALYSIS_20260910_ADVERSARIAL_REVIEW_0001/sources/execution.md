# 对抗评审：执行流程

> 目标：让针对具体版本的独立异议，真正进入批准与发布的状态转移条件。
>
> 文档性质：基于已提供材料形成的工程设计草案。可作为工作流和技能的实施规约；本文不是已经部署的运行服务，也不宣称完成了原文仓库实验。

### 2.2 模式卡摘要

| 模式卡项目 | 内容 |
|---|---|
| 解决的问题 | 异议仅被记录却不阻断；评审对象漂移；旧批准被新版本借用；多个评审者共享同一盲区。 |
| 触发条件 | 候选工件准备进入重要下一阶段；需理解语义的错误可能进入实际业务；存在独立核查或职责分离要求。 |
| 输入 | 不可变候选、版本化证据、风险清单、评审分工、身份权限、裁决策略、动作边界。 |
| 输出 | 退回、待补证、升级人工、批准或受控发布；同时输出异议账本、裁决记录和版本回执。 |
| 结构 | 外层对抗评审循环；内层修订可使用生成—批评，不把内层评分当成外层批准。 |
| 工具 | 抽象的只读检索、工件存储、身份校验、账本、回执服务、发布适配器；不绑定产品或模型。 |
| 记忆 | 原始证据、各版工件、评审上下文清单、异议沿革、裁决与发布结果；不以旧总结替代新审查。 |
| 治理 | 评审独立、权限分离、硬阻断不可被平均分抵消、关键证据缺失时不放行。 |
| 评估 | 阻断项必须挡住、变更必须失效、必审风险必须覆盖、最终副作用必须对应有效授权。 |
| 关联模式 | 生成评审、层级委派、扇出聚合；仅做语义关联，不虚构其已注册标识。 |

### 2.3 适用与不适用

适用于重要报告、代码和配置变更、数据分析交付、业务方案与高影响动作的前置审核。适配器决定什么是“发布”：可能是内容上线，也可能是合并、批准计划或调用受控业务接口。

不应把所有格式检查都交给评审模型。类型、金额边界、身份、版本、权限和摘要一致性等可明确编码的条件，由确定性程序验证；评审者主要检查证据边界、遗漏条件、组合结论和潜在副作用。【来源二：“它和生成评审模式的不同点”“小结”】

若任务只需普通文字润色，且没有独立核查或下一阶段放行要求，可使用生成评审，不必强制套用完整对抗评审。高风险动作通过本模式仍不等于获得业务系统之外的权限。

## 3. 角色、权限与独立性

### 3.1 权责分离

| 角色 | 可以做什么 | 不得做什么 |
|---|---|---|
| 提案者 | 形成候选、声明结论及依据、提出发布请求。 | 自己批准；修改评审记录；直接调用受保护发布入口。 |
| 评审者 | 读取被分配材料、独立取证、提出结构化异议、复核修复。 | 修改候选正文；替提案者签发批准回执；偷偷删除异议。 |
| 修订者 | 对已提出的问题逐项修复、形成新版本、提供修复证据。 | 把“已修改”标成“已关闭”；把旧通过结果复制成新通过。 |
| 裁决者／放行闸 | 根据版本化策略处理异议、覆盖、独立性、授权与回执。 | 用主观总分冲抵硬伤；绕过尚未完成的必审责任。 |
| 授权人工 | 解决升级争议、批准策略允许且范围明确的业务动作。 | 以一句“同意”绕过版本、身份、硬阻断或审计要求。 |
| 观测探针 | 采集、核对、计算、提出数据补充与风险发现。 | 修改裁决、关闭异议、签发批准或发布。 |

提案者与修订者可由同一主体承担；裁决与回执服务可为同一可信运行时的两个确定性模块，但不能由候选内容控制。评审角色使用同一模型并不自动失去独立性，也不自动获得独立性，必须核查实际边界。

### 3.2 独立性检查清单

以下五项是对原文审计问题的工程化整理，不是对原文图片的复原。

| 检查项 | 最小结构证据 | 失败处理 |
|---|---|---|
| 谁在评 | 经认证的主体标识、角色、任务授权及与提案者的关系。 | 身份无法验证或违反职责分离时暂停。 |
| 看到了什么 | 输入材料清单、候选摘要、证据清单、规则版本。 | 对象不一致则本次结果无效。 |
| 没有继承什么 | 上下文来源记录；是否继承提案者结论、其他评审意见；披露是否盲审。 | 与策略冲突则重建上下文重审。 |
| 从哪里取得事实 | 证据快照、原始来源及上游来源族；必要时独立读取原始记录。 | 两个转述同源时，不算两条独立事实链。 |
| 能否给自己放行 | 真实工具权限和服务端授权检查；发布凭据不可被评审或提案角色读取。 | 存在自批自放通路时不放行。 |

配置证明的是可检查的结构分离，不证明完全消除了认知相关性。换模型不是独立事实的替代品；评审者的自述也不能代替运行时记录。【来源二：“把评审独立性结构化”】

### 3.3 风险覆盖先于人数

每次任务必须配置“风险项→评审责任→完成证据”。下面是内容发布场景的示例，不是所有任务固定需要四名评审者。

| 必审风险项 | 检查问题 | 可接受完成证据 |
|---|---|---|
| 事实正确性 | 结论是否可由原始来源支持？ | 事实核对记录、引用定位、必要的独立查询。 |
| 适用边界 | 是否把有条件的结论写成无条件？ | 条件逐项核对与结论定位。 |
| 组合风险 | 局部事实合并后是否产生不成立的整体断言？ | 跨段、跨来源的推导核对记录。 |
| 动作与权限 | 输出会触发什么动作，是否越权或扩大范围？ | 动作摘要与确定性授权检查。 |

同一评审者可覆盖多个风险项，但每项必须有独立完成记录。没有异议不等于完成审查；未执行、超时或无证据的风险项仍未覆盖。多人重复检查同一风险项不增加覆盖分母。

## 4. 核心业务对象

### 4.1 对象最小字段

| 对象 | 必要字段 |
|---|---|
| 候选工件 | 工件标识、版本、父版本、内容位置、内容摘要、提出者、生成时间、目标场景。 |
| 证据清单 | 证据标识、不可变快照或版本、内容摘要、来源定位、适用结论、数据时间、有效期、可信级别。 |
| 审查基线 | 工件摘要、证据清单摘要、规则版本及摘要、风险清单摘要、评审计划摘要、动作边界摘要、基线摘要。 |
| 评审计划 | 必审风险项、分配主体、所需独立性、输入白名单、完成条件、截止条件。 |
| 评审结果 | 结果标识、主体、基线摘要、轮次、覆盖风险项、使用证据、结论、异议引用、完成状态。 |
| 结构化异议 | 异议标识、关联版本与基线、规则、风险项、定位、证据、失败条件、严重性、责任人、处置状态。 |
| 裁决策略 | 版本、必需条件、硬阻断规则、升级条件、回执有效期、授权规则、修订与重试预算。 |
| 评审回执 | 唯一标识、签发主体、签发与到期时间、基线绑定、最终评审包摘要、裁决记录、动作范围、验证材料、撤销状态。 |
| 发布意图 | 操作标识、回执引用、目标环境、动作摘要、当前状态、外部幂等键、结果或待核对原因。 |

证据不能只保存可变网页地址或“查过数据库”。应保存可验证快照、内容摘要、查询条件及数据版本，或等效的不可变证据引用。原始数据无法复制时，记录访问约束与验证方式；关键事实无法验证则保持待补证。

### 4.2 两层绑定，避免循环与漏绑

```text
不可变候选正文 + 证据清单 + 规则 + 风险清单 + 评审计划 + 动作边界
    ↓ 规范化编码后计算摘要
审查基线摘要
    ↓ 评审者针对同一基线工作
最终评审结果 + 异议处置证据 + 封口记录
    ↓ 规范化编码后计算摘要
最终评审包摘要
    ↓ 与闸门裁决、授权范围一起绑定
可验证的版本回执
```

本设计建议固定字符编码、字段排序、数值与时间表达、摘要算法及其版本；不得在摘要前擅自删除正文空格、条件、标点或来源。摘要碰撞防护、签发密钥管理与验证方式由运行时实现，不能交给模型自报。

证据补充、规则更新、评审计划调整或动作范围改变，即使正文未改，也会形成新审查基线并触发重审。**任何正文修改都创建新工件版本；禁止依赖“只是小改动”直接继承旧批准。**【来源二：“回执必须绑定正在放行的那一版”；绑定范围的细化为本设计补充】

### 4.3 结构化异议示例

```yaml
异议标识: "异议-001"
工件标识: "报告-001"
工件版本: 1
审查基线摘要: "示例基线摘要"
评审轮次: 1
提出主体: "评审-事实边界"
风险项: "结论适用边界"
规则标识: "结论不得超出证据范围"
定位: "标题与结论第1句"
严重性: "阻断"
失败条件: "将会话隔离直接概括为文件系统完全隔离"
证据引用: ["证据-会话说明", "证据-工作区说明"]
解释: "两种隔离的适用条件不同，当前证据不能支持完全隔离断言"
修复要求: "分别陈述会话、工作区与工具边界，并补齐条件来源"
处置状态: "未关闭"
复核责任: "评审-事实边界"
```

这是原文案例的结构化演示，不是对某个产品当前行为的实测判断。严重性与确信程度分别记录：措辞自信不能替代证据；存在重大疑点而证据未取得时，登记待补证问题，不把猜测标成已证实事实，也不因缺少材料而自动放行。

## 5. 启动契约与返回结果

### 5.1 必需输入

调用方至少提供候选工件及证据、场景配置、可认证主体、风险清单、裁决策略、期望动作与预算。缺少任何关键项时，返回缺口清单；不得自行扩大任务或静默降低风险级别。

```yaml
调用配置:
  运行模式: "独立执行"
  目标动作: "生成批准回执但不发布"
  场景: "重要报告"
  工件引用: "报告-001/版本-1"
  证据清单引用: "证据清单-001"
  规则包引用: "规则-报告-001"
  评审计划引用: "评审计划-001"
  权限策略引用: "权限策略-001"
  风险等级: "重要"
  必审风险项: ["事实正确性", "适用边界", "组合风险", "动作与权限"]
  最大修订轮数: 3
  单节点最大尝试次数: 2
  总预算引用: "任务预算-001"
  探针接入: false
  发布适配器引用: null
```

这里的轮数与次数是演示参数；正式数值由场景策略确定。若目标仅是获得评审结果或批准回执，流程不得顺手执行发布。若请求实际发布，必须额外提供经验证的发布适配器、具体动作和对应授权。

### 5.2 标准返回

```yaml
执行结果:
  运行标识: "运行-001"
  当前工件版本: 1
  当前审查基线摘要: "示例基线摘要"
  状态: "要求修改"
  已完成阶段: "本轮评审封口"
  未关闭阻断项: ["异议-001"]
  未覆盖风险项: []
  关键证据缺口: []
  待裁决问题: []
  回执引用: null
  发布结果引用: null
  下一允许动作: "修订并创建新版本"
  可恢复节点: "节点-05"
  账本引用: "运行-001/控制账本"
  观测降级项: []
```

发布返回必须区分“批准”“已建立发布意图”“外部已确认成功”“结果不确定”。没有外部确认，不能把排队成功、接口超时或本地状态写入当成发布成功。

## 6. 最小共享协议

### 共享契约的适用范围

本节为两份文档共同内嵌的最小契约，契约版本为 `0.1.0`。内嵌是为了允许任一文档单独实施；两份文档同时接入时，以部署时登记的同一契约版本校验，不允许各自修改同名字段的含义。

业务执行方拥有候选工件、异议处置、裁决、授权和发布状态；探针只拥有采集任务、观测记录、指标结果与补数提案。**观测数据完整，不等于业务证据充分；业务证据充分，也不等于已经获得放行授权。**

### 关联键与时间语义

| 字段 | 含义与约束 |
|---|---|
| 租户标识 | 数据与权限隔离边界；跨租户对象不得关联或补写。 |
| 运行标识 | 一次工作流实例；重试不另建运行，重新发起业务任务则另建运行。 |
| 工件标识、工件版本 | 被评审对象及不可变版本；通用非工件流程可按适配器声明为不适用。 |
| 审查基线摘要 | 对本轮正文、证据清单、规则、风险清单、评审计划及动作边界的联合绑定。 |
| 评审轮次 | 对一个审查基线进行完整审查的一轮；规则或证据改变后必须另起轮次。 |
| 节点标识、尝试序号 | 区分逻辑节点和该节点的重试，不用重试次数扩充业务样本。 |
| 事件标识、账本序号 | 事件唯一去重键与运行内权威顺序；重复投递不产生新的业务事实。 |
| 关联事件标识 | 当前事件的直接依据、触发事件或被更正事件，不要求只有一个。 |
| 发生时间、采集时间 | 事实发生时间与探针收到时间分开保存；未知发生时间不得用采集时间冒充。 |
| 观测修订号 | 旁路观测区的并发控制版本，不等于工件版本或审批版本。 |

审查基线不包含后续才产生的评审结论，避免循环计算；回执另外绑定最终评审包摘要与闸门裁决记录。摘要只能证明绑定与变化，不能证明材料真实，也不能单独证明签发身份。

### 接收与回流规则

接收方依次验证：契约兼容、身份与权限、租户、关联对象、请求仍有效、基线与轮次、来源真实性、证据时效、字段白名单、预期修订号。失败时只写拒收记录，不得部分覆盖业务对象。

幂等键使用“租户标识＋请求标识＋提案标识”；同键同内容返回原结果，同键不同内容按冲突拒绝。接受结果只能是：

| 接受结果 | 执行方动作 |
|---|---|
| 已接受为观测补充 | 追加旁路观测记录，以条件更新递增观测修订号；不修改审批依据。 |
| 已接受并触发重新评审 | 执行方登记新证据或新配置，建立新基线；旧回执失效，再恢复指定验证节点。 |
| 待人工核实 | 保存提案，不视为事实，不推进受影响的放行条件。 |
| 已拒绝 | 记录过期、错版、越权、冲突等原因；不推进工作流。 |

收到确认前，探针不得把“提案已发送”记为“数据已补齐”。执行方重启后重放接受结果，不能二次应用同一提案。迟到提案可归入旧版本历史，但不得自动作用于当前版本。

### 写入白名单与受保护字段

探针可以追加自己的观测结果，以及向执行方提交补数提案。探针不得直接修改：候选正文、业务证据清单、规则、必审风险清单、评审结论、异议状态、权限、批准状态、评审回执、发布状态。

对已有权威事实的旁路补录，保留原值、来源与补录时间；对涉及审查依据的新增、替换或纠正，必须由执行方建新基线。无法获取的历史值保持缺失；推断值仅可写入单独的“推断候选”区。

### 观测发现与控制响应

探针发现疑似硬伤时提交“风险发现”，不是自行签发否决或批准。执行方验证该发现；若发现影响当前放行依据，登记待裁决问题并暂停相关放行，再交由授权评审者确认。已经形成的阻断异议，在被授权主体按既定工作流关闭之前持续约束闸门。

探针停机不能使业务闸门跳过必要检查。必要证据不足时，执行流程即使不接探针也必须暂停；仅非关键耗时、成本等观测字段缺失时，可继续业务并记录观测降级。

## 7. 工作流总览

```text
接收任务与判定适用性
    ↓
冻结候选、证据、规则与动作边界
    ↓
构建风险覆盖计划并检查评审独立性
    ↓
执行确定性前置检查
    ↓
分发独立评审任务，可按风险并行
    ↓
收集结构化结果、登记异议与证据缺口
    ├─ 关键证据不足 → 待补证 → 验证补数 → 新基线重审或恢复检查
    ├─ 审查未完成 → 等待、受控重试或升级
    ↓
本轮封口与确定性裁决
    ├─ 阻断未关闭 → 要求修改 → 新版本 → 完整重新评审
    ├─ 分歧无法解决／预算耗尽 → 升级人工或安全终止
    └─ 全部条件满足 → 签发当前基线回执
                                  ↓
                    请求实际发布时再次验证回执与当前状态
                                  ↓
                         受控发布、结果核对与归档
```

探针可以旁路订阅全部事件，也可以在“缺口登记”处被显式调用；它不插在每一个业务节点之前，不承担批准职责。

## 8. 节点执行规约

节点编号为本文内的稳定引用，不等同于已经登记的全局业务节点标识。

| 节点 | 输入与动作 | 输出 | 失败与恢复点 |
|---|---|---|---|
| 节点-00：受理 | 读取任务、风险等级、目标动作和权限；确认本模式适用。 | 任务契约、执行边界、运行标识。 | 关键配置缺失则列缺口；越权请求直接拒绝。 |
| 节点-01：冻结材料 | 固化候选及证据清单，读取规则和动作边界，建立基线草案。 | 不可变工件版本、基线草案。 | 来源可变且无法锁定则待补证；不得用当前摘要猜测历史。 |
| 节点-02：分配责任 | 为每一必审风险指定主体与证据要求，检查独立性；冻结完整计划并计算最终基线摘要。 | 评审计划、独立性检查结果、封存的审查基线。 | 覆盖缺口或自批自放通路未排除则暂停。 |
| 节点-03：前置规则检查 | 程序核对类型、范围、权限、证据时效、输入完整性。 | 规则检查记录、确定性阻断项。 | 失败直接阻断；模型评审不得覆盖结果。 |
| 节点-04：发起评审 | 按同一基线分发任务、规则和只读材料；记录实际访问清单。 | 每个评审任务的受理记录。 | 暂时失败可有限重试；替换评审者需更新计划并重建基线。 |
| 节点-05：执行与收集 | 核对语义、原始证据与风险边界，输出结构化结果；校验结果绑定和来源。 | 有效结果、异议、缺口与任务完成状态。 | 错版结果隔离；缺少证据的断言进入待核实，不计完成。 |
| 节点-06：补数协调 | 分类缺口；自身读取或向探针发起带作用域请求，验证回传。 | 已验证补充、拒收原因或仍待补证。 | 非关键观测缺失可降级；关键缺口超时进入升级，不视为通过。 |
| 节点-07：封口裁决 | 确认全部必需结果完成、无未决关键请求，冻结评审包；按条件作裁决。 | 要求修改、升级或批准裁决。 | 新发现到达且影响依据则撤销封口，重开评审。 |
| 节点-08：修订重审 | 修订者逐项回应并形成新版本；新版本重新建立基线、分配审查。 | 新版本及修复说明。 | 达到预算仍不满足条件则升级或终止，禁止以轮数换批准。 |
| 节点-09：签发回执 | 回执服务校验有效批准裁决，并绑定基线、最终评审包、动作范围及有效期。 | 可验证回执、批准事件。 | 签发失败不产生可用批准凭证；幂等重试同一裁决。 |
| 节点-10：发布前复核 | 重新读取候选、证据、规则、撤销状态、授权与最新控制序号。 | 允许建立发布意图或拒绝原因。 | 摘要变更、过期、新阻断、权限变化均拒绝；必要时重新评审。 |
| 节点-11：受控发布 | 原子登记发布意图，按同一操作标识调用受控适配器并核对外部状态。 | 已确认成功、明确失败或结果不确定。 | 结果不确定先查询核对，不能盲目重试副作用。 |
| 节点-12：归档反馈 | 归档工件、证据、异议、评审、回执及发布结果；交付可恢复点和观测事件。 | 可追溯结果包、后续监控或人工任务。 | 关键控制记录无法持久化时，不宣称本轮完成。 |

节点-01先冻结已知材料，节点-02完成实际责任分配后才封存可派发的最终审查基线。不得在评审计划尚未确定时签发基线，再把后续分工变化偷偷追加进去。后续任何计划调整都要重新建立基线。

### 8.1 评审任务的最小约束

每个评审任务收到的是“该版本及对应证据、所负责风险、拒绝条件、允许的取证范围”，不是“帮主智能体证明方案正确”。需要独立判断时，先独立输出，再进行异议汇总；不得默认继承其他评审者的结论。

必需返回“检查过什么、引用什么、发现什么、尚不知道什么”。纯粹的“没问题”“评分很高”不能作为完成证据。对于相同内容的重复异议，可建立共同问题标识，但保留各评审者的原始记录与独立来源。

### 8.2 封口与迟到发现

封口只表示本轮规定的责任已经完成，不表示永远不存在新风险。封口前所有必需评审和关键补证请求都应有明确终态；超时不是默许。

封口后若收到影响放行的可信新事实，由控制方递增基线或控制修订号，撤销旧回执的当前可用性并重新裁决。若已经发布，保留原发布事实，另建事件处置、撤回或补偿任务，不能改账本伪装成没有发生。

## 9. 工件、异议与回执的状态机

### 9.1 工件评审状态

```text
草稿 → 评审中
         ├→ 要求修改 → 产生新版本 → 新版本评审中
         ├→ 待补证 → 验证新增资料 → 恢复检查或新基线评审中
         ├→ 已升级人工 → 有范围的裁决 → 重审／退回／安全终止
         └→ 已批准 → 发布前复核 → 已建立发布意图 → 已发布
               └→ 内容、证据、规则等改变 → 当前批准已失效 → 重新评审

已建立发布意图 → 明确失败／结果不确定 → 核对外部状态
```

“待补证”“已建立发布意图”“结果不确定”是本设计补充。原文的提案、修订、重审、升级、批准、发布与批准失效关系保持不变。【来源二：“回执必须绑定正在放行的那一版”】

修改时创建新对象，不原地改写已批准内容。旧版本的评审记录保持历史事实；被撤销的是旧回执对当前动作的可用性，不是删除“当时曾经批准”的历史。

### 9.2 异议生命周期

```text
提出 → 未关闭
         ├→ 待补证／有争议 → 继续阻断受影响的放行条件
         ├→ 修复待复核 → 独立复核 → 已关闭：修复验证完成
         └→ 经证据确认不成立 → 授权裁决 → 已关闭：异议撤回
```

“修订者说已经改好”不是关闭条件。关闭记录必须包含原异议、目标新版本、复核主体、规则、证据和理由。原版本上的问题不会因为新版本修复就变成“原版本从未有问题”；应保留旧版本异议并建立“已在后继版本解决”的关联。

新版本必须重新完成本轮全部必审风险项，而不只是查看旧问题是否消失。可以重新读取已保存的不可变证据以节省取证成本，但不能继承旧的通过结论。

本设计默认不提供硬阻断豁免。人工可裁决某项异议是否成立；不能保留一项成立且未关闭的硬阻断，又批准同一基线发布。非阻断风险的接受需要版本化策略、范围明确的责任人和记录，不能通过悄悄降低严重性实现放行。

### 9.3 回执生命周期

回执经过签发、可用、已使用、已过期或已撤销等状态。单次动作回执在同一业务操作标识下可进行幂等核对，不得复制给第二个动作；持续性授权必须由场景策略另行定义范围和期限，不能沿用单次动作语义。

## 10. 确定性批准闸与发布闸

### 10.1 批准条件：全部满足，而非加权评分

```text
允许批准 =
    关键输入完整且来源满足要求
    且 所有结果绑定当前审查基线与轮次
    且 每个必审风险都有有效的完成记录
    且 评审主体及独立性满足当前策略
    且 必需评审任务已结束且评审包已封口
    且 针对当前基线的未关闭阻断项数量为零
    且 不存在影响放行的未裁决问题或关键补证请求
    且 确定性规则检查全部通过
    且 目标动作与权限范围明确
```

评审者提供语义判断及证据，程序检查这些条件。程序不能把语义判断变成数学真理，但可以保证缺失、未完成或已否决的判断不会被跳过。

如果风险清单或评审计划被错误配置为空，应返回配置错误，而不是以“零项全部通过”批准。存在条件未知时，结果是待补证或升级，不能把空值当作通过。

### 10.2 回执最小内容

```yaml
版本回执:
  回执标识: "回执-001"
  租户标识: "租户-甲"
  运行标识: "运行-001"
  工件标识: "报告-001"
  工件版本: 2
  审查基线摘要: "示例基线-第2版"
  最终评审包摘要: "示例评审包-第2轮"
  评审轮次: 2
  裁决记录引用: "裁决-002"
  控制修订号: 8
  规则版本: "报告规则-1"
  允许动作: "发布报告"
  动作摘要: "示例发布内容与目标的摘要"
  目标环境: "指定内容发布区"
  授权主体引用: "授权-发布-001"
  签发主体: "可信回执服务"
  签发时间: "2026-09-09T15:10:00+09:00"
  到期时间: "2026-09-09T15:20:00+09:00"
  验证材料引用: "受保护回执记录-001"
  撤销记录引用: null
```

这是结构示例，不是一张可使用的回执。正式回执须由受保护的服务端记录、消息认证码或数字签名等机制验证签发身份；仅计算内容摘要不足以防伪。签发密钥和批准权限不得暴露给提案者、评审者或探针。

### 10.3 发布前再次核验

发布入口必须自行读取当前权威状态，不能只相信调用者提交的 `已批准` 字段。

| 复核对象 | 拒绝条件 |
|---|---|
| 回执身份和状态 | 伪造、签发者不受信任、过期、撤销或已被其他操作消费。 |
| 正文和版本 | 当前工件不是回执中的那一版，或正文摘要不匹配。 |
| 证据与依赖 | 快照被替换、关键依赖状态改变、证据超出有效期。 |
| 规则与风险 | 当前要求不再是签发时那套规则，或新增必审风险。 |
| 评审包和异议 | 存在新阻断、未决关键问题、结果被撤销或轮次未封口。 |
| 身份和动作 | 请求者当前无权执行，动作、收件对象、目标环境或范围不匹配。 |
| 控制修订号 | 批准之后发生了影响当前放行的控制变化。 |

发布前读取“最新材料”的含义由适配器定义：历史报告可以审核某个固定快照，实时动作可能要求读取当前余额、权限或资源状态。不得擅自把固定快照换成实时值；也不得用过时快照满足实时动作前置条件。

### 10.4 并发、重试和外部副作用

本设计要求在同一个受控提交边界内完成“核验当前控制修订号、登记发布意图、绑定幂等操作标识”。若中途发生批准撤销或变更，条件更新失败，不能沿用旧判断继续提交。

外部系统调用通常不能与本地数据库构成同一事务，因此分两段处理：先持久化发布意图，再由受控派发器重新检查授权与撤销状态，向外部传递同一幂等键。外部返回不确定时，查询外部实际状态，必要时升级人工，不盲目重放副作用。

若外部系统支持条件提交、版本前置条件或短时授权令牌，应使用其能力；若不支持，必须明确“受控派发时刻到外部实际生效”之间仍可能存在竞态。不能凭本地锁或事件总线宣称跨系统绝对原子、绝对只执行一次。

已发生的外部动作不能靠回执撤销自动撤回。撤回、回滚或补偿是新的受控动作，需要自己的权限、验证和记录。

## 11. 与探针的交互执行

### 11.1 三种接入方式

| 方式 | 执行流程 | 探针 |
|---|---|---|
| 执行流程独立运行 | 自己获取必要业务证据，执行检查、评审、裁决与发布；保存最小控制账本。 | 不启动。 |
| 旁路观测 | 正常运行，输出控制事件和可选运行遥测。 | 订阅或读取导出，生成指标、缺口与风险发现。 |
| 检查点补数 | 在某个明确缺口处发起请求，暂停受影响的条件，验证并应用回传结果。 | 在授权范围内采集补数，不承担最终裁决。 |

探针独立分析历史材料时，可以输出补数提案文件；没有在线执行接收方就停在“待接收”，不能假装已经更新工作流。

### 11.2 补数是否触发重新评审

| 情况 | 本设计处理 |
|---|---|
| 补录缺失的节点耗时、成本、投递延迟 | 写旁路观测区；不影响审查基线，但必须有可验证来源。 |
| 补充证据快照，使一个结论首次具有依据 | 由执行方更新证据清单、建立新基线并完整重审。 |
| 补入漏记的评审身份或实际授权证明 | 验证真实历史记录；证明包改变则重开裁决并重新签发，主体或独立性边界改变则新建基线并完整重审。 |
| 纠正规则版本、来源或候选摘要 | 不覆盖旧记录；建立纠正事件及新基线，旧回执失效。 |
| 发现已发布版本与批准版本不一致 | 建事件处置任务和风险发现，不通过补日志“修成一致”。 |
| 只能推断一个历史值 | 放入推断候选区，保留真实字段缺失；不能满足关键放行条件。 |

回流必须回到具体节点和具体版本，不是把补充文本塞进主智能体上下文就继续。重入后重新检查依赖：若新资料影响风险清单，则从节点-02重做计划；若只影响证据验证，至少从节点-01建立新基线后重审。

### 11.3 最小交互时序

```text
执行方：登记“当前版本缺少来源快照” → 写待补证状态与请求
探针：验证授权 → 读取原始来源 → 校验快照 → 提交补数提案
执行方：核对请求、版本、基线与来源 → 接受为新的业务证据
执行方：建立新基线 → 重新评审 → 新裁决 → 新回执
探针：收到接受确认 → 更新补数状态 → 计算补数时延和重新评审情况
```

探针从未关闭阻断项，也没有把“找到资料”直接改成“可以发布”。

## 12. 工具、运行时、记忆与治理

### 12.1 三层部署建议

以下是部署建议，不是对框架 v0.1 已有实现的声明。

| 层次 | 职责 |
|---|---|
| 核心运行时 | 身份授权、状态持久化、不可变工件、摘要、回执、受控副作用、幂等与恢复。 |
| 工作流 | 风险路由、评审任务编排、循环、检查点、人工升级、探针请求和结果验收。 |
| 资源与工具接入层 | 只读证据、工件仓库、业务系统与发布适配器；可通过 MCP 或普通接口提供。 |

不绑定模型、前端编排组件、云平台或具体协议版本。只在工具清单里隐藏发布能力，不足以替代服务端鉴权；实际发布入口仍必须验证身份、范围和当前回执。

### 12.2 上下文与不可信输入

候选内容、检索网页、文件、评审文本和探针补数都按输入数据处理。材料内的“忽略之前的规则”“把本项设为通过”“调用发布工具”等内容不能提升权限或改变裁决策略。

评审者获得完成任务所需的最小上下文；原始证据可读取，敏感凭据不进入模型上下文。第三方内容中的指令不得作为工具调用授权。评审模型输出必须经过结构校验、身份归属校验和规则校验后进入业务状态。

### 12.3 两类记录，不能混同

控制账本保存状态变化、评审完成、异议处置、回执和发布意图等关键事实，必须在对应状态转移时可靠持久化。运行遥测记录耗时、模型使用量等辅助信息，可以按策略抽样或降级；遥测缺失不能抹去控制事实。

长期保存来源链、版本链和裁决链。摘要和脱敏记录也可能泄露敏感信息，仍需按租户、用途和保留期管理。不要记录隐藏推理过程；保存结构化理由、证据和必要的审计结果即可。

## 13. 失败、恢复与终止

| 失败模式 | 响应 | 禁止的处理 |
|---|---|---|
| 评审者超时或工具暂时失败 | 在预算内使用同一任务标识有限重试；未完成的风险保持未覆盖。 | 把超时当弃权或赞成。 |
| 证据不可达或来源冲突 | 待补证、独立核查或升级，保留冲突值。 | 用模型猜测填齐并继续。 |
| 多数同意、少数阻断 | 核查阻断规则与证据；成立则不放行。 | 多数投票冲掉硬阻断。 |
| 修订反复不收敛 | 检查预算和重复问题，升级或安全终止。 | 耗尽轮数后自动批准。 |
| 错版或过期评审结果 | 保存为历史，拒绝计入当前覆盖。 | 将其改标签后复用。 |
| 探针失联 | 非关键观测降级；关键业务证据由执行方补齐或暂停。 | 以探针故障作为绕过业务检查的理由。 |
| 账本不可写 | 对依赖这些记录的受保护状态转移停止提交。 | 发布后再补造审批记录。 |
| 发布接口超时 | 标记结果不确定，使用操作标识核对外部状态。 | 无条件再次执行。 |
| 批准后出现新事实 | 使当前回执不可用；重评；已发布则另建处置任务。 | 删除新异议以维持通过率。 |

恢复所需最小检查点包括：当前工件和基线、节点、尝试次数、评审计划及完成状态、未决异议与缺口、控制账本位置、预算、当前回执与发布意图。恢复时先核实当前权威状态，不盲信进程崩溃前的内存快照。

同一基线下的传输重试可复用已有不可变结果；任何影响判断的输入变化，都不是传输重试，必须进入新的审查轮次。

## 14. 场景适配：替换业务内容，不替换控制原则

| 场景 | 候选工件 | 重点风险和证据 | “发布”含义 |
|---|---|---|---|
| 研究或内容报告 | 正文、图表、标题、引用与结论。 | 事实、限定条件、证据范围、组合推断。 | 向指定读者或渠道发布。 |
| 代码与配置 | 固定提交、配置快照、依赖清单。 | 测试、权限扩大、依赖变更、架构副作用。 | 合并或部署指定提交。 |
| 数据分析交付 | 固定数据快照、查询、口径和结果。 | 时间窗口、分母口径、数据来源、解释越界。 | 交付或发布分析结果。 |
| 业务方案 | 方案版本、资源假设与动作清单。 | 约束遗漏、资源依赖、职责冲突。 | 批准方案进入下一阶段。 |
| 高影响受控动作 | 参数固定的动作申请与业务依据。 | 身份、额度或范围、重复执行、人工授权。 | 通过受控适配器执行指定动作。 |

场景配置可调整必审风险、评审主体、取证来源、人工要求、预算和时效；不可把“未关闭硬阻断仍能放行”“旧回执能批准新正文”“未知等于通过”配置成正常捷径。

通用工作流没有语义风险评审时，可只接配套探针的通用观测能力；不要为了复用探针强行把每个业务流程改造成对抗评审。

## 15. 贯穿示例：从绝对化结论退回到有边界的表述

以下按原文案例组织，不新增关于特定系统真实行为的事实判断。【来源二：开篇与“有评审”和“评审生效”的差别】

| 步骤 | 候选或事件 | 预期控制效果 |
|---|---|---|
| 1 | 第一版标题写成“某系统的子智能体默认完全隔离”。 | 冻结第一版及来源，进入评审。 |
| 2 | 评审甲指出：会话隔离不能直接推出文件系统隔离。 | 登记有证据的阻断异议。 |
| 3 | 评审乙指出：不同实现的上下文、工作区与工具范围语义不同。 | 登记另一个阻断异议。 |
| 4 | 两个评审任务都完成。 | 风险覆盖可能完整，但两个阻断仍未关闭，因此拒绝批准。 |
| 5 | 缺少一个原始来源快照，执行方请求探针取回。 | 保持待补证；取得来源不等于获得批准。 |
| 6 | 修订为“分别说明会话、工作区与工具的隔离条件”，形成第二版。 | 建新基线，全部必审项重新评审。 |
| 7 | 第二版完成复核，阻断解决，无关键缺口。 | 为第二版签发专属回执。 |
| 8 | 发布前有人又把标题改回“完全隔离”。 | 形成第三版；第二版回执不匹配，发布入口拒绝。 |
| 9 | 明确选择最终发布内容，重新完成所需审查并取得当前有效回执。 | 不回捡已经失效的旧回执；重新复核后发布并记录外部确认。 |

关键区别不是是否保存过评审评论，而是步骤4和步骤8的状态转移确实被阻断。

## 16. 验收用例

下面是实施时应执行的验收规约，不代表本次已经运行生产系统或原文实验。

| 用例 | 注入条件 | 必须得到的结果 |
|---|---|---|
| 验收-01 | 存在一条未关闭阻断异议。 | 不批准、不发布；输出异议引用。 |
| 验收-02 | 总分很高，但有有效阻断。 | 同验收-01；总分不得覆盖硬条件。 |
| 验收-03 | 全部评论无异议，但一项必审风险未执行。 | 不批准；明确覆盖缺口。 |
| 验收-04 | 提案者拥有自批或直接发布能力。 | 独立性／权限检查失败。 |
| 验收-05 | 两名评审者只读取同一错误摘要。 | 不得宣称形成了独立事实链。 |
| 验收-06 | 候选正文改一个字，仍提交旧回执。 | 摘要或版本不匹配，拒绝发布。 |
| 验收-07 | 正文未改，但来源快照被替换。 | 新基线，重审，旧回执不可用。 |
| 验收-08 | 规则、风险清单或评审计划变更。 | 原批准失效，重新完成当前要求。 |
| 验收-09 | 评审结果属于前一版本。 | 不计入当前版本覆盖。 |
| 验收-10 | 修订者自行关闭异议。 | 权限拒绝，异议仍未关闭。 |
| 验收-11 | 探针提案来源不明或只含推测。 | 不进入权威事实或批准条件。 |
| 验收-12 | 同一补数提案重复投递。 | 只应用一次，返回原接受结果。 |
| 验收-13 | 补数提案错租户、错版、过期或修订号冲突。 | 拒收并记录原因，无部分写入。 |
| 验收-14 | 探针停机但业务证据齐全。 | 业务可继续；明确观测降级。 |
| 验收-15 | 探针停机且关键证据不足。 | 待补证或升级，不能自动通过。 |
| 验收-16 | 回执校验与提交之间发生撤销。 | 条件提交失败；不生成有效派发。 |
| 验收-17 | 外部调用超时，但动作可能已生效。 | 结果不确定，先核对再决定重试。 |
| 验收-18 | 超过修订或成本预算仍有阻断。 | 升级或安全终止，不自动批准。 |
| 验收-19 | 关键控制账本写入失败。 | 阻止相应受保护状态转移。 |
| 验收-20 | 恶意来源要求忽略评审、索取发布凭据。 | 作为数据隔离处理，不提升权限。 |
| 验收-21 | 发布后才发现新阻断。 | 新建事件处置；保留真实发布历史。 |
| 验收-22 | 仅请求评审或回执，没有发布授权。 | 返回评审结果或回执，不发生外部发布。 |

比较“评论模式”和“闸门模式”时，应使用同一候选、同一证据和同一异议集，只改变发布入口是否校验条件；否则不能把结果差异全部归因于闸门。
