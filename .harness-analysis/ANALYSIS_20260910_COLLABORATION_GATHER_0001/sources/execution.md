# 扇出聚合：执行流程

> 目标：将能够独立推进的工作分发给多个执行者，把返回材料聚合为保留覆盖、口径、冲突和来源的类型化报告，再交给有权的业务节点裁决。
>
> 本文是一份独立使用的技能执行规范，不依赖探针才能完成基本运行。宿主仍须接入执行器、存储、权限控制和事件接口；本文不表示这些服务已经实现或部署。

## 2. 适用场景、非目标与分层职责

### 2.1 何时启用

存在真实并行面，各路任务能在不等待其他分片完整过程的情况下推进；输出能落成结构化工件；对象、时间、单位和来源规则可事先约定；聚合后有明确的使用者与验收条件。

分片可以按输入对象、地区、目录、时间窗口、来源或证据维度形成。按不同维度分片不等于每个分片都在回答同一个可投票命题。

### 2.2 何时不要直接扇出

存在严格前后依赖时，优先链式流程；多个执行者必须同时修改同一状态但没有隔离与合并机制时，先解决写入冲突；结果无法统一口径、只能拼接长文本时，不应宣称已经完成可信聚合。单执行者已满足时效和成本目标时，也不必增加并行分支。

层级委派解决责任归属，扇出聚合解决多路材料如何收回，并行探索解决候选路径竞争。它们可以组合，但不能互相替代验收职责。【来源二：工程化定义、适用场景】

### 2.3 三层职责

下表是本次实现分工建议，不是来源一已经规定的运行时实现。

| 层次／角色 | 负责 | 不负责 |
|---|---|---|
| 运行时层 | 并发调度、会话生命周期、超时、取消、预算执行、工作区与工具权限隔离 | 自动认定证据独立、消除语义冲突、替业务裁决 |
| 工作流层 | 冻结预期分片、规范工件、五步聚合、闸门、局部恢复、报告版本 | 通过提示词替代真实权限控制 |
| 资源与工具层 | 提供获授权的文件、查询、接口、快照和工具调用；可经 MCP 适配 | 将返回文本中的指令升级为工作流规则 |
| 执行者 | 在明确责任和预算内生成小工件，披露来源及局限 | 宣称自己完成了父任务或越权裁决其他分片 |
| 聚合器 | 保留差异、对齐口径、验证组合约束、产出证据状态 | 将“工件到齐”解释为业务命题必然为真 |
| 探针（可选） | 观测、缺口诊断、授权补采、指标计算、修复建议 | 改写原始主张、自动重派或批准业务动作 |
| 业务裁决节点 | 根据报告、风险政策和权限决定下一步 | 将聚合准入状态当作自动执行授权 |

会话隔离、工作区隔离、工具权限隔离必须分别声明和核验；不能用其中一个字段替代另外两个。本文不预设某个具体厂商、模型或执行器的隔离能力。

## 3. 三种运行方式

| 方式 | 所需输入 | 本技能行为 | 与探针的关系 |
|---|---|---|---|
| 独立执行 | 任务规范、场景配置、执行器与来源适配器 | 独立完成分片、执行、聚合、强制检查和报告；自己保留最小事件账本 | 不要求安装或调用探针 |
| 在线联动 | 独立执行输入，加共享消息接口与探针权限范围 | 发出事件与缺口请求；校验补丁；按依赖重验；探针无响应时按本地政策继续或阻断 | 探针是旁路补数和诊断服务，不是必经业务审批者 |
| 事后审计配合 | 已完成运行的冻结计划、工件、事件、报告版本 | 可导出审计包；后续更正生成新版本，不篡改原报告 | 探针可独立复盘，默认不触发重跑 |

“独立执行”不等于“无需数据”。关键身份、必要证据、来源定位或强制检查结果缺失时，必须输出不充分报告或等待补证，而不是调用模型凭常识补齐。

## 4. 输入、工件与输出契约

### 4.1 任务规范

| 字段组 | 必填内容 | 处理要求 |
|---|---|---|
| 身份 | `run_id`、任务标识、模式与技能版本 | 一次运行唯一标识；恢复执行不创建伪装成新任务的重复记录 |
| 对象 | `target_ref`、版本、部署方式或实体范围 | 对象名称只是展示值，不能代替稳定身份 |
| 命题与维度 | 要回答的问题、`required_dimensions`、允许取值语义 | 不同维度不得折叠成同一布尔字段 |
| 预期分片 | `expected_shards`、每片责任、必选／可选、所需工件与维度 | 先冻结全集，再启动执行；可选项也必须披露结果 |
| 可比口径 | 时间窗口、有效时间、单位、币种、统计周期、分母、置信语义 | 不适用字段显式标记不适用；未知不能当作相同 |
| 验收规则 | 必要证据、来源要求、冲突政策、接缝不变量、业务输出格式 | 版本化；探针和执行者均无权自行降低标准 |
| 资源 | 并发上限、尝试上限、总调用上限、截止时间、可用费用上限 | 由宿主强制执行；示例阈值不得冒充通用行业标准 |
| 权限 | 工具白名单、来源范围、写入范围、是否需人工批准 | 对每次实际动作复核，不仅在提示中描述 |
| 观测 | 最小事件要求、探针是否启用、主动补采范围、补数轮数 | 没有探针时也保留业务所需最小账本 |
| 版本 | 工件模式、归一化词表、实体映射、去重、冲突及接缝规则版本 | 绑定本次报告，避免规则变化造成不可解释的差异 |

### 4.2 分片计划

每片至少含 `shard_id`、责任说明、输入引用、目标与版本、必需维度、截止时间、工具范围和资源份额。

设当前冻结计划的必选分片集合为 **R**。每片还有自己必须覆盖的“对象—命题—维度”义务集合。只有某片所有必要义务均有符合局部工件契约的材料时，才进入合格分片集合 **Q**。

物理返回不等于合格：一个成功回调却缺少来源或必需维度的分片，不进入 Q。同一分片重试多次也只占一个分片位置。重复来源的工件可以局部合格，但不因此增加独立证据数量。

必选分片不能因为超时而从 R 中删除。合法范围变更须由任务所有者或授权规则产生新的 `plan_revision`，保留旧版全集、变更原因和前后指标。分片之间需要排他处理的对象要明确分区键；允许重叠核验的场景则显式声明重叠目的。

### 4.3 证据卡

保留来源二的 `EvidenceCard` 思路及核心字段，并增加运行和审计元数据。每张卡表达一个对象、一个明确维度下的一个可检验主张；多个来源分别建立证据项或来源引用，不能把一段混合叙述当作一张独立证据。

| 字段 | 规则 |
|---|---|
| `card_id`、`artifact_revision`、`content_hash` | 唯一标识、不可变版本、摘要 |
| `worker_id`、`run_id`、`plan_revision`、`shard_id`、`attempt_id` | 绑定执行来源与计划，防止不同运行混入 |
| `target_ref`、`target_version` | 稳定对象身份与版本 |
| `proposition_id`、`dimension` | 命题与维度；不同维度不自动构成冲突 |
| `value`、`claim` | 类型化原始值与带条件的说明；原始内容不可由探针覆盖 |
| `unit`、`currency`、`period`、`denominator` | 适用时填写；保留归一化前后的数值及换算依据 |
| `source_id`、`source_version`、`source_ref` | 稳定来源标识、版本及可定位引用；网页可沿用 `source_url`，本地文件和快照使用相应引用 |
| `source_lineage`、`lineage_status` | 已核验的上游关系与核验状态；空列表不代表独立来源 |
| `observed_at`、`valid_time` | 获取时间与内容适用时间分开；当前网页不能冒充历史快照 |
| `confidence`、`confidence_semantics` | 可为空；主观把握、模型概率与统计概率不得混算 |
| `evidence_kind`、`limitations` | 区分真实记录与固定样例，披露未覆盖范围及不确定性 |
| `raw_ref`、`normalized_ref` | 原件与派生归一化工件分别保存 |

原文教学代码用来源地址的简单格式判断作轻量校验。本文扩展为按资源类型检查定位、版本和读取证据；地址有格式并不等于内容真实。本文不要求所有来源都必须是网页。【来源二：证据卡、类型化报告】

### 4.4 聚合报告

必须保留 `GatherReport` 的核心职责：`cards`、`missing_dimensions`、`conflicting_dimensions`、`accepted` 与 `verdict`。本设计将缺失和冲突绑定完整对象键，避免只用维度名称掩盖不同实体。

| 字段组 | 最小输出 |
|---|---|
| 身份和版本 | 运行、计划、规则、报告版本及其摘要 |
| 覆盖 | 预期／合格／缺失分片集合，缺失对象与维度；可选分片另列 |
| 原件与处理结果 | 全部证据卡索引、有效卡、隔离卡、拒收原因、归一化结果 |
| 去重 | 结论簇、来源族、同源关系、未核验血缘与原卡映射 |
| 差异与冲突 | 不同维度限定、真实未决冲突、原始双方证据、已裁决冲突及裁决引用 |
| 来源 | 主张到卡、卡到来源、来源到快照／日志／代码位置的引用链 |
| 结构准入 | `accepted` 及逐项检查结果；不与业务表述混用 |
| 组合约束 | `seam_check` 的规则清单、通过／失败／未知及原因 |
| 上层交接 | `admitted_to_business`、交接对象、发送或回执引用 |
| 业务表述 | `verdict`、限定条件、风险、不能证明什么；不代表动作授权 |
| 可观测性 | 观测是否完整、未解决数据缺口、探针报告引用；不吞并业务状态 |
| 资源 | 尝试、重试、时长、费用或费用未知原因 |

`cards` 中保留原始材料，即使聚合展示已去重。工件可按引用保存，不要求把所有全文塞进聚合模型上下文。

## 5. 执行状态与责任边界

### 5.1 状态分层

| 状态层 | 示例 | 不得混淆的含义 |
|---|---|---|
| 资产状态 | `draft`、`review`、`active` | 文档与技能注册生命周期，沿用框架 |
| 任务运行状态 | 待校验、已规划、执行中、聚合中、待补证、已产出、已终止 | 运行是否推进或结束 |
| 分片尝试状态 | 已创建、运行中、成功、失败、超时、取消 | 单次尝试的运行结果，不代表工件合格 |
| 报告准入 | `accepted: true/false` | 必要材料、来源及未决冲突检查是否满足结构准入 |
| 接缝状态 | 通过、失败、未知 | 已声明的全局组合约束是否满足 |
| 业务表述 | 有条件成立、证据不足、存在风险等 | 证据支持的表述，不是批准业务动作 |
| 观测状态 | 完整、部分可用、不可判定 | 观测信息能否支撑指标与诊断 |

产出一份“证据不足”的报告可以意味着流程已正常完成收口，但不意味着证据准入成功。执行者失败、报告拒收、业务不批准也必须分别记录。

### 5.2 原子提交与终止

每个逻辑分片可以有多次尝试，但只有通过版本核验后被明确提交的工件进入当前有效视图。不得按“最后到达”选择权威结果。超时后迟到、旧计划返回或已被替代的工件先隔离，不能覆盖当前版本。

全局取消后停止新分派，向已运行任务发送取消请求并收集实际终态；取消请求发出不等于外部动作已撤回。涉及业务写入时必须另有幂等、状态核对或补偿机制。默认研究与核验场景采用只读执行。

### 共享协议：扇出聚合补数协议/0.1.0

本节在执行流程与探针文档中保持一致，是本次设计新增的接口约定。对方不在线时，消息可以写入本地目录、数据库表或消息队列；不得把“未收到对方响应”解释为业务检查通过。

#### 一、消息信封

| 字段 | 约束 |
|---|---|
| `schema_version` | 固定为本协议版本 `0.1.0`；不兼容版本先转换，禁止静默丢字段 |
| `message_type`、`message_id` | 消息类型与全局唯一消息标识 |
| `run_id`、`plan_revision` | 必须对应同一次业务运行及冻结的计划版本；探针自己的运行另用 `probe_run_id` |
| `producer_id`、`producer_sequence` | 生产者标识及其单调递增序号；序号只在同一生产者实例内比较 |
| `node_id`、`shard_id`、`attempt_id` | 适用时填写；运行级事件可为空，不得伪造分片归属 |
| `artifact_ref`、`artifact_revision`、`artifact_hash` | 涉及工件时绑定其确切版本和内容摘要，避免读取可变“最新版” |
| `occurred_at`、`observed_at` | 事实发生时间与被观测时间分别记录；历史发生时间无法恢复时为空并说明原因 |
| `causation_id`、`correlation_id` | 前者关联直接原因，后者关联同一条补数链；首次消息可无直接原因 |
| `data_origin` | 区分原始记录、来源读取、确定性推导、历史重放；模型猜测不是可采纳的数据来源 |
| `payload`、`evidence_refs` | 类型化载荷与支撑该消息的日志、快照或工件引用；敏感正文留在受控存储 |

#### 二、五类消息

| 消息类型 | 最小载荷 | 接收者的动作 |
|---|---|---|
| `observation_event` | 事件名称、业务对象版本、事实引用、生产者权限域 | 追加观测记录；不直接更新业务权威状态 |
| `gap_request` | `gap_id`、缺口类别、目标字段、所需语义、时间范围、必要性、允许来源、截止时间与预算 | 接收方判断能否补采；无法恢复则明确返回不可恢复 |
| `data_patch` | `patch_id`、`gap_id`、目标工件及基准摘要、字段路径、补充值、来源、采集时间、校验结果 | 执行方校验后生成派生工件新版本；不覆盖原件 |
| `action_proposal` | `action_id`、关联缺口、建议动作、限定分片、权限需求、预计资源、原因 | 仅提出补证、重派、局部重算或人工处理建议；执行方自行授权与调度 |
| `apply_receipt` | 对应补丁或建议标识、采纳状态、拒绝原因、新工件引用、重验节点及结果 | 探针据此区分已提交、已采纳和已闭环，不把发出建议计为修复成功 |

采纳状态统一为：`已采纳`、`已拒绝`、`重复消息`、`待处理`。其中“已采纳”不等于缺口已经闭环；只有后续重验通过、缺口状态更新后，才能计入闭环数量。

#### 三、补数允许与禁止

允许补充的内容包括：已有日志中的尝试状态和实际时间、已有快照中的来源版本、经过核验的来源血缘关系、依据明确规则计算的单位换算及统计值。必须能回到原始记录，且使用相应版本的规则。

**以下内容不得作为补数直接写入：**原始证据卡的观点与原始数值、业务结论、`accepted`、接缝通过状态、权限、预算、预期分片集合、验收阈值。证据主张需要变化时，应提出补证建议，由执行方取得新的证据卡；计划需要变化时，应创建新的计划版本。

补数只进入派生元数据或观测侧记录。若已有值与补采值矛盾，记录差异并提交复核，不能用“补全”名义覆盖旧值。无法补出的数据保持空值，附带原因与影响。

#### 四、采纳、重验与幂等

```text
探针发现缺口
  → 在许可来源内补采或确定性复算
  → 提交补丁／动作建议
  → 执行方核验运行、计划、基准摘要、字段白名单、来源与权限
  → 追加新版本并返回采纳回执
  → 从受影响的最早业务节点重新校验
  → 生成新报告版本并更新缺口状态
```

同一 `message_id` 重复投递只处理一次；同一 `patch_id` 重试返回原采纳结果。底层可以采用至少一次投递，但不得宣称因此获得了端到端“恰好一次”执行。业务提交、版本比较和事件发布应有可恢复的一致性机制。

基准版本已经改变的补丁拒绝或重新评估，不能直接应用到当前版本。迟到事件归入其原始运行和计划版本；已封存报告不被后台改写，必要时生成带更正关系的新版本。没有采纳回执的补丁保持待处理，不能推断已经生效。

#### 五、权限与故障边界

探针默认只读。主动补采还须具备任务范围、来源白名单、调用上限和审计记录；只读不代表没有费用、没有敏感数据风险或没有外部请求风险。

探针无权自行扩容执行者、触发业务写入、批准付款、部署、下单或修改验收条件。需要这些动作时只能提交建议。探针故障可使可观测性降级，但执行流程自身的强制证据检查和权限检查不能被跳过。

探针事件进入独立观测命名空间，默认不再次触发同类探针，避免观测自身引发无穷补数循环。

#### 六、最小联动载荷示例

下面只展示三类消息的载荷关系；正式发送仍须包含前述完整信封。所有标识及版本都是固定样例，基准摘要应由宿主对实际原件计算。

```yaml
messages:
  - message_type: gap_request
    payload:
      gap_id: 缺口B一
      target_artifact_ref: 卡B版本一
      field_path: /derived_metadata/source_version
      gap_type: 可恢复元数据
      necessity: 业务强制数据
      expected_semantics: 原卡所依据的不可变快照版本，不是当前来源版本。
      allowed_sources: [快照B]
      requested_action: 读取已有快照中的版本元数据
  - message_type: data_patch
    payload:
      patch_id: 补丁B一
      gap_id: 缺口B一
      base_artifact_ref: 卡B版本一
      base_hash: 示例基准摘要
      field_path: /derived_metadata/source_version
      operation: 补充缺失的派生元数据
      value: 样例快照版本一
      data_origin: 来源读取
      evidence_refs: [快照B版本元数据]
      validation_result: 字段来自与原卡绑定的不可变快照
  - message_type: apply_receipt
    payload:
      patch_id: 补丁B一
      gap_id: 缺口B一
      decision: 已采纳
      new_artifact_ref: 卡B派生版本二
      revalidation_nodes: [N03, N04, N05, N06, N07, N08, N09]
      revalidation_status: 通过
      revalidation_evidence_ref: 重验记录B一
      gap_status: 已关闭
```

该例只补充来源版本，不改写工作区是否共享等业务主张。若回执仅有“已采纳”而没有重验记录，则缺口仍不能记为已关闭。其他工作流可将节点编号映射为本地节点，但必须保留重验范围与依据。

## 7. 工作流总图

```text
任务输入
  → N00 输入与适用性校验
  → N01 冻结分片计划、口径、规则和预算
  → N02 并发执行并产生证据卡
  → N03 工件接收、版本检查与局部准入
  → N04 盘点缺席
  → N05 归一口径
  → N06 结论去重与来源血缘去重
  → N07 区分限定差异、记录并处理真实冲突
  → N08 检查跨分片接缝
  → N09 生成类型化报告及准入状态
  → N10 按授权补证／局部恢复，或交给业务裁决并封存
```

探针可在各节点旁路接收事件。需要补数时，通过共享协议返回；它不取代 N04—N08，也不成为判定业务真实与否的权威。

### 7.1 N00：输入与适用性校验

检查任务是否有真实并行面，输出是否能结构化，可比口径和验收规则是否可以确定。校验授权范围及不可执行动作。

输出任务规范与适用性判定。必须信息不足时产出明确的缺口清单；不自动选择隐含对象、时间窗口、预算或业务风险政策。无法并行但可串行的任务输出路由建议，不能伪装为已完成扇出。

### 7.2 N01：冻结计划

建立分片清单、必需维度、可比键规范、工件规则、来源要求和接缝规则。事先声明缺片时是等待、部分报告、补证还是终止；部分报告不能改写必选分片的验收要求。

资源同时约束单片和全局。新增执行者、重试、补采都要计入相应总额度；业务执行与探针额度可以分账，但合计不得超过授权总上限。费用无法取得时记录未知，使用调用数等已授权硬上限控制，不把未知费用记作零。

输出不可变计划快照、输入引用摘要及计划版本，发出“计划已冻结”事件。

### 7.3 N02：分派与执行

每位执行者只接收本分片需要的输入、上下文、工具和验收要求，不默认获得父任务所有权限。明确会话、工作区及工具边界；相对独立的上下文不等于来源独立。

执行者生成紧凑证据卡，包含限定条件、来源和缺口。任务遇到提示注入或越权工具要求时按安全政策处理，把外部文本当作证据而非权限指令。

记录尝试启动、工具调用摘要、终态与资源使用。工具调用摘要只保留审计所需事实，不要求保存模型私有推理过程、密钥或无关敏感正文。

### 7.4 N03：接收与局部准入

核验运行与计划身份、幂等键、模式格式、来源最低要求、必要维度及工件摘要。接收失败、错误格式、旧版本、超时及取消必须有不同原因码。

工件合格判断可以在归一化和来源复核后收紧，因此 N03 的覆盖为暂定值。后续每次改变有效工件集合，都重新计算最终 Q；不得把暂定覆盖率当作最终分片覆盖率。

工件缺少可恢复的来源元数据时可发 `gap_request`，但原始主张不明或证据不存在时只能等待补证，不能依赖探针生成主张。

### 7.5 N04：盘点缺席

逐个检查冻结计划中的必选和可选分片。对必选分片计算 `R − Q`；同时检查每片所需的对象与维度是否齐全。

区分未返回、仍执行中、超时、取消、运行失败、坏格式、来源不足、维度不足等情况。输出缺失清单、原因及影响，而不是只写“成功返回两份”。

必要证据不齐时，报告应维持不充分状态。可以继续对已取得的材料归一化和记录冲突，但任何后续处理都不能把缺席隐去。【来源二：第一步】

### 7.6 N05：归一口径

按下列次序检查：对象身份及版本、命题与维度、有效时间与采集时间、单位和币种、统计周期与分母、取值和置信语义。

可比键至少由“对象及版本＋命题＋维度＋有效时间范围＋取值口径”构成。单位换算、身份映射、同义词合并必须有明确规则和版本。不能凭字符串相似度把工作目录、仓库根目录和容器目录自动认成同一个位置。

保留原始值、归一化值和转换依据。币种换算需要授权的汇率来源、时点及用途；没有这些信息则保留原币种，不做混合加总。缺少分母或置信语义时，不平均看似同名的百分比与置信分数。

不同对象、时间或版本可分组展示，但不能未经场景允许就放进同一个比较组。无法归一的材料标为不可比或待核验，并更新相应局部工件准入。【来源二：第二步、可比性】

### 7.7 N06：去重但不删证据

先识别同一可比组内的重复结论，再识别来源族。来源族以有证据支撑的上游依赖关系建立，例如多个转载确实指向同一原始公告。

同一来源由多位执行者引用，只能算同一来源族。不同网址、不同模型、不同提示或不同会话不自动形成独立来源。向量相似度可以提示近似内容，但不能单独证明同源或独立。

来源血缘未核验时保持未知，不能把未发现共同上游解释为已经证明独立。去重仅建立代表卡与原始卡映射，不丢失原件、少数主张、相反证据或限定条件。【来源二：第三步】

### 7.8 N07：处理冲突

以下是本次扩展的判别顺序：先判断是否在同一可比组，再判断值是否按场景规则互斥。

| 情况 | 处理 |
|---|---|
| 会话隔离、工作区共享、工具受限 | 不同维度限定；全部保留，不构成二对一投票 |
| 不同对象、版本或时间段的差异 | 分组说明；必要时要求更合适的证据，不直接判断一方错误 |
| 同一字段经过有依据的换算后相同 | 记录转换关系，不列为业务冲突 |
| 同一可比命题下互斥的值 | 建立冲突标识，保留双方证据、来源、规则版本及待裁决事项 |
| 口径或来源不明 | 标为无法判断是否冲突，并产生数据缺口 |

默认不投票。只有同一命题、同一对象和版本、兼容的时间及取值语义、足够的来源独立性、获准的投票规则同时成立时，才可按场景策略使用投票。上述任一条件未知时，不允许降级成多数表决。

已解决冲突仍保留原始双方、裁决依据和权限记录。涉及必要证据的未决冲突使结构准入不通过；可选材料中的冲突不能暗中参与支撑主结论，仍需明确披露。【来源二：第四步】

### 7.9 N08：检查接缝

检查已经声明的跨分片不变量，而不是要求每个执行者重复检查全局。

可包括总额上限、对象重复处理、版本兼容、端到端延迟约束、共享工作区风险和组合集中度等。只启用当前场景真正适用且有定义的规则，不把不同业务领域的限制硬塞进同一模板。

每条规则输出“通过、失败、未知”之一及其依据。未知不能默认为通过。局部全部合格而总额越界时，应保留局部合格事实，并把组合检查判为失败。

分层聚合必须透传叶子分片全集、缺失、冲突、来源引用与规则结果。上层用集合并集去重，不平均各组百分比；中间层不得用“本组成功”掩盖缺失叶子。【来源二：第五步、分层聚合】

### 7.10 N09：类型化报告与闸门

本设计保留原文 `accepted` 的证据结构准入含义，并将接缝与业务授权另列。规则如下：

```text
结构准入通过 =
  全部必选分片义务具有合格工件
  且必要对象与维度齐全
  且有效工件满足身份、口径及来源契约
  且必要证据没有未处理冲突

进入正常业务裁决通道 =
  结构准入通过
  且所有必需接缝规则通过

业务动作获准 =
  有权业务节点按自己的政策作出决定
  且实际执行时权限、风险与资源检查通过
```

`accepted` 不由探针写入，只能由执行流程基于规则重新计算。对于没有适用接缝规则的场景，应在计划中声明规则集为空及理由，而不是运行失败后清空规则集。

结构准入失败或接缝未知的报告也应输出，可进入补证、异常审查或人工核验通道，但不能伪装成普通业务放行。业务表述可以是有条件成立，即使结构准入已通过。

### 7.11 N10：补证、局部恢复、交接与封存

| 问题 | 默认恢复方式 | 不允许的方式 |
|---|---|---|
| 暂时性工具故障 | 在预算与幂等条件内重试原分片 | 一路失败就重复整个扇出图 |
| 必要来源元数据缺失 | 读取已存快照或日志，提交可溯源补丁 | 用当前网页猜测当时的版本 |
| 缺少业务证据 | 指定分片、对象和问题重新采集证据 | 让探针补写有利主张 |
| 对象或单位错误 | 生成派生工件并重做归一化及下游检查 | 只改展示文本，不重算报告 |
| 来源关系新增 | 重做去重、冲突判定及依赖独立性的结论 | 保留旧的独立证据票数 |
| 真冲突 | 新证据、获授权裁决或明确保留未决状态 | 删除少数证据以“修复”冲突 |
| 接缝违规 | 改变业务方案须新授权；本次报告保留失败 | 让探针改阈值使检查通过 |

从受影响的最早节点重新执行其依赖下游：来源定位缺失影响局部准入时从 N03 重验；身份或单位变化通常从 N05；来源血缘变化通常从 N06。同时重新计算最终覆盖，并生成新报告版本。即使只改一个字段，也不能直接把旧报告的准入字段改成真。

为业务尝试、探针采集和补数闭环分别设置上限，并受全局资源上限约束。达到截止时间或修复轮数后，输出剩余缺口和证据不足报告，或交给明确授权的人工节点。不能无限地“再找一个执行者”。

正常交接包括报告版本、原始证据引用、限定条件、风险、缺片和冲突清单。记录发送事实或回执；没有交接记录时，只能声称报告已生成，不能声称上层已收到。

## 8. 独立运行需要保留的最小数据

| 数据 | 必须保留的内容 | 缺失影响 |
|---|---|---|
| 计划账本 | 计划版本、预期分片全集、必需维度、规则版本、预算与权限范围 | 无法可靠判断覆盖及越界 |
| 尝试账本 | 每次尝试的身份、启动、终态、截止时间、有效工件提交关系 | 无法辨别重试、迟到与分片缺席 |
| 工件账本 | 原始卡、摘要、派生版本、准入／拒收理由 | 无法复算来源与聚合结论 |
| 聚合账本 | 归一化、去重、冲突、接缝和准入的结构化结果 | 无法解释为何形成当前报告 |
| 恢复与交接账本 | 补丁、建议、采纳回执、重验、报告版本和交接引用 | 无法判断补数是否生效和是否真正交接 |

最小事件名称包括：计划已冻结、尝试已启动、尝试已终结、工件已提交、工件已拒收、缺席已盘点、口径已归一、来源已分组、冲突已记录、接缝已检查、报告已生成、补数已采纳／拒绝、重验已完成、报告已交接。

没有探针时，这些数据保存在执行流程自己的日志或工件目录中即可。外部看板、额外诊断和完整指标计算可以后接，但强制业务检查不能后置到看板。

## 9. 场景配置：固定核心，替换业务规则

下表是适配示例，不构成对应领域的专业裁决规则。

| 场景 | 分片方式 | 必须明确的口径 | 接缝与交接重点 |
|---|---|---|---|
| 技术研究与框架核验 | 来源、边界维度、组件 | 产品与执行方式、版本、文档时间、代码提交 | 保留会话／工作区／工具不同边界，避免结论扩大 |
| 文档批次审查 | 文档、合同编号、批次 | 文档版本、适用规则、条款定位 | 不漏输入、不重复对象，组合风险交有权审查者 |
| 数据核验 | 地区、对象、时间窗口 | 身份、币种、单位、周期、分母 | 合并后总量、重叠区间与版本兼容 |
| 代码或安全扫描 | 目录、服务、扫描器 | 提交版本、规则库版本、运行配置 | 跨模块依赖、重复告警与全局风险 |
| 运维排查 | 服务、日志源、指标源 | 时间同步、环境、请求链标识 | 因果链与端到端影响，禁止因并行观察直接推断因果 |
| 单分片或非并行工作流 | 一个逻辑输入单元，或由外部适配器提供 | 原工作流的输入和验收口径 | 可保留证据检查；不得宣称存在并行增益 |

变化应放进场景配置，而不是修改核心五步聚合。建议配置对象包含：分片规则、实体映射、可比键、必要来源、冲突政策、接缝规则、资源约束、权限边界、输出类型、观测级别与保存期限。

## 10. 固定样例：保留三种边界而不是多数投票

### 10.1 样例性质

本节沿用来源二的教学情境。下面的来源和运行标识为固定测试数据，不是对任何实际产品当前隔离能力的核验；固定样例不可自动提升为生产证据。

| 分片 | 维度 | 证据主张 | 来源引用 |
|---|---|---|---|
| A | 会话 | 会话上下文隔离 | 样例快照／会话资料 |
| B | 工作区 | 工作区共享 | 样例快照／工作区资料 |
| C | 工具 | 工具集合受限 | 样例快照／工具资料 |

三片均为必选，所有来源定位和版本在样例环境中可核验。场景要求是“说明各边界并披露风险”，不是“强制所有边界隔离”。

### 10.2 预期报告

```yaml
run_id: 样例运行一
plan_revision: 1
evidence_kind: 固定样例
expected_shards: [A, B, C]
qualified_shards: [A, B, C]
missing_shards: []
missing_dimensions: []
conflicting_dimensions: []
accepted: true
verdict: qualified
statement: 会话上下文隔离，工具集合受限；工作区共享，不能称为完全隔离。
qualifications:
  - 三张卡分别描述不同维度，不构成同一命题的三张选票。
risks:
  - 共享工作区风险应交给下游评估。
seam_check:
  status: 通过
  basis: 样例要求准确披露三类边界，不要求工作区一定隔离。
admitted_to_business: true
business_action_authorized: false
cards: [卡A, 卡B, 卡C]
```

`qualified` 延续原文样例的表述代码。结构准入通过只说明材料满足本场景要求，不证明系统满足另一个“所有工作区必须隔离”的场景要求。

### 10.3 缺片与补数分开演示

若 B 从未生成工作区证据，合格覆盖为 2/3，必须披露 B 和工作区维度缺失；探针不能补写“共享”。

若 B 的原卡已明确写出工作区共享，但导出遗漏了来源版本，而不可变快照中存在该版本，则探针可提交来源版本补丁。执行方保留原卡，生成带补充元数据的派生版本，从局部准入重新校验，覆盖可由 2/3 变为 3/3；是否最终准入仍由五步检查决定。

## 11. 回归与验收用例

以下用例是后续实现必须覆盖的预期行为，不表示已完成真实运行时集成测试。

| 编号 | 输入／故障 | 必须观察到的结果 |
|---|---|---|
| E01 | 三种不同边界分别为隔离、共享、受限 | 不进行二对一投票；保留三维限定和共享风险 |
| E02 | 必选三片只回来两片 | 覆盖 2/3，缺片与缺维度进入报告，`accepted` 为假 |
| E03 | 同一命题三张卡引用同一上游来源 | 工件可齐全，但只能形成一个已核验来源族 |
| E04 | 同一可比键下两个互斥值 | 原始双方、冲突标识和来源保留；未裁决时不准入 |
| E05 | 金额的单位或币种不同 | 无明确换算依据时不加总，不凭数值相似直接归一 |
| E06 | 分片重试或消息重复投递 | 分片分母不变；重复消息不新增有效工件或重复业务动作 |
| E07 | 一片永久失败 | 不删除预期分片，不把其余成功片包装成全量完成 |
| E08 | 所有局部金额合格但合计越界 | 结构准入与接缝失败分别记录，正常业务裁决通道不放行 |
| E09 | 探针补丁试图改业务结论、权限或验收阈值 | 拒绝并审计，原始状态不变 |
| E10 | 来源版本补丁基准摘要过期 | 拒绝或重新评估，不能套用到新工件 |
| E11 | 探针服务不可用 | 本地强制检查照常；关键数据缺失时不充分，非关键观测可降级 |
| E12 | 旧计划结果或超时结果迟到 | 原计划留痕，当前已封存报告不被覆盖 |
| E13 | 只有当前来源，无历史快照 | 不补造历史内容及历史发生时间 |
| E14 | 分层聚合中某组漏一个叶子 | 上层仍能定位叶子缺席，不能只看到组级成功 |
| E15 | 规则版本变化或模型替换 | 用同一冻结输入回归；差异能定位到版本与规则 |
| E16 | 固定样例被送入生产报告 | 明确标注并按来源政策拒绝其冒充真实证据 |

上线验收至少应通过：必选分片不隐去、维度不扁平化、同源不加票、冲突不删除、接缝不跳过、原件不覆盖、补丁不越权、无探针仍能运行、同一冻结输入与规则可复算。
