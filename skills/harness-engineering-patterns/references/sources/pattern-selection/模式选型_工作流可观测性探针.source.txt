# 1. 文档定位

工作流可观测性探针是一套可独立挂载、也可与模式选型执行流程交互运行的观测与补全机制。

它不只记录服务是否成功、接口是否报错，而是把一次任务中的以下内容关联起来：

```text
任务目标
  → 事实与来源
    → 候选判断
      → 路由、审批或计划
        → 工具调用和副作用
          → 实际业务状态
            → 对用户的最终表述
```

探针的核心作用有三项：

1. **看清过程**：知道系统读取了什么、判断了什么、为什么选择某条路径。
2. **补全数据**：发现执行记录缺少的事实、来源、前置检查、后置结果、计划版本或人工交接信息，并生成追加式补全补丁。
3. **验证一致性**：检查建议、批准、执行、副作用、业务状态和用户表述是否彼此一致。

探针默认不拥有业务决策权，不静默改变业务数据，不替代审批、权限或权威事实源。

---

# 2. 与模式选型执行流程的关系

两套文档可以独立运行：

- 《模式选型_执行流程.md》在没有探针时，可以通过人工记录完成选型和验证。
- 本探针在没有选型流程时，可以接入任意已有工作流，采集运行轨迹并输出覆盖率、异常和补全建议。

两套文档也可以交互运行：

```text
执行流程负责：定义任务、作出选择、执行控制、承担业务责任
探针负责：采集证据、关联上下文、计算指标、发现缺口、生成补全补丁
```

交互运行时，探针补全执行流程的数据，但不把“观测不到”自动解释成“没有发生”，也不把推断值提升为权威事实。

---

# 3. 设计目标

本探针应实现：

1. 统一一次运行中的任务、阶段、步骤、计划、模型、工具、审批和业务结果标识。
2. 区分直接观测、权威验证、用户声明、模型推断、人工判断、未知和冲突。
3. 记录关键决策所依据的事实、规则、版本和责任主体。
4. 识别“缺事实却继续推理”“建议正确但执行错误”“工具成功但业务状态未变化”等问题。
5. 量化模型调用是否必要、拓扑是否被正确执行、治理控制是否覆盖。
6. 对固定流程、路由、并行、编排、循环和层级提供不同的探针点。
7. 生成可回填执行流程的追加式数据补丁。
8. 支持按场景启用不同探针集合，避免所有工作流都承担同样的观测成本。
9. 保留完整运行史，使后续复盘能够还原当时看到的事实和采取的动作。

---

# 4. 非目标

本探针不负责：

- 替业务系统定义正确结果；
- 替模型或程序选择业务动作；
- 自动批准高风险操作；
- 静默修改订单、资金、权限、发布或客户承诺；
- 在没有证据时补造事实；
- 因为没有采集到事件，就断言某件事没有发生；
- 用单一“成功率”掩盖正确拒绝、正确转人工和高风险误执行；
- 把运行日志等同于完整可观测性。

# 5. 核心原则

## 5.1 追加式记录

原始事件、决策和补丁一旦写入，不应被覆盖。修正通过新版本、新事件或撤销记录表达。

```text
原判断保留
  + 新证据
  + 修订判断
  + 修订原因
```

## 5.2 事实状态必须显式

探针不只记录值，还记录值的来源与状态：

| 状态 | 含义 |
|---|---|
| 已验证 | 权威来源或责任人已确认 |
| 已观测 | 系统直接采集，但未完成业务确认 |
| 用户声明 | 用户或外部参与者声称 |
| 人工判断 | 有责任的人工判断，但可能仍需事实支撑 |
| 模型推断 | 模型基于材料形成的候选判断 |
| 未知 | 当前没有可用信息 |
| 冲突 | 多个来源不一致 |
| 过期 | 超出有效期或版本已变 |
| 不适用 | 当前步骤不需要 |

## 5.3 关联优先于堆日志

每条关键记录必须尽可能关联：

- 哪个任务；
- 哪次运行；
- 哪个步骤；
- 哪个对象；
- 哪一版规则、计划和工件；
- 哪个主体；
- 哪个审批；
- 哪个工具调用；
- 哪个副作用；
- 哪个最终业务结果。

无法关联的孤立日志不能支撑完整复盘。

## 5.4 业务结果优先于接口返回

工具返回成功，只能说明调用层面成功。探针还要检查实际业务状态是否发生预期变化。

```text
接口成功 ≠ 指令生效 ≠ 业务完成 ≠ 用户已收到结果
```

## 5.5 未知也是有效观测

发现关键事实未知，应记录“未知”及其影响，而不是省略字段或默认填入否定值。

## 5.6 推断不能静默升级

探针可以推断事件之间的关联或缺失阶段，但必须标注推断方法和置信度。推断结果不能直接支持高风险动作。

## 5.7 按风险分级采集

低风险信息问答可以轻量采集；金钱、权限、发布、法律和外部承诺必须完整记录事实、审批、前后状态和副作用。

## 5.8 最小必要数据

可观测性不是无限收集。应避免记录不必要的个人信息、机密原文和完整敏感载荷，优先保存摘要、哈希、引用和访问控制信息。

# 6. 运行模式

## 6.1 独立旁路模式

探针被动接收现有系统的事件、日志、审计记录和业务状态。

### 特点

- 不要求工作流采用《模式选型_执行流程.md》；
- 通过适配器映射已有事件；
- 无法映射的步骤标记为“未分类”；
- 默认只提示，不阻塞业务；
- 适合现有系统审计、问题复盘和逐步补齐观测。

### 输出

- 运行轨迹；
- 证据账本；
- 决策账本；
- 行动与副作用账本；
- 覆盖率报告；
- 异常报告；
- 补全建议。

## 6.2 交互补全模式

探针与模式选型执行流程使用统一事件和补丁协议。

### 特点

- 执行流程主动发送阶段、步骤和决策上下文；
- 探针能精确知道当前应收集哪些数据；
- 在安全门处返回数据缺口或异常；
- 可按策略将严重异常升级为阻塞信号；
- 补丁可回填选型卡、验证报告和运行记录。

### 默认权限

```text
采集：允许
关联：允许
计算指标：允许
生成补丁：允许
自动覆盖原字段：禁止
自动改变业务状态：禁止
自动批准或撤销审批：禁止
```

## 6.3 离线复盘模式

对历史事件进行重放、关联和指标计算。

### 适用

- 事故复盘；
- 模式选型回顾；
- 新旧版本比较；
- 规则变更影响分析；
- 采样人工标注后计算审计指标。

离线复盘不能改变当时业务状态，只能生成新版本分析结果。

# 7. 输入契约

## 7.1 最小输入

```yaml
探针输入:
  workflow_run_id: 工作流运行标识
  event_id: 事件标识
  event_type: 事件类型
  occurred_at: 事件发生时间
  actor: 执行主体
  object_ref: 目标对象引用
  phase_or_step: 阶段或步骤
  payload_summary: 载荷摘要
```

最小输入只能提供基础链路追踪，无法计算完整治理和业务一致性指标。

## 7.2 推荐输入

```yaml
推荐输入:
  selection_run_id: 模式选型运行标识
  workflow_run_id: 工作流运行标识
  trace_id: 端到端链路标识
  span_id: 当前跨度标识
  parent_span_id: 父跨度标识
  event_id: 事件标识
  event_type: 事件类型
  occurred_at: 发生时间
  ingested_at: 采集时间

  task:
    task_id: 任务标识
    task_version: 任务版本
    task_type: 任务类型
    risk_level: 风险等级

  object:
    object_type: 对象类型
    object_id_hash: 对象标识摘要
    owner_ref: 所属主体引用

  actor:
    actor_type: 程序 | 模型 | 人工 | 外部系统 | 探针
    actor_id: 主体标识
    authority_scope: 权限范围

  structure:
    cognition_refs: [认知引用]
    topology_ref: 拓扑引用
    pattern_refs: [模式引用]
    phase_id: 阶段标识
    step_id: 步骤标识
    plan_id: 计划标识
    plan_version: 计划版本

  evidence:
    fact_refs: [事实引用]
    rule_refs: [规则引用]
    source_refs: [来源引用]
    artifact_version: 工件版本

  operation:
    decision_type: 判断类型
    decision_value: 判断值
    tool_ref: 工具引用
    action_type: 动作类型
    side_effect_type: 无 | 可逆 | 不可逆

  result:
    technical_status: 技术状态
    business_status: 业务状态
    error_code: 错误码
    latency_ms: 时延
    cost_value: 成本
```

## 7.3 可选上下文

- 模型名称和版本；
- 提示模板版本；
- 输入与输出摘要；
- 令牌或调用成本；
- 工具请求和响应摘要；
- 审批对象、范围和有效期；
- 前置检查结果；
- 后置验证结果；
- 重试、循环和计划变更原因；
- 人工交接的责任人、待办事项和证据；
- 对用户的最终回复摘要。

# 8. 输出契约

探针输出由八类工件组成。

## 8.1 运行轨迹

按时间和因果关系呈现完整步骤，支持从任务下钻到模型、工具、审批和业务结果。

## 8.2 证据账本

记录每个关键事实的值、来源、状态、版本、有效期和被哪些判断使用。

## 8.3 决策账本

记录建议、候选、规则判断、人工决定和审批，明确责任主体及依据。

## 8.4 行动与副作用账本

记录工具调用、动作对象、幂等键、前置条件、预期副作用、实际副作用和后置验证。

## 8.5 计划历史

记录计划版本、依赖、完成步骤、变更原因和被保留的历史状态。

## 8.6 指标快照

按运行、任务类型、版本、模式、拓扑和风险等级计算指标。

## 8.7 异常报告

输出异常编号、严重级别、证据、影响范围和建议处理方式。

## 8.8 补全补丁

以追加方式补充执行流程缺失的数据，明确观测、推断或人工录入来源。

# 9. 标识与关联模型

## 9.1 核心标识

| 标识 | 作用 |
|---|---|
| `selection_run_id` | 一轮模式选型过程 |
| `workflow_run_id` | 一次具体业务工作流运行 |
| `trace_id` | 端到端因果链 |
| `span_id` | 一项局部操作或判断 |
| `parent_span_id` | 父子关系 |
| `event_id` | 单个不可变事件 |
| `task_id` | 任务定义 |
| `object_ref` | 业务对象 |
| `plan_id` | 计划身份 |
| `plan_version` | 计划版本 |
| `artifact_id` | 文档、报告、代码或其他工件 |
| `approval_id` | 一次批准 |
| `tool_call_id` | 一次工具调用 |
| `side_effect_id` | 一项外部副作用 |
| `handoff_id` | 一次责任交接 |
| `supplement_id` | 一条补全补丁 |

## 9.2 关联要求

- 同一工作流中的所有关键事件必须共享 `workflow_run_id`。
- 工具调用与返回必须通过 `tool_call_id` 配对。
- 风险动作必须关联前置检查事件和后置验证事件。
- 审批必须关联其对象、动作、版本、范围和有效期。
- 计划变更必须关联上一版本。
- 人工交接必须关联来源步骤、接收责任人和待核实事项。
- 最终回复必须关联实际业务状态，而不是只关联模型草稿。

# 12. 探针生命周期

```text
P0 注册探针
  ↓
P1 接收运行上下文
  ↓
P2 映射任务、阶段和步骤
  ↓
P3 采集事实、决策、动作和结果事件
  ↓
P4 关联因果链与版本
  ↓
P5 检查数据完整性和一致性
  ↓
P6 计算可直接计算的指标
  ↓
P7 触发异常规则
  ↓
P8 生成追加式补全补丁
  ↓
P9 在安全门返回提示或阻塞信号
  ↓
P10 生成运行摘要并归档
```

独立旁路模式通常只执行 P1 至 P8 和 P10；交互补全模式可以在 P9 与执行流程同步交互。

# 14. 指标体系

指标分为三类：

1. **直接指标**：仅依赖运行事件即可计算。
2. **对照指标**：需要任务集预期结果、规则真值或人工标注。
3. **审计指标**：通过抽样复核计算，不能假装为全量真值。

探针必须同时输出指标值和可计算性状态：

```text
已计算
数据不足
需要真值
需要人工审计
不适用
```

| MTR-008 | 回复事实可追溯率 | 可关联到事实来源的关键回复断言数 ÷ 关键断言总数 | 审计 | 回复是否有据可查 |
| MTR-009 | 交接契约完整率 | 同时有状态、责任、证据、待办和版本的交接数 ÷ 交接总数 | 直接 | 下一棒能否接住正确状态 |

# 23. 严重级别与处置策略

| 级别 | 含义 | 默认处置 |
|---|---|---|
| 信息 | 正常观测或趋势 | 记录 |
| 提醒 | 可能优化，但不影响当前正确性 | 汇总提示 |
| 中 | 数据不完整或结构质量下降 | 要求补全或进入复核 |
| 高 | 可能导致错误决定、错误说明或恢复困难 | 暂停相关步骤或降级 |
| 严重 | 可能产生越权、资金、发布、不可逆副作用或错误承诺 | 立即阻塞、隔离并人工处理 |

独立旁路模式默认不阻塞，只输出建议。交互补全模式可按风险策略把高或严重异常映射为工作流门控信号。

# 24. 补全补丁协议

## 24.1 补丁结构

```yaml
补全补丁:
  schema_version: 0.1.0
  supplement_id: SUP-唯一标识
  created_at: 创建时间

  target:
    selection_run_id: 选型运行标识或空
    workflow_run_id: 工作流运行标识
    phase_id: 目标阶段
    step_id: 目标步骤或空
    field_path: 目标字段路径

  content:
    value: 补充值或引用
    value_type: 事实 | 关联 | 指标 | 缺失提示 | 异常 | 推断 | 摘要
    evidence_refs: [证据引用]

  provenance:
    collection_method: 直接采集 | 适配映射 | 人工录入 | 探针推断
    evidence_state: 已验证 | 已观测 | 人工判断 | 模型推断 | 未知 | 冲突
    confidence: 仅推断时填写
    probe_ref: 探针编号

  application:
    policy: 自动追加 | 评审后追加 | 仅提示 | 阻塞信号
    overwrite_allowed: false
    accepted_by: 接收主体或空
    accepted_at: 接收时间或空
    rejection_reason: 拒绝原因或空
```

## 24.2 补丁类型

| 类型 | 示例 | 默认策略 |
|---|---|---|
| 直接观测事实 | 工具实际返回状态 | 自动追加 |
| 关联补丁 | 将工具调用与审批关联 | 自动追加 |
| 指标补丁 | 前置检查覆盖率 | 自动追加到评估数据 |
| 缺失提示 | 缺少禁止动作定义 | 仅提示或按风险阻塞 |
| 异常补丁 | 审批范围不匹配 | 高风险时阻塞 |
| 推断补丁 | 根据时间和对象推测事件属于某步骤 | 评审后追加 |
| 摘要补丁 | 本轮异常与成本摘要 | 自动追加，不改变业务状态 |

## 24.3 补丁合并规则

1. 不覆盖原始字段。
2. 新值与旧值不一致时，创建冲突记录。
3. 权威事实优先于探针推断，但不能删除推断历史。
4. 补丁被拒绝时保留拒绝原因。
5. 高风险动作不得使用“仅推断”的补丁满足前置条件。
6. 同一事实的多个来源按版本、时间和权威级别并存。

# 25. 数据缺口处理

探针发现缺失数据时，按以下顺序处理：

```text
能从现有事件直接关联 → 生成关联补丁
能从权威系统重新查询 → 生成观测事实
只能根据上下文推断 → 标记推断和置信度
需要责任人确认 → 创建人工补全任务
无法获得 → 明确标记未知
```

禁止：

- 用默认值掩盖未知；
- 因为没有错误日志，就标记为成功；
- 因为没有发票记录，就标记为未开票；
- 因为模型表达肯定，就把推断升级为事实。

# 26. 数据质量检查

## 26.1 完整性

- 关键事件是否齐全；
- 必填字段是否存在；
- 调用与返回是否配对；
- 风险动作是否有前后状态。

## 26.2 一致性

- 同一对象标识是否一致；
- 计划和步骤版本是否一致；
- 审批范围与动作是否一致；
- 回复与业务结果是否一致。

## 26.3 新鲜度

- 数据和规则是否在有效期；
- 缓存是否已过期；
- 运行上下文是否使用当前版本。

## 26.4 唯一性

- 事件标识是否重复；
- 幂等键是否被正确使用；
- 同一副作用是否被多次创建。

## 26.5 可追溯性

- 事实能否追到来源；
- 决定能否追到事实和规则；
- 动作能否追到决定和批准；
- 结果能否追到实际业务状态。

## 26.6 隐私与最小化

- 是否采集了不必要的个人信息；
- 是否可以只保存摘要或引用；
- 敏感字段是否脱敏；
- 访问是否按角色控制。

| G1 | 任务契约完成后 | 完成条件、安全出口、禁止动作 |
| G2 | 困难诊断后 | 证据是否支持根因 |
| G3 | 模型边界确定后 | 模型调用必要性和越权风险 |
| G4 | 拓扑和模式选择后 | 结构控制是否齐全 |
| G5 | 风险动作前 | 事实、权限、审批、额度、幂等 |
| G6 | 风险动作后 | 实际副作用和业务状态 |
| G7 | 回复发送前 | 回复依据和状态一致性 |
| G8 | 运行结束后 | 安全完成、指标和未闭环异常 |

# 30. 采样策略

## 30.1 不应采样的事件

以下事件默认全量采集：

- 高风险审批；
- 权限检查；
- 风险动作前置检查；
- 不可逆副作用；
- 工具调用失败；
- 后置验证失败；
- 回滚和补偿；
- 严重异常；
- 计划版本变更；
- 人工交接；
- 最终业务状态。

## 30.2 可采样的事件

在低风险、高频场景中可采样：

- 重复的正常查询；
- 模型令牌明细；
- 非关键调试日志；
- 高频中间状态。

## 30.3 自适应采样

出现以下情况时自动提高采样率：

- 新版本刚发布；
- 异常率上升；
- 任务风险等级提高；
- 规则或数据源发生变化；
- 进入人工复核；
- 发生重试、循环或计划变更。

# 31. 隐私、安全与保留

## 31.1 最小必要原则

优先记录：

- 脱敏对象引用；
- 输入输出摘要；
- 工件哈希；
- 来源引用；
- 规则和版本；
- 状态差异。

避免默认记录：

- 完整身份证件；
- 完整支付信息；
- 无关聊天原文；
- 完整机密文档；
- 与复盘无关的个人信息。

## 31.2 访问控制

- 业务人员只能查看本职责范围；
- 审计人员可以查看关联记录但不自动获得业务操作权限；
- 模型输入应经过脱敏和最小化；
- 探针管理权限与业务执行权限分离。

## 31.3 保留策略

按风险和法规配置：

```yaml
保留策略:
  raw_events: 原始事件保留期
  summaries: 摘要保留期
  high_risk_audit: 高风险审计保留期
  model_payloads: 模型载荷保留期
  deletion_policy: 删除或匿名化策略
  legal_hold: 法律保全策略
```

## 31.4 完整性保护

对关键事件可使用：

- 事件哈希；
- 前序哈希；
- 只追加存储；
- 签名或可信时间戳；
- 版本化快照。

# 33. 退款场景示例

## 33.1 发票状态未知

### 关键事件

```text
workflow.run.started
workflow.fact.observed          退款金额=347，已观测
workflow.fact.marked_unknown     发票状态=未知
workflow.decision.proposed       建议=转人工
workflow.route.selected          路由=人工核实
workflow.guard.checked           付款前置条件不满足
workflow.handoff.created         待核实=是否开票
workflow.tool.called             创建人工处理单
workflow.tool.returned           技术成功
workflow.side_effect.verified    人工处理单已存在
workflow.outcome.verified        退款状态=pending_human
workflow.response.grounded       说明仍需核实发票
workflow.run.completed
```

### 探针结论

- 未发生付款指令；
- 未知事实进入安全出口；
- 人工单包含待核实事项；
- 对用户表述与业务状态一致；
- 本次属于安全完成，而不是失败。

## 33.2 财务已确认未开票

### 关键事件

```text
workflow.fact.verified           发票状态=none，来源=财务确认
workflow.decision.proposed       建议=自动批准
workflow.guard.checked           金额、凭证、权限和发票条件通过
workflow.tool.called             创建付款指令
workflow.tool.returned           技术成功
workflow.side_effect.verified    付款指令 PI-0311 已存在
workflow.outcome.verified        退款状态=approved
workflow.response.grounded       仅说明已获批或已创建指令，不宣称到账
```

### 探针结论

- 同样金额下，结果变化来自新增的权威事实；
- 工具成功后又验证了实际指令；
- `approved` 没有被误报为客户已收到退款。

## 33.3 客户追问为什么还要等

探针检查第二次模型调用：

- 第一次模型调用只整理诉求和候选订单；
- 中间程序新增了凭证检查和发票状态；
- 第二次模型调用获得了新材料，属于必要调用；
- 回复只使用已核实材料，说明等待原因是发票尚未核实。

因此不会把第二次调用判定为冗余。

# 34. 独立部署流程

1. 确定接入的工作流和风险等级。
2. 建立事件适配表，将现有日志映射到标准事件。
3. 先接入运行、步骤、工具和业务结果四类最小事件。
4. 再补事实、判断、审批、计划和回复事件。
5. 配置场景探针集和不应采样事件。
6. 运行一批历史数据，检查关联率和误报。
7. 对无法计算的指标明确标记“数据不足”或“需要真值”。
8. 先以旁路提示运行，再决定哪些严重异常需要门控。
9. 建立补丁接收流程和人工复核责任。
10. 定期复盘探针本身的覆盖、成本、隐私和误报。

---

# 35. 与执行流程交互部署流程

1. 统一 `selection_run_id`、`workflow_run_id`、阶段和步骤编号。
2. 在执行流程 S0、S1、S3、S4、S5、S7、S8、S9 设置安全门。
3. 执行流程发布标准事件，不把完整敏感载荷直接送入探针。
4. 探针返回覆盖、异常、指标和补丁。
5. 直接观测和关联补丁自动追加；推断补丁进入复核。
6. 高风险异常按策略暂停或阻塞。
7. 运行结束后，探针生成摘要，回填验证报告和模式选型卡。
8. 版本或任务实质变化时，触发重新选型事件。

# 36. 探针自检

探针本身也需要被验证。

## 36.1 自检指标

| 指标 | 含义 |
|---|---|
| 事件摄取成功率 | 发送事件是否被接收 |
| 关联成功率 | 事件是否正确归属到运行和步骤 |
| 误关联率 | 不同对象或运行被错误串联的比例 |
| 异常准确率 | 告警是否真实反映问题 |
| 异常召回率 | 已知问题是否被发现 |
| 补丁接受率 | 补丁是否有用且来源清楚 |
| 补丁冲突率 | 补丁与权威事实冲突的比例 |
| 探针时延 | 观测结果返回耗时 |
| 探针成本 | 存储、计算和人工复核成本 |
| 业务影响 | 探针是否造成不可接受的阻塞或性能下降 |

## 36.2 自检原则

- 探针失效不能默认放开高风险动作，具体行为由业务安全策略决定；
- 探针异常不能篡改业务原始记录；
- 误报和漏报必须进入版本化改进；
- 规则变化后需要重跑已知测试集。

# 37. 评估用例

```yaml
探针评估用例:
  case_id: PROBE-CASE-001
  scenario: 场景
  input_events: [输入事件]
  missing_events: [故意缺失事件]
  expected_links: [预期关联]
  expected_metrics: [预期指标]
  expected_anomalies: [预期异常]
  expected_supplements: [预期补丁]
  forbidden_outputs:
    - 不得把推断写成已验证事实
    - 不得改变业务状态
```

### 最低测试集

1. 完整固定链，所有步骤正确关联。
2. 工具调用有开始无返回，触发链路缺口。
3. 发票未知却创建付款指令，触发严重异常。
4. 模型在相同材料上重复评审，触发冗余调用提示。
5. 第二次模型调用获得新业务事实，不应误报为冗余。
6. 计划变更保留已完成步骤，指标正确。
7. 计划变更丢失已完成状态，触发异常。
8. 重试使用相同幂等键且无重复副作用，判定正常。
9. 工具返回成功但业务状态未变化，触发后置不一致。
10. 回复把“已批准”写成“已到账”，触发状态夸大。
11. 探针无法关联事件时，标记数据不足，不虚构结论。
12. 推断补丁未经确认，不得满足高风险前置条件。
13. 敏感载荷超量采集，触发隐私异常。
14. 规则版本变化后仍使用旧选型，触发重新选型提示。

## 38.6 隐私与保留

- [ ] 仅采集最小必要数据。
- [ ] 敏感字段已脱敏或只保存引用。
- [ ] 访问权限按角色隔离。
- [ ] 保留期和删除策略已配置。
- [ ] 探针自身行为可审计。

# 39. 与框架的挂载关系

本探针不是单一监控指标集合，而是可挂载到不同认知与拓扑坐标的工程模式：

```text
感知：采集任务、事实、工具、状态和环境信号
记忆：保存追加式运行史、版本、计划和证据账本
推理：关联因果链、识别缺口和计算派生指标
反思：比较基线与候选、发现错误模式和触发重新选型
协作：观察委派、交接、评审、聚合和责任变化
治理：检查权限、审批、额度、前后条件和副作用
```

```text
链式：观察步骤传递和版本一致性
路由：观察条件、事实和出口
并行：观察分支独立性和聚合冲突
编排：观察计划、依赖、进度和变更
循环：观察新信息、预算和停止条件
层级：观察责任、工件、验收和交接
```

探针输出的证据、指标和补丁可以挂载到工程模式评估、Skill 运行记录和治理审计中，但源注册表、矩阵视图与执行 Skill 仍应保持分层。
