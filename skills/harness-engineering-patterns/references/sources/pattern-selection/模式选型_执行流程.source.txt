# 1. 文档定位

本执行流程用于回答一个核心问题：

> 面对一项具体任务，哪些工作应由确定性程序完成，哪些工作需要模型参与，采用什么组织结构，以及如何证明这次选型有效。

它不是“模式清单”，也不是要求每个系统都接入模型。它从最小可行方案开始，只在现有办法确实存在缺口时增加模型、模式、角色或动态编排。

本流程支持两种运行方式：

1. **独立运行**：只使用本文件完成任务澄清、困难诊断、结构选型、治理设计、试运行和选型归档。
2. **交互运行**：与《模式选型_工作流可观测性探针.md》配合，由探针采集事实、判断、工具调用、审批、计划变更和业务结果，补全本流程的证据数据。

两种方式采用同一套阶段编号、运行标识和输出契约。没有探针时，观测字段可以人工填写；接入探针后，不改变本流程的业务决策权，只增强可追溯性与验证能力。

---

# 2. 目标

本流程应产出以下结果：

1. 明确任务怎样才算完成，以及哪些事情禁止发生。
2. 判断现有程序、规则、模板或人工流程是否已经足够。
3. 定位真正的困难属于信息缺失、语义理解、推理判断、流程组织、协作分工还是治理风险。
4. 明确模型的职责边界，避免让模型猜测已有权威来源的数据。
5. 选择最少且足够的认知能力、拓扑结构和工程模式。
6. 把工具调用前后的检查、权限、审批、额度、副作用和恢复路径写进执行设计。
7. 用同一批任务比较基线方案与候选方案，记录成功、错误、时间和费用。
8. 形成可执行、可验证、可回退、可继续演化的选型记录。

# 3. 核心原则

## 3.1 先定义正确，再讨论结构

必须先写清：

- 什么结果算正确完成；
- 哪些安全退出也算正确完成，例如转人工、拒绝、等待补充事实；
- 哪些副作用绝对不能发生；
- 哪些状态只代表“已受理”或“已批准”，不代表最终业务结果已经发生。

不能把“没有执行成功”一概视为失败。若事实不足、权限不足或风险条件不满足，正确地停止、拒绝或转人工，本身就是成功结果。

## 3.2 已有办法够用，就继续使用

若输入规范、规则明确、步骤固定、异常分支已知，则优先采用程序、规则引擎、工作流或模板。

学习了模式，不等于每项任务都要增加模型调用、评审角色、计划器或多代理结构。

## 3.3 缺事实，不等于缺推理

当关键事实不存在、未同步、相互冲突或尚未核实时，增加一次模型分析或模型评审不能凭空获得该事实。

此类问题应转向：

- 查询权威数据源；
- 请求用户补充；
- 调用检测工具；
- 交由具备责任和权限的人核实；
- 明确标记为未知，并阻止依赖该事实的高风险动作。

## 3.4 模型只负责需要判断的部分

金额、身份、权限、库存、订单状态、发票状态、政策版本、执行结果等有明确来源的数据，应由程序读取并校验。

模型可以承担：

- 理解非结构化表达；
- 从候选对象中提出待核对对象；
- 在材料齐备后组织解释；
- 在固定流程无法覆盖时提出候选计划；
- 对开放性材料提出假设或候选结论。

模型的输出默认是“建议、候选或草稿”，不是未经检查即可生效的事实或操作授权。

## 3.5 下一步由谁决定，决定了结构

- 开发时写好的程序决定下一步：固定流程。
- 当前条件决定不同出口：路由。
- 几项任务互不依赖：并行。
- 根据新结果继续调整：循环。
- 不同角色承担不同局部责任：层级。
- 模型先提出计划，由程序保存并推进依赖：编排。

## 3.6 模式越多，运行责任越多

每增加一种结构，都必须补上对应控制：

- 增加循环，要定义停止条件、预算和最大次数；
- 增加角色，要定义输入、输出、责任和验收；
- 增加计划，要定义依赖、版本、变更和恢复；
- 增加审批，要定义批准对象、有效范围和过期条件；
- 增加工具调用，要定义前置检查、幂等、副作用和后置验证。

## 3.7 选型结论必须可验证

最终记录至少回答四个问题：

1. 遇到了什么具体问题；
2. 为什么采用这种安排；
3. 用什么证据说明它有效；
4. 还有什么没有验证。

---

# 4. 适用场景

本流程适用于：

- 从传统程序或工作流向模型辅助系统演化；
- 为新 Agent、Skill 或自动化流程选择结构；
- 判断是否需要第二次模型调用、评审、计划器或多角色协作；
- 对高风险业务操作设计审批、护栏和执行后验证；
- 对已有系统出现的错误进行结构性复盘；
- 为不同业务场景建立可复用的模式选型卡；
- 在固定流程、边查边决定、规划执行之间作取舍。

---

# 5. 不适用场景

以下情况不应直接进入复杂选型：

1. 任务输入、步骤和输出完全确定，普通程序已稳定完成。
2. 当前问题只是基础数据质量缺陷，应先修复数据源或同步链路。
3. 权威制度、接口或责任人尚未确定，无法定义正确结果。
4. 高风险操作缺少必要权限、审批和审计基础，不能先用模型绕过。
5. 任务尚处于纯探索阶段，连要解决的问题都未形成，可先做问题发现，不急于定型。

# 6. 角色与责任边界

| 角色 | 主要责任 | 不承担的责任 |
|---|---|---|
| 任务提出者 | 描述目标、场景、约束和期望结果 | 不替代权威数据源确认事实 |
| 业务责任人 | 定义正确结果、禁止动作、规则和例外 | 不把责任转移给模型 |
| 流程设计者 | 诊断困难、选择结构、设计契约和控制 | 不擅自改变业务规则 |
| 确定性程序 | 读取权威数据、执行规则、检查权限、保存状态 | 不猜测缺失事实 |
| 模型 | 理解语言、提出候选、组织解释、生成候选计划 | 不自行获得授权，不把推断写成事实 |
| 人工审批者或核实者 | 对责任边界内的事实和动作作出有效判断 | 一次批准不自动扩展到其他对象或后续动作 |
| 可观测性探针 | 采集、关联、补全和验证运行数据 | 不静默改写业务状态，不替代审批 |

# 7. 输入契约

## 7.1 必填输入

```yaml
任务输入:
  任务标识: 唯一标识
  任务名称: 简明名称
  场景描述: 当前要解决的业务或工程问题
  请求对象: 用户、订单、设备、代码库、文档或其他目标对象
  期望结果: 希望系统交付什么
  完成条件: 可验证的完成判据
  安全完成条件: 转人工、拒绝、等待或降级何时也算正确
  禁止动作: 不能发生的行为或副作用
  权威事实源: 已知数据源、规则源和责任人
  当前流程: 现有程序、人工流程、规则、模板或工作流
  可用工具: 查询、检测、执行、通知、回滚等能力
  权限边界: 当前身份可以读取、建议、批准和执行什么
  风险等级: 低、中、高或自定义等级
  时间约束: 截止时间、超时和等待限制
  成本约束: 模型、工具、人工和外部服务预算
```

## 7.2 可选输入

```yaml
可选输入:
  历史案例: 成功、失败和边界案例
  评估任务集: 用于比较候选方案的固定样本
  当前指标: 成功率、人工率、时延、成本、错误类型
  已知模式: 希望复用或避免的工程模式
  合规要求: 审计、隐私、保留期、地域和行业要求
  运行环境: 线上、离线、交互式、批处理或边缘环境
  变更频率: 规则、数据、工具和任务结构的变化频率
```

## 7.3 事实状态枚举

所有关键事实必须标记状态：

| 状态 | 含义 | 是否可直接支持高风险动作 |
|---|---|---:|
| 已验证 | 已由权威来源确认 | 是，但仍需通过规则和权限检查 |
| 已观测 | 系统直接读取，但尚未完成业务验证 | 视规则而定 |
| 用户声明 | 来自用户或外部角色的陈述 | 通常否 |
| 模型推断 | 模型根据材料形成的候选判断 | 否 |
| 未知 | 尚无可用事实 | 否 |
| 冲突 | 多个来源不一致 | 否 |
| 过期 | 曾有效，但已超过有效期 | 否 |
| 不适用 | 当前任务无需该事实 | 不适用 |

# 8. 输出契约

流程完成后必须形成以下工件：

## 8.1 模式选型卡

记录问题、基线、困难、模型边界、认知、拓扑、工程模式、治理要求、证据和未验证项。

## 8.2 可执行工作流说明

至少包含：

- 步骤及依赖；
- 每步输入、事实来源和执行者；
- 决策者和决策规则；
- 工具调用和副作用；
- 前置条件与后置条件；
- 失败出口、人工出口和恢复点；
- 计划版本或状态保存方式；
- 可观测事件和探针挂载点。

## 8.3 控制清单

包括身份、权限、审批、额度、幂等、超时、重试、回滚、数据新鲜度、隐私和审计要求。

## 8.4 验证报告

记录基线方案和候选方案在同一任务集上的：

- 正确完成；
- 正确拒绝或转人工；
- 新增错误；
- 关键风险；
- 时延；
- 成本；
- 人工负担；
- 尚未覆盖的样本。

## 8.5 可观测清单

即使不接入独立探针，也必须列明需要记录的事件、事实、判断、工具调用、业务结果和关联标识。

# 9. 运行状态机

```text
initialized       已初始化
contracting       正在定义任务契约
baseline_testing  正在运行现有办法或最小方案
diagnosing        正在诊断具体困难
selecting         正在选择认知、拓扑和工程模式
designing         正在形成可执行结构
validating        正在同批任务上比较验证
review_required   等待业务、风险或人工评审
active            已批准投入运行
suspended         因事实、权限、异常或风险暂停
reselect_required 任务发生实质变化，需要重新选型
completed         本轮选型完成
rejected          候选方案未通过验证
archived          已归档
```

状态迁移必须记录触发原因。禁止把 `review_required`、`suspended` 或 `rejected` 静默改写为 `active`。

# 10. 总体执行结构

```text
S0 初始化运行
  ↓
S1 定义任务正确性与禁止动作
  ↓
G1 任务契约是否完整？
  ├─ 否 → 补充事实、规则或责任人 → S1
  └─ 是
       ↓
S2 运行现有办法或最小方案
  ↓
G2 现有办法是否足够？
  ├─ 是 → 固化程序、规则或模板 → S8
  └─ 否
       ↓
S3 定位具体困难
  ↓
S4 划定模型与程序边界
  ↓
S5 选择最小拓扑结构
  ↓
S6 选择工程模式与治理控制
  ↓
S7 形成可执行工作流
  ↓
S8 用同一任务集比较验证
  ↓
G3 是否同时满足正确性、安全性和成本约束？
  ├─ 否 → 调整、降级或放弃 → S3 / rejected
  └─ 是
       ↓
S9 发布选型卡与运行约束
  ↓
S10 运行中监测任务变化
  ├─ 无实质变化 → 继续运行
  └─ 有实质变化 → reselect_required → S1
```

# 11. 详细执行流程

## S0. 初始化运行

### 目标

建立唯一运行身份，冻结本轮输入版本，确定责任人和风险等级。

### 操作

1. 生成 `selection_run_id`。
2. 记录任务输入版本和规则版本。
3. 指定业务责任人、流程设计者和审批责任人。
4. 标记是否接入工作流可观测性探针。
5. 创建追加式决策记录，不允许后续覆盖原始判断。

### 输出

```yaml
运行头:
  selection_run_id: SEL-日期-序号
  task_id: 任务标识
  input_version: 输入版本
  rule_version: 规则版本
  risk_level: 风险等级
  owner: 业务责任人
  designer: 流程设计者
  probe_mode: 未接入 | 独立旁路 | 交互补全
```

### 完成门

- 运行标识唯一；
- 任务对象可识别；
- 责任人存在；
- 高风险任务已指定审批责任人。

---

## S1. 定义正确性、禁止动作和安全出口

### 目标

在讨论模型与模式之前，建立可验证的任务契约。

### 必答问题

1. 任务最终要改变什么业务状态，或交付什么信息工件？
2. 哪个系统、数据源或责任人能证明完成？
3. 哪些中间状态不能被误报为最终完成？
4. 哪些情况应停止、拒绝、等待或转人工？
5. 哪些副作用一旦发生就不可接受？
6. 用户看到的答复必须说明到什么程度？

### 任务结果分类

| 结果类型 | 说明 | 示例 |
|---|---|---|
| 正确执行 | 满足条件并完成授权动作 | 创建有效付款指令 |
| 正确受理 | 已进入后续流程，但最终结果尚未发生 | 已提交人工核实 |
| 正确拒绝 | 权限、规则或风险不允许 | 拒绝越权操作 |
| 正确等待 | 缺少关键事实，保持原状态 | 等待检测结果 |
| 正确降级 | 高级能力不可用，使用安全替代方案 | 使用固定模板回复 |
| 错误执行 | 条件不满足却产生副作用 | 发票未知仍付款 |
| 错误宣称 | 实际未完成却告知已完成 | 仅获批却说已到账 |

### 完成门 G1

只有以下内容都明确，才能继续：

- 完成条件；
- 安全完成条件；
- 禁止动作；
- 权威验证来源；
- 关键未知事实的处理方式。

否则返回补充，不进入模式选型。

---

## S2. 运行现有办法或最小方案

### 目标

先验证现有程序、规则、模板或人工流程到底缺什么，避免凭想象增加复杂性。

### 最小方案优先级

```text
确定性程序
  → 规则或决策表
    → 固定工作流
      → 模板
        → 单次模型辅助
          → 多次模型调用
            → 动态计划或多角色结构
```

优先级不是价值排序，而是复杂度递增顺序。只有前一层无法满足任务，才评估后一层。

### 操作

1. 选取代表性任务和边界任务。
2. 用当前流程实际走一遍。
3. 记录失败发生在哪个步骤。
4. 区分“没有完成”和“完成方式不理想”。
5. 记录现有方案是否产生原本不会出现的错误。

### 基线输出

```yaml
基线结果:
  baseline_id: BASE-001
  current_solution: 当前程序、流程或模板
  completed_cases: 正确完成样本
  safe_exit_cases: 正确转人工、拒绝或等待样本
  failed_cases: 失败样本
  new_error_types: 新增错误类型
  latency: 时延
  cost: 成本
  manual_load: 人工负担
  observed_gap: 具体缺口
```

### 完成门 G2

若现有办法满足：

- 正确性；
- 安全性；
- 可解释性；
- 时延与成本；
- 可维护性；

则停止增加模式，直接进入 S8 进行轻量验证和归档。

---

## S3. 定位具体困难

### 目标

把“系统不够智能”拆成可处理的具体问题。

### 困难分类表

| 困难编号 | 具体困难 | 典型信号 | 首选补救方向 |
|---|---|---|---|
| D1 | 输入表达模糊 | 没有标准字段、对象不明确、多意图混合 | 模型理解或结构化提取，随后程序核对对象 |
| D2 | 关键事实缺失 | 数据未同步、记录不存在、用户仅声明 | 查询权威源、检测、补充材料或人工核实 |
| D3 | 事实相互冲突 | 多系统值不一致、版本不同 | 冲突仲裁、数据治理、暂停高风险动作 |
| D4 | 规则适用复杂 | 多条规则组合、例外多 | 规则引擎、决策表；必要时模型提出候选解释 |
| D5 | 回复需要结合多处事实 | 固定模板无法回答具体疑问 | 材料齐备后再次调用模型组织答复 |
| D6 | 每项任务步骤不同 | 现有流程难覆盖，需临时安排依赖 | 候选计划、编排和进度追踪 |
| D7 | 下一步依赖新结果 | 边查边决定、假设需验证 | 循环或动态工具选择 |
| D8 | 多项工作互不依赖 | 可同时调查或处理 | 并行、扇出聚合 |
| D9 | 不同角色需独立负责 | 各自有资料、边界和验收 | 层级委派或交接链 |
| D10 | 高风险动作需要责任判断 | 金钱、权限、发布、承诺 | 审批门、权限检查、额度和后置验证 |
| D11 | 输出正确但不可追溯 | 无法说明使用了什么事实和规则 | 决策记录、证据账本、可观测性探针 |
| D12 | 成本或时延不可接受 | 模型调用过多、重复查询、等待过长 | 降级、缓存、路由、减少不必要调用 |

### 诊断规则

- 一个失败可对应多个困难，但每个困难必须有具体证据。
- 不允许把“模型回答错”直接作为最终根因。
- 必须继续区分：资料未找到、资料过期、事实冲突、推理错误、规则错误、执行错误或结果误报。

### 输出

```yaml
困难诊断:
  difficulty_refs:
    - difficulty_id: D2
      evidence_refs: [证据标识]
      affected_step: 受影响步骤
      impact: 影响
      current_workaround: 当前替代办法
      confidence: 已验证 | 高 | 中 | 低
```

## S4. 划定模型、程序与人工的边界

### 目标

明确每项工作由谁负责，模型是否真的必要。

### 模型必要性判断表

| 情况 | 默认选择 | 模型可承担 | 模型不得承担 |
|---|---|---|---|
| 输入结构化、步骤明确 | 程序 | 通常不需要 | 不得改写规则或金额 |
| 用户表达模糊 | 模型辅助理解 | 提取意图、候选对象、疑问 | 不得直接确认对象归属 |
| 关键事实缺失 | 数据源或人工 | 可说明缺什么 | 不得把未知猜成已知 |
| 规则明确但分支多 | 规则或程序路由 | 可解释规则结果 | 不得越过规则出口 |
| 模板足够 | 模板 | 通常不需要 | 不应为了“更自然”增加风险和成本 |
| 模板无法回答具体疑问 | 第二次模型调用 | 基于已核实材料组织答复 | 不得添加材料中没有的事实 |
| 流程固定 | 工作流 | 可在局部理解或解释 | 不得自行重排关键步骤 |
| 每次计划不同 | 模型提出候选计划，程序推进 | 安排候选步骤和依赖 | 不得跳过强制条件 |
| 高风险动作 | 程序与人工审批 | 可整理事实和影响 | 不得给自己授权 |
| 开放性调查 | 模型、工具与循环 | 提出假设、选择下一项调查 | 不得把未验证假设当结论 |

### 责任拆分模板

```yaml
责任项:
  - work_id: W-001
    work_name: 工作名称
    responsible_party: 程序 | 模型 | 人工 | 外部系统
    input_sources: [来源]
    output_type: 事实 | 建议 | 计划 | 决定 | 动作 | 解释
    authority_level: 读取 | 建议 | 批准 | 执行
    verification: 验证方式
    prohibited_behavior: 禁止行为
```

### 完成门

- 每个关键事实有来源；
- 每个决定有责任主体；
- 每个动作有授权主体；
- 模型输出类型被明确标记为事实、候选、建议、计划或草稿；
- 不存在“模型既提出动作、又自行批准、又自行验证”的闭环。

## S5. 选择最小拓扑结构

### 目标

根据任务组织方式选择链式、路由、并行、编排、循环或层级。允许组合，但必须有主结构和明确理由。

### 拓扑选择表

| 拓扑 | 选择条件 | 必须补充的控制 | 不应选择的情况 |
|---|---|---|---|
| 链式 | 步骤有固定先后，后一步需要前一步结果 | 步骤契约、版本传递、失败出口 | 步骤本可并行却无故串行 |
| 路由 | 不同条件进入不同出口 | 路由规则、默认出口、未知分支 | 缺事实却强行选择某一分支 |
| 并行 | 子任务互不依赖，可独立完成 | 子任务边界、聚合规则、超时策略 | 实际存在隐藏依赖或共享副作用 |
| 编排 | 每次任务计划可能不同，需保存依赖与进度 | 计划版本、依赖检查、变更记录、恢复点 | 固定流程已足够 |
| 循环 | 需根据反馈继续查询、验证或修正 | 停止条件、最大次数、预算、收敛判据 | 明确规则可一次决定下一步 |
| 层级 | 多角色分工且需要逐层验收 | 委派契约、责任边界、交接工件、组合闸 | 只是调用多个数据接口 |

### 选择顺序

1. 能用单步完成，不用多步。
2. 能用固定链式，不用动态编排。
3. 能用明确路由，不让模型自由决定。
4. 能用程序并行，不增加不必要角色。
5. 只有反馈真正改变下一步时，才使用循环。
6. 只有存在独立责任和验收时，才使用层级。

### 多拓扑组合规则

组合时按以下格式记录：

```yaml
拓扑组合:
  primary_topology: 主拓扑
  secondary_topologies:
    - topology: 辅助拓扑
      scope: 仅作用于哪些步骤
      reason: 为什么需要
  forbidden_combinations:
    - 不能出现的组合行为
```

示例：

```text
主结构：链式
局部路由：根据事实完整性进入自动处理、人工核实或拒绝
局部并行：两个互不依赖的查询同时执行
禁止：并行查询未完成前进入依赖其结果的付款步骤
```

## S6. 选择工程模式与治理控制

### 目标

针对已确认的困难选择少量工程模式，不按模式名称堆叠系统。

### 候选模式映射

| 具体困难 | 可考虑模式 | 选择前必须回答 |
|---|---|---|
| 模糊输入需要分阶段处理 | 提示链 | 后一次调用是否获得了前一次没有的新材料？ |
| 条件决定自动、人工或拒绝 | 审批门或治理路由 | 条件是否来自权威事实和规则？ |
| 工具调用存在风险 | 护栏三明治 | 调用前检查什么，调用后验证什么？ |
| 任务计划因请求而异 | 规划执行与进度追踪 | 固定流程真的不能覆盖吗？ |
| 多项调查可独立展开 | 扇出聚合 | 子任务是否独立，聚合时怎样处理冲突？ |
| 多角色各负局部责任 | 层级委派 | 每个角色交付什么工件，谁验收？ |
| 结果需跨角色、跨系统继续 | 交接链 | 状态、责任、证据和版本是否一起交付？ |
| 结论需要独立异议约束 | 对抗评审 | 评审是否绑定具体版本和证据？ |
| 需根据检测逐步排除原因 | 迭代假设检验 | 何时停止，最多试几次，预算多少？ |
| 高风险能力逐步开放 | 渐进承诺 | 能力升级依据是什么，何时降级？ |
| 即使批准仍需限制损失 | 爆炸半径控制 | 单次、周期、对象、地域和时间上限是什么？ |
| 运行过程需要可追溯 | 工作流可观测性探针 | 哪些事实、判断和副作用必须被关联？ |

### 治理最低要求

所有会产生外部副作用的流程至少检查：

1. **对象一致性**：当前操作对象是否与用户、任务和审批对象一致。
2. **事实新鲜度**：关键事实是否仍在有效期内。
3. **权限有效性**：执行身份是否有当前动作权限。
4. **审批绑定**：批准是否只对当前对象、版本、金额、动作和时限有效。
5. **额度限制**：单次、累计、并发、地域和资源范围是否受限。
6. **幂等性**：重试是否会重复产生副作用。
7. **前置检查**：动作前必须满足的条件是否完整。
8. **后置验证**：实际业务状态是否与预期一致。
9. **恢复路径**：失败后从哪里继续，能否撤销或补偿。
10. **用户表述**：不得把建议、受理、批准、提交误报为最终完成。

## S7. 形成可执行工作流

### 目标

把选型结果转为程序、人和模型都能遵守的步骤契约。

### 步骤模板

```yaml
工作流步骤:
  step_id: STEP-001
  step_name: 步骤名称
  purpose: 本步目的
  cognition_refs: [认知引用]
  topology_ref: 拓扑引用
  pattern_refs: [工程模式引用]
  executor: 程序 | 模型 | 人工 | 外部系统
  decision_owner: 决定由谁作出
  inputs:
    - name: 输入名称
      source: 权威来源
      required: true
      accepted_states: [已验证, 已观测]
  preconditions:
    - 前置条件
  operation:
    type: 查询 | 推理 | 路由 | 计划 | 审批 | 执行 | 验证 | 回复
    tool_ref: 工具标识或无
    side_effect: 无 | 可逆 | 不可逆
  outputs:
    - name: 输出名称
      type: 事实 | 候选 | 建议 | 计划 | 决定 | 动作结果 | 回复
  postconditions:
    - 后置条件
  failure_routes:
    - condition: 失败条件
      route_to: 重试 | 降级 | 人工 | 拒绝 | 暂停 | 回滚
  observability_events:
    - 事件类型
  recovery_point: 可恢复位置
```

### 计划类工作流附加字段

```yaml
计划控制:
  plan_id: 计划标识
  plan_version: 版本
  dependency_graph: 依赖关系
  completed_steps: 已完成步骤
  pending_steps: 待执行步骤
  blocked_steps: 被阻塞步骤
  change_reason: 变更原因
  immutable_history: 历史版本不可覆盖
```

### 强制规则

- 已完成步骤不能因重写计划而变回未完成。
- 模型漏写强制步骤时，程序仍必须执行强制检查。
- 计划顺序不等于授权，动作仍需通过权限和前置条件。
- 任何新计划都要说明对已完成副作用的影响。

## S8. 用同一任务集比较验证

### 目标

证明新增结构解决了真实困难，而不是只增加复杂度。

### 任务集构成

至少包含：

- 正常样本；
- 缺少关键事实样本；
- 冲突事实样本；
- 权限不足样本；
- 边界金额或边界条件样本；
- 工具失败或超时样本；
- 重试样本；
- 用户表达含糊样本；
- 不应使用模型的简单样本；
- 需要转人工或拒绝的样本。

### 比较对象

```text
基线方案
候选方案 A
候选方案 B（如确有必要）
```

通常不建议同时比较过多候选。候选越多，评估成本和解释复杂度越高。

### 必看指标

| 指标 | 含义 |
|---|---|
| 正确完成率 | 正确执行、正确受理、正确拒绝、正确等待的比例 |
| 高风险误执行数 | 条件不足却产生副作用的次数 |
| 事实误写率 | 把未知、声明或推断写成已验证事实的比例 |
| 新增错误类型数 | 候选方案带来的基线中没有的错误 |
| 人工核实准确率 | 转人工是否发生在真正需要人工的样本上 |
| 模型必要调用率 | 模型调用是否对应明确的判断需求 |
| 冗余调用数 | 没有获得新材料、没有改变有效结论的调用 |
| 前置检查覆盖率 | 风险动作前要求的检查完成比例 |
| 后置验证覆盖率 | 风险动作后实际结果核验比例 |
| 平均与高分位时延 | 常态和尾部耗时 |
| 单任务成本 | 模型、工具、人工和外部服务成本 |
| 恢复成功率 | 中断、超时、重试后正确继续的比例 |

### 通过条件

候选方案只有在以下条件同时满足时才能进入 `active`：

1. 解决了已确认的具体困难；
2. 没有引入不可接受的新错误；
3. 高风险误执行为零或低于明确阈值；
4. 时延和成本在预算内；
5. 关键路径可追溯；
6. 未验证项已明确，不被包装成已验证结论。

## S10. 运行变化与重新选型

出现以下任一变化，应进入 `reselect_required`：

1. 输入从规范表单变为自由对话，或反向变化；
2. 系统从只读建议变为可执行外部动作；
3. 新增金钱、权限、发布、法律或客户承诺风险；
4. 原本固定的流程开始频繁出现临时步骤；
5. 新增跨部门、跨角色或跨系统责任交接；
6. 数据源、规则或工具发生版本变化；
7. 模型调用从一次增加到多次，且中间材料不同；
8. 计划可以在运行中修改；
9. 原有错误类型显著变化；
10. 时延、成本或人工负担超过阈值。

重新选型不是全部推倒重来。应保留已经验证且仍有效的部分，只重新评估发生变化的职责和结构。

# 12. 独立运行方式

不接入探针时，按以下最小步骤执行：

1. 手工生成 `selection_run_id`。
2. 填写任务契约和事实状态。
3. 运行最小基线并记录具体缺口。
4. 使用困难分类表定位问题。
5. 完成模型、程序、人工责任拆分。
6. 选择一个主拓扑，必要时添加局部辅助拓扑。
7. 选择少量工程模式和治理控制。
8. 用步骤模板形成工作流。
9. 用同一任务集比较基线与候选。
10. 发布模式选型卡，并列出未验证项。

独立运行时，以下记录不可省略：

- 关键事实及来源；
- 决策及依据；
- 工具调用前置条件；
- 工具调用结果；
- 实际业务状态；
- 人工转交原因；
- 计划变更原因；
- 最终对用户的表述。

# 13. 与工作流可观测性探针交互运行

## 13.1 交互目标

探针用于补全数据和暴露缺口，不改变本流程的决策责任。

执行流程向探针发送：

- 当前阶段；
- 任务契约；
- 事实及来源；
- 候选判断和路由；
- 模型调用；
- 工具调用；
- 审批；
- 计划版本；
- 副作用与业务结果。

探针返回：

- 数据缺失提示；
- 证据关联结果；
- 前后状态差异；
- 异常和违规信号；
- 指标快照；
- 追加式补全补丁；
- 本轮运行摘要。

## 13.2 事件接口

执行流程至少支持以下事件：

```text
selection.run.started
selection.contract.recorded
selection.baseline.completed
selection.difficulty.diagnosed
selection.boundary.decided
selection.topology.selected
selection.patterns.selected
selection.workflow.published
selection.validation.completed
selection.decision.published
selection.reselection.triggered

workflow.step.started
workflow.fact.observed
workflow.decision.proposed
workflow.decision.approved
workflow.guard.checked
workflow.tool.called
workflow.tool.returned
workflow.side_effect.verified
workflow.handoff.created
workflow.plan.changed
workflow.response.generated
workflow.run.completed
```

## 13.3 补全补丁接收规则

探针返回的补丁只能按以下方式处理：

| 补丁类型 | 处理方式 |
|---|---|
| 直接观测事实 | 追加到证据记录，可自动接收，但不得覆盖权威事实 |
| 关联结果 | 追加关联标识，可自动接收 |
| 推断字段 | 标记为“推断”，需要规则或人工确认后才能进入关键判断 |
| 缺失提示 | 阻塞或告警，是否阻塞由任务风险策略决定 |
| 异常提示 | 进入复核、暂停、降级或人工路由 |
| 指标快照 | 用于评估，不直接改变业务状态 |

### 强制约束

- 探针不能静默修改任务目标、业务规则、权限或审批结果。
- 探针不能把“未观测到”解释为“没有发生”。
- 探针推断不能替代权威事实。
- 对高风险路径的异常补丁，必须保留原记录并显式处理。

# 14. 通用场景适配

## 14.1 制度问答与知识检索

### 最小结构

```text
问题理解 → 检索现行制度 → 返回条款和出处
```

### 增加模型的条件

- 用户问法复杂，需要整合多处条款；
- 需要基于已找到的材料解释差异；
- 固定摘录不能回答具体疑问。

### 不需要的结构

若不替用户办理业务，不应照搬付款、审批和执行后验证的完整结构。

## 14.2 金钱、订单、权限或发布操作

### 最小结构

```text
对象核对 → 事实查询 → 规则路由 → 审批或权限检查 → 执行动作 → 查询实际结果 → 准确告知状态
```

### 强制控制

- 模型不得猜金额、权限和状态；
- 动作前后都要检查；
- 批准只对具体对象和具体动作有效；
- “已创建指令”不等于“资金已到账”。

## 14.3 设备故障调查

### 选择逻辑

- 有成熟诊断树：程序沿固定分支查询；
- 多份记录冲突：先做数据核对；
- 需要提出原因并用检测排除：迭代假设检验；
- 机械、电气、控制可独立调查：并行或扇出聚合；
- 三方只是读取接口：不必建立三个 Agent。

## 14.4 研究与资料分析

### 选择逻辑

- 固定资料链：链式；
- 多主题独立检索：并行；
- 证据不足时继续查找：循环；
- 需要独立事实核查：评审，但必须绑定具体版本和证据；
- 结论发布前：记录资料版本、推断和未验证项。

## 14.5 代码修复

### 选择逻辑

- 错误可稳定复现且修复路径明确：固定流程；
- 需边测试边定位：循环；
- 多模块可独立分析：并行；
- 修改有生产风险：审批门、范围限制和回滚；
- 测试通过不等于线上结果正确，部署后仍需验证。

## 14.6 跨部门业务流程

### 选择逻辑

- 仅从多个系统查询资料：程序调用多个工具；
- 各部门需独立调查并承担结论责任：层级或交接链；
- 需要等待多个部门完成后再继续：编排依赖；
- 任何交接都要带状态、版本、责任和证据。

# 15. 退款场景压缩示例

## 15.1 任务契约

```yaml
请求: 处理一笔 347 元退款
正确完成:
  - 条件满足时创建付款指令
  - 发票状态未知时创建人工处理单
  - 权限不足时拒绝操作
禁止动作:
  - 发票未知时创建付款指令
  - 把“已批准”表述成“已到账”
```

## 15.2 基线与困难

- 规范表单已包含申请号和原因：程序即可办理。
- 自由对话“上周那单想退掉”：存在 D1 输入模糊，需要模型提出候选订单。
- 发票没有查到：存在 D2 事实缺失，不应增加模型评审，应转人工核实。
- 客户追问“照片已传为什么还要等”：存在 D5，需要在程序核实凭证和发票后，再由模型组织具体答复。

## 15.3 结构选择

```text
主结构：链式
局部路由：自动处理 / 人工核实 / 拒绝
局部提示链：理解诉求 → 查询事实 → 组织答复
治理模式：审批门 + 护栏三明治
暂不选择：规划执行、层级委派、多模型评审
```

## 15.4 关键检查

- 候选订单必须属于当前客户；
- 金额从申请记录读取；
- 发票状态从业务数据源查询；
- 发票未知只能进入人工路由；
- 动作后查询人工单或付款指令是否实际创建；
- 回复使用实际状态，而非模型预期状态。

# 16. 常见失败模式

| 失败模式 | 表现 | 修复方向 |
|---|---|---|
| 模式先行 | 先决定使用多 Agent，再寻找理由 | 回到基线和具体困难 |
| 把未知当否定 | 没查到记录就认为不存在 | 增加未知状态和人工核实出口 |
| 多一次模型等于多一份事实 | 重复分析同一材料 | 查询新证据或停止调用 |
| 模型包办事实与授权 | 模型既判断又执行 | 拆分事实、建议、批准和动作 |
| 只检查建议，不检查副作用 | 建议正确但工具执行错误 | 增加前置和后置检查 |
| 计划即授权 | 模型计划写了付款就直接付款 | 强制规则与权限检查独立存在 |
| 多系统等于多 Agent | 只是读取三个接口也建立三角色 | 优先程序工具调用 |
| 只看办成率 | 转人工被算失败，误执行被忽略 | 使用安全完成率和高风险误执行数 |
| 状态误报 | 已提交、已批准被表述为已完成 | 明确业务状态语义 |
| 选型无证据 | 只记录模式名称 | 记录困难、比较、证据和未验证项 |
| 动态计划覆盖历史 | 修改计划后丢失已完成状态 | 计划版本化和追加式历史 |
| 探针越权 | 观测系统静默改写业务状态 | 限制为采集、提示和补全 |

# 17. 评估用例模板

```yaml
评估用例:
  case_id: CASE-001
  case_name: 用例名称
  input: 输入
  authoritative_facts: 权威事实
  unknown_facts: 未知事实
  expected_result_type: 正确执行 | 正确受理 | 正确拒绝 | 正确等待 | 正确降级
  expected_route: 预期路由
  prohibited_side_effects: [禁止副作用]
  required_checks: [必须检查]
  expected_user_message: 必须表达的状态
  cost_limit: 成本上限
  latency_limit: 时延上限
  recovery_expectation: 故障后的恢复要求
```

### 最低验收用例

1. 规范输入且条件满足，程序直接完成。
2. 模糊输入，模型提出候选对象，程序核对后继续。
3. 关键事实未知，系统转人工且不产生风险副作用。
4. 关键事实冲突，系统暂停并暴露冲突。
5. 权限不足，系统拒绝。
6. 工具调用超时，重试不产生重复副作用。
7. 工具返回成功但业务状态未变化，后置验证发现异常。
8. 模型生成了材料外事实，输出校验将其拦截。
9. 计划遗漏强制步骤，程序仍阻止后续动作。
10. 模板足够的简单问题，不发生不必要的模型调用。

# 18. 执行完成检查表

## 18.1 任务与事实

- [ ] 已定义正确完成、安全完成和禁止动作。
- [ ] 已区分建议、受理、批准、提交和最终完成。
- [ ] 所有关键事实都有来源和状态。
- [ ] 未知、冲突和过期事实不会支持高风险动作。

## 18.2 最小方案与模型边界

- [ ] 已实际运行现有办法或最小方案。
- [ ] 已记录具体缺口，而非笼统描述“智能不足”。
- [ ] 每次模型调用都有必要性说明。
- [ ] 缺事实的问题没有被错误地交给模型重复推理。
- [ ] 模型输出被标记为候选、建议、计划或草稿。

## 18.3 结构与治理

- [ ] 已选择一个主拓扑，并说明局部辅助拓扑。
- [ ] 没有因为多系统就无故建立多角色。
- [ ] 循环有停止条件和预算。
- [ ] 计划有依赖、版本和恢复点。
- [ ] 审批绑定具体对象、版本、动作和有效期。
- [ ] 外部副作用前后都有检查。

## 18.4 验证与归档

- [ ] 基线和候选使用同一任务集比较。
- [ ] 已统计新增错误，而不仅是成功率。
- [ ] 时延、成本和人工负担在约束内。
- [ ] 未验证项已显式记录。
- [ ] 选型卡与实际运行版本一致。
- [ ] 已定义触发重新选型的变化条件。

## 18.5 可观测性

- [ ] 任务、事实、判断、动作和结果能通过运行标识关联。
- [ ] 关键工具调用有前置检查和后置结果。
- [ ] 计划变更保留历史版本。
- [ ] 人工转交包含原因、待核实项和责任人。
- [ ] 即使未接入独立探针，也保留最低运行记录。

# 19. 与框架的挂载关系

本执行流程作为一个可执行 Skill，同时引用多个认知和拓扑坐标：

```text
感知：读取任务、事实、规则和运行环境
记忆：保存任务契约、计划版本、决策历史和恢复点
推理：诊断困难、比较候选、判断模型必要性
行动：执行固定流程、工具调用和状态推进
反思：用同一任务集验证、识别新增错误并重新选型
协作：在确有独立责任时进行委派、评审和交接
治理：权限、审批、额度、前后检查和安全退出
```

```text
链式：固定先后步骤
路由：条件分支和安全出口
并行：独立子任务
编排：动态计划、依赖和进度
循环：根据反馈继续调查或修正
层级：多角色责任拆分与验收
```

本文件是执行化产物，不替代认知注册表、拓扑注册表或工程模式注册表。后续应把稳定模式登记到注册表，再由矩阵视图呈现其挂载关系。
