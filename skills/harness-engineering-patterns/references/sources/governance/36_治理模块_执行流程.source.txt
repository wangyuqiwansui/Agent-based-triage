# 第36讲工程化拆解：治理模块执行流程

> 目标：把“准备做什么、依据什么规则、谁有权同意、最多影响多少、实际发生了什么”连成可检查的执行链。允许执行不是业务成功，记录齐全不是授权有效，探针补证也不是重新授权。

## 0. 使用边界与来源

本文结合用户提供的黄佳《36｜治理模块导论：把边界写清楚，才敢把事交出去》，以及 `hanerss_skill_framework_v0_1.md` 的三大基座、注册表、模式卡和技能模板编写。

第36讲提供治理定义、薪酬限额实验、提案—策略—回执分离、四眼原则和生产系统检查方向。本文将其扩展为输入输出契约、状态机、预算占用、执行检查、恢复规则和探针接口；这些具体协议与测试是本次工程设计，不冒充讲义仓库的既有实现。

本文件可独立作为运行时执行规范；不需要先运行探针。配套文件《36_治理模块_工作流可观测性探针.md》可选接入，必要的共享协议已在本文件内置。本文不是已部署的软件，未接入真实身份、审批、业务系统或生产账本；缺少适配器时只能执行只读演练，不得宣称已审批、已付款或已回滚。

新增模式、技能和节点标识均为本次建议的局部标识，注册前应查重；已有等价资产时复用其标识，发布后保持稳定。资产状态使用 v0.1 的 `draft → review → active → deprecated → archived`，与业务运行状态分开保存。本文处于草稿状态，不因为文档可读就自动获得生产权限。

## 1. 模式名称

**运行时行动权治理**，由审批门、影响范围控制、权限调整和最小审计共同组成。

它是治理模块的组合执行入口，不把全部约束塞进一个“是否安全”的模型判断，也不新增一个冒充官方目录编号的模式。可观测性作为横切能力接入，而非付款许可的替代品。

## 2. 所属基座

### 2.1 认知

治理负责分配、限制和回收行动权；推理负责形成结构化提案及风险说明；行动负责消费有效凭证并执行；协作负责移交审批与异常责任；反思负责用核验结果提出改进建议。模型给出的风险分析只是输入，不能自行授予权限。

### 2.2 拓扑

| 拓扑 | 挂载方式 | 不得丢失的约束 |
|---|---|---|
| 链式 | 每个产生外部影响的节点前设置执行检查 | 上一步批准不自动覆盖下一步动作 |
| 路由 | 在自动执行、人工审批、拒绝、只读演练之间选择 | 路由不得变相寻找较松的策略 |
| 并行 | 子任务独立提案，共享父级预算和资源限额 | 不能每个分支都领取完整父预算 |
| 编排 | 主流程连接策略、审批、预算、执行、对账 | 编排器不能绕过最终执行入口 |
| 循环 | 每轮使用当前提案、有效凭证和累计消耗 | 重试、循环和更换任务标识不能重置额度 |
| 层级 | 子执行者的权限取父级授权与自身授权的交集 | 父级“已同意”不能替代子动作的具体批准 |

## 3. 适用工程节点

| 节点位置 | 输入 | 必须产出的可核验结果 |
|---|---|---|
| 外部动作提案前 | 用户请求、目标、任务边界 | 有责任主体的任务契约 |
| 策略裁决时 | 冻结提案、当前策略、权威上下文 | 允许、拒绝或转人工回执 |
| 人工审批时 | 具体版本、影响范围、风险和变更说明 | 身份与权限经过核验的批准或拒绝 |
| 资源占用时 | 已获允许的动作、累计预算 | 原子额度预留或明确的拒绝 |
| 实际提交前 | 回执、凭证、预算、资源版本 | 最终检查记录与持久化派发意图 |
| 工具返回后 | 接口响应、外部查询结果 | 已核实成功、已核实失败或结果未知 |
| 异常恢复时 | 原请求、幂等身份、检查点 | 对账、补偿、转人工或受控停止 |
| 权限调整时 | 已核验历史、事故记录、策略 | 新授权凭证或撤销记录 |

适用场景包括支付与退款、优惠券、采购、生产发布、数据库变更、文件操作、对外消息和数据导出。纯分析任务可只使用来源和审计子集；不能因为不付款就忽略数据泄露、错误发布或批量删除的影响。

不适用于以提示词代替最终检查、无法识别操作者、无权访问目标系统却要求真实操作、要求事后补造批准、或者要求模型自己提升权限的流程。

## 4. 解决的问题

核心问题不是“模型有没有调用某个接口的资格”，而是“这个主体此刻能否对这批对象执行这版动作”。接口访问权、业务准入、人工批准、预算和结果证明必须分开。

| 问题 | 本流程给出的约束 |
|---|---|
| 放行记录没有规则版本 | 所有裁决均绑定策略标识、版本和完整内容摘要 |
| 已批内容在执行前发生变化 | 从实际提交载荷重算摘要，并重新核验当前规则 |
| 每笔都合规，累计却越界 | 按业务主体、父任务、时间窗等共同占用额度 |
| 同一主体自己提出放宽、自己批准 | 核验真实身份、授权范围和职责分离 |
| 请求超时后重复操作 | 保留结果未知状态，先对账，不盲目重发 |
| 多次成功被用于无限扩权 | 仅按指定场景、时间窗和可核验结果调整权限 |
| 有日志却无法解释责任 | 连接请求、提案、策略、审批、执行与业务结果 |
| 探针发现问题却越权改业务 | 探针只能补观测和提建议，执行侧重新裁决 |

## 5. 触发条件

每一次可能产生外部影响的动作都触发本流程。金额、对象、参数、范围、任务契约、工件、适用策略或权限版本变化，均触发重新核验；重试不豁免检查。

规则放宽、临时授权、批量操作、跨租户访问、不可逆动作、异常累计消耗、审批过期、外部结果未知和紧急停止信号必须进入相应支路。

允许自动完成的范围必须预先配置。没有配置不是“默认无限制”；必需约束缺失时，阻断相关写入，保留只读分析能力。是否需要人工，按动作的风险和当前策略判定，不按“模型很有信心”判定。

## 6. 输入

### 6.1 最小输入契约

| 输入对象 | 最低内容 | 缺失处理 |
|---|---|---|
| 任务契约 | 目标、禁止事项、责任主体、完成标准、有效期 | 不产生真实动作提案 |
| 身份与委托链 | 用户、执行者、审批者的可信身份；授权范围与有效期 | 不使用自报姓名替代 |
| 工件快照 | 标识、版本、完整摘要、来源、核验结论 | 不操作可变别名指向的未知内容 |
| 动作提案 | 具体参数、对象、作用域、预期影响、业务幂等身份 | 退回补全，不自动猜测金额或对象 |
| 策略集合 | 当前生效版本、规则内容、来源、变更审批 | 不以旧缓存推定当前有效 |
| 权限凭证 | 可执行能力、资源范围、限额、有效期、撤销版本 | 无有效凭证则不执行 |
| 预算与占用账本 | 总额、已确认消耗、预留、结果未知占用 | 不按日志估算余额后付款 |
| 工具能力描述 | 可执行动作、参数约束、幂等与查询能力 | 降级为演练或转人工 |
| 运行环境 | 租户、时间源、停止开关、审计持久化能力 | 必需控制不可用时阻断高风险操作 |

### 6.2 提案、策略和回执分开保存

**动作提案**至少包含：提案标识与版本、任务契约摘要、工件摘要、请求主体、动作类型、规范化参数、资源范围、业务幂等身份、影响量、风险分类及其来源、可逆性、资源前置版本、有效期。

**策略引用**至少包含：策略标识、版本、完整内容摘要、适用租户和作用域、生效与失效时间、优先级、可信内容位置。执行时使用适用于该动作的策略集合，不以一条宽松规则覆盖其他限制。

**治理回执**至少包含：回执标识、控制类型、提案摘要、策略集合摘要、裁决上下文摘要、裁决主体、裁决结果、原因、签发时间、有效期和撤销状态。允许、拒绝、需人工审批均保留回执。

裁决上下文应区分内容绑定与动态条件。提案、适用策略、关键授权和资源前置版本变化需要重新裁决；预算余额等高频数据保留裁决时快照，但最终检查核验当前约束和本次有效预留，不以整库余额摘要的任何变化机械地否定所有回执。

自动审批阈值与硬预算上限分别建模：前者决定是否转人工，后者决定是否还有可分配资源。获得人工批准不能突破硬预算，提高自动审批阈值也不增加账户余额。

本设计在讲义三个对象的基础上补充有效期、上下文绑定、撤销和多策略组合，属于工程扩展。审批记录、额度预留、权限凭证和业务结果仍为独立对象，不能把它们压成一个布尔值。

### 6.3 摘要与实际载荷的绑定

摘要覆盖执行语义：金额与币种、收款人或目标对象、资源范围、参数、工件内容、任务契约、幂等身份和前置版本。金额使用最小货币单位的整数或明确精度的十进制值，禁止二进制浮点在不同组件之间产生不一致解释。

规范化规则应固定字符编码、字段顺序、空值含义、时间格式及默认值展开方式。只有业务上无序的集合才能排序；操作步骤等有序列表不能为了计算摘要而重排。审批展示和工具实际提交必须读取同一个不可变快照。

完整摘要用于核验；短摘要仅用于展示。摘要不是签名，也不能证明审批者有权批准。回执必须来自受保护存储或经过身份认证的签发服务。

### 6.4 场景配置与默认边界

```yaml
运行模式: 只读演练
允许真实外部写入: false
身份来源: null
策略来源: null
业务适配器: null
审计存储: null
未知策略处理: 阻断相关写入
结果未知处理: 保留占用并查询原请求
权限晋升方式: 独立审批后签发新凭证
探针连接: 可选
探针允许回填范围: [observation_enrichment]
```

空配置表示尚未接入，不表示控制已通过。生产模式必须由有权主体提供各适配器、预算维度、审批路由、重试上限、证据时效和停止策略；模型不得自行填充并视为已获批准。

## 7. 输出

每次运行输出结构化结果包，包含任务状态、分项动作状态、最后检查点、未解决问题、当前责任人、下一步允许动作及证据引用。

| 输出对象 | 内容 | 不能被解释为 |
|---|---|---|
| 裁决包 | 提案、适用策略、原因和回执 | 已经完成业务操作 |
| 执行包 | 权限凭证引用、预留记录、派发意图、调用结果 | 外部系统最终确认 |
| 核验包 | 原请求对账、业务对象变化、分项完成情况 | 可以重新发起同一付款 |
| 审计包 | 原始事件、来源、变更轨迹、责任和异常 | 每条规则都一定合理 |
| 权限调整包 | 新旧凭证、依据、审批、生效和撤销范围 | 通用能力或所有场景的永久授权 |
| 观测补全包 | 已采纳的补充证据与逐项回执 | 原始事实被改写 |

未完成必须说明是“待审批、待证据、预算不足、结果未知、待对账、部分完成、已停止”中的哪一种，不用一句“失败”遮住已产生的外部影响。

## 8. 工作流结构

### 8.1 总体流程与权责

```text
建立任务边界与可信身份
→ 冻结动作提案
→ 加载当前策略及其来历
→ 核验权限、风险、单次与累计边界
→ 策略裁决／必要时人工审批
→ 原子预留额度
→ 最终执行检查与持久化派发意图
→ 受限工具提交
→ 核验业务结果
→ 结算占用、保留审计
→ 继续、移交、停止或申请权限调整
```

模型只提出动作；策略服务负责裁决；审批人对指定版本作出决定；执行入口控制工具凭证；业务系统提供结果；探针关联证据并提出建议。它们可以部署在同一进程，但职责、写权限和记录边界仍须分离。

### 8.2 运行状态机

```text
已受理 → 待补输入／已冻结提案 → 待裁决
待裁决 → 已拒绝／待审批／待额度
待审批 → 已拒绝／已过期／重新裁决
待额度 → 额度不足／已预留
已预留 → 待最终检查 → 已阻断／已建立派发意图
已建立派发意图 → 已提交／派发状态待查
已提交 → 已核实成功／已核实失败／结果未知／部分完成
结果未知 → 对账中 → 已核实成功／已核实失败／仍未知
部分完成 → 分项核验与处置 → 已关闭／待人工
已核实失败 → 已关闭／经重新批准进入补偿
任一可停止阶段 → 已停止待处置
```

“已允许”仅是裁决结果，不是业务终态。“已停止”表示禁止新的派发，不保证已经发往外部的动作被撤回。补偿是独立业务动作；它也可能失败，且不抹去原操作历史。

### 8.3 执01：受理与环境自检

验证租户、用户、执行者和委托关系，加载可信时间源、停止开关与审计存储状态。记录任务及运行实例，区分演练与真实执行。

输出受理事件和输入缺口。身份、策略或最终执行入口不可验证时，不尝试业务写入；可输出只读诊断和所需接入项。

### 8.4 执02：建立任务契约和组合边界

明确最终目标、允许动作、禁止动作、目标对象、预算、完成条件及失败后的责任人。批次任务必须给出总范围和分项标识；多个任务共享同一业务主体额度时，绑定同一额度账户。

把整串动作作为计划检查：单次读取无害但累计导出超量、每次补偿合规但累计超限、多个子任务各自获批但总量超预算，都不能只按单步判断。暂时无法估算的影响维度标为未知，由策略决定暂停或采用预先批准的保守上界。

### 8.5 执03：冻结具体提案

从可信工件生成实际动作参数，核验对象和资源前置版本，形成不可变提案。给逻辑业务操作分配稳定幂等身份；同一业务意图的技术重试保留该身份。

变更金额、对象或执行语义必须形成新提案版本并重新裁决；不得为了绕过重复检查而更换幂等键。业务上确需再次操作时，必须建立新的业务依据，并核查前一操作的实际状态。

### 8.6 执04：解析当前生效的策略集合

从可信策略库取得当前适用规则及不可变内容，核验生效范围、版本、批准来历和撤销情况。形成策略集合摘要和裁决上下文摘要。

额度规则、审批规则、权限等级、资源限制和紧急停止分别核验。按本设计的保守组合规则，任一适用的强制拒绝条件成立即不放行；需人工审批的条件未满足时不能被其他允许结果覆盖。若业务使用不同组合算法，必须显式版本化并测试。

### 8.7 执05：处理独立的策略变更支路

只有收到明确的策略变更任务且提出者有权申请时才进入；业务超限不能自动触发“把规则改到足够宽”。变更单保存前后版本差异、影响范围、理由、有效期、提出者、批准者及回退方案。

核验提出者与批准者是不同的真实主体，并检查批准者在该范围内有审批权；不能只比较显示名称。高风险场景还应按组织规则检查同一实际控制人及审批人之间的独立性。

批准后发布新版本并保留旧版本；按生效时间使新版本进入适用规则集合。原业务提案返回执04重新取规则、重新裁决，不能沿用原回执。临时放宽到期自动失效；紧急例外也需要独立授权与记录。

### 8.8 执06：核验行动权与影响范围

检查实际主体的权限凭证、动作范围、风险等级、可逆性、单次上限、对象数量、并发上限、时间窗和累计消耗。风险结论必须来自已配置规则和权威上下文；不能仅采信执行者把动作标成“低风险”。

预算按租户、真实业务主体、资源域、时间窗、父级计划等适用维度共同约束。具体额度账户键由策略服务确定，不由 Agent 通过重命名任务选择。子权限必须受父权限约束，子预算之和不能超过父预算。

本阶段先检查是否可行，真正防并发超用依赖执08的原子预留。预检查通过不能当成额度已经锁定。

### 8.9 执07：裁决与人工审批

生成允许、拒绝或需人工审批回执，三类结果都绑定提案与策略。人工审批界面必须展示该版的对象、金额或影响量、累计占用、不可逆风险、异常与版本差异，而不只显示一段模型摘要。

审批人仅批准自己有权处理的范围，批准记录绑定提案内容、适用策略上下文、有效期与审批身份。等待期间发生版本变化，应重新审查变更，不把旧点击转移给新申请。

人工同意后返回裁决服务生成当前有效的允许回执；人工拒绝、超时或撤销均留痕。不得用自动总结替代人工决定，也不得静默把“未回复”解释为同意。

### 8.10 执08：原子预留额度

用权威额度账本进行条件更新，核验适用预算账户后预留。所有分支、执行者和重试共享同一逻辑操作的占用，不重复预留，不各自读取旧余额后独立扣减。

对每个适用额度维度，保持：

```text
已确认消耗 + 待执行预留 + 结果未知占用 ≤ 当前准入上限
可分配额度 = 当前准入上限 − 上述三类占用
```

三类占用互斥迁移，不能把同一笔未知交易既计入预留又计入未知。金额、条数、次数、存储量等维度分别核算，不混加不同单位或币种。时间窗切换不能自动释放未决暴露：原窗口账目保留，并按另设的跨窗口在途约束继续限制新动作；不得用新建窗口洗掉旧请求的风险。

预留失败时等待、缩小提案后重审或转人工，不能悄悄减少其他任务的占用。额度降低后已有在途操作的暴露应单独处置；不能把旧时合法支出按新限额追溯判为当时违规，也不能继续按旧额度派发新动作。

### 8.11 执09：最终执行检查

在唯一持有业务工具凭证的执行入口，重新核验实际载荷摘要、当前适用策略、允许回执、人工批准、凭证有效性、撤销版本、额度预留、资源前置状态、幂等记录和停止开关。

任意内容变化或必需证据缺失，都阻断本次派发，保存原因并进入重新裁决、补证或人工处置。仅页面、提示词或上游节点检查过，不满足该要求。

本地可事务化部分应一次性完成最终校验、占用关联和持久化派发意图。意图至少包含冻结载荷引用、幂等身份、执行围栏版本、回执引用及占用标识；审计意图写入失败时不得先向外部提交。

### 8.12 执10：受限派发与并发围栏

派发器以条件更新认领意图，核验当前执行围栏、停止状态、适用策略版本和凭证。策略生效、权限撤销和停止都必须更新相应围栏；待派发意图与当前版本不一致时退回重新检查。策略与派发服务必须约定版本生效和确认语义，无法确认当前版本时不派发高风险写操作。派发器不得在校验后重新读取可变对象并换一套参数提交。网络请求前保留可恢复的提交意图，返回后关联外部请求标识。

最终授权与撤销必须有明确的本地生效顺序：在派发许可生效前到达的撤销阻断新请求；已取得许可并进入外部提交的动作按在途处理。不能保证在外部系统已接收后瞬间撤销，也不能仅靠跨进程“先查一下再发送”消除全部竞态。

有服务端幂等能力时使用稳定业务幂等身份，并记录其作用域与保留期限。没有可靠幂等或结果查询能力时，不自动重试非幂等写操作，转人工确认。外部提交与本地数据库不能被假定为同一原子事务。

### 8.13 执11：观察并核实业务结果

分别记录接口接收、传输失败、处理中、终态结果和业务对象的实际变化。接口返回成功只能按适配器的明确语义解释；“请求已接收”不能标为“付款已完成”。

通过外部交易状态、订单状态、部署版本、数据库核验或其他权威读回确认结果。批次逐项核验，保留已成功、已失败和未知项；不因一个总返回码把整个批次重做。

### 8.14 执12：结果未知、恢复与补偿

超时、断线、进程崩溃、返回无法解释或本地记录与外部状态不一致时，将相关动作设为结果未知，并保留额度占用。先按原业务身份查询外部状态，无法查询时由有权人员处理。

确认已成功则补回结果证据并结算；确认未执行且外部不会继续执行时，才可释放占用或按当前策略重试。只观察到暂时“查无记录”，不必然满足“确定未执行”，应使用适配器的查询一致性与终态判定规则。

执行租约过期只回收执行者资格，不证明外部动作未发生。幂等保留期到期也不能自动换键重发。回滚仅适用于确有回滚能力且已授权的步骤；退款、撤单、恢复数据等补偿动作必须单独提案、核验和留痕。

### 8.15 执13：结算占用并形成审计包

对已核实成功的分项，将预留或未知占用迁移为已确认消耗；对确认无副作用且不会继续执行的失败项释放占用；仍未知部分继续保留。结算按业务操作标识幂等处理，禁止重复扣减或释放。

累计支出与可恢复的在途额度要按策略分别定义，不能因为退款就默认重置全年补偿次数或历史风险。审计包连接用户请求、提案、规则、审批、占用、提交、外部结果、核验、异常与当前责任人。

### 8.16 执14：评估权限升级、降级与撤销

使用独立核验的结果、事故记录、场景覆盖、观察窗口和证据完整性评估权限；没有事故不等于没有风险，低风险成功不能直接兑换高风险权限。

晋升默认要求独立审批，由授权服务签发范围、限额、期限明确的新凭证。自动缩权或停止也应由事先批准的规则和授权控制服务执行；探针只提供证据或建议。撤销需覆盖尚未派发的队列、子任务和委托凭证，在途操作另行追踪。

### 8.17 执15：接收探针补全并重新核验

按附录乙校验补丁，只追加到观测补全层。证据缺失可以查询当时确已存在的合法记录；事实未发生必须建立新业务步骤，不能在补丁里写成已完成。

如果补回的证据被用于解除待执行状态，回到执04、执07或执09重新核验，不从“补丁已采纳”直接跳到工具调用。来源冲突、审批版本不匹配或已过期时继续保持阻断。

### 8.18 执16：关闭、继续或交接

明确任务是全部完成、部分完成、被拒绝、停止还是仍有未知结果；输出最后有效检查点、分项清单、未解决额度占用、下一步负责主体和允许动作。

交接包绑定具体工件、提案、策略和证据版本，并要求接收方确认。新的接收者获得任务责任，不自动获得原执行者全部权限；换执行者后仍需核验自身委托和凭证。

### 8.19 三种运行方式

| 方式 | 启动条件 | 运行与结束 |
|---|---|---|
| 执行侧独立运行 | 本地身份、策略、预算、执行和最小审计能力可用 | 自行完成执01—执16；输出结果包与原始事件，缺观测数据标未知 |
| 执行侧与探针交互 | 在独立能力上配置可信消息通道及补丁接收器 | 发布事件、接受观测补全、重新裁决；断开后仍保留原有硬约束 |
| 只读演练 | 提供任务、策略快照和样例数据，无真实写权限 | 计算预期分支与缺口，所有输出注明演练，不生成有效业务凭证 |

探针不在线不等于所有业务都必须暂停，也不等于可以跳过审计。必要证据不可用的高风险写操作阻断；已经具备全部必要证据的低风险操作可按原策略继续。

## 9. 工具依赖

| 能力 | 最小职责 | 权限边界 |
|---|---|---|
| 身份与授权服务 | 核验主体、委托、角色、权限范围 | 不信任模型填写的操作者名称 |
| 工件与策略存储 | 提供不可变内容、版本和来源 | 业务执行者不能擅自覆盖规则 |
| 裁决与审批服务 | 保存裁决、审批、有效期和撤销记录 | 提案者不能自行签发高权限批准 |
| 预算与幂等账本 | 原子预留、状态迁移、业务去重 | 以业务主体聚合，跨分支共享 |
| 执行入口与业务适配器 | 最终检查、提交、结果读回 | 凭证不交给无约束模型上下文 |
| 最小审计与停止服务 | 持久记录、撤销围栏、停止新派发 | 不依赖 Agent 自己决定是否配合 |
| 可选观测通道 | 发送事件、接收补丁与建议 | 不提供策略修改或业务写入权限 |

工具名、工具自带说明、网页内容和检索文件均不是授权来源。实际调用要校验目标、参数、资源范围及当前凭证；不允许从证据文本读取指令后扩大工具权限。

## 10. 记忆依赖

将定义与运行记录分层：定义层保存模式、技能和规则版本；事实层保存不可变提案、审批和外部结果；运行层保存状态、占用和检查点；观测层保存补充证据与指标；经验层保存经核验的复盘。

历史批准只用于解释当时操作，不能当作当前授权；历史成功只用于有限范围的权限评估，不能自动成为能力凭证。日志脱敏，敏感原件保存在受控存储，通过引用核验；保留期限和删除权限由组织策略配置。

摘要链、只追加记录、备份和访问审计可作为防篡改设计的一部分，但不能仅凭“有摘要”就宣称证据来源可信或绝对不可篡改。

## 11. 治理要求

### 11.1 四类控制分别变化

| 控制面 | 可以改变什么 | 不能顺带改变什么 |
|---|---|---|
| 审批门 | 某类动作需要谁批准、批准多久有效 | 不能增加总预算或更换收款对象 |
| 影响范围控制 | 单次、累计、资源域和并发上限 | 不能让无权主体获得执行资格 |
| 渐进权限 | 特定场景可自主执行的范围和期限 | 不能改写原始成功率或跨域继承信用 |
| 可观测性 | 证据关联、缺口、指标和运行诊断 | 不能创建批准、修改余额或放宽规则 |

按照本讲提供的目录说明，审批门、爆炸半径控制、渐进承诺分别对应 G1、G2、G3，可观测性对应横切工程面 X1。这里只保留讲义提供的映射，不将其称为已独立核验的当前目录。[讲义]

### 11.2 必须持续成立的不变量

有外部副作用的动作必须经过最终执行入口；放行回执必须绑定实际内容和适用规则；未知结果不能当作失败后直接重试；所有分支受相同上层预算约束；策略放宽必须具备有效变更审批；探针不能改写业务真值；紧急停止不能依赖模型自觉执行。

自动化范围扩大时上述不变量保持不变。不能以降低人工打断为由取消必需审批，也不能为提高通过率让缺证据的操作进入生产。

### 11.3 生产就绪检查

真实身份和职责分离可核验；规则历史可追溯；最终入口能拒绝旧回执与越权载荷；预算并发测试通过；外部超时可以查询或转人工；关键事件可以在派发前可靠落盘；停止和撤销覆盖待派发任务；已发送动作有在途清单；日志脱敏且可访问原证据；恢复演练不会重复业务效果。

教学数据、本地数据库和单进程测试不能自动证明以上能力已在生产满足。每个适配器都要给出自身的幂等、查询一致性、异常语义和权限测试结果。

## 12. 评估方式

评估分为静态契约检查、固定样例回放、并发与故障注入、适配器集成和生产前演练。下表为验收设计，并非本次已执行的业务测试。

| 编号 | 输入或故障 | 必须出现的结果 |
|---|---|---|
| 执验01 | 任一允许回执缺策略版本 | 不放行，记录策略证据缺口 |
| 执验02 | 任一拒绝回执缺原因或策略 | 标记裁决记录不完整，禁止误称可追责 |
| 执验03 | 批准后金额变化 | 旧回执失效，新提案重新裁决 |
| 执验04 | 批准后目标对象或工件变化 | 摘要不匹配，阻断派发 |
| 执验05 | 相同策略标识和版本对应不同内容 | 隔离冲突版本，不任选一份 |
| 执验06 | 放宽额度的提出者与批准者是同一主体 | 拒绝策略发布 |
| 执验07 | 批准者身份不同但无对应审批权 | 拒绝批准 |
| 执验08 | 临时规则过期 | 新动作不再按临时规则执行 |
| 执验09 | 两分支各申请80，剩余额度100 | 最多一笔成功预留，不出现160的新增占用 |
| 执验10 | 更换任务标识再次申请同一业务补偿 | 仍受主体累计额度与业务幂等约束 |
| 执验11 | 子执行者申请父权限之外动作 | 拒绝，不继承无限权限 |
| 执验12 | 超时但外部已成功 | 对账确认成功，不重复提交 |
| 执验13 | 查无记录但外部可能延迟写入 | 保持未知，不立即释放或换键重发 |
| 执验14 | 幂等保留期已过且结果仍不明 | 转人工，禁止盲目重试 |
| 执验15 | 批次一部分成功 | 分项结算，不能整批重做 |
| 执验16 | 进程在派发前后崩溃 | 恢复意图并查询原操作，不凭内存判断结果 |
| 执验17 | 关键意图无法持久化 | 阻断派发 |
| 执验18 | 探针离线但本地必要控制完备 | 可按原授权继续，观测缺口单独记录 |
| 执验19 | 探针补丁试图写审批结果或预算 | 拒绝补丁并告警 |
| 执验20 | 补丁过期或基线状态已变化 | 返回过期或冲突，不恢复执行资格 |
| 执验21 | 同补丁重复发送 | 返回原处理结果，不重复改变视图 |
| 执验22 | 撤销先于本地派发授权生效 | 新请求不发送，待派发队列受阻 |
| 执验23 | 停止时外部已有在途动作 | 不宣称撤回成功，输出待核验清单 |
| 执验24 | 用低风险成功记录申请高风险权限 | 无特定场景证据与独立批准则不晋升 |
| 执验25 | 无真实工具，只提供样例数据 | 仅输出演练预期，不生成真实成功回执 |
| 执验26 | 业务完成之后才产生批准 | 不能回填为事前获批，保留违规事实 |

关键指标至少覆盖放行策略绑定、最终检查证据、累计暴露、重复副作用、未知结果、审计链和撤销生效情况。没有配套探针时也必须保留计算这些指标所需的原始数据，不能用“监控未接入”解释缺少审批记录。

## 13. 失败模式

| 失败模式 | 典型误判 | 修正与恢复 |
|---|---|---|
| 提示词治理 | 模型说会遵守，所以执行入口不检查 | 把硬约束放到持有凭证的入口 |
| 只记录拒绝 | 成功结果无需保存策略 | 所有裁决使用同一证据要求 |
| 策略漂移 | 调大限额即解决审批问题 | 单独审查变更来历与权限，业务重新裁决 |
| 检查与执行脱节 | 审批看A，实际提交B | 冻结快照，按实际载荷核验 |
| 预算分裂 | 并发分支分别读取同一余额 | 权威账本原子预留及父级聚合 |
| 重试放大 | 超时就是未成功 | 结果未知、原请求查询、稳定幂等身份 |
| 事后补批准 | 记录完整就算当时合规 | 保留发生时间，不能补造事前授权 |
| 观测越权 | 探针发现缺字段便直接改业务状态 | 补全层隔离，重新进入执行检查 |
| 审批疲劳 | 所有动作都要求人点同意 | 用明确且预先批准的低风险边界减少打断 |
| 一键回滚幻觉 | 本地状态回退等于外部操作撤销 | 核查外部状态，必要时执行独立补偿 |

## 14. 示例

### 14.1 薪酬清单：保留原文事实，不把回放当付款

原文测试账本包含798张标为已付款的工资单和2张已冲正工资单，检查清单总额为13,706,097元。将全款自动通过上限从13,000,000元改到30,000,000元，在原文实验的其他条件不变时，检查结果从转人工变为通过。[讲义]

这里的13,000,000元与30,000,000元是该检查的自动通过阈值，不代表公司现金余额，也不替代独立的硬预算。

这些是讲义提供的测试账本与检查结果，**不表示本次执行了付款**。标为已付款的项目不得因此重新发起付款；清单检查通过与确认存在新的应付义务是不同问题。

| 场景 | 提案内容 | 采用规则 | 本文要求的处理 |
|---|---|---|---|
| 原文低限额回放 | 清单13,706,097元 | 上限13,000,000元 | 转人工并记录规则 |
| 原文旧式高限额回放 | 同一清单 | 上限30,000,000元 | 原文指出通过回执缺策略标记，留下审计缺口 |
| 本文改造验收预期 | 同一检查清单 | 经合法发布的高限额规则 | 检查回执绑定规则版本，仍不意味着实际付款 |
| 非法放宽 | 同一主体提出并批准提高限额 | 变更来源不合格 | 拒绝发布，不以新限额执行 |
| 审批后改对象 | 金额不变但对象改变 | 旧批准与新提案不匹配 | 最终入口拒绝，重新审批 |

用“分”存储上述金额时，总额为1,370,609,700分；两档限额分别为1,300,000,000分和3,000,000,000分。只转换表示单位，不改变金额语义。

原文提供的 `governance/payroll-lab/ungoverned_policy_lab.py` 和 `governance/boundary_contract.py` 是讲义中的仓库路径；本次未取得或运行这些程序，不把下述设计当作其运行输出。

### 14.2 优惠券：单次100元不能变成无限累计

示例任务只允许对指定工单发放一次100元优惠券。提案绑定工单、用户、券规则和100元金额；业务幂等身份由工单及补偿事项共同确定。

工具超时后查询原发券请求；已成功则补证并关闭，未知则保留占用。换执行者、重试十次或创建新运行实例都不能形成十张券。需要追加补偿时应有新的业务依据，并继续受该用户、该工单和所属时间窗累计上限约束。

### 14.3 非资金场景的替换项

| 场景 | 提案绑定对象 | 影响范围 | 最终结果证明 |
|---|---|---|---|
| 生产发布 | 构建摘要、环境、服务、配置版本 | 服务数量、流量比例、区域、并发 | 实际部署版本与健康核验 |
| 数据库变更 | 规范化变更、表、条件、预计行集 | 行数、表域、租户、锁定时间 | 变更回执与业务数据核验 |
| 文件操作 | 冻结路径范围、对象版本、动作 | 文件数、总大小、目录边界 | 文件清单与读回校验 |
| 数据导出 | 数据集、字段、筛选、接收方 | 记录数、敏感级别、目的地 | 实际导出清单与交付记录 |
| 对外消息 | 内容摘要、接收人集合、渠道 | 接收人数、频次、时间窗 | 渠道状态；接收不等于阅读 |
| 采购下单 | 品类、数量、供应商、价格、交付条件 | 金额、件数、供应商范围 | 订单状态和后续收货证明 |

替换的是业务适配器和影响维度，提案绑定、策略来历、最终检查、未知结果和责任链保持一致。

## 15. 关联模式

与审批门共享版本绑定和审批有效期；与影响范围控制共享累计账本与原子预留；与渐进承诺共享权限证据和撤销；与交接链共享责任、工件和检查点；与对抗评审共享独立异议及放行约束；与规划执行、局部恢复共享受控重试和恢复范围。

与工作流可观测性探针的关系是“执行产生事实，探针补全观测，治理决定是否推进”。未读取对应完整实现的关联模式只作为接口挂载点，不自动继承其中未核实的字段或承诺。

## 附录乙：共享交互契约（两份文档均完整内置）

### 乙.1 版本、传输与信任

本对文档使用协议 `GOV_BOUNDARY_OBS`，版本 `1.0.0`。它是本次新增协议，不替代项目中其他已有协议。相同主版本才能直接交换消息；不兼容时隔离消息并输出版本错误，不静默丢字段。运行时必须另外校验发送者身份、租户和调用权限；摘要只能校验内容一致性，不能证明发送者身份。

共享的是接口，不是彼此的运行进程。执行侧可以只使用本地治理组件；探针可以只分析输入的历史材料。消息传输可采用本地文件、事件队列、接口或远程工具适配器，必须保留相同语义。

| 消息类型 | 发起方 → 接收方 | 语义 |
|---|---|---|
| 运行事件 | 执行侧 → 探针 | 已发生的提案、裁决、调用、核验等事实，原记录不可覆盖 |
| 补全请求 | 任一侧 → 另一侧 | 指明缺少哪个字段、对应哪一版动作，以及补全期限；不授权业务操作 |
| 观测补丁 | 探针 → 执行侧 | 提供可验证来源、确定性派生值或明确标注的待核验线索 |
| 控制建议 | 探针 → 治理裁决服务 | 建议暂停、复核、缩权、对账；本身不是执行凭证 |
| 采纳回执 | 接收侧 → 发起侧 | 逐项说明采纳、拒绝、冲突、过期或待人工，并给出原因 |

### 乙.2 通用消息信封

下列字段构成接口约定；对象尚未产生时允许相应标识为空，但必须写明原因。不得用同一个空值将“尚未产生”“没有权限读取”和“采集失败”混为一谈。

```yaml
protocol_id: GOV_BOUNDARY_OBS
protocol_version: 1.0.0
message_id: 消息唯一标识
message_type: 运行事件
tenant_id: 租户标识
trace_id: 跨步骤关联标识
run_id: 运行实例标识
step_id: 步骤实例标识
skill_id: 技能定义标识
skill_version: 0.1.0
emitter_identity_ref: 可信发送者身份引用
emitted_at: '2026-09-22T07:00:00Z'
causation_id: 上游消息或事件标识
content_digest: 规范化消息内容的完整摘要
payload: {}
```

计算 `content_digest` 时排除摘要字段本身和传输签名字段，纳入消息类型、关联标识及完整载荷。使用约定的规范化序列化；金额、时间、空值和有序列表不能由不同组件各自解释。身份凭证、签名或受保护存储由适配器验证，不允许模型自行声称“已验证”。

所有时间使用带时区时间或统一协调时。生产者的发生时间与采集器接收时间分别保留；展示时才转换本地时区。不同来源时间不可直接当作严格因果顺序。

### 乙.3 运行事件的最低字段

| 字段 | 规则 |
|---|---|
| `event_id`、`event_type`、`node_id` | 事件标识不可复用；节点指向定义，步骤标识指向实例 |
| `task_id`、`action_id`、`attempt_id` | 任务、逻辑动作与某次尝试分离；重试不得伪装成新业务需求 |
| `proposal_id`、`proposal_version`、`proposal_digest` | 所有裁决、派发和结果事件必须绑定具体提案内容 |
| `artifact_id`、`artifact_digest`、`contract_digest` | 指向实际使用的工件快照和任务边界，而非可变文件别名 |
| `policy_refs`、`policy_set_digest` | 每个策略引用含标识、版本、完整内容摘要；放行与拒绝均要记录 |
| `decision_context_digest`、`receipt_id` | 绑定身份授权、资源前置版本等裁决依赖；原回执留在受保护存储 |
| `credential_id`、`credential_version` | 标记实际执行使用的权限凭证；不可记录密钥明文 |
| `reservation_id`、`business_operation_id`、`idempotency_key` | 关联额度占用与业务幂等身份；跨重试保持正确对应关系 |
| `external_request_id` | 外部系统的请求或交易标识；尚未发送与发送后未获取标识须区分 |
| `occurred_at`、`ingested_at`、`emitter_sequence` | 发生时间、接收时间、来源内序号；序号不代表跨来源全局顺序 |
| `result_status`、`reason_code` | 区分允许执行、已提交、已核实成功、已核实失败和结果未知 |
| `evidence_refs`、`quality_state` | 引用证据来源与质量；无来源不能标为已核验 |

并非每类事件都具有全部业务字段。节点契约决定必填项；裁决缺策略、派发缺提案、核验缺业务结果来源都属于缺口，不能以“可选字段”为由忽略。策略变更类事件应额外包含前后版本、提出者、批准者、生效时间和变更原因。

### 乙.4 补全请求、补丁与采纳回执

补全请求至少含：请求标识、目标运行与动作、目标字段、预期提案和策略摘要、缺口类型、允许查询的来源、截止时间、证据要求、请求预算。缺口类型为“证据缺失、事实未发生、来源冲突、时效失效、权限不足、关联不明”之一。

下面展示观测补丁结构。字段值为接口示意，不代表真实审批或付款记录。

```yaml
patch_id: 补丁唯一标识
request_id: 原补全请求标识
mode: 当前运行补全
target:
  tenant_id: 租户标识
  run_id: 运行实例标识
  action_id: 逻辑动作标识
  base_state_revision: 12
  proposal_digest: 目标提案完整摘要
  policy_set_digest: 目标策略集合完整摘要
  artifact_digest: 目标工件完整摘要
expires_at: '2026-09-22T07:05:00Z'
fields:
  - path: observation_enrichment.回执核验线索
    value:
      receipt_ref: 受保护审批库中的记录引用
      source_version: 原记录版本
      verification_status: 待执行入口复核
    evidence_refs:
      - source_id: 审批库
        record_id: 原始记录标识
        content_digest: 原始记录完整摘要
        occurred_at: '2026-09-22T06:55:00Z'
        retrieved_at: '2026-09-22T07:01:00Z'
    value_kind: 来源事实
    derivation: null
    quality_state: 已核验
```

`quality_state: 已核验` 仅表示探针对来源和内容完成了自身校验，**不表示该审批足以授权当前动作**。执行入口仍须自行验证身份、权限、摘要、有效期、撤销状态和当前策略。

每个补丁字段必须具备来源、来源版本、采集时间、适用对象、质量状态；派生字段还应带公式或规则版本。模型推测只能标为待核验，不能生成审批、付款成功或额度余额等权威事实。置信度即使很高，也不能替代授权证据。

允许写入的命名空间仅为 `observation_enrichment`。禁止补丁修改任务目标、金额、对象、提案、策略、审批结果、执行状态、业务余额、权限凭证、原始事件或审计时间。补回合法原记录的引用，与“新增一份批准”是两回事。

采纳回执至少含：回执标识、补丁标识与摘要、接收主体、核验时间、逐字段结果、拒绝原因、采纳后的观测版本。结果枚举为：已采纳、部分采纳、拒绝、冲突、已过期、待人工。

### 乙.5 执行侧采纳顺序

```text
验证消息来源、权限、协议和租户
→ 检查补丁标识是否重复；同标识异内容立即拒绝
→ 核对目标运行、动作、提案、策略、工件及基线状态版本
→ 检查有效期和字段白名单
→ 复核来源、来源时效、证据适用范围及派生规则
→ 只追加到观测补全层，保留原始缺口和历史记录
→ 生成逐字段采纳回执
→ 如补全影响待执行条件，重新进入治理裁决和最终执行检查
```

同一补丁重传且内容相同，应返回原采纳结果，不重复追加；状态版本已变化时返回冲突，由发起方基于新状态重新生成补丁，不得直接替换摘要冒充匹配。

“历史审计补全”模式只能关联明确的历史快照，不能覆盖当前视图或恢复执行资格。实际操作之后才形成的批准，不能回填为操作之前已经获批；事后找到当时确已存在的原记录，也必须保留“何时发现”的采集时间。

### 乙.6 闭环、降级与停止条件

```text
执行产生原始事件
→ 探针发现缺口并检索授权来源
→ 提交观测补丁或业务补做请求
→ 接收方采纳、拒绝、转人工或返回冲突
→ 探针重算指标，记录缺口关闭依据
```

业务补做请求不是执行指令。事实尚未发生时，执行侧必须建立新步骤或新提案，重新审批后完成业务；探针只记录其结果。缺口关闭要求证据已经被接收方核验并满足原验收条件，不能仅因“补丁已发送”或“人工已查看”而关闭。

每个请求都设重试上限、查询预算、去重键和截止时间。回执事件标记来源请求，避免探针把自己的输出无限当作新缺口。超限后保留未解决状态并交给指定责任人。

探针中断时，执行侧继续维持本地裁决、权限、预算、幂等和最小审计；是否暂停取决于缺失的必要证据与预先配置的风险策略。探针本身不直接停机、放行、扩权或回滚，控制建议由有授权的治理服务核实并执行。
