# 可观测性执行流程

## 1. 文档目的

本模式把一项智能体任务从“收到请求”推进到“业务结果已确认”，并在每个关键位置留下可关联、可核对、可重放、可追责的运行事实。

它解决的不是“多记一些日志”，而是以下四个工程问题：

1. 一项行动为什么发生。
2. 它依据了哪一版提案、规则、批准、额度、权限和工具能力。
3. 技术调用、业务受理与业务完成分别处于什么状态。
4. 出现偏差后，能否定位原因、修正系统，并验证下一版是否真的改对。

本模式可以独立执行，也可以与《工作流可观测性探针》交互运行。独立执行时，执行流程自行生成最小运行史；交互运行时，探针负责校验、补全、关联和派生观测数据。

---

## 2. 模式定位

### 2.1 模式类型

本模式属于工程模式基座中的“执行流程模式”，可进一步包装为 Skill。

### 2.2 核心定义

可观测性执行流程，是在任务执行过程中，将目标、上下文、提案、控制、工具调用、业务回执、对外表达和最终结果串联为一条运行史的通用工作流。

### 2.3 核心边界

本模式负责：

- 组织执行阶段；
- 规定每个阶段必须产生的事实；
- 区分技术状态、受理状态和业务结果；
- 指定最终结果的确认来源；
- 形成调查、审计和回归测试所需的证据包；
- 向工作流可观测性探针暴露标准事件和补全接口。

本模式不负责：

- 替业务负责人定义所有成功标准；
- 替审批人作出高风险批准；
- 把日志平台中的“未发现记录”解释为“动作没有发生”；
- 在重放时重新执行不可逆外部动作；
- 将模型内部不可验证的推理文字当作业务证据。

---

## 3. 适用场景

本模式适用于存在下列任一特征的任务：

- 调用外部工具、接口、数据库、消息队列或业务系统；
- 存在异步受理、延迟回调或长事务；
- 需要审批、额度、权限、身份或策略控制；
- 多智能体、多进程、多服务或跨语言协作；
- 可能发生重试、重复提交、部分成功或结果未知；
- 结果需要到另一个权威业务系统确认；
- 需要处理用户投诉、审计、复盘、评测或回归验证；
- 需要依据历史成绩调整智能体权限和自治范围。

典型场景包括客服补偿、付款结算、订单履约、软件发布、数据变更、内容生成、报告交付、工单处理、设备控制、文件处理和多智能体研究任务。

### 3.1 不适用场景

以下任务可以采用简化流程：

- 无外部副作用、无异步状态、无需审计的一次性文本草稿；
- 不保存用户数据、不调用工具、失败成本很低的临时探索；
- 已由上层系统完整记录且本层没有新增决策或业务动作的纯转发。

即使采用简化流程，也应至少保留任务标识、输入版本、输出结果和失败状态。

---

## 4. 设计原则

### 4.1 结果优先于接口

接口返回成功，只能证明某次调用被技术系统接收或处理，不能自动证明业务目标已经兑现。

必须区分：

- 技术调用是否成功；
- 业务请求是否被受理；
- 业务动作是否最终完成；
- 用户是否实际得到预期结果。

### 4.2 状态告诉现在，运行史解释来路

当前状态可以被覆盖，运行史必须保留关键变化。任何对结果有影响的状态变更，都应能追溯到其触发事件、责任主体、规则版本和证据来源。

### 4.3 时间先后不等于因果关系

审批发生在执行之前，不代表该审批一定授权了该执行。系统必须记录“本次执行消费了哪一张批准票”“本次额度扣减对应哪一项动作”“本次权限调整由哪一次事故触发”。

### 4.4 记录完整性包括“该出现而没有出现”

完整性不仅检查已有记录是否被修改，还要检查本来应该存在的审批、额度、权限校验、业务回执和对外答复记录是否缺失或被绕过。

### 4.5 记录事实，不伪造解释

所有观测数据必须标记为以下三类之一：

- 已观测事实；
- 基于证据推导的结论；
- 尚未取得或无法确认的信息。

不得用推测填补缺失事实。

### 4.6 先定义最终确认源

每项任务在执行前就应指定最终结果到哪里确认。确认源可以是订单系统、券系统、银行回执、部署平台、工单系统、文件仓库或人工验收记录。

### 4.7 可恢复不等于可重做

结果未知时，优先查询原业务申请号，不得直接重试不可逆动作。只有确认原动作未生效，并且当前批准、额度和权限仍有效时，才允许继续执行。

### 4.8 观测失败也是运行故障

关键记录写入失败时，必须按风险等级决定继续、降级或暂停。高风险动作不能在审计证据完全丢失的情况下静默执行。

## 5. 参与角色与职责

| 角色 | 主要职责 |
|---|---|
| 请求发起者 | 提供目标、约束、期望结果和必要授权 |
| 执行智能体 | 形成提案、选择工具、执行步骤、解释状态 |
| 编排器 | 管理阶段、分支、依赖、重试、超时和恢复 |
| 策略控制器 | 执行规则、审批、额度、权限和风险校验 |
| 工具或服务 | 执行局部技术动作并返回原始响应 |
| 权威业务系统 | 确认业务结果是否真实生效 |
| 记录器 | 写入结构化事件、版本和证据引用 |
| 可观测性探针 | 校验、补全、关联、派生指标和发现缺口 |
| 调查者 | 根据运行史定位问题和根因 |
| 业务评审者 | 判断结果是否符合业务要求 |
| 发布负责人 | 审核修复、回归结果和上线条件 |
| 治理负责人 | 决定权限、额度、规则和保留策略的调整 |

同一实现可以合并多个角色，但职责和证据边界不能因此消失。

## 6. 输入契约

### 6.1 必需输入

```yaml
task_context:
  task_id: 全局业务任务标识
  run_id: 本次运行标识
  objective: 本次任务目标
  expected_result: 可核验的期望结果
  result_confirmation_source: 最终结果确认源
  actor_identity: 本次实际执行身份
  risk_level: 低 | 中 | 高 | 极高
  input_refs: 输入内容或工件引用
  policy_snapshot_ref: 规则快照引用
  permission_snapshot_ref: 权限快照引用
  tool_catalog_snapshot_ref: 当时可见工具清单引用
  version_snapshot:
    workflow_version: 工作流版本
    prompt_version: 提示版本
    model_version: 模型版本
    tool_versions: 工具版本映射
    schema_version: 事件结构版本
```

### 6.2 条件必需输入

当场景涉及相应控制时，还必须提供：

```yaml
control_context:
  proposal_id: 提案标识
  approval_ticket_id: 批准票标识
  approval_scope: 批准范围
  approval_expiry: 批准有效期
  budget_envelope_id: 额度信封标识
  reserved_amount: 已预留额度
  idempotency_key: 幂等键
  business_application_id: 外部业务申请号
  parent_task_id: 父任务标识
  parent_run_id: 父运行标识
  artifact_id: 工件标识
  artifact_version: 工件版本
```

### 6.3 输入校验要求

执行前必须确认：

- `task_id` 与 `run_id` 不为空且不重复；
- 期望结果可被某个权威来源核验；
- 高风险任务存在明确执行身份；
- 输入工件版本与任务要求一致；
- 规则、权限、工具清单均有版本或快照；
- 涉及副作用时存在幂等键或等效防重复机制；
- 涉及异步结果时存在稳定的业务申请号。

## 7. 输出契约

### 7.1 标准输出

```yaml
execution_result:
  task_id: 原任务标识
  run_id: 本次运行标识
  final_status: 已确认成功 | 已确认失败 | 部分完成 | 等待外部结果 | 结果未知 | 已取消 | 已补偿
  technical_status: 技术调用汇总状态
  business_status: 权威业务结果
  user_commitment_status: 对外承诺与业务状态的一致性
  result_confirmation:
    source: 权威确认源
    checked_at: 确认时间
    receipt_ref: 回执或结果引用
  evidence_bundle_ref: 证据包引用
  unresolved_gaps: 未解决记录缺口
  anomalies: 异常与冲突
  next_action: 下一步动作
  replay_bundle_ref: 可选，离线重放材料引用
```

### 7.2 最终状态定义

| 最终状态 | 定义 |
|---|---|
| 已确认成功 | 权威业务系统或约定验收方确认目标已经兑现 |
| 已确认失败 | 权威来源确认目标未兑现或被拒绝 |
| 部分完成 | 目标由多个子结果组成，只有部分得到确认 |
| 等待外部结果 | 请求已被受理，仍处于合法等待期 |
| 结果未知 | 无法确认是否生效，继续执行可能造成重复副作用 |
| 已取消 | 在外部副作用发生前或按规则终止 |
| 已补偿 | 原动作发生后，已完成撤销、退款、回滚或替代处理 |

`技术成功` 不得直接映射为 `已确认成功`。

---

## 8. 统一运行标识

不同标识解决不同关联问题，不应只依赖一个编号。

| 标识 | 作用域 | 主要用途 |
|---|---|---|
| `task_id` | 跨运行 | 标识同一个业务任务 |
| `run_id` | 单次运行 | 区分任务的每次执行、恢复或重放 |
| `trace_id` | 一次调用链 | 关联跨服务、跨进程的执行路径 |
| `span_id` | 单个操作 | 标记一段有起止时间的工作 |
| `parent_span_id` | 调用关系 | 表示直接父子关系 |
| `link_ids` | 非父子关系 | 关联异步、并行、批次和跨追踪事件 |
| `business_application_id` | 外部业务 | 将运行与券、付款、订单、发布等外部对象关联 |
| `artifact_id` | 工件 | 标识报告、清单、代码、文件或提案 |
| `artifact_version` | 工件版本 | 防止使用错误版本继续执行 |
| `approval_ticket_id` | 治理控制 | 证明本动作消费了哪一项批准 |
| `budget_envelope_id` | 额度控制 | 证明本动作占用了哪一份额度 |
| `idempotency_key` | 副作用控制 | 防止重试造成重复业务动作 |

长任务可能跨越多次运行，`task_id` 和 `business_application_id` 必须保持稳定；每次恢复则生成新的 `run_id`。

## 9. 执行状态机

```text
已创建
  ↓
上下文已固定
  ↓
提案已形成
  ↓
控制校验中
  ├─→ 已拒绝
  └─→ 已放行
          ↓
      资源已预留
          ↓
        执行中
          ↓
      技术调用结束
          ├─→ 业务已完成
          ├─→ 等待外部结果
          ├─→ 业务已失败
          └─→ 结果未知
                    ↓
              查询与对账
                    ↓
        已确认成功 / 已确认失败 / 部分完成 / 已补偿
```

状态变化必须追加事件，不得只覆盖当前状态。

## 10. 标准执行流程

### 阶段 0：建立任务基线

**目标：** 在做任何外部动作前，明确“要办成什么”和“到哪里确认”。

**动作：**

1. 生成或接收 `task_id`、`run_id` 和 `trace_id`。
2. 把自然语言目标转成可核验的期望结果。
3. 指定权威结果确认源和允许的等待时间。
4. 标记风险等级、可逆性和最大允许损失。
5. 定义成功、失败、部分完成、等待和结果未知的判定口径。

**必须记录：**

- 原始请求引用；
- 结构化目标；
- 结果确认源；
- 风险等级；
- 判定口径；
- 初始化时间与执行身份。

**闸门：** 无法指定结果确认源的高风险任务不得进入执行阶段。

---

### 阶段 1：固定运行上下文

**目标：** 保存当时实际可见、可用和生效的条件。

**动作：**

1. 固定输入工件及版本。
2. 固定模型、提示、工作流、工具和结构版本。
3. 固定规则、权限和工具可见性快照。
4. 记录被过滤的工具以及过滤原因。
5. 对敏感数据执行最小化、脱敏和引用化处理。

**必须记录：**

- 输入引用和校验值；
- 版本快照；
- 工具清单快照；
- 权限快照；
- 数据分级和保留等级。

**闸门：** 工件版本不符、权限身份不明或敏感信息处理失败时暂停。

---

### 阶段 2：形成提案与执行计划

**目标：** 把“想做什么”与“实际执行”分开，使后续批准能够绑定具体版本。

**动作：**

1. 形成结构化提案。
2. 列出预计使用的工具、资源、金额、影响范围和外部副作用。
3. 标明假设、依赖、未知项和替代方案。
4. 生成 `proposal_id` 与 `proposal_version`。
5. 对并行、路由、循环或层级任务生成拓扑计划。

**必须记录：**

- 提案内容引用；
- 提案版本；
- 候选方案；
- 选择理由；
- 预计副作用；
- 计划终止条件。

**闸门：** 实际执行参数不得超出提案描述；发生实质变化时必须生成新版本并重新校验。

---

### 阶段 3：执行治理控制

**目标：** 确认本次动作具有有效批准、额度和权限。

**动作：**

1. 检查批准票是否绑定当前提案版本。
2. 检查批准范围、有效期、对象、金额和条件。
3. 检查额度是否足够并进行预留。
4. 检查实际执行身份和工具权限。
5. 检查智能体自治等级是否覆盖当前任务风险。
6. 记录拒绝、过滤、降级和人工接管原因。

**必须记录：**

- 规则版本；
- 控制输入；
- 控制结果；
- 批准票引用；
- 额度预留引用；
- 权限快照；
- 决策主体；
- 失效时间。

**闸门：**

- 批准票与提案版本不匹配：拒绝执行；
- 额度不足：拒绝或缩小动作；
- 权限不足：拒绝、降级或转人工；
- 关键控制记录无法写入：高风险任务暂停。

---

### 阶段 4：执行前校验

**目标：** 在产生副作用前再次核对目标、参数、版本和幂等条件。

**动作：**

1. 比较提案参数与即将发送的实际参数。
2. 检查业务对象、账户、收件人、环境和工件版本。
3. 生成或确认幂等键。
4. 检查重复执行和未决申请。
5. 确认回调地址、查询接口和超时策略。
6. 确认探针或最小记录器可用性。

**必须记录：**

- 最终请求摘要；
- 参数差异；
- 幂等键；
- 重复检查结果；
- 预检结论。

**闸门：** 账户、对象、环境或版本出现差异时，不得沿用旧批准继续执行。

---

### 阶段 5：调用工具或服务

**目标：** 执行局部技术动作，并完整保留原始业务语义。

**动作：**

1. 记录工具调用开始事件。
2. 发送请求并记录请求摘要、参数引用和执行身份。
3. 记录返回码、原始业务状态、回执号、耗时和错误。
4. 对响应进行结构化解析，但保留原始响应引用。
5. 记录超时、重试、熔断、回退和人工介入。

**必须记录：**

- 工具名称与版本；
- 请求引用；
- 响应引用；
- 技术返回码；
- 业务状态字段；
- 业务申请号；
- 重试序号；
- 幂等键；
- 开始和结束时间。

**关键规则：**

- `200`、`success=true` 或“调用成功”只描述技术层；
- `pending`、`accepted`、`queued` 等状态必须原样传递；
- 中间转换层不得把多值业务状态压缩成单一布尔值；
- 任何重试都必须复用幂等键或先查询原结果。

---

### 阶段 6：解释技术结果与业务状态

**目标：** 防止把“已受理”误说成“已完成”。

**动作：**

1. 将工具响应分解为技术状态、受理状态和业务状态。
2. 根据规则映射允许的对外表达。
3. 检查状态字段是否在各组件间完整传递。
4. 对状态冲突、未知值和结构变化发出异常事件。
5. 需要时向探针请求状态保真校验。

**示例映射：**

| 原始业务状态 | 允许的内部结论 | 允许的对外表达 |
|---|---|---|
| `pending_review` | 申请已受理，等待审核 | 已提交申请，审核完成后再发放 |
| `issued` | 已发放 | 已发放，可到指定位置查看 |
| `rejected` | 已拒绝 | 申请未通过，并说明可公开原因 |
| `unknown` | 结果未知 | 当前无法确认结果，正在查询，不得重复承诺 |

**闸门：** 对外答复必须以当前可证明的业务状态为上限，不得超出证据承诺。

---

### 阶段 7：等待、回调与跨运行接续

**目标：** 处理异步受理、延迟回调和长任务恢复。

**动作：**

1. 使用稳定的 `business_application_id` 注册未决事项。
2. 保存回调关联条件、最晚确认时间和查询策略。
3. 回调到达时，将新事件链接回原任务和原业务申请。
4. 进程恢复时生成新 `run_id`，保留原 `task_id`。
5. 验收交接工件、版本、回执和未决事项。
6. 到期无回调时主动查询权威业务系统。

**必须记录：**

- 等待开始时间；
- 回调或查询来源；
- 跨运行链接；
- 交接验收结果；
- 未决事项列表；
- 超时处理决定。

**关键规则：** 回调缺失不等于业务没有发生；必须凭业务申请号查询。

---

### 阶段 8：确认最终业务结果

**目标：** 从权威来源核对事情是否真正办成。

**动作：**

1. 查询约定的最终确认源。
2. 将实际结果与期望结果逐项比较。
3. 对批量任务记录逐项、分组和总体结果。
4. 标记成功、失败、部分完成、等待或未知。
5. 若执行记录和业务账不一致，优先保留冲突并启动对账。
6. 形成结果回执引用。

**必须记录：**

- 权威来源；
- 查询条件；
- 查询时间；
- 业务结果；
- 回执引用；
- 差异明细；
- 确认责任主体。

**闸门：** 在高风险任务中，未取得权威结果不得关闭为“成功”。

---

### 阶段 9：生成对外答复或交付物

**目标：** 让自然语言表达与可证明事实一致。

**动作：**

1. 根据最终业务状态选择答复模板。
2. 检查承诺用语是否超过证据。
3. 对用户可见内容进行敏感信息过滤。
4. 保存答复版本、输入状态和生成组件版本。
5. 对报告、文件、代码等工件生成唯一版本和校验值。

**必须记录：**

- 对外答复引用；
- 使用的业务状态；
- 工件版本；
- 脱敏结果；
- 一致性检查结果。

**闸门：** “已提交”“已受理”“处理中”“已完成”必须严格区分。

---

### 阶段 10：关闭运行并形成证据包

**目标：** 让任务可以被调查、审计、重放和复用。

**动作：**

1. 汇总阶段事件和因果链接。
2. 检查应有记录是否齐全。
3. 生成运行摘要和未解决缺口。
4. 将关键控制和业务回执存入长期证据区。
5. 将普通调试详情按策略采样或过期。
6. 生成可重放材料，但排除真实副作用凭证。

**证据包至少包含：**

- 原始请求引用；
- 目标与期望结果；
- 输入工件及版本；
- 提案及版本；
- 规则、批准、额度和权限记录；
- 工具请求和原始响应引用；
- 异步回调或查询记录；
- 权威业务结果；
- 对外答复；
- 异常、重试和人工纠正；
- 版本快照；
- 记录完整性报告。

---

### 阶段 11：评测、修复与回归验证

**目标：** 将一次失败转化为下一版可验证的改进。

**动作：**

1. 区分问题位于工具、知识、状态传递、策略、执行、业务系统还是表达层。
2. 从失败运行中提取最小重放样本。
3. 使用保存的工具响应或模拟回执替代真实外部动作。
4. 对修改后的代码、提示、规则或工作流重新运行。
5. 比较旧版与新版的状态传递、决策和最终答复。
6. 扩充正向、拒绝、等待、未知和边界样本。
7. 经业务评审和发布审核后上线。

**关键规则：**

- 调查旧记录时，不重新作业务决定；
- 测试新版本时，可以重新运行程序，但必须隔离真实副作用；
- 单个失败样本通过后，还要验证相邻状态，避免修成新的单一偏差。

---

### 阶段 12：反馈到治理调整

**目标：** 用真实运行结果决定下一次允许智能体做多少。

**动作：**

1. 汇总纠正率、未知结果率、重复副作用、投诉和审批偏差。
2. 判断问题是否具有系统性。
3. 由责任人决定规则、额度、权限、工具或自治范围调整。
4. 记录调整原因、决定者、生效时间和版本。
5. 下一次运行读取新版本，不改写历史解释。

**必须记录：**

- 调整依据；
- 受影响范围；
- 旧值与新值；
- 决定者；
- 生效时间；
- 回滚条件。

---

## 11. 不同拓扑下的适配规则

### 11.1 链式

- 每一步必须引用前一步的输出版本；
- 任一步状态丢失都会影响后续解释；
- 必须记录阶段序号、输入引用和输出引用；
- 关闭前检查链条是否有断点。

### 11.2 路由

- 记录候选路由、被选路由和选择依据；
- 记录因权限、成本、风险或能力不足而被过滤的路径；
- 路由规则必须有版本；
- 结果异常时可判断是路由错误还是执行错误。

### 11.3 并行

- 每个分支使用独立 `span_id` 或子 `trace_id`；
- 记录分支输入、完成状态、超时和取消原因；
- 聚合时记录采用了哪些分支、忽略了哪些分支；
- 部分失败不能被总体成功掩盖。

### 11.4 编排

- 保存依赖图、调度决定和阶段闸门；
- 记录被跳过、延后、回退和重排的节点；
- 编排器不得吞掉工具的业务状态；
- 关闭时验证计划节点与实际节点的差异。

### 11.5 循环

- 记录迭代编号、终止条件和每次修订差异；
- 限制最大迭代次数、时间和成本；
- 防止相同输入无变化地重复调用；
- 结果只在达到终止条件并完成业务确认后关闭。

### 11.6 层级

- 父任务保留最终责任；
- 子任务必须有明确边界、验收条件和返回工件；
- 记录委派者、接收者、版本和责任范围；
- 子任务成功不自动等于父任务成功；
- 交接时必须验收清单、回执和未决事项。

---

## 12. 独立运行方式

执行流程不依赖专门可观测性平台也能运行，但必须具备最小记录能力。

### 12.1 最小事件集

独立模式至少写入以下事件：

1. 运行开始；
2. 上下文已固定；
3. 提案已形成；
4. 控制校验完成；
5. 工具调用开始；
6. 工具调用结束；
7. 业务状态已解释；
8. 最终结果已确认或标记未知；
9. 对外答复已生成；
10. 运行关闭。

### 12.2 最小存储要求

- 事件按追加方式保存；
- 关键事件带校验值；
- 原始敏感内容不直接写入普通日志；
- 关键控制、业务回执和权限变更单独长期保存；
- 记录失败产生独立告警；
- 删除或更正必须保留原记录与更正说明。

### 12.3 独立模式输出

独立模式仍必须输出：

- 最终状态；
- 结果确认源；
- 证据索引；
- 未解决缺口；
- 是否可重放；
- 是否需要人工介入。

---

## 13. 与工作流可观测性探针的交互运行

### 13.1 交互目标

探针不接管业务执行，而是补全以下能力：

- 检查事件是否齐全；
- 校验跨阶段状态是否保真；
- 关联审批、额度、权限和业务回执；
- 发现“接口成功但任务未完成”；
- 发现缺失、冲突、越权、过度承诺和重复副作用；
- 生成指标、告警、证据包和重放材料。

### 13.2 执行流程发送给探针的事件

```text
运行开始
阶段开始
上下文快照
提案形成
控制校验
工具调用
工具返回
业务状态转换
等待登记
回调接收
结果确认
对外答复
运行关闭
规则调整
```

### 13.3 探针返回给执行流程的消息

```text
记录确认
字段缺口
关联缺口
状态冲突
版本冲突
敏感信息告警
补全请求
暂停建议
降级建议
结果确认请求
证据包已就绪
```

### 13.4 补全协议

1. 探针发现必需字段缺失。
2. 探针生成 `gap_id`，说明缺失字段、影响阶段、风险等级和允许响应时间。
3. 执行流程返回证据引用、明确的“不适用”理由，或声明无法取得。
4. 探针重新校验。
5. 未解决缺口进入运行摘要。
6. 对关键治理记录缺失，高风险动作按策略暂停或转人工。

### 13.5 探针不可用时的降级

| 风险等级 | 处理方式 |
|---|---|
| 低 | 使用本地最小事件集继续，稍后补传 |
| 中 | 继续前确认本地记录器可用，并限制副作用范围 |
| 高 | 关键记录或关联能力不可用时暂停 |
| 极高 | 必须同时满足记录、审批、额度和结果确认条件，否则禁止执行 |

## 14. 通用异常处理

| 异常 | 判断原则 | 处理方式 |
|---|---|---|
| 接口成功但业务等待 | 技术成功不等于完成 | 保留等待状态，登记查询或回调 |
| 接口成功但业务失败 | 以业务状态为准 | 标记失败，禁止对外宣称完成 |
| 调用超时 | 超时不等于未生效 | 使用原业务申请号查询，禁止盲目重试 |
| 找不到审批记录 | 未找到不等于未批准 | 查询审批系统；确认缺失后再判断违规 |
| 已执行但无记录 | 业务账优先用于确认事实 | 触发记录故障、补存和审计 |
| 重复回调 | 回调可能至少一次送达 | 按事件标识和业务申请号去重 |
| 重复提交 | 重试可能造成副作用 | 幂等校验或先查原结果 |
| 工件版本不一致 | 版本错误可能污染后续 | 停在交接或预检阶段 |
| 对外答复超出状态 | 属于过度承诺 | 阻断答复或改用受限模板 |
| 记录含敏感数据 | 可观测性不能扩大泄露面 | 立即脱敏、隔离、审计访问 |
| 版本已更新 | 历史运行按历史版本解释 | 不用新规则反推旧行为 |
| 权威系统不可用 | 无法确认最终结果 | 标记等待或未知，不关闭为成功 |

---

## 15. 数据与隐私治理

### 15.1 最小化

只记录调查、审计、评测和恢复所需内容。密码、访问令牌、私钥、完整证件号不得进入普通观测记录。

### 15.2 可核对但不过度暴露

账户、用户、文件等敏感对象可使用受控标识、令牌化标识或带权限的映射引用。不同记录必须仍能判断“是否为同一对象”。

### 15.3 分级访问

- 客服查看任务进度和公开业务状态；
- 工程人员查看技术输入输出和错误；
- 审计人员查看批准、身份、额度和实际执行范围；
- 安全人员查看敏感数据处理和访问历史。

### 15.4 分级保留

| 记录类型 | 建议策略 |
|---|---|
| 普通调试详情 | 短期、采样、可按成本淘汰 |
| 模型输入输出 | 依敏感等级和业务需要保留 |
| 审批、额度、权限 | 长期、追加式、限制修改 |
| 外部业务回执 | 按业务与合规期限长期保留 |
| 规则和版本变更 | 长期保留，支持历史解释 |
| 重放测试样本 | 脱敏后进入受控数据集 |

### 15.5 更正规则

发现记录有误时，应追加更正事件，包含原记录引用、错误原因、更正内容、操作者和时间，不直接删除或覆盖原记录。

## 17. 场景示例

### 17.1 客服补偿券

- 期望结果：指定用户的卡包中出现指定面额的补偿券；
- 技术调用成功：发券服务接收请求；
- 受理状态：等待审核；
- 最终确认源：券系统中的券实例或用户卡包；
- 关键风险：把等待审核说成已经发放；
- 必需关联：用户、补偿申请、审批、券实例、对外答复。

### 17.2 付款任务

- 期望结果：指定收款方收到指定金额，且只支付一次；
- 技术调用成功：银行接口接收付款请求；
- 最终确认源：银行交易状态与内部账；
- 关键风险：超时后重复付款；
- 必需关联：工资单版本、审批票、额度、账户、业务申请号、银行回执。

### 17.3 软件发布

- 期望结果：指定版本部署到指定环境并通过健康检查；
- 技术调用成功：发布任务已创建；
- 最终确认源：部署平台、运行实例和业务健康指标；
- 关键风险：发布任务成功但服务不可用；
- 必需关联：代码版本、构建产物、审批、环境、发布批次、回滚记录。

### 17.4 分析报告

- 期望结果：报告基于指定数据版本完成并通过业务验收；
- 技术调用成功：文件生成并上传；
- 最终确认源：工件仓库与评审结果；
- 关键风险：使用错误数据版本或结论未被采用；
- 必需关联：数据快照、分析版本、评审意见、最终工件和采用记录。

## 18. 评估方式

执行流程自身至少接受以下评估：

1. 能否从任一用户投诉定位到对应运行；
2. 能否找出当时实际使用的输入、工具、规则、权限和版本；
3. 能否区分技术成功、业务受理和业务完成；
4. 能否证明批准、额度和执行之间的因果关联；
5. 能否确认最终结果来自权威业务系统；
6. 能否在不重复真实业务动作的情况下构造重放测试；
7. 能否在记录缺失时明确标注缺口，而不是伪造结论；
8. 能否在不同拓扑中保持标识和上下文连续；
9. 能否对敏感信息实施最小化和访问控制；
10. 能否将真实运行结果反馈到规则、权限和自治等级调整。

## 19. 失败模式

### 19.1 只记录模型调用

后果：可以看到提示词和令牌，却不知道业务动作是否兑现。

### 19.2 只记录最终文本

后果：无法判断答案来自何种输入、工具和规则，也无法定位状态在哪一层丢失。

### 19.3 用布尔值压缩业务状态

后果：`pending_review` 被压成 `success=true`，后续组件误判为完成。

### 19.4 没有最终确认源

后果：运行只能停留在接口层，无法证明任务完成。

### 19.5 所有内容全部记录

后果：敏感数据泄露、存储成本过高、关键信号被噪声淹没。

### 19.6 记录不可关联

后果：每个服务都有日志，但无法从用户投诉走到工具调用和业务回执。

### 19.7 以缺失日志证明动作没发生

后果：可能重复付款、重复发券或重复发布。

### 19.8 重放直接调用真实外部系统

后果：测试过程再次产生业务副作用。

### 19.9 历史运行按新规则解释

后果：无法还原当时的真实条件，错误归因。

### 19.10 探针替代业务判断

后果：观测系统越权修改业务结果或审批结论。

### 20.2 执行前

- [ ] 批准票绑定当前提案；
- [ ] 额度已预留；
- [ ] 实际执行身份和权限已确认；
- [ ] 业务对象、参数和环境已复核；

- [ ] 异步业务申请号已保存；

## 21. 与 Hanerss Skill Framework 的映射

### 21.1 认知基座

- 感知：获取工具、业务系统、回调和用户反馈的事实；
- 记忆：保存运行史、版本和跨运行关联；
- 推理：解释状态、比较期望与实际、定位原因；
- 行动：执行工具调用、查询、补偿和交付；
- 反思：从失败样本生成修复与回归测试；
- 协作：支持多角色、多智能体和跨系统交接；
- 治理：关联审批、额度、权限、记录和规则调整。

### 21.2 拓扑基座

本模式对链式、路由、并行、编排、循环和层级拓扑均提供适配规则，不绑定单一实现。

### 21.3 工程模式基座

本文件作为模式卡的具体填充，包含问题、上下文、触发、输入、输出、工作流、治理、评估、失败模式和关联模式，可登记到工程模式注册表，并进一步包装为可执行 Skill。

## 附录 A：与进度追踪、交接链的边界

三种模式都会保存记录，但回答的问题不同。

| 模式 | 核心问题 | 主要输出 | 典型使用时机 |
|---|---|---|---|
| 进度追踪 | 任务现在做到哪里，下一步从哪里继续 | 当前阶段、已完成项、未完成项、未知项、恢复位置 | 中断恢复、长任务续跑 |
| 交接链 | 下一棒接到了什么，版本、责任和待办是否正确 | 工件清单、版本、回执、验收结果、责任转移记录 | 多人、多智能体、多进程交接 |
| 可观测性执行流程 | 先前发生了什么，为什么发生，结果是否真实兑现 | 运行史、因果链、控制证据、业务结果、重放材料 | 排障、审计、评测、治理调整 |

三者可以共用 `task_id`、`artifact_id` 和 `business_application_id`，但不能互相替代：

- 有进度记录，不代表能证明审批和执行之间的因果关系；
- 有交接清单，不代表能确认外部业务动作是否最终生效；
- 有完整运行史，也不代表接手者已经验收了正确版本的工件；
- 恢复任务时，应先用进度追踪确定恢复位置，再用交接链验收材料，最后用可观测性查清未知结果和历史原因。
