# 工作流可观测性探针

## 1. 文档目的

工作流可观测性探针是一套横切式工程模式，用于在工作流关键位置采集结构化事实，校验因果和版本关系，发现缺失与冲突，并主动补全执行流程的数据。

探针不是单纯的指标看板，也不是只记录模型调用的追踪器。它面向完整业务运行，连接以下对象：

- 用户请求与结构化目标；
- 输入工件和版本；
- 提案、路由和计划；
- 规则、批准、额度和权限；
- 工具调用与原始业务状态；
- 异步回调与跨运行接续；
- 权威业务结果；
- 对外答复和交付物；
- 用户反馈、人工纠正和规则调整。

本模式既可以独立运行，对已有日志、追踪、业务账和工件进行重建；也可以与《可观测性执行流程》交互运行，在执行过程中实时发现并补全数据缺口。

---

## 2. 模式定位

### 2.1 核心定义

工作流可观测性探针，是一个可配置、可插拔、与具体平台解耦的观测单元。每个探针围绕一个明确问题，规定：

- 在什么位置触发；
- 需要哪些输入；
- 采集哪些事实；
- 如何判断完整、冲突、异常或不适用；
- 缺失时向谁请求补全；
- 产生哪些事件、指标、告警和证据引用；
- 是否允许执行继续。

### 2.2 探针与指标的关系

探针负责产生可信数据，指标是对探针输出的聚合视图。

```text
工作流事件
  ↓
探针采集与校验
  ↓
结构化观测事实
  ↓
缺口、冲突、告警、证据
  ↓
指标、评测、看板、调查和治理调整
```

没有可靠探针，指标可能只是在统计不完整或含义错误的数据。

### 2.3 探针不负责的事项

- 不代替业务系统确认最终结果；
- 不自动批准高风险动作；
- 不修改原始业务事实；
- 不把推测写成已发生事实；
- 不为了“记录完整”而保存所有敏感原文；
- 不在重放时重新触发真实付款、发券、发布或删除；
- 不把观测平台自身的成功当作业务成功。

---

## 3. 运行方式

### 3.1 独立运行

探针对既有数据进行离线或准实时重建：

1. 读取日志、追踪、事件、业务账、审批记录、工件和回执；
2. 识别共同标识和版本；
3. 重建运行时间线与因果链；
4. 标记已观测、推导、缺失和冲突；
5. 生成完整性报告、证据索引和调查入口；
6. 对无法关联的数据给出置信度和补录建议。

独立运行适用于遗留系统、事故调查、投诉分析、历史数据迁移和平台选型验证。

### 3.2 交互运行

探针作为执行流程的旁路或内联组件：

1. 接收标准运行事件；
2. 实时校验必需字段和关联关系；
3. 发现缺口后发出补全请求；
4. 对状态丢失、版本冲突、越权和过度承诺发出告警；
5. 按风险策略提出继续、降级、暂停或转人工建议；
6. 在运行关闭时生成证据包和派生指标。

### 3.3 混合运行

实时阶段只执行关键探针，离线阶段执行高成本分析、聚类、根因归类、评测和数据集构建。

### 3.4 采集部署形态

探针可部署为：

- 进程内钩子；
- 工作流中间件；
- 服务旁车；
- 事件总线消费者；
- 集中式采集器；
- 批处理审计任务；
- 业务系统适配器；
- 重放与评测管道。

部署形态可以不同，但事件语义和标识规则必须一致。

## 4. 探针设计原则

### 4.1 从业务问题反推采集内容

先问“任务到底办成没有、由哪里确认、出错后要查什么”，再决定记录字段。不得仅依赖模型开发包自动提供的令牌、耗时和输入输出。

### 4.2 事实、推导、缺失、冲突分开

每条观测结论必须带状态：

| 状态 | 含义 |
|---|---|
| 已观测 | 直接来自可信事件或权威系统 |
| 已推导 | 基于一组已观测事实得出，并保存推导规则 |
| 缺失 | 应出现但未取得，或来源不可用 |
| 冲突 | 两个或多个来源给出不一致事实 |
| 不适用 | 当前场景按配置不要求该数据 |

### 4.3 先关联，再聚合

只有事件能通过任务、运行、追踪、业务申请、工件和控制票据正确关联后，才允许进入指标计算。

### 4.4 原始语义优先

保留工具原始业务状态和响应引用。任何转换都必须可追溯，不能只留下 `success=true`。

### 4.5 完整性是主动检查

探针要知道在某一场景、风险和阶段中“应该出现哪些记录”，并能发现绕过、丢失和未发送。

### 4.6 因果关系显式化

探针需要验证：

- 哪项批准授权了哪项执行；
- 哪份额度被哪次动作预留和消费；
- 哪个子任务产出了哪个工件；
- 哪次失败触发了哪项规则或权限调整；
- 哪个工具返回被用于生成哪段对外答复。

### 4.7 观测系统自身也要被观测

必须监测采集延迟、丢失率、存储失败、结构漂移、访问异常和敏感数据泄露。

### 4.8 风险决定阻断级别

低风险缺口可以记录后继续；高风险治理证据缺失必须暂停。探针输出建议，最终控制权由执行和治理策略决定。

## 5. 标准探针定义结构

```yaml
probe_definition:
  probe_id: PROBE_XXXX
  probe_name: 探针名称
  version: 0.1.0
  status: draft
  purpose: 要回答的问题
  scope: 适用阶段与对象
  trigger: 触发事件或周期
  required_inputs: 必需输入字段
  optional_inputs: 可选输入字段
  sources: 数据来源优先级
  collection_mode: 被动采集 | 主动查询 | 补全请求 | 离线重建
  validation_rules: 校验规则集合
  output_facts: 输出事实集合
  derived_metrics: 可派生指标
  missing_policy: 缺失处理
  conflict_policy: 冲突处理
  severity: 信息 | 提醒 | 警告 | 严重 | 阻断
  blocking: true | false
  privacy_policy: 脱敏与访问要求
  retention_class: 保留等级
  owner: 责任人或责任组
```

每个探针只解决一个清晰问题。复杂探针应拆为多个探针并通过探针组组合。

## 6. 标准事件结构

### 6.1 基础字段

```yaml
observation_event:
  event_id: 全局唯一事件标识
  event_type: 事件类型
  event_time: 业务事件时间
  ingest_time: 采集时间
  sequence_no: 同一运行内序号
  schema_version: 事件结构版本

  task_id: 业务任务标识
  run_id: 本次运行标识
  trace_id: 调用链标识
  span_id: 当前操作标识
  parent_span_id: 直接父操作标识
  link_ids: 非父子关联列表
  business_application_id: 外部业务申请号

  stage: 工作流阶段
  component_id: 组件标识
  actor_id: 实际执行主体
  actor_type: 用户 | 智能体 | 服务 | 人工审批者 | 定时任务
  action: 动作名称

  technical_status: 技术状态
  business_status: 业务状态
  observation_status: 已观测 | 已推导 | 缺失 | 冲突 | 不适用

  input_refs: 输入引用
  output_refs: 输出引用
  evidence_refs: 证据引用
  error_refs: 错误引用

  versions:
    workflow_version: 工作流版本
    prompt_version: 提示版本
    model_version: 模型版本
    policy_version: 规则版本
    tool_version: 工具版本
    artifact_version: 工件版本

  controls:
    approval_ticket_id: 批准票标识
    budget_envelope_id: 额度标识
    permission_snapshot_id: 权限快照标识
    tool_catalog_snapshot_id: 工具可见性快照标识
    idempotency_key: 幂等键

  governance:
    data_classification: 数据分级
    retention_class: 保留等级
    access_scope: 访问范围
    checksum: 内容校验值
    correction_of: 被更正事件标识
```

### 6.2 事件质量要求

- `event_id` 全局唯一；
- `task_id`、`run_id` 在运行内始终存在；
- 事件时间与采集时间分开；
- 状态字段不得只使用单一布尔值；
- 证据引用必须可访问或明确过期；
- 更正事件必须引用原事件；
- 敏感内容优先保存引用、摘要或受控标识；
- 时钟不一致时使用序号、父子关系和业务回执共同排序。

## 7. 关联模型

### 7.1 标识层次

```text
业务任务 task_id
  ├── 运行 run_id
  │     ├── 追踪 trace_id
  │     │     ├── 操作 span_id
  │     │     └── 操作 span_id
  │     └── 工件 artifact_id + artifact_version
  └── 外部业务对象 business_application_id

治理控制
  ├── approval_ticket_id
  ├── budget_envelope_id
  ├── permission_snapshot_id
  └── tool_catalog_snapshot_id
```

### 7.2 标准关系类型

| 关系 | 含义 |
|---|---|
| `parent_of` | 直接父子调用 |
| `linked_to` | 异步、并行、批次或跨追踪关联 |
| `produced_by` | 工件由某个操作产生 |
| `consumed_by` | 批准、额度或输入被某动作消费 |
| `authorized_by` | 动作由某批准票授权 |
| `reserved_from` | 动作从某额度信封预留资源 |
| `confirmed_by` | 结果由某权威来源确认 |
| `triggered_by` | 规则、权限或动作由某事件触发 |
| `supersedes` | 新版本替代旧版本 |
| `compensates` | 当前动作补偿先前动作 |
| `retries` | 当前尝试是对先前尝试的重试 |
| `corrects` | 当前事件更正先前记录 |

### 7.3 关联优先级

1. 业务系统原生唯一编号；
2. 明确传播的任务、运行和追踪标识；
3. 工件、批准和额度引用；
4. 幂等键；
5. 时间、主体和参数的组合匹配；
6. 人工确认。

使用推测性关联时，必须标记置信度，不得冒充确定关系。

## 8. 探针分层

### 第 0 层：运行身份探针

回答“这是谁的哪一次运行”。

### 第 1 层：上下文与版本探针

回答“当时看到了什么、使用了哪一版”。

### 第 2 层：提案与决策探针

回答“为什么选择这条路径、有哪些候选项”。

### 第 3 层：治理控制探针

回答“谁批准、额度如何使用、权限是否有效”。

### 第 4 层：工具与状态保真探针

回答“调用了什么、原始状态有没有被正确传递”。

### 第 5 层：异步与恢复探针

回答“延迟回调、重试、恢复和交接是否接回原任务”。

### 第 6 层：业务结果探针

回答“事情到底办成没有、由哪里确认”。

### 第 7 层：对外承诺探针

回答“系统说的是否超过它能证明的事实”。

### 第 8 层：反馈与演进探针

回答“投诉、纠正、评测和规则调整是否形成闭环”。

### 第 9 层：记录治理探针

回答“记录是否完整、未被篡改、没有泄露、按期保存”。

## 9. 核心探针目录

### 9.1 运行与上下文探针

| 探针 ID | 探针名称 | 触发点 | 核心检查 | 缺失处理 |
|---|---|---|---|---|
| PROBE_RUN_001 | 运行身份连续性 | 运行开始、跨服务、运行关闭 | `task_id`、`run_id`、`trace_id` 是否连续 | 请求补传；无法关联则标记孤儿事件 |
| PROBE_CTX_001 | 输入工件版本 | 上下文固定、交接、执行前 | 实际工件版本是否符合任务要求 | 版本冲突时暂停 |
| PROBE_CTX_002 | 模型与提示版本 | 模型调用 | 是否记录真实使用版本 | 缺失时影响重放评分 |
| PROBE_CTX_003 | 工具可见性快照 | 规划与工具选择前 | 当时可用、被过滤和不可见工具 | 缺失时无法判断“没选”还是“看不见” |
| PROBE_CTX_004 | 规则与权限快照 | 控制校验前 | 是否保存生效规则和权限 | 高风险缺失时阻断 |

### 9.2 提案、路由与计划探针

| 探针 ID | 探针名称 | 触发点 | 核心检查 | 缺失处理 |
|---|---|---|---|---|
| PROBE_PLAN_001 | 提案版本绑定 | 提案形成、批准、执行前 | 批准和执行是否指向同一版提案 | 不一致时阻断 |
| PROBE_PLAN_002 | 路由决策 | 路由发生 | 候选路径、选择理由、规则版本 | 记录缺口，必要时转人工 |
| PROBE_PLAN_003 | 并行分支登记 | 分支创建与聚合 | 分支是否完整登记、是否有遗漏 | 聚合前补全或标记部分结果 |
| PROBE_PLAN_004 | 循环终止条件 | 每次迭代 | 次数、成本、变化和终止原因 | 超限时暂停 |
| PROBE_PLAN_005 | 层级委派边界 | 委派和回收 | 子任务边界、验收和责任主体 | 边界不明时拒绝委派 |

### 9.3 治理控制探针

| 探针 ID | 探针名称 | 触发点 | 核心检查 | 缺失处理 |
|---|---|---|---|---|
| PROBE_GOV_001 | 批准证据匹配 | 控制校验、外部动作前 | 批准主体、对象、范围、版本、有效期 | 高风险缺失或不匹配时阻断 |
| PROBE_GOV_002 | 额度预留与消费 | 预留、执行、释放 | 预留、消费、释放是否闭环 | 超额时阻断；悬挂时告警 |
| PROBE_GOV_003 | 实际执行身份 | 工具调用前 | 计划身份与实际身份是否一致 | 不一致时阻断或转人工 |
| PROBE_GOV_004 | 权限边界 | 工具调用前 | 当前权限是否覆盖对象、动作和环境 | 越权时阻断 |
| PROBE_GOV_005 | 自治等级适配 | 高风险任务开始 | 智能体当前自治等级是否足够 | 不足时降级或人工批准 |
| PROBE_GOV_006 | 控制绕过检测 | 运行关闭 | 应出现的批准、额度、权限记录是否存在 | 严重告警并启动审计 |

### 9.4 工具与状态探针

| 探针 ID | 探针名称 | 触发点 | 核心检查 | 缺失处理 |
|---|---|---|---|---|
| PROBE_TOOL_001 | 工具请求响应完整性 | 工具调用 | 请求、响应、版本、耗时和回执是否齐全 | 请求原始引用或标记不可重放 |
| PROBE_TOOL_002 | 业务状态保真 | 响应转换后 | 原始状态与下游状态是否一致 | 状态丢失时严重告警 |
| PROBE_TOOL_003 | 幂等与重复副作用 | 重试、超时、回调 | 幂等键是否复用，是否重复办理 | 发现风险时暂停重试 |
| PROBE_TOOL_004 | 参数与批准一致性 | 工具调用前后 | 实际参数是否超出批准范围 | 超范围时阻断 |
| PROBE_TOOL_005 | 工具结构漂移 | 响应解析 | 新字段、未知状态、结构变化 | 进入隔离解析并告警 |
| PROBE_TOOL_006 | 回退与替代工具 | 回退发生 | 是否记录回退原因和差异风险 | 需要重新控制校验时触发 |

### 9.5 异步、恢复与交接探针

| 探针 ID | 探针名称 | 触发点 | 核心检查 | 缺失处理 |
|---|---|---|---|---|
| PROBE_ASYNC_001 | 业务申请号稳定性 | 异步受理 | 是否保存稳定外部申请号 | 缺失时禁止盲目重试 |
| PROBE_ASYNC_002 | 回调关联 | 回调到达 | 回调是否接回正确任务和提案 | 无法关联则进入隔离队列 |
| PROBE_ASYNC_003 | 超时查询 | 等待超时 | 是否查询权威系统而非直接重试 | 违规时阻断重试 |
| PROBE_ASYNC_004 | 跨运行恢复 | 新运行接手 | 新旧运行、未决事项和状态是否接续 | 生成补全请求 |
| PROBE_ASYNC_005 | 交接工件验收 | 交接发生 | 工件版本、回执和待办是否完整 | 验收失败时停在交接点 |

### 9.6 业务结果与对外承诺探针

| 探针 ID | 探针名称 | 触发点 | 核心检查 | 缺失处理 |
|---|---|---|---|---|
| PROBE_RESULT_001 | 权威结果确认 | 运行关闭前 | 是否从指定业务系统确认最终结果 | 高风险任务不得关闭为成功 |
| PROBE_RESULT_002 | 期望与实际差异 | 结果确认后 | 每个验收项是否满足 | 生成差异明细 |
| PROBE_RESULT_003 | 接口成功但任务未完成 | 工具结束、结果确认 | 技术成功与业务结果是否分离 | 生成专用异常 |
| PROBE_RESULT_004 | 结果未知保护 | 超时、冲突 | 未知状态是否阻止重复副作用 | 未保护时严重告警 |
| PROBE_COMMIT_001 | 对外承诺一致性 | 答复发送前 | 表达是否超过当前业务状态 | 不一致时阻断答复 |
| PROBE_COMMIT_002 | 工件采用与验收 | 交付后 | 产物是否被使用、接受或创建后续任务 | 记录业务采用事实 |

### 9.7 反馈、评测与演进探针

| 探针 ID | 探针名称 | 触发点 | 核心检查 | 缺失处理 |
|---|---|---|---|---|
| PROBE_FB_001 | 用户反馈关联 | 投诉、评分、人工纠正 | 反馈是否关联到具体运行和阶段 | 无法关联则进入人工匹配 |
| PROBE_FB_002 | 失败样本入集 | 根因确认后 | 输入、预期、版本和模拟响应是否齐全 | 不完整时不可进入回归集 |
| PROBE_EVAL_001 | 回归重放 | 版本变更前 | 新版是否在历史样本上通过 | 未通过时阻止发布建议 |
| PROBE_EVOLVE_001 | 规则调整因果 | 规则或权限变更 | 调整是否有事故、评测或业务依据 | 无依据变更告警 |
| PROBE_EVOLVE_002 | 调整后效果 | 新规则生效后 | 指标是否改善，是否产生副作用 | 触发回滚评审 |

### 9.8 记录治理探针

| 探针 ID | 探针名称 | 触发点 | 核心检查 | 缺失处理 |
|---|---|---|---|---|
| PROBE_REC_001 | 必需事件完整性 | 阶段结束、运行关闭 | 场景要求的事件是否齐全 | 生成缺口清单 |
| PROBE_REC_002 | 顺序与因果一致性 | 事件到达 | 时间、序号、父子和业务关系是否冲突 | 保留冲突，不强行排序 |
| PROBE_REC_003 | 防篡改与更正链 | 写入、读取、导出 | 校验值、更正引用是否有效 | 发现异常立即审计 |
| PROBE_REC_004 | 敏感信息泄露 | 写入前后 | 密码、令牌、证件号是否进入记录 | 阻断写入并隔离 |
| PROBE_REC_005 | 访问权限 | 查询与导出 | 访问者是否只看到必要内容 | 拒绝访问并记录 |
| PROBE_REC_006 | 保留期限 | 周期任务 | 是否按类型保留或删除 | 生成合规任务 |
| PROBE_REC_007 | 采集器健康 | 持续 | 丢失、延迟、积压和存储失败 | 触发降级或暂停策略 |

## 10. 数据补全机制

工作流可观测性探针必须具备主动补全能力，而不是只在看板上显示空值。

### 10.1 缺口类型

| 缺口类型 | 含义 |
|---|---|
| 未生成 | 执行流程没有产生应有事实 |
| 未发送 | 事实已产生，但未发送给探针 |
| 未接收 | 传输或采集失败 |
| 未关联 | 数据存在，但无法接回当前任务 |
| 已过期 | 证据引用失效或已按策略删除 |
| 无权限 | 探针没有读取所需来源的权限 |
| 结构漂移 | 字段或枚举变化导致无法解析 |
| 不适用未声明 | 场景不需要该字段，但没有明确标记 |

### 10.2 补全流程

```text
发现缺口
  ↓
生成 gap_id
  ↓
判断缺口类型和风险
  ↓
向责任组件请求证据、字段或“不适用”声明
  ↓
重新校验
  ├─→ 已补全：关闭缺口
  ├─→ 部分补全：保留剩余项
  └─→ 无法补全：升级告警或阻断
```

### 10.3 补全请求结构

```yaml
gap_request:
  gap_id: 缺口标识
  task_id: 任务标识
  run_id: 运行标识
  probe_id: 发现缺口的探针
  stage: 影响阶段
  missing_fields: 缺失字段列表
  expected_source: 预期来源
  impact: 对调查、治理、结果确认或重放的影响
  severity: 提醒 | 警告 | 严重 | 阻断
  response_deadline: 允许补全时间
  allowed_responses:
    - 提供字段
    - 提供证据引用
    - 声明不适用并给出规则依据
    - 声明无法取得并说明原因
```

### 10.4 补全优先级

1. 业务系统原始回执；
2. 审批、额度和权限系统记录；
3. 执行组件原始事件；
4. 经过校验的中间转换结果；
5. 人工确认；
6. 有置信度的推导。

### 10.5 阻断策略

| 缺口 | 低风险 | 中风险 | 高风险或极高风险 |
|---|---|---|---|
| 模型耗时缺失 | 继续 | 继续并补录 | 继续并补录 |
| 工具原始业务状态缺失 | 告警 | 降级或转人工 | 暂停 |
| 批准票缺失 | 记录 | 暂停或人工确认 | 阻断 |
| 权限快照缺失 | 记录 | 暂停 | 阻断 |
| 最终结果确认缺失 | 标记等待 | 不得关闭成功 | 不得关闭成功并启动对账 |
| 记录器完全不可用 | 本地缓存 | 限制副作用 | 阻断关键动作 |

## 11. 完整性规则

### 11.1 阶段完整性

每个场景配置必须给出阶段到必需事件的映射。

```yaml
required_event_matrix:
  运行开始:
    - 运行身份
    - 目标与结果确认源
  控制校验:
    - 提案版本
    - 批准票
    - 权限快照
  工具执行:
    - 请求引用
    - 原始响应引用
    - 业务申请号
  结果确认:
    - 权威来源
    - 业务结果
    - 回执引用
  运行关闭:
    - 最终状态
    - 对外答复引用
    - 未解决缺口
```

### 11.2 因果完整性

探针检查以下链条是否闭合：

```text
请求
  → 提案
  → 控制决定
  → 实际执行
  → 工具回执
  → 业务结果
  → 对外答复
  → 反馈或纠正
  → 规则与权限调整
```

任一箭头缺少明确引用时，标记为因果缺口。

### 11.3 控制完整性

高风险动作至少需要证明：

- 当前提案被批准；
- 执行参数在批准范围内；
- 额度已预留并正确消费；
- 实际身份拥有相应权限；
- 智能体自治等级覆盖该风险；
- 执行结果已由权威系统确认。

### 11.4 版本完整性

同一运行必须能还原：

- 输入和工件版本；
- 提案版本；
- 工作流版本；
- 规则版本；
- 模型与提示版本；
- 工具版本；
- 事件结构版本。

## 12. 状态保真规则

### 12.1 三层状态模型

```yaml
status_model:
  technical_status: 连接、调用、超时、返回码等技术状态
  acceptance_status: 已接收、已排队、待审核、处理中等受理状态
  business_status: 已完成、已拒绝、部分完成、已撤销、未知等业务状态
```

### 12.2 保真校验

探针比较：

1. 工具原始响应；
2. 适配器解析结果；
3. 工作流内部状态；
4. 对外答复使用的状态；
5. 权威业务系统最终状态。

任何状态升格都必须有新证据。例如从“待审核”变为“已发放”，必须出现审核通过和券实例确认，而不能仅由语言模型改写。

### 12.3 未知状态处理

- 未知枚举进入隔离，不映射为成功；
- 结构漂移触发工具版本和结构版本告警；
- 无法解释时保留原始响应引用；
- 对外表达使用最保守且不误导的模板。

## 13. 派生指标

指标必须注明分母、时间窗口、场景范围和数据完整性。缺少关键探针数据时，指标应标记“不可用”或给出覆盖率，不能默认为零。

### 13.1 业务结果指标

| 指标 | 计算方式 | 用途 |
|---|---|---|
| 真实完成率 | 已确认成功任务数 ÷ 已关闭任务数 | 判断任务是否真正办成 |
| 结果未知率 | 结果未知任务数 ÷ 已进入执行任务数 | 衡量对账和恢复风险 |
| 部分完成率 | 部分完成任务数 ÷ 已关闭任务数 | 发现批量或组合任务问题 |
| 接口成功但任务未完成率 | 技术成功且业务未成功任务数 ÷ 技术成功任务数 | 发现接口层误判 |
| 过度承诺率 | 对外表达高于业务状态的任务数 ÷ 已答复任务数 | 衡量状态解释质量 |
| 补偿率 | 发生补偿的任务数 ÷ 已产生副作用任务数 | 衡量错误动作后果 |
| 业务采用率 | 被采纳工件数 ÷ 已交付工件数 | 观察报告、建议等产物的实际价值 |

### 13.2 过程完整性指标

| 指标 | 计算方式 | 用途 |
|---|---|---|
| 必需事件完整率 | 已取得必需事件数 ÷ 应有事件数 | 判断运行史是否可用 |
| 因果链完整率 | 已建立有效因果关系数 ÷ 应有因果关系数 | 判断是否能解释“为什么发生” |
| 追踪上下文连续率 | 成功传递追踪标识的跨边界次数 ÷ 总跨边界次数 | 衡量跨服务关联能力 |
| 业务申请号覆盖率 | 有稳定业务申请号的异步任务数 ÷ 异步任务数 | 衡量延迟结果可恢复性 |
| 版本快照覆盖率 | 版本字段齐全运行数 ÷ 总运行数 | 衡量历史可解释性 |
| 工具状态保真率 | 原始状态与下游状态一致次数 ÷ 可比较次数 | 发现状态丢失和压缩 |
| 对外答复可追溯率 | 可关联到业务状态和证据的答复数 ÷ 总答复数 | 支持投诉调查 |

### 13.3 治理指标

| 指标 | 计算方式 | 用途 |
|---|---|---|
| 批准证据匹配率 | 批准范围与执行完全匹配次数 ÷ 需批准执行次数 | 发现错版或越范围执行 |
| 额度闭环率 | 完成预留、消费或释放闭环的额度项 ÷ 总额度项 | 发现悬挂额度和超额消费 |
| 权限快照覆盖率 | 有有效权限快照的受控执行数 ÷ 受控执行总数 | 证明当时可做什么 |
| 控制绕过率 | 缺少必需控制但发生执行的次数 ÷ 受控执行总数 | 发现治理漏洞 |
| 自治等级越界率 | 实际风险超过自治等级的执行数 ÷ 总执行数 | 支持渐进承诺调整 |
| 规则调整可追溯率 | 有依据、决定者和生效版本的调整数 ÷ 总调整数 | 支持治理审计 |

### 13.4 可靠性与恢复指标

| 指标 | 计算方式 | 用途 |
|---|---|---|
| 重试率 | 重试尝试数 ÷ 总尝试数 | 观察稳定性和成本 |
| 重复副作用率 | 重复业务动作数 ÷ 有副作用任务数 | 发现幂等和对账缺陷 |
| 回调关联成功率 | 正确接回原任务的回调数 ÷ 总回调数 | 衡量异步关联能力 |
| 恢复成功率 | 正确接续并完成的恢复任务数 ÷ 恢复任务数 | 衡量长任务恢复能力 |
| 平均定位时间 | 从投诉或告警到确定问题阶段的平均时长 | 衡量调查效率 |
| 一次定位率 | 无需跨团队反复查询即可定位的事件数 ÷ 调查事件数 | 衡量证据可用性 |

### 13.5 质量与评测指标

| 指标 | 计算方式 | 用途 |
|---|---|---|
| 人工纠正率 | 被人工修改结果的任务数 ÷ 已评审任务数 | 识别模型或规则弱点 |
| 回归通过率 | 通过样本数 ÷ 回归样本总数 | 判断修改是否有效 |
| 失败复现率 | 能在隔离环境复现的失败数 ÷ 选定失败数 | 衡量证据与重放质量 |
| 根因确认率 | 已确认根因事件数 ÷ 已调查事件数 | 区分表象与根因 |
| 反馈关联率 | 能关联到具体运行的反馈数 ÷ 总反馈数 | 让用户反馈影响下一版 |

### 13.6 成本与性能指标

| 指标 | 计算方式 | 用途 |
|---|---|---|
| 成功任务单位令牌成本 | 总令牌消耗 ÷ 已确认成功任务数 | 将失败尝试成本计入 |
| 成功任务单位计算成本 | 总计算成本 ÷ 已确认成功任务数 | 比较版本和方案 |
| 成功任务端到端耗时 | 从运行开始到业务结果确认的耗时分布 | 不被接口耗时误导 |
| 失败任务耗时 | 失败或未知任务的耗时分布 | 识别反复重试长尾 |
| 探针延迟开销 | 启用探针后新增的端到端耗时 | 控制观测侵入性 |
| 探针存储成本 | 单位任务观测数据量与保留成本 | 优化采样和分层保留 |

### 13.7 记录治理指标

| 指标 | 计算方式 | 用途 |
|---|---|---|
| 敏感字段拦截率 | 写入前被正确识别并处理的敏感字段数 ÷ 检出的敏感字段数 | 衡量泄露防护 |
| 未授权访问率 | 被拒绝或确认违规的访问数 ÷ 总访问数 | 发现日志平台权限问题 |
| 采集丢失率 | 预期事件数与实际接收事件数的差额 ÷ 预期事件数 | 监控探针自身健康 |
| 采集延迟 | 采集时间减业务事件时间的分布 | 发现积压和延迟告警 |
| 更正链完整率 | 有原记录引用的更正数 ÷ 总更正数 | 保证追加式审计 |

## 14. 探针输出

### 14.1 单次运行报告

```yaml
probe_run_report:
  task_id: 任务标识
  run_id: 运行标识
  coverage:
    required_probes: 必需探针数
    completed_probes: 已完成探针数
    coverage_rate: 覆盖率
  facts:
    observed: 已观测事实数
    inferred: 已推导结论数
    missing: 缺失项数
    conflicts: 冲突项数
  result_assessment:
    technical_status: 技术状态
    business_status: 业务状态
    commitment_consistency: 一致 | 不一致 | 无法判断
  governance_assessment:
    approval: 完整 | 缺失 | 冲突 | 不适用
    budget: 完整 | 缺失 | 冲突 | 不适用
    permission: 完整 | 缺失 | 冲突 | 不适用
  gaps: 缺口列表
  alerts: 告警列表
  evidence_index_ref: 证据索引
  replay_bundle_ref: 重放材料引用
  confidence: 整体置信度
```

### 14.2 跨运行聚合报告

- 失败模式聚类；
- 状态丢失热点；
- 控制绕过趋势；
- 工具和版本对比；
- 业务结果与接口结果差异；
- 反馈和纠正集中场景；
- 成本、耗时和重试长尾；
- 自治等级升级或降级建议。

### 14.3 证据索引

证据索引只保存定位信息和访问条件，不必复制全部原始内容。每项证据应包含来源、版本、校验值、保留等级和访问范围。

## 15. 告警与严重度

| 级别 | 含义 | 默认动作 |
|---|---|---|
| 信息 | 正常运行事实或低影响偏差 | 记录，不打断 |
| 提醒 | 数据质量问题，暂不影响安全 | 请求补全 |
| 警告 | 可能影响结果、重放或调查 | 限制关闭或转人工 |
| 严重 | 可能越权、重复副作用、过度承诺或丢失关键证据 | 暂停相关阶段 |
| 阻断 | 明确违反关键治理条件或继续执行可能造成重大损失 | 禁止执行并升级 |

告警必须去重、聚合并关联到具体任务，不得用大量重复告警淹没真正问题。

## 16. 重放证据包

### 16.1 目标

在不重复真实业务动作的情况下，重建当时的判断路径，并验证修改后的系统是否正确处理同一输入。

### 16.2 必需内容

- 原始请求或脱敏后的等价输入；
- 输入工件版本；
- 当时规则、权限和工具清单快照；
- 模型、提示、工作流和工具版本；
- 提案和控制决定；
- 工具原始响应或受控模拟响应；
- 权威业务结果；
- 当时对外答复；
- 预期正确结果；
- 不允许执行的真实副作用列表。

### 16.3 重放类型

| 类型 | 目的 |
|---|---|
| 只读重建 | 查看已经发生的路径，不重新运行程序 |
| 转换层重放 | 验证状态字段能否完整传递 |
| 决策层重放 | 验证新规则、提示或模型的判断 |
| 工作流重放 | 验证阶段、路由、重试和关闭逻辑 |
| 回归批量重放 | 用数据集比较多个版本 |

### 16.4 安全规则

- 外部工具使用保存响应或模拟适配器；
- 禁止访问真实付款、发券、删除和发布接口；
- 明确标记测试身份和隔离环境；
- 输出与旧版比较，但不改写历史记录；
- 记录重放使用的新版本和结果。

## 18. 不同拓扑下的探针策略

### 18.1 链式探针

重点检查阶段连续性、状态保真和输入输出版本。任一环节缺失都可能使后续判断失去依据。

### 18.2 路由探针

重点检查候选路径、过滤原因、规则版本和路由结果。避免只看到“走了哪条路”，看不到“为什么没有走另一条路”。

### 18.3 并行探针

重点检查分支登记、完成状态、聚合规则、被忽略分支和部分失败。所有分支共享任务标识，但拥有独立操作标识。

### 18.4 编排探针

重点检查计划图与实际执行图的差异、节点跳过、依赖满足、重排、回退和关闭条件。

### 18.5 循环探针

重点检查迭代次数、每次变化、停止条件、成本上限和无效重复。循环必须能够解释“为什么继续”和“为什么停止”。

### 18.6 层级探针

重点检查委派边界、父子责任、子任务工件、交接验收和父任务最终组合结果。

## 19. 探针自身的可靠性与安全

### 19.1 采集失败

- 本地缓冲并记录缓冲水位；
- 重试必须去重；
- 高风险场景触发降级或暂停；
- 恢复后补传并生成迟到事件标记；
- 不得因补传改变原业务事件时间。

### 19.2 重复和乱序

- 使用 `event_id` 去重；
- 使用业务事件时间、序号和因果关系排序；
- 无法确定时保留多种可能顺序并标记冲突；
- 不为美化时间线而删除异常事件。

### 19.3 时钟偏差

- 记录来源时钟和采集时钟；
- 使用单调序号或逻辑时钟补充；
- 跨系统对账以业务回执和因果链接为准。

### 19.4 高基数字段

- 对用户、任务和工件标识采用索引与分层存储；
- 不把无限增长的原始标识直接作为所有指标标签；
- 指标用于聚合，明细用于追踪，二者分开。

### 19.5 敏感数据

- 写入前检测并脱敏；
- 令牌、密码和私钥默认拒绝采集；
- 对需要比对的账户等对象使用受控令牌化标识；
- 原始敏感证据置于更严格的业务系统或证据库；
- 查询、导出和分享均记录访问审计。

### 19.6 防篡改

- 关键事件追加式保存；
- 事件带校验值；
- 更正通过新事件完成；
- 关键控制和业务回执可使用独立存储或签名；
- 定期检查事件连续性和校验链。

## 20. 平台适配原则

本模式不绑定具体可观测性平台、模型平台、日志系统、指标系统或追踪实现。

适配器至少应提供：

```text
写入结构化事件
传播追踪上下文
查询运行与事件
关联外部业务对象
写入和查询证据引用
发出缺口与告警
执行主动业务结果查询
导出重放证据包
控制访问与保留策略
```

已有监控体系可以继续使用。新增能力的重点是补齐智能体决策、控制证据、业务结果和跨运行关联，而不是替换所有基础设施。

## 21. 评估探针是否有效

### 21.1 单条真实投诉测试

选择一条真实投诉，检查是否能沿着以下路径完成调查：

```text
用户反馈
  → 对外答复
  → 当时业务状态
  → 工具原始返回
  → 提案和控制记录
  → 实际执行身份
  → 权威业务结果
```

记录在哪一段断裂，并区分：

- 没有生成；
- 生成但没有采集；
- 已采集但无法关联；
- 有记录但含义错误；
- 权威业务结果本身缺失。

### 21.2 探针质量指标

| 指标 | 说明 |
|---|---|
| 缺口发现率 | 已知缺口中被探针发现的比例 |
| 误报率 | 实际完整却被判断为缺失或冲突的比例 |
| 补全成功率 | 发出补全请求后成功关闭的缺口比例 |
| 关联准确率 | 事件被关联到正确任务、运行和业务对象的比例 |
| 调查缩短时间 | 启用探针前后平均定位时间差 |
| 重放可用率 | 选定运行中能形成有效重放包的比例 |
| 探针开销 | 延迟、计算、存储和网络开销 |
| 隐私事件数 | 探针导致的敏感数据暴露或越权访问事件 |

### 21.3 验收门槛

探针上线前至少通过：

- 正常完成；
- 等待审核；
- 明确拒绝；
- 工具超时但业务成功；
- 工具超时且业务未生效；
- 重复回调；
- 工件版本错误；
- 批准票错版；
- 额度不足；
- 权限不足；
- 记录器故障；
- 敏感字段误写；
- 对外答复过度承诺；
- 跨运行恢复；
- 重放隔离。

## 22. 反模式

### 22.1 把探针当成打印语句

只输出非结构化文本，无法稳定关联、校验和聚合。

### 22.2 只看模型调用

缺少审批、额度、权限和业务结果，无法回答事情是否真正办成。

### 22.3 所有场景使用同一套必需字段

导致低风险场景负担过重，高风险场景又缺少关键证据。应使用场景配置和风险分级。

### 22.4 缺失值默认填零或成功

掩盖采集故障和未知状态，产生错误指标。

### 22.5 只保留当前状态

无法解释状态如何变化，也不能判断谁、何时、依据什么作出决定。

### 22.6 只用时间接近做关联

容易把并发任务、批次和重复尝试串错。时间只能作为弱证据。

### 22.7 探针拥有业务写权限

观测组件越权修改订单、付款或审批，破坏职责边界。

### 22.8 为追求完整而记录所有原文

扩大敏感信息暴露面，增加成本和噪声。

### 22.9 看板正常就认为业务正常

探针和监控本身正常，不代表业务结果已经兑现。

### 22.10 用新版本重写历史

历史运行必须按当时版本解释，新版结果应作为独立重放记录。

## 23. 验收清单

### 23.1 探针定义

- [ ] 每个探针只回答一个清晰问题；
- [ ] 已定义触发点、输入、来源、规则和输出；
- [ ] 已定义缺失、冲突和不适用处理；
- [ ] 已定义严重度和是否阻断；
- [ ] 已定义隐私和保留策略；
- [ ] 已指定责任人和版本。

### 23.2 数据与关联

- [ ] 任务、运行、追踪、操作和业务申请号能够区分；
- [ ] 批准、额度、权限和执行有显式因果关系；
- [ ] 工件和版本可追踪；
- [ ] 原始业务状态被保留；
- [ ] 跨进程、跨队列和跨运行能继续关联；
- [ ] 推导关系有规则和置信度。

### 23.3 补全与阻断

- [ ] 探针能生成结构化缺口请求；
- [ ] 执行流程能返回证据、不适用或无法取得；
- [ ] 高风险关键缺口具有阻断策略；
- [ ] 探针不可用时有降级规则；
- [ ] 未解决缺口进入最终报告。

### 23.4 结果与重放

- [ ] 最终结果来自权威业务系统；
- [ ] 对外承诺与业务状态可比较；
- [ ] 能生成隔离的重放证据包；
- [ ] 外部副作用在重放时被替代；
- [ ] 反馈能关联到具体运行；
- [ ] 规则调整能关联到真实依据。

### 23.5 安全与治理

- [ ] 敏感内容写入前处理；
- [ ] 查看权限按角色最小化；
- [ ] 关键记录追加式保存；
- [ ] 更正不覆盖原记录；
- [ ] 采集器自身有健康监测；
- [ ] 记录缺失不被解释为动作未发生。

## 24. 与 Hanerss Skill Framework 的映射

### 24.1 认知基座

- 感知：采集模型、工具、业务系统、回调和用户反馈；
- 记忆：保存运行史、证据、版本和跨运行链接；
- 推理：校验状态、因果、完整性和冲突；
- 反思：归类失败、构建数据集、执行回归；
- 协作：连接业务、工程、质量、审计和治理角色；
- 治理：检查批准、额度、权限、自治等级和记录管理。

### 24.2 拓扑基座

探针可挂载到链式、路由、并行、编排、循环和层级拓扑，并针对不同拓扑使用不同完整性规则。

### 24.3 工程模式基座

本文件是一个可独立登记的工程模式，与《可观测性执行流程》互为关联模式。它可以进一步包装为通用探针 Skill，也可以按行业和业务节点派生专用探针配置。

## 附录 A：观测信号分类

工作流可观测性探针可以采集多种信号，但不同信号承担不同职责。

| 信号 | 回答的问题 | 典型内容 | 局限 |
|---|---|---|---|
| 日志 | 某个局部组件做过什么 | 错误、状态变化、参数摘要、处理结果 | 单独看时难以连接完整任务 |
| 追踪 | 一次请求经过了哪些步骤 | 调用链、操作起止、父子关系、跨服务传播 | 不自动证明最终业务结果 |
| 指标 | 一批运行呈现什么趋势 | 完成率、未知率、重试率、成本、延迟 | 聚合后会丢失单次运行细节 |
| 评测 | 当前版本是否达到质量要求 | 正确性、合规性、语气、回归通过率 | 依赖可靠样本和预期结果 |
| 重放证据 | 当时为什么作出这个决定，修改后是否改对 | 历史输入、版本、决定、工具响应、预期结果 | 必须隔离真实外部副作用 |
| 业务回执 | 事情是否真正兑现 | 订单、券实例、银行状态、发布健康、验收记录 | 可能位于独立业务系统，需要额外关联 |

探针应把这些信号通过共同标识和证据引用连接起来，而不是要求某一种信号承担全部职责。

## 附录 B：调查顺序

排查“接口全成功但任务没完成”时，建议从上往下查：

1. **先看业务结果。** 到权威业务系统确认目标是否兑现。
2. **再看工作流过程。** 找出任务停在哪一阶段、哪个状态被错误解释、哪项控制或回调缺失。
3. **最后看局部组件。** 检查模型、工具适配器、消息队列、数据库、网络和存储等组件。

只从组件监控开始，容易得到“所有接口都正常”的结论，却漏掉业务结果没有发生。只从最终结果开始而没有运行史，又无法判断应该修改工具、状态转换、提示规则、审批流程还是业务系统。

## 附录 C：指标解释约束

- 成功与失败任务的耗时、成本和重试应分开统计；
- 少数反复重试的长尾任务应单独展示，不能只看平均值；
- 产物被采用不等于产物正确，采用率应配合抽检或业务评测；
- 数据覆盖率不足时，指标必须同时显示覆盖范围；
- 指标变化只能提示调查方向，不能自动替代根因确认；
- 规则、模型或工具版本变化后，趋势分析应按版本分组。
