# 工作流可观测性探针：补全执行证据与改进指标

> 版本：0.1.0。适用于智能体、自动化任务、数据分析、代码变更、业务审批及传统软件工作流。可独立用于诊断，也可与《执行流程》交互运行。

## 1. 目标与边界

探针用于回答： 1. 实际发生了什么？ 2. 偏差最早出现在哪里？ 3.
当前结果是否有足够证据支持？ 4. 哪些数据可以支持下一次流程设计变更？

探针优先复用已有日志、状态记录、工具返回、业务数据和人工审核记录。必要时才执行经过授权的只读查询或对照检查。探针负责补全证据与诊断，不直接替代业务验收，也不应仅凭单一指标自动修改生产流程。

## 2. 两种运行方式

### 独立运行

用户提供工作流说明、日志、任务记录或失败案例。探针先列出已有证据，再识别缺口，提出最少量的补查动作，最后输出时间线、指标、可能根因和待验证假设。缺少数据时明确标记"未知"，不臆测补齐。

### 与执行流程交互运行

执行流程在输入整理、节点交接、工具调用、异常处理、业务验收和发布后观察等位置调用探针。探针返回补充证据、缺失字段、异常标记和指标结果；执行流程据此决定继续、补查、暂停、转人工或进入设计复盘。

探针可以发起只读补查，但任何有副作用的操作、生产配置变更和高风险动作仍须由执行流程的权限与审批规则控制。

## 3. 最小事件模型

每条事件建议记录以下字段：

  字段               说明
  ------------------ --------------------------------------------------------
  事件编号           唯一事件标识
  任务编号           关联一次完整运行
  工作流编号与版本   确认当时使用的设计
  场景编号           识别业务场景及配置
  节点编号           定位业务节点
  事件类型           开始、结束、工具调用、状态变更、验收、异常、人工介入等
  事件时间           发生时间，尽可能统一时区和精度
  尝试次数           区分首次执行和重试
  输入输出引用       指向安全存储中的原文、结构化数据或摘要
  工具与对象引用     识别实际调用的工具和目标对象
  状态与错误         记录结果状态、错误类型和原因
  证据引用           指向支持判断的原始材料
  版本信息           模型、提示词、工具、规则、知识源或配置版本
  成本与耗时         实测值及其单位
  隐私与权限标签     限制访问和传播范围

事件模型应允许按场景扩展。不要把不同含义塞入同一个字段。敏感输入默认记录引用或脱敏摘要，不应无差别保存完整内容。

## 4. 探针执行步骤

### 第一步：确定观测对象

明确要诊断的工作流、场景、时间范围、版本和问题。区分单次故障诊断、批量质量评估、版本对照和上线后观察。

### 第二步：盘点已有证据

优先检索： - 任务输入和用户目标； - 工作流与配置版本； -
节点开始、结束和状态变化； - 检索命中、资料来源及时间； -
模型输入输出的安全摘要； - 工具名称、参数摘要、返回值和错误； -
关键业务状态和外部副作用； - 业务验收结果、人工修正和投诉； -
重试、超时、回滚和人工接手记录。

每项证据标记来源、时间、关联任务、可信状态和是否完整。

### 第三步：重建时间线

按任务编号和事件时间排列事件，补齐节点之间的交接关系。识别： -
缺失事件； - 状态不可能迁移； - 节点未执行却被标记成功； -
工具返回与下游参数不一致； - 旧数据或旧规则被继续使用； -
重试后重复产生外部副作用； - 验收只检查技术状态，未检查业务目标。

如果无法确定事件先后或关联关系，应输出不确定区间，不强行还原。

### 第四步：定位首个偏差

从最终错误往前追踪，找到最早出现的可证实偏差，并区分： -
**事实**：日志、数据或工具返回直接证明的内容； -
**推断**：依据事实提出的解释； -
**待验证假设**：需要新查询或对照实验才能判断的原因。

例如：工具返回的对象编号正确，但下游调用使用了不同编号，这是可验证的交接偏差；"模型注意力不足"则只是未经验证的解释，不能直接作为根因结论。

### 第五步：补全证据

按风险和成本从低到高执行： 1. 读取已有日志和结构化状态； 2.
检查来源、时间、版本和字段完整性； 3. 对照上下游输入输出； 4.
只读查询权威业务明细； 5. 用同一输入重放非生产流程； 6.
对照旧版和候选版； 7. 必要时请求人工核验。

每次补查都记录目的、查询范围、结果引用和成本。不得为了让结论完整而无限扩张查询。

### 第六步：计算指标并解释

只计算定义清楚、分母明确、数据覆盖足够的指标。展示时间范围、样本量、缺失率和计算口径。小样本或高缺失时，明确说明结果不稳定。

### 第七步：输出诊断包

输出： - 观测范围和版本； - 事实时间线； - 证据清单与缺口； -
首个偏差点； - 影响范围； - 指标值、分母、趋势和限制； -
根因假设及验证状态； - 建议的最小改动； - 需要执行流程采取的下一步动作。

## 5. 指标目录

指标不应全部默认启用。先选与业务目标、风险和可采集性直接相关的指标。

### 5.1 业务结果指标

  -------------------------------------------------------------------------------
  指标                    建议口径                       适用场景
  ----------------------- ------------------------------ ------------------------
  业务成功率              通过业务验收的任务数 ÷         所有工作流
                          已验收任务数                   

  关键错误率              存在关键业务错误的任务数 ÷     资金、数据、代码和审批
                          已验收任务数                   

  结果可追溯率            关键结论均能关联来源的任务数 ÷ 分析、检索、审核
                          已完成任务数                   

  验收证据完整率          具备全部必需验收证据的任务数 ÷ 高风险业务
                          应验收任务数                   

  人工修正率              需人工修改结果的任务数 ÷       内容生成、分析、配置
                          已完成任务数                   

  副作用发生率            发生非预期外部影响的任务数 ÷   有写操作的工作流
                          执行任务数                     
  -------------------------------------------------------------------------------

### 5.2 执行稳定性指标

  --------------------------------------------------------------------------------------
  指标                                建议口径
  ----------------------------------- --------------------------------------------------
  节点成功率                          成功节点尝试数 ÷ 已结束节点尝试数

  端到端完成率                        正常结束的任务数 ÷ 启动任务数

  重试率                              至少发生一次重试的节点数 ÷ 执行节点数

  超时率                              超时任务数 ÷ 启动任务数

  回滚率                              发生回滚的任务数 ÷ 执行任务数

  人工接手率                          需要人工介入的任务数 ÷ 启动任务数

  无进展循环率                        达到循环上限但未产生新证据或有效状态变化的任务数 ÷
                                      循环任务数
  --------------------------------------------------------------------------------------

必须说明统计对象是"任务""节点"还是"调用"，不可混用分母。

### 5.3 证据与交接指标

  指标               建议口径
  ------------------ -------------------------------------------------------
  关键字段完整率     已具备的必需字段数 ÷ 应有必需字段数
  来源可验证率       可验证来源的关键字段数 ÷ 全部关键字段数
  交接一致率         上游输出与下游实际输入一致的交接次数 ÷ 已检查交接次数
  资料新鲜度达标率   未超过场景规定时效的资料数 ÷ 已使用资料数
  证据冲突率         存在未解决冲突的任务数 ÷ 已检查任务数
  观测覆盖率         已采集的必需事件数 ÷ 应采集的必需事件数

### 5.4 效率与成本指标

  指标           建议口径
  -------------- -------------------------------------------------------
  端到端耗时     任务完成时间减去启动时间
  节点耗时       节点结束时间减去开始时间
  单任务成本     任务相关模型、工具、计算及人工成本之和
  每次成功成本   总执行成本 ÷ 业务验收通过任务数
  无效调用率     未产生有效证据、状态变化或业务价值的调用数 ÷ 总调用数
  评审增益       有评审路径相对无评审路径新增发现的有效问题数及严重度
  评审额外耗时   启用评审路径的耗时减去可比的无评审路径耗时

不同场景应按风险设定阈值。没有可靠成本数据时，应报告缺失，不要假装计算完整成本。

## 6. 诊断规则：指标异常不等于根因

  -------------------------------------------------------------------------------------------------------
  观测现象                     优先核查                                           不应直接得出的结论
  ---------------------------- -------------------------------------------------- -----------------------
  成功率下降                   输入分布、业务规则、资料时效、版本变化、验收口径   直接换更强模型

  重试率升高                   工具稳定性、参数、超时、依赖和幂等                 一律增加重试

  交接一致率下降               状态存储、字段映射、摘要重写和版本兼容             一律增加智能体

  证据完整率下降               采集点、权限、数据源和日志丢失                     直接放宽验收

  耗时增加                     各节点耗时分布、循环、并行等待和外部服务           直接删掉所有评审

  成本上升                     调用次数、上下文长度、重复工具和无效循环           只压缩提示词

  多路数据一致但业务结果错误   原始明细、业务定义和验收条件                       继续增加相同汇总查询

  新模型上线后错误减少         分场景对照、严重错误、回归集和置信范围             立即撤掉所有防护
  -------------------------------------------------------------------------------------------------------

先定位最早偏差，再提出根因假设。只有获得新证据或通过对照实验，才能提升根因结论的可信度。

## 7. 对照验证与架构演化

当团队考虑增加评审、合并工具、改变路由、调整循环或升级模型时，探针应支持可比的验证：

1.  固定一组代表性任务，包括旧失败案例和原本成功案例；
2.  尽量保持输入、权限、业务规则和测试环境一致；
3.  对比旧方案与候选方案；
4.  同时观察业务正确性、关键错误、证据完整性、耗时、成本和人工接手量；
5.  对高风险错误单独统计，不让总体平均值掩盖严重问题；
6.  记录样本量、数据缺口和不可比因素；
7.  输出是否支持保留、修复、重组、简化或退役的证据。

模型升级或提示词调整不应自动触发删除防护。只有在可比测试证明某个环节不再提供足够增益、且后续验收仍能发现重要问题时，才考虑简化。

## 8. 与执行流程的交互协议

建议统一以下请求与返回结构，具体实现可按项目扩展。

### 执行流程向探针发起请求

``` yaml
probe_request:
  request_id: PROBE_REQ_0001
  run_id: RUN_YYYYMMDD_0001
  workflow_id: WORKFLOW_0001
  workflow_version: 0.1.0
  scope:
    node_ids: []
    time_range: null
  question: "定位失败节点并补齐业务验收证据"
  required_evidence: []
  permissions:
    read_only: true
  budget:
    max_queries: 10
    max_duration_seconds: 60
```

### 探针返回

``` yaml
probe_result:
  request_id: PROBE_REQ_0001
  status: complete
  evidence_refs: []
  missing_evidence: []
  timeline_refs: []
  metrics: []
  first_deviation:
    node_id: null
    evidence_ref: null
    confidence: unknown
  hypotheses:
    - description: null
      supporting_evidence: []
      contradicting_evidence: []
      status: unverified
  recommended_next_step: "补查、继续、暂停、转人工或进入设计复盘"
  limitations: []
```

"建议下一步"不是执行授权。执行流程应依据风险、权限和业务规则决定是否采纳。

## 9. 安全、隐私和数据质量

-   只采集诊断目的所需的最少数据；
-   对个人信息、密钥、凭据和敏感业务字段脱敏；
-   使用访问控制、保留期限和审计记录；
-   默认保存证据引用与摘要，完整原文按需受控访问；
-   区分缺失、未知、零值和不适用；
-   检查时间戳、重复事件、时钟偏差、版本缺失和采样偏差；
-   指标应同时呈现分子、分母、时间范围和口径；
-   不把模型生成的解释当作原始证据。

## 10. 可复用的探针检查单

``` text
[ ] 已明确观测目标、时间范围和工作流版本
[ ] 已关联任务编号、节点编号和业务对象
[ ] 已盘点输入、输出、工具返回和验收记录
[ ] 已重建实际执行时间线
[ ] 已区分事实、推断和待验证假设
[ ] 已定位最早可证实的偏差
[ ] 已记录缺失、冲突和过期证据
[ ] 指标有清楚定义、分母、样本量和时间范围
[ ] 已检查业务正确性，而非只检查技术成功
[ ] 已评估成本、延迟、人工接手和副作用
[ ] 已提出有边界的补查或对照验证
[ ] 未将诊断建议当成生产操作授权
```

## 11. 完成标准

一次探针诊断在观测范围明确、主要事件已关联、事实与假设已区分、关键缺口已列出、指标口径可复查、建议动作有证据依据时，可以标记为完成。若数据不足，应以"部分完成"结束，并明确哪些结论尚不能成立。

探针的价值不是制造更多日志，而是让运行事实能够解释业务结果、支持设计决策，并进入下一轮验证。
