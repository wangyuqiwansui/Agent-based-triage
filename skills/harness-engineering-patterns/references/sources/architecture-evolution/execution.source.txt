# 执行流程：基于证据的工作流设计与演化

> 版本：0.1.0。适用于智能体、自动化流程、数据分析、代码修改、业务审批、知识检索及传统软件流程。

## 1. 目标与原则

本文件规定任务如何进入执行、如何处理失败、如何验收结果，以及如何依据运行证据调整工作流。它不绑定具体模型、平台、工具或业务领域；每个场景应补充自己的规则、权限、输入输出和验收条件。

核心原则： - 先定位偏差，再决定改法。"回答不对"只是现象，不是根因。 -
必须成立的业务条件、权限和精确参数由程序保证；不确定的调查方向允许根据证据调整。 -
技术步骤成功不等于业务目标达成。 -
采用最小有效改动，并以旧失败案例和原本成功案例共同验证。 -
不允许智能体仅凭自我分析直接修改生产配置。

## 2. 核心对象

-   **任务**：有目标、范围和完成条件的一次工作。
-   **业务节点**：有独立输入、处理、输出、风险和验收条件的工作单元。
-   **工作流**：业务节点及其依赖、分支、循环和交接关系。
-   **业务证据**：用于证明输入、判断、操作和结果是否符合目标的材料。
-   **运行记录**：描述某次任务实际发生的事件、版本、工具结果和验收结果。
-   **设计决定**：保留、修复、重组、简化或退役某项安排的可追溯决定。

## 3. 通用执行步骤

### 第一步：界定任务

明确业务目标、涉及对象、时间范围、排除项、成功条件、失败条件，以及是否涉及资金、权限、个人信息、生产环境或不可逆操作。必要条件不清晰时先澄清，不得猜测高风险信息。

输出：任务说明、范围边界、成功条件和风险等级。

### 第二步：整理输入与证据

为关键输入记录来源、时间、可信度、时效和缺失项。区分用户提供的事实、工具返回的数据、按规则计算的结果和未经验证的推断。

关键编号、金额、权限标识和状态应保存为结构化字段，并保留来源。不得只把它们写入自然语言摘要，再让后续步骤重新生成。

证据缺失、过期或冲突时，进入补查、澄清、暂停或人工核查分支。

### 第三步：选择最小可行结构

  -----------------------------------------------------------------------------------------
  任务特征                     优先结构                注意事项
  ---------------------------- ----------------------- ------------------------------------
  步骤固定、依赖明确           链式或程序化工作流      程序保证顺序和前置条件

  按输入选择不同路径           路由                    路由依据应可说明、可测试

  子任务独立且可同时进行       并行                    明确汇总规则、超时和部分失败处理

  多步骤存在依赖、分支和汇合   编排                    维护统一任务状态

  需要依据新证据反复调查       有上限的循环            设置轮数、成本、停止条件和人工升级

  任务需要分层拆解             层级                    明确各层责任和交付物
  -----------------------------------------------------------------------------------------

不要为了使用某种架构而增加组件。只有确实需要独立职责、权限或并行工作时，才增加角色或智能体。

### 第四步：划分模型判断与程序约束

优先由程序保证： - 前置条件、固定顺序和不可绕过的审批门； -
精确参数、对象标识、金额和状态的保存传递； -
权限、额度、幂等、防重复和回滚边界； -
数据格式、类型、必填字段和范围检查； - 停止条件与审计记录。

模型可辅助完成意图理解、证据整理、候选方案比较、调查方向选择、澄清问题和结果解释。模型推断不得自动视为事实；高风险操作需由规则、工具结果或授权人员确认。

### 第五步：定义节点契约

每个关键节点至少定义： 1. 稳定节点编号，如 `NODE_0001`； 2. 节点目标；
3. 输入字段、来源、时效与格式； 4. 前置条件； 5.
处理责任：程序、模型、人工或混合； 6. 输出结构和证据引用； 7.
可检验的成功条件； 8. 失败处理：重试、补查、回滚、暂停或转人工； 9.
权限边界； 10. 必须记录的事件和指标。

下游必需的精确值应通过结构化状态传递，不要让模型从对话中重新填写。

### 第六步：执行与状态管理

每次执行创建任务编号，记录工作流版本、配置版本、输入引用和启动时间。节点状态建议统一为：待执行、执行中、成功、失败、已跳过、等待补充、等待审批、已取消、已回滚。

状态变化应记录时间和原因。重试必须区分首次执行与后续尝试；重试前确认操作是否幂等，防止重复付款、重复提交或重复修改。

### 第七步：按异常类型处理

  异常                 优先动作
  -------------------- ----------------------------------------
  输入缺失或含糊       澄清或补充输入
  资料过期、检索错误   修复来源、索引或更新机制
  规则解释错误         校正规则来源、定义和判断条件
  精确参数错绑         从可信状态读取，校验字段和目标对象
  工具调用失败         检查权限、参数、依赖、超时和服务状态
  多系统结果冲突       保留冲突证据，按权威来源和业务规则核验
  验收条件不足         增补直接对应业务目标的检查
  高风险或不可逆操作   暂停、审批、限额或回滚
  多轮调查无新证据     达到上限后停止并转人工

不得把重试或增加评审当成通用解法。循环必须设置最大轮数、时间或成本上限、停止条件和人工升级路径。

### 第八步：业务验收

至少检查： - 结果是否满足业务规则； - 关键证据是否齐备、可信且足够新； -
操作对象和参数是否正确； - 权限、审批和限制是否满足； -
是否存在未解决冲突或副作用； - 输出是否完整、可追溯。

多路结果一致，只能证明被比较的字段在这些来源间相符，不能自动证明业务结论正确。应补足与业务目标直接相关的明细和规则。

### 第九步：输出与交接

输出结论、关键证据、未解决事项、执行状态和后续动作。失败时说明失败节点、已完成部分、是否产生外部副作用，以及恢复或人工处理建议。

区分供人阅读的任务叙述、供程序继续执行的结构化状态、供审计复查的证据引用；三者有关联但不能互相替代。

### 第十步：基于证据演化

当失败、业务规则变化、工具集变化、模型升级或成本变化时： 1.
还原实际运行路径； 2. 找到最早出现偏差的节点； 3.
区分根因、伴随现象和最终影响； 4.
复核原设计当时要解决的问题及其理由是否仍成立； 5. 选择最小改动； 6.
用旧失败案例和原本成功案例对照测试； 7. 小范围发布并观察； 8.
保留、回滚或继续调整； 9. 记录决定依据、验证结果和重新评估条件。

改动类型： - **保留**：原设计仍有价值； -
**修复**：补足错误或缺失的条件； -
**重组**：调整职责、状态和交接方式； -
**简化**：删除冗余步骤、工具或重复检查； -
**退役**：证据表明不再需要时移除旧机制。

## 4. 工作流可观测性探针的接入点

与《工作流可观测性探针》配合时，在以下位置补齐运行数据： -
输入整理：来源、时效、缺失与冲突； -
节点开始和结束：耗时、状态、重试和异常； -
模型判断：使用的证据、候选选择及理由； -
工具调用：工具名称、参数摘要、返回状态和目标对象； -
状态交接：关键字段来源、完整性和一致性； -
业务验收：规则引用、证据引用和判定结果； -
异常复盘：调用链和首个偏差点； -
发布后观察：成功率、成本、延迟、人工接手量和副作用。

无法采集的数据应标记为"未采集"或"未知"，不得将估算伪装成实测值。

## 5. 场景配置清单

每个场景应单独配置： - 场景名称、编号和版本； - 业务目标与范围； -
输入输出契约； - 业务规则及权威来源； - 节点清单和依赖； -
风险等级与权限边界； - 必须满足的前置条件； - 成功、失败和转人工条件； -
必须采集的事件； - 验收样例和回归用例； - 负责人、审批人和变更记录。

通用流程提供骨架，场景配置决定具体节点、规则和指标。不要把不同场景强行塞入同一条固定流程。

## 6. 与框架基座的挂载

遵循"注册表是源头、矩阵是视图、工程模式是可挂载资产、技能是执行化产物"的原则： -
认知引用：感知、记忆、推理、行动、反思、协作、治理； -
拓扑引用：链式、路由、并行、编排、循环、层级； -
业务节点：使用稳定编号； -
工程模式：引用模式编号，不把模式名称写死在流程逻辑中； -
技能：将稳定且重复使用的流程封装； -
评估：关联验收用例、回归用例和风险检查。

建议先稳定编号，再逐步完善定义。新增分类不得破坏既有引用关系。

## 7. 运行记录模板

``` yaml
run_id: RUN_YYYYMMDD_0001
workflow_id: WORKFLOW_0001
workflow_version: 0.1.0
scenario_id: SCENARIO_0001
status: running
started_at: null
finished_at: null
input_refs: []
nodes:
  - node_id: NODE_0001
    attempt: 1
    status: pending
    input_refs: []
    output_refs: []
    evidence_refs: []
    started_at: null
    finished_at: null
    error_code: null
    retry_reason: null
business_validation:
  status: pending
  rule_refs: []
  evidence_refs: []
  findings: []
human_handoff:
  required: false
  reason: null
change_decision:
  action: none
  rationale: null
  validation_refs: []
```

模板字段可按场景扩展，但同一字段不可表达多种语义。

## 8. 完成标准

一次任务只有在必需节点完成或按规则跳过、关键输出可追溯、业务验收通过、高风险异常已暂停或转交、外部副作用已明确、必要审计记录已保存时，才可标记为业务完成。

一次工作流改造只有在旧失败案例得到处理、原有成功案例未明显退化、安全与权限条件未削弱、成本和延迟经过比较、发布与回滚条件明确、修改理由可追溯时，才可标记为验证完成。
