# 1. 文档目的

本文件定义“审批门”的通用执行流程。

审批门位于一项具体动作真正生效之前。它不负责完成业务动作，而是根据动作主体、参数、目标资源、环境、影响、可逆性和当前策略，将动作路由到以下路径之一：

1. 自动放行；
2. 补充事实或证据；
3. 人工审批；
4. 明确拒绝；
5. 升级到更高责任层级；
6. 中止并等待外部条件恢复。

审批门的核心约束是：

> 一次批准只授权当前提案、当前策略、当前身份、当前范围以及限定的时间和次数。

批准不得被解释为对相似动作、后续批次、其他对象、其他环境或未来会话的永久授权。

# 2. Hanerss 框架映射

## 2.1 认知基座

审批门以治理为主认知，关联行动、协作、记忆和反思。

| 认知引用 | 在本模式中的职责 |
|---|---|
| COG_GOVERNANCE | 分配行动权、解释策略、绑定批准范围、执行拒绝与升级 |
| COG_ACTION | 将已经批准的提案转化为受控外部动作 |
| COG_COLLABORATION | 在提案发起者、审批者、执行器、业务所有者之间交接责任 |
| COG_MEMORY | 持久化等待状态、批准回执、策略快照和恢复位置 |
| COG_REFLECTION | 在恢复、执行失败或对象漂移后重新检查原判断是否仍成立 |

## 2.2 拓扑基座

审批门以路由为主拓扑，并由链式、编排和层级结构共同完成。

| 拓扑引用 | 在本模式中的职责 |
|---|---|
| TOP_ROUTING | 在自动放行、补证、人审、拒绝和升级之间分流 |
| TOP_CHAIN | 按“准备提案—审批—重新验证—执行—归档”顺序推进 |
| TOP_ORCHESTRATION | 协调证据服务、策略引擎、审批系统、执行器和账本 |
| TOP_HIERARCHY | 根据金额、敏感度、对象规模和责任范围选择审批层级 |

## 2.3 工程模式定位

本模式是可复用的治理工程模式，可挂载到：

- 付款、退款、薪资、采购和报销；
- 生产发布、数据变更、命令执行和基础设施操作；
- 邮件发送、群发消息、合同签署和外部公告；
- 数据导出、权限变更、隐私处理和模型调用；
- 折扣、补偿、积分、优惠券和客户权益变更；
- 策略、阈值、白名单和免审规则变更；
- 任何会改变外部世界、且责任超过自动权限的动作。

# 3. 模式目标

审批门需要同时实现以下目标：

1. 在高风险动作生效之前设置明确责任边界；
2. 让进入人审的提案已经具备可判断所需的事实；
3. 将自然语言中的“同意”编译成范围有限的机器可验证许可；
4. 防止批准对象、参数、工具版本、环境或策略在批准后被替换；
5. 在等待和恢复之间保存可重建的运行状态；
6. 在真正执行前重新验证批准和业务条件；
7. 防止重复执行、批准重放、越权批准和审批绕行；
8. 记录实际执行效果，支持审计、补偿和责任追踪；
9. 与工作流可观测性探针共享稳定标识和事件契约；
10. 允许不同业务场景通过配置扩展，而不改动核心安全语义。

---

# 4. 非目标

审批门不承担以下职责：

- 不把所有不确定性都交给人；
- 不要求审批人替系统查对象、算金额或补齐基础字段；
- 不记录或暴露模型的完整内部推理过程；
- 不以一次审批替代身份认证、权限校验和职责分离；
- 不以审批结果替代执行前业务条件重检；
- 不保证外部系统永远成功；
- 不允许探针、日志系统或审计系统代替有权限的审批者签字；
- 不把“有人点过按钮”视为有效的人类监督；
- 不把相似动作自动合并为同一批准范围；
- 不允许通过先放宽策略、再执行原本受限动作的方式绕过治理。

# 5. 核心原则

## 5.1 先做到可审，再进入审批

提案进入审批之前，至少满足：

- 执行对象已经确定；
- 关键证据已经取得；
- 重要差异已经标出；
- 外部影响已经说明；
- 可计算的金额、数量和范围已经算清；
- 可逆性、补偿方式和后续步骤已经说明；
- 适用策略已经确定，或策略冲突已经显式暴露；
- 审批者能够仅凭审批材料理解自己正在批准什么。

缺少以上条件时，状态应为“补证”“澄清”“策略冲突”或“停止”，而不是“等待审批”。

## 5.2 批准绑定具体提案

批准必须绑定：

- 提案摘要；
- 策略摘要；
- 审批者身份；
- 审批者角色；
- 批准对象范围；
- 生效环境；
- 有效时间；
- 可使用次数；
- 审批条件；
- 决定产生时的关键版本。

任何会改变提案语义的变化，都必须生成新提案和新摘要。

## 5.3 最窄授权

审批门只发放完成当前动作所需的最窄许可。

例如：

- 批准一张发票，不等于批准该供应商未来所有付款；
- 批准一个发布工件，不等于批准同分支的后续构建；
- 批准一个收件人列表，不等于批准发送给新增收件人；
- 批准一次数据导出，不等于批准持续访问数据源；
- 批准一次策略例外，不等于修改长期策略。

## 5.4 检查与使用分离

批准完成后，执行器仍需在真正调用外部系统之前重新检查：

- 决定是否为允许；
- 提案摘要是否一致；
- 策略摘要是否一致；
- 回执是否过期；
- 使用次数是否耗尽；
- 审批者集合是否满足角色与人数要求；
- 业务前置条件是否仍成立；
- 对象、余额、库存、版本、人员状态等是否变化；
- 幂等键是否已经被消费；
- 当前执行环境是否与批准环境一致。

## 5.5 原始记录不可覆盖

提案、策略快照、审批决定、回执、恢复检查和实际效果均采用追加式记录。

修正错误时创建新版本或撤销记录，不直接覆盖历史事实。

## 5.6 规则变更本身也受治理

任何扩大自动权限、提高免审阈值、放宽审批角色或关闭重检的变更，必须作为独立高风险动作进入审批门。

# 6. 角色与责任

| 角色 | 主要责任 | 不得承担的责任 |
|---|---|---|
| 提案发起者 | 表达业务意图、提供初始上下文 | 不得自行扩大审批范围 |
| 执行代理 | 规范化动作、收集证据、计算影响、形成提案 | 不得伪造审批决定，不得在批准后修改提案 |
| 证据提供者 | 提供对象状态、业务凭证、版本和核验结果 | 不得替审批者作价值判断 |
| 策略引擎 | 匹配规则、计算路线、确定审批角色和限制 | 不得绕过显式拒绝规则 |
| 审批协调器 | 建票、分配审批人、收集决定、计算人数和角色条件 | 不得把无效签字计入通过 |
| 审批者 | 判断例外、权衡后果、承担角色责任 | 不得批准超出自身权限的范围 |
| 执行适配器 | 重新验证回执、原子消费许可、执行外部动作 | 不得只凭“已批准”文本直接执行 |
| 业务所有者 | 定义业务前置条件、补偿和责任归属 | 不得跳过治理策略 |
| 策略所有者 | 维护策略、阈值、角色和版本 | 不得为单笔动作临时放宽规则后自行批准 |
| 审计与探针 | 重建链路、发现缺口、补全可验证数据、输出指标 | 不得签发批准回执或修改原始决定 |

# 7. 稳定标识

所有对象必须使用稳定标识。建议最小集合如下：

| 标识 | 含义 |
|---|---|
| `trace_id` | 跨系统关联的一条治理链路 |
| `run_id` | 一次工作流运行 |
| `intent_id` | 一次业务意图 |
| `proposal_id` | 一份动作提案 |
| `proposal_version` | 提案版本 |
| `proposal_digest` | 规范化提案摘要 |
| `policy_id` | 策略标识 |
| `policy_version` | 策略版本 |
| `policy_digest` | 策略快照摘要 |
| `approval_request_id` | 审批请求 |
| `approval_decision_id` | 单个审批决定 |
| `approval_receipt_id` | 可供执行器验证的治理回执 |
| `checkpoint_id` | 等待与恢复检查点 |
| `execution_id` | 一次执行尝试 |
| `idempotency_key` | 防止重复外部效果的幂等键 |
| `effect_id` | 一项实际外部效果 |
| `supplement_id` | 探针补全数据包 |

标识不得使用可变业务名称替代。名称可变，标识必须稳定。

### 提案规范化要求

提案摘要必须基于确定性序列化结果计算。规范化时至少做到：

- 字段顺序稳定；
- 数值单位统一；
- 金额精度固定；
- 对象集合排序稳定；
- 空值和缺失值语义不同；
- 时间统一到带时区格式；
- 参数别名归一；
- 不把请求时间、展示顺序等无关易变字段纳入摘要；
- 将工具版本、环境、对象版本和资源范围纳入摘要；
- 敏感值可以使用摘要或安全引用，但必须能在执行前验证。

# 9. 风险输入模型

审批门不得仅根据工具名称判断风险。至少评估以下维度：

| 风险维度 | 示例 |
|---|---|
| 动作主体 | 用户、代理、服务账户、外部系统 |
| 委托链 | 谁授权谁、授权是否仍有效 |
| 动作类型 | 读取、写入、删除、发送、付款、发布、授权 |
| 目标资源 | 单个对象、批次、全量数据、生产环境 |
| 对象数量 | 1 个、100 个、10 万个 |
| 金额和价值 | 单笔金额、批次总额、累计暴露 |
| 数据敏感度 | 公开、内部、机密、个人信息、受监管数据 |
| 外部可见性 | 内部草稿、客户可见、公开发布、不可撤回通知 |
| 可逆性 | 可撤销、可补偿、部分可逆、不可逆 |
| 新颖度 | 常规动作、首次对象、首次工具、首次账户变更 |
| 环境 | 测试、预生产、生产、跨区域 |
| 时间压力 | 常规、紧急、窗口即将关闭 |
| 策略变更 | 是否会扩大后续自动权限 |
| 历史异常 | 近期拒绝、欺诈信号、失败率、绕过尝试 |
| 业务前置条件 | 余额、库存、对象状态、合约、合规限制 |

风险评估输出不得只是一个分数，还应包含触发规则、关键理由和未决项。

# 10. 路由结果

审批门标准路由结果如下：

| 路由 | 适用条件 | 后续动作 |
|---|---|---|
| 自动放行 | 明确低风险、规则充分、前置条件完整 | 签发机器回执并进入重新验证 |
| 补充证据 | 对象不清、证据缺失、事实冲突、状态过期 | 返回补证任务，不进入审批队列 |
| 人工审批 | 事实基本清楚，但责任和影响超过自动权限 | 生成审批卡并持久化等待 |
| 明确拒绝 | 命中禁止规则、越权、不可接受风险 | 终止当前提案并记录原因 |
| 升级审批 | 当前角色无权决定或影响超出本层级 | 重新计算责任人和人数要求 |
| 等待外部条件 | 依赖窗口、余额、工单、监管状态尚未满足 | 保存检查点并在条件变化后重新评估 |

路由优先级建议为：

```text
明确拒绝
  > 策略冲突或证据不足
  > 升级审批
  > 人工审批
  > 自动放行
```

任何硬拒绝规则不得被较低优先级规则覆盖。

# 11. 审批卡结构

审批卡面向责任判断，不是完整运行日志。建议分为以下区域：

## 11.1 动作摘要

- 准备执行什么；
- 由谁发起；
- 使用什么身份和工具；
- 在什么环境生效。

## 11.2 对象和范围

- 对象标识；
- 对象数量；
- 金额或数据规模；
- 目标环境；
- 外部可见性。

## 11.3 关键变化

优先显示与上一次、基准版本或常规状态相比的变化，例如：

- 收款账户变化；
- 人员集合变化；
- 金额变化；
- 发布工件变化；
- 权限范围扩大；
- 收件人增加；
- 数据敏感度提高；
- 策略阈值放宽。

## 11.4 核验结果

- 已验证事实；
- 证据来源；
- 数据时间；
- 冲突和例外；
- 尚未解决但允许人工判断的风险。

## 11.5 影响与可逆性

- 执行后会发生什么；
- 是否可撤销；
- 补偿成本；
- 失败时可能影响的对象和金额；
- 是否会产生法律、财务、客户或生产影响。

## 11.6 批准范围

- 仅哪一项动作；
- 仅哪些对象；
- 仅哪个环境；
- 仅哪个工具版本；
- 有效期；
- 使用次数；
- 附加条件。

## 11.7 建议与责任

- 代理建议；
- 建议依据；
- 所需审批角色；
- 是否需要多人会签；
- 是否禁止发起者自批。

# 12. 状态机

## 12.1 标准状态

| 状态值 | 含义 |
|---|---|
| `draft` | 提案草稿，尚未完成规范化 |
| `preparing` | 正在确认对象、参数、证据和影响 |
| `evidence_incomplete` | 缺少关键证据，不能进入审批 |
| `policy_conflict` | 多条策略冲突或适用规则不明确 |
| `ready_for_gate` | 提案已达到可路由条件 |
| `auto_allowed` | 被策略自动放行，尚未执行 |
| `pending` | 已进入人工审批，尚未满足人数或角色条件 |
| `partially_approved` | 已收到部分有效决定 |
| `allowed` | 已满足批准条件并签发回执 |
| `rejected` | 被审批者或策略拒绝 |
| `expired` | 请求或回执过期 |
| `invalidated` | 提案、策略或关键状态变化导致旧批准失效 |
| `revalidating` | 恢复后正在重新检查当前事实 |
| `executing` | 正在执行外部动作 |
| `succeeded` | 动作完成且效果已核对 |
| `failed` | 执行失败，尚未完成补偿或升级 |
| `compensating` | 正在进行撤销、冲正或其他补偿 |
| `compensated` | 补偿完成 |
| `escalated` | 已转交更高责任层级或人工处置 |
| `closed` | 运行已收口并归档 |

## 12.2 关键转移约束

```text
draft
  → preparing

preparing
  → evidence_incomplete
  → policy_conflict
  → ready_for_gate

ready_for_gate
  → auto_allowed
  → pending
  → rejected
  → escalated

pending
  → partially_approved
  → allowed
  → rejected
  → expired
  → invalidated

allowed 或 auto_allowed
  → revalidating

revalidating
  → executing
  → evidence_incomplete
  → invalidated
  → expired
  → rejected

executing
  → succeeded
  → failed

failed
  → compensating
  → escalated
  → closed

compensating
  → compensated
  → escalated

succeeded 或 compensated 或 rejected 或 expired
  → closed
```

不允许从 `pending` 直接跳到 `executing`。

# 13. 标准执行流程

## 13.1 阶段一：接收业务意图

输入：

- 用户指令；
- 上游业务事件；
- 定时任务；
- 其他代理的委托；
- 恢复后的未完成运行。

动作：

1. 创建 `trace_id`、`run_id` 和 `intent_id`；
2. 记录发起者身份和委托链；
3. 区分“查询建议”和“改变外部状态”；
4. 判断是否进入治理范围；
5. 冻结原始意图引用，避免后续上下文覆盖。

输出：标准化业务意图。

## 13.2 阶段二：规范化动作

动作：

1. 选择具体动作类型；
2. 明确工具、版本和环境；
3. 将自然语言参数转换为规范化参数；
4. 展开默认值和隐式范围；
5. 明确对象集合；
6. 计算对象、数量、金额和数据范围；
7. 识别是否包含策略变更或权限扩大。

输出：动作提案草稿。

## 13.3 阶段三：确认对象与版本

动作：

1. 解析每个目标对象的稳定标识；
2. 读取对象当前版本；
3. 记录对象摘要；
4. 拒绝仅凭名称或模糊描述执行；
5. 对批量对象生成确定性清单；
6. 对动态查询保存查询条件和结果快照；
7. 确认对象是否存在、是否可操作、是否受锁定或监管限制。

输出：已确认的对象集合。

## 13.4 阶段四：收集证据

动作：

1. 根据动作类型加载证据清单；
2. 查询业务状态、主数据、合同、工单、账户、版本和历史记录；
3. 对高风险变化执行独立核验；
4. 记录来源、版本、采集时间和有效期；
5. 标记缺失、冲突、过期和低可信证据；
6. 构建证据包摘要。

输出：证据包。

## 13.5 阶段五：计算差异和影响

动作：

1. 与基准版本、上一次成功动作或策略基线比较；
2. 识别新增、删除、替换和范围扩大；
3. 计算金额、对象数、数据量和潜在损失；
4. 判断可逆性和补偿成本；
5. 确认外部可见性和不可撤回后果；
6. 将关键变化排序，优先展示最需要人判断的差异。

输出：差异清单、影响说明和可逆性说明。

## 13.6 阶段六：检查可审条件

检查：

- 对象是否明确；
- 证据是否完整；
- 影响是否已说明；
- 差异是否已突出；
- 可逆性是否已说明；
- 策略是否可确定；
- 审批人是否能够理解批准范围。

不满足时：

- 生成补证任务；
- 请求澄清；
- 进入策略冲突处理；
- 或明确停止。

满足时：进入策略评估。

## 13.7 阶段七：策略匹配与风险路由

动作：

1. 加载当前生效策略；
2. 生成不可变策略快照；
3. 匹配硬拒绝规则；
4. 匹配自动放行规则；
5. 计算所需审批角色、人数和层级；
6. 应用职责分离、自批限制和代理审批规则；
7. 确定有效期、使用次数和恢复前重检项；
8. 输出路由决定和触发理由。

输出：策略快照和路由结果。

## 13.8 阶段八：生成审批卡

当路由为人工审批时：

1. 生成面向决策的审批卡；
2. 绑定提案摘要和策略摘要；
3. 显示关键差异、证据、影响和批准范围；
4. 隐藏与判断无关的冗长过程；
5. 对敏感信息进行最小披露；
6. 生成审批请求标识。

输出：审批请求。

## 13.9 阶段九：分配审批者

动作：

1. 根据角色而不是个人姓名查找候选人；
2. 验证候选人的当前权限和任职状态；
3. 检查利益冲突和职责分离；
4. 禁止发起者、执行者或策略修改者在被禁止时自批；
5. 处理代理、代班和升级关系；
6. 记录分配理由；
7. 设置超时和升级路线。

输出：审批者分配结果。

## 13.10 阶段十：持久化等待状态

等待人工决定前，必须保存：

- 运行标识；
- 当前提案和摘要；
- 当前策略和摘要；
- 审批请求；
- 已收到的决定；
- 尚缺的角色；
- 有效期；
- 恢复节点；
- 业务前置条件；
- 工作流状态版本；
- 幂等和重放保护信息。

等待不得仅存在于模型上下文、单个进程内存或临时网页请求中。

## 13.11 阶段十一：接收审批决定

对每个决定执行：

1. 验证审批者身份；
2. 验证审批者角色；
3. 验证决定所绑定的审批请求；
4. 验证请求尚未过期或失效；
5. 验证审批者未被撤权；
6. 验证职责分离；
7. 记录允许、拒绝、附条件允许或请求补充；
8. 对重复决定进行幂等处理；
9. 不将模糊聊天语句自动解释为长期授权。

输出：单个审批决定。

## 13.12 阶段十二：计算会签结果

动作：

1. 统计有效身份和角色；
2. 检查是否满足全部必需角色；
3. 检查人数要求；
4. 检查是否要求不同身份；
5. 检查是否存在拒绝或撤回；
6. 检查附加条件是否相容；
7. 生成最终治理决定。

可能结果：

- 继续等待；
- 允许；
- 拒绝；
- 失效；
- 升级；
- 重新生成提案。

## 13.13 阶段十三：签发治理回执

仅在满足策略条件时签发回执。

回执必须包含：

- 最终决定；
- 提案摘要；
- 策略摘要；
- 审批决定引用；
- 生效范围；
- 有效期；
- 使用次数；
- 条件；
- 回执摘要和可信签名。

回执存入可信存储，不依赖调用方自行保存的未验证副本。

## 13.14 阶段十四：恢复运行

恢复时：

1. 读取最新工作流状态；
2. 校验恢复请求与 `run_id`；
3. 读取当前提案、当前策略和当前业务状态；
4. 不直接从暂停点后的工具调用继续；
5. 进入统一的“执行前重新验证”节点。

## 13.15 阶段十五：执行前重新验证

至少验证：

```text
回执决定为允许
且回执提案摘要等于当前提案摘要
且回执策略摘要等于当前策略摘要
且当前时间未超过有效期
且使用次数未耗尽
且审批者集合仍满足规则
且业务前置条件仍成立
且对象版本、范围和环境未漂移
且幂等键未被使用
```

任一项失败时不得执行。

失败后根据原因：

- 重新收集证据；
- 重新生成提案；
- 重新审批；
- 明确拒绝；
- 升级人工处置。

## 13.16 阶段十六：原子消费许可

在执行外部动作之前，执行器应在可信存储中原子完成：

1. 锁定或比较回执版本；
2. 再次确认回执可用；
3. 将使用次数加一；
4. 写入幂等键；
5. 创建执行尝试记录；
6. 防止两个并发执行同时消费同一张一次性回执。

若无法保证原子性，则不得把一次性批准用于高风险动作。

## 13.17 阶段十七：执行受控动作

执行器仅使用提案中已批准的：

- 工具；
- 工具版本；
- 环境；
- 参数；
- 对象集合；
- 金额和数量；
- 身份；
- 时间窗口。

执行器不得在运行时自行扩大范围或补加对象。

## 13.18 阶段十八：核对实际效果

动作完成后：

1. 从外部系统读取结果；
2. 计算实际效果摘要；
3. 与请求效果摘要比较；
4. 记录部分成功、重复、超额、遗漏和异常；
5. 保存外部引用；
6. 更新业务状态；
7. 触发补偿或升级条件。

只有实际效果与批准范围一致，才可标记成功。

## 13.19 阶段十九：失败与补偿

根据动作类型执行：

- 自动重试；
- 查询外部状态后决定是否重试；
- 冲正、撤销、回滚或停止后续批次；
- 限制损失范围；
- 转交人工；
- 生成事件报告。

任何重试不得重新消费已成功的对象，也不得绕过原批准范围。

## 13.20 阶段二十：归档与学习

归档内容：

- 原始意图；
- 提案各版本；
- 证据包；
- 策略快照；
- 审批请求和决定；
- 治理回执；
- 等待与恢复记录；
- 执行尝试；
- 实际效果；
- 补偿结果；
- 探针补全包及其采纳结果；
- 最终状态和关闭原因。

后续可以基于长期数据评估哪些动作应继续人审、哪些规则可以收紧或放宽，但任何策略变更必须走独立治理流程。

# 14. 治理回执验证规则

执行器应实现等价于以下语义的验证：

```text
可授权 =
  回执决定为允许
  且回执未被撤销
  且当前提案摘要与回执绑定摘要一致
  且当前策略摘要与回执绑定摘要一致
  且当前时间不晚于回执有效期
  且回执使用次数小于使用上限
  且当前执行身份、工具、环境和对象范围均在批准范围内
  且审批者集合满足角色、人数和职责分离规则
  且全部强制业务前置条件仍成立
```

验证失败必须返回结构化原因，例如：

- `proposal_digest_mismatch`；
- `policy_digest_mismatch`；
- `receipt_expired`；
- `usage_limit_exhausted`；
- `approver_role_invalid`；
- `business_precondition_changed`；
- `environment_mismatch`；
- `tool_version_mismatch`；
- `target_scope_changed`；
- `receipt_revoked`；
- `idempotency_key_consumed`。

这些原因用于流程路由和探针诊断，不应用模糊错误文本代替。

# 15. 提案漂移处理

## 15.1 必须生成新提案的变化

以下变化默认属于语义变化：

- 新增或删除对象；
- 金额、数量或范围变化；
- 收款账户、目标地址、收件人、数据目的地变化；
- 工具或工具版本变化；
- 生产与测试环境切换；
- 权限范围扩大；
- 条件、时间窗口或执行顺序变化；
- 关键业务前置条件变化；
- 策略版本变化；
- 可逆性变化；
- 外部可见性变化。

发生后：

1. 旧提案标记为已替代或失效；
2. 生成新提案和新摘要；
3. 计算差异；
4. 重新路由；
5. 不沿用旧批准。

## 15.2 可不改变提案摘要的变化

仅与展示相关、且不影响动作语义的变化可以不改变摘要，例如：

- 排版；
- 语言表达优化；
- 不参与执行的注释；
- 审批卡视觉布局；
- 与安全无关的排序展示。

是否属于非语义变化应由规范化规则明确，不由运行时临时判断。

# 16. 多人会签与层级审批

## 16.1 常见会签模式

| 模式 | 说明 |
|---|---|
| 单角色单人 | 任一具有指定角色的人批准即可 |
| 多角色全部满足 | 每个指定角色至少一人批准 |
| 同角色多人 | 同一角色需要两个不同身份批准 |
| 阶段式审批 | 先业务确认，再资金或风险确认 |
| 条件升级 | 超过阈值后增加更高层角色 |
| 否决优先 | 任一硬否决立即终止 |
| 独立复核 | 第二审批者不得复用第一审批者的身份或直接下属关系 |

## 16.2 决定冲突

当不同审批者给出冲突决定时：

- 存在明确拒绝时，默认不签发允许回执；
- 附条件允许之间条件冲突时，转入澄清或升级；
- 角色不匹配的同意不计入人数；
- 过期后到达的决定只保留审计记录，不改变状态；
- 审批者撤回决定时，已签发但尚未消费的回执应按策略撤销或重新计算。

# 17. 等待、恢复与并发

## 17.1 持久化要求

等待状态必须支持：

- 进程重启；
- 服务迁移；
- 审批等待数小时或数天；
- 多审批者并发签字；
- 重复回调；
- 网络超时；
- 恢复请求重放；
- 策略版本变化；
- 对象状态变化。

## 17.2 并发控制

建议使用：

- 状态版本比较；
- 条件写入；
- 事务锁；
- 原子计数；
- 唯一幂等键；
- 消息去重；
- 回执消费记录。

## 17.3 恢复原则

恢复不是继续执行旧上下文，而是：

```text
加载检查点
  → 读取当前事实
  → 验证提案与策略
  → 重检业务条件
  → 验证回执
  → 原子消费许可
  → 执行动作
```

---

# 18. 自动放行

自动放行不是“没有治理”。它仍应：

1. 生成完整提案；
2. 匹配明确规则；
3. 保存策略快照；
4. 记录自动放行原因；
5. 签发受限机器回执；
6. 设置有效期和使用次数；
7. 在执行前重新验证；
8. 记录实际效果；
9. 接受探针审计。

自动放行规则应满足：

- 业务边界稳定；
- 对象和金额可计算；
- 风险低且可补偿；
- 历史数据支持；
- 不涉及高敏感个人权益；
- 不命中首次变化、异常账户或新环境等条件；
- 有持续监控和撤回机制。

---

# 19. 明确拒绝

硬拒绝适用于：

- 法律或政策禁止；
- 无法验证身份；
- 关键证据缺失且无法补充；
- 对象范围超出任何可授权边界；
- 审批者试图批准自身不具备权限的动作；
- 请求绕过职责分离；
- 请求使用失效、过期或被撤销回执；
- 提案摘要与当前动作不一致；
- 试图放宽策略后立即执行受益动作；
- 已发现欺诈、账户劫持或其他不可接受风险。

拒绝结果应包含可解释原因、适用规则和允许的后续路线。

---

# 20. 策略变更的审批门

策略变更提案至少包含：

- 当前规则；
- 新规则；
- 差异；
- 将新增自动放行的动作规模；
- 历史模拟结果；
- 最坏影响；
- 回滚方案；
- 生效范围；
- 生效时间；
- 观察期；
- 所需治理角色和风险角色。

策略变更者不得单独批准自己提出的放宽方案。

对以下变更建议采用更高等级审批：

- 提高金额阈值；
- 减少审批人数；
- 允许自批；
- 延长回执有效期；
- 增加回执使用次数；
- 关闭执行前重检；
- 扩大默认工具权限；
- 增加长期白名单；
- 降低数据敏感度分级；
- 允许跨环境复用批准。

---

# 21. 与工作流可观测性探针的交互

## 21.1 独立运行

执行流程可以在没有探针的情况下独立运行，但必须自行保存最小治理证据：

- 提案；
- 策略快照；
- 审批决定；
- 回执；
- 检查点；
- 执行效果；
- 状态转移事件。

缺少探针时，执行流程不得降低安全条件。

## 21.2 交互运行

探针通过以下方式补全执行数据：

1. 订阅标准事件；
2. 检查标识关联和字段完整性；
3. 从可信事件、快照和账本重建缺失事实；
4. 生成补全包；
5. 将补全包提交给执行流程；
6. 执行流程验证补全来源、时效和冲突；
7. 明确记录采纳、部分采纳或拒绝；
8. 需要改变提案语义时生成新提案，而不是静默覆盖。

## 21.3 权限边界

探针不得：

- 将缺失审批推断为已批准；
- 生成或签发治理回执；
- 修改审批者决定；
- 直接执行外部动作；
- 将推测值写成原始事实；
- 覆盖源系统记录；
- 以指标良好为由绕过审批。

## 21.4 交互事件

建议事件：

- `probe_gap_detected`；
- `probe_supplement_requested`；
- `probe_supplement_ready`；
- `probe_supplement_accepted`；
- `probe_supplement_partially_accepted`；
- `probe_supplement_rejected`；
- `probe_control_suggestion`。

控制建议只作为输入，由审批门依据策略决定是否采纳。

# 24. 失败处理

| 失败 | 处理 |
|---|---|
| 对象解析失败 | 返回澄清，不得进入审批 |
| 证据过期 | 重新采集并重算提案 |
| 策略冲突 | 转交策略所有者或使用明确优先级规则 |
| 审批者无权限 | 决定无效，重新分配 |
| 回执过期 | 重新审批或重新路由 |
| 提案漂移 | 旧回执失效，生成新提案 |
| 策略变化 | 重新匹配策略，旧回执默认失效 |
| 恢复状态缺失 | 停止执行并进入人工恢复 |
| 并发消费回执 | 仅一个成功，其余拒绝 |
| 外部调用超时 | 先查询外部状态，再决定重试 |
| 部分成功 | 逐对象核对，执行补偿或人工处置 |
| 实际效果超出范围 | 立即停止后续动作并升级事件 |
| 探针补全冲突 | 不覆盖源数据，记录冲突并请求确认 |

# 25. 反模式

## 25.1 只有一句“是否继续”

问题：审批者看不到对象、差异、证据、影响和批准范围。

## 25.2 证据不足也送人审

问题：把代理尚未完成的调查工作推给人。

## 25.3 批准后继续改参数

问题：人批准的对象和实际执行对象不一致。

## 25.4 只绑定审批请求编号

问题：请求编号不证明提案内容未变化，必须绑定摘要。

## 25.5 批准可以无限复用

问题：一次点头变成长期授权。

## 25.6 审批后直接调用工具

问题：忽略等待期间的对象、策略和业务状态变化。

## 25.7 只检查模型上下文中的“已批准”

问题：上下文可丢失、被污染或无法审计。

## 25.8 只在审批门检查，执行器不检查

问题：无法防止检查与使用之间的漂移。

## 25.9 高频弹窗造成审批疲劳

问题：审批者机械点击，监督失去意义。

## 25.10 代理先改策略再批准动作

问题：通过治理绕行扩大自身权限。

## 25.11 探针直接修补原始记录

问题：观测系统成为不可见的事实修改者。

## 25.12 审批通过就认为执行成功

问题：批准只允许动作，不证明外部效果符合预期。

---

# 26. 最小可用实现

最小实现至少包含：

1. 动作提案和确定性摘要；
2. 证据完整性检查；
3. 策略快照；
4. 自动、人审、补证和拒绝四路路由；
5. 审批者身份与角色校验；
6. 提案摘要和策略摘要绑定；
7. 有效期和一次性使用限制；
8. 持久化等待状态；
9. 恢复后的重新验证；
10. 原子消费回执；
11. 幂等执行；
12. 实际效果记录；
13. 标准事件输出；
14. 审计查询能力。

缺少第 6、8、9 或 10 项时，不建议用于高风险生产动作。

# 27. 验收标准

## 27.1 功能验收

- 同一提案在满足策略时能够正确自动放行或进入人审；
- 多人会签未满足前不能签发允许回执；
- 无权限审批者的决定不计入通过；
- 提案任一语义字段变化后旧回执失效；
- 策略版本变化后旧回执按规则失效；
- 回执过期后执行器拒绝执行；
- 一次性回执不能被并发消费两次；
- 恢复时会重新检查业务前置条件；
- 部分成功能够生成可核对的实际效果记录；
- 探针补全包可被采纳、部分采纳或拒绝，并保留记录。

## 27.2 安全验收

- 发起者不能绕过职责分离；
- 审批者不能批准超出角色权限的范围；
- 执行器不接受未签名、已撤销或来源不可信的回执；
- 工具版本、环境和对象范围与批准不一致时拒绝执行；
- 规则变更不能由受益代理单独批准；
- 所有高风险执行均可追溯到有效回执。

## 27.3 恢复验收

- 服务重启后能够恢复等待状态；
- 重复审批回调不会重复计数；
- 重复恢复请求不会重复执行；
- 外部调用超时后能先查状态再决定重试；
- 检查点损坏时系统选择停止，而不是猜测继续。

## 27.4 可观测验收

- 每个关键阶段均有事件；
- 事件可通过 `trace_id`、`run_id` 和对象标识关联；
- 提案、策略、回执和实际效果摘要可比对；
- 审批等待时间、失效率、漂移率和绕过尝试可计算；
- 数据缺口可由探针形成补全包；
- 补全包不覆盖原始记录。

# 28. 示例：工资清单在批准后变化

## 28.1 原提案

```yaml
proposal_id: PROP-PAYROLL-001
proposal_version: 1
scope:
  subject_count: 798
  amount: 13706097.00
proposal_digest: sha256:原摘要
```

两位审批者完成会签，回执绑定 `sha256:原摘要`。

## 28.2 变化后的提案

新增两名人员，金额增加 38444.00：

```yaml
proposal_id: PROP-PAYROLL-002
proposal_version: 1
scope:
  subject_count: 800
  amount: 13744541.00
proposal_digest: sha256:新摘要
```

## 28.3 执行前验证

```text
回执绑定摘要 = sha256:原摘要
当前提案摘要 = sha256:新摘要
结果 = 不一致
```

处理结果：

1. 拒绝使用旧回执；
2. 标记原回执对新提案无效；
3. 展示新增人员和 38444.00 差额；
4. 对新提案重新路由和审批；
5. 不产生付款效果。

# 31. 与其他工程模式的组合

审批门可与以下模式组合：

- 证据链：为审批卡提供可验证事实；
- 层级委派：确定父目标、局部责任和审批权限；
- 扇出聚合：对批量对象并行核验后形成单一提案；
- 对抗评审：对高风险提案提供独立异议；
- 交接链：把提案、版本、责任和证据交给审批者与执行器；
- 限额与爆炸半径：限制一次合法动作最多影响的金额、对象和次数；
- 幂等执行：防止重试放大外部效果；
- 补偿事务：在部分失败后恢复或限制损失；
- 工作流可观测性探针：补全事件、指标、缺口和漂移证据。

组合时，审批门仍是行动权的最终路由点；其他模式不得隐式扩大回执范围。

---

# 32. 总结

审批门不是一个“弹出确认框”的界面模式，而是一套完整的治理执行协议。

它要求代理先把动作做到可审，将对象、差异、证据、影响和可逆性整理清楚；要求审批者只对自己有权限且能够理解的范围作出决定；要求系统把这一决定绑定到具体提案、具体策略、具体身份、具体时间和有限次数；要求执行器在真正改变外部世界前重新验证，并将实际效果写回可信账本。

执行流程可以独立运行；与工作流可观测性探针联动时，探针补全的是关联、证据、事件和诊断数据，而不是审批权。任何会改变动作语义的补全，都必须触发新提案和重新审批。
