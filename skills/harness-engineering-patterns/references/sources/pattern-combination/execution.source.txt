# 模式组合执行流程

## 1. 文档定位

本文件把“模式组合”整理为一套可直接落地、可按场景裁剪的通用执行流程。

它不是要求所有任务都依次经过“检索、生成、评审、执行”，也不是要求每项任务都覆盖感知、记忆、推理、行动、反思、协作、治理七类能力。它解决的是另一类问题：

- 一项任务需要哪些材料；
- 哪些步骤可以并行，哪些步骤必须等待；
- 哪些判断可以由模型灵活完成，哪些依赖必须由程序固定管理；
- 谁能够修改什么；
- 失败后回到哪里；
- 最终凭什么认定任务已经完成。

本流程可以独立运行，也可以与《模式组合_工作流可观测性探针_v0.1.md》交互运行。探针不是执行流程的必需依赖；它用于补齐和核对任务、状态、证据、权限、责任及验收数据。

---

## 2. 设计目标

### 2.1 核心目标

1. 从任务实际困难出发选择最少但足够的模式。
2. 把需要探索的部分留给 Agent，把明确依赖、权限和验收交给确定性机制。
3. 让每个步骤的输入、输出、等待条件、失败回退点和责任人可识别。
4. 让原始证据、压缩结果、生成结果和评审结论保持可追溯关系。
5. 让局部循环受任务级预算约束，避免嵌套循环失控。
6. 让审批、影响范围和调用前后检查直接约束真实动作。
7. 支持中断续做、重新规划、交接和人工接管。

### 2.2 非目标

本流程不负责：

- 强制指定模型、工具、平台、接口或部署方式；
- 把每次内部思考都固化成服务或接口；
- 把所有任务都改造成多 Agent 系统；
- 用模式名称代替业务规则；
- 用评审代替证据；
- 用审批代替范围控制或结果核验；
- 用日志数量代替可观测性。

## 3. 与 Hanerss Skill Framework 的对应关系

### 3.1 认知基座在本流程中的职责

| 认知项 | 本流程中的主要职责 |
|---|---|
| 感知 | 获取原文、日志、文件、系统状态、工具结果和当前环境信息 |
| 记忆 | 保存进度、证据、计划版本、排除项、动作结果和恢复点 |
| 推理 | 识别任务地形、形成假设、选择下一步、判断是否重新规划 |
| 行动 | 调用检索、代码、业务、配置、发布等工具并产生外部效果 |
| 反思 | 检查结果、发现偏差、触发修订、回退、重试或重新调查 |
| 协作 | 管理并行分支、层级委派、聚合、评审与角色交接 |
| 治理 | 管理审批、权限、作用范围、预算、审计和责任边界 |

### 3.2 拓扑基座在本流程中的职责

| 拓扑项 | 适用关系 |
|---|---|
| 链式 | 后一步依赖前一步的确定结果 |
| 路由 | 根据任务类型、证据、风险或状态选择不同路径 |
| 并行 | 多个相互独立的方向可以同时推进 |
| 编排 | 多节点存在依赖、状态、等待和恢复要求 |
| 循环 | 需要假设验证、修订、重试或自愈 |
| 层级 | 父任务需要拆成可验收的子责任并逐级收回 |

### 3.3 工程模式与 Skill 的关系

本文件描述的是可复用的工程模式执行结构。落地时可以：

1. 将本模式登记到工程模式注册表；
2. 挂载到一个或多个认知与拓扑坐标；
3. 针对具体业务节点裁剪；
4. 将高频场景包装成独立 Skill；
5. 为每个 Skill 配置专用工具、治理规则和评估用例。

## 4. 运行方式

### 4.1 独立运行

不接入工作流可观测性探针时，执行流程至少自行维护四类记录：

- 当前任务状态；
- 当前计划及版本；
- 关键证据及来源；
- 动作、结果和验收结论。

独立运行时允许采用简单文件、数据库记录、任务表或内存状态，但必须保证中断后能够判断：已经做了什么、依据是什么、下一步是什么、哪些动作已经产生外部效果。

### 4.2 与探针交互运行

接入探针后，执行流程额外执行以下动作：

1. 为任务、运行、节点、分支、尝试和证据分配稳定标识；
2. 在关键状态变化时发送事件；
3. 响应探针的数据补全请求；
4. 将探针发现视为待核对事实，不直接视为业务真相；
5. 只有治理规则明确授权时，探针提出的阻断建议才可以暂停真实动作。

### 4.3 普通程序优先

满足以下条件时，应优先使用普通程序或固定工作流，不必引入复杂模式组合：

- 输入结构稳定；
- 规则明确且可穷举；
- 步骤固定；
- 异常种类有限；
- 不需要开放式搜索；
- 不需要根据新证据改变调查方向；
- 不需要模型理解模糊业务表达；
- 固定程序已经能够稳定通过验收。

---

## 5. 输入契约

每次运行至少需要建立一份任务契约。

| 字段 | 必需 | 说明 |
|---|---:|---|
| 任务标识 | 是 | 全局稳定，不因重试或恢复而变化 |
| 任务目标 | 是 | 要解决的问题，不写成某个预设步骤 |
| 必需交付物 | 是 | 最终必须交出的结果及格式 |
| 验收条件 | 是 | 判定完成所需事实、测试、查询或人工确认 |
| 禁止事项 | 是 | 不得修改、不得访问、不得推断或不得发布的内容 |
| 允许范围 | 是 | 可读取、可修改、可调用和可影响的对象范围 |
| 风险等级 | 是 | 决定审批、隔离、人工接管和记录强度 |
| 可用材料 | 否 | 文档、日志、知识库、代码、配置和历史记录 |
| 可用工具 | 否 | 检索、执行、测试、写入、发布或通知工具 |
| 时间与费用预算 | 否 | 总预算及各分支、循环、工具的局部预算 |
| 恢复点 | 否 | 中断续做时使用的状态版本和已完成节点 |
| 探针配置 | 否 | 事件出口、补全策略、阻断策略和采样策略 |

### 5.1 任务契约示例

```yaml
任务标识: TASK_0001
任务目标: 比较三个地区的现行退货政策并形成有出处的说明
必需交付物:
  - 三地逐项比较表
  - 每项关键结论的原文位置
  - 冲突或缺失说明
验收条件:
  - 三个地区均有结果或明确缺失原因
  - 适用范围、期限、例外和生效时间均已覆盖
  - 每个关键结论可以回到原始材料
禁止事项:
  - 不把摘要当作唯一证据
  - 不在证据不足时补写确定性结论
允许范围:
  - 指定知识库
  - 指定公开站点
风险等级: 中
总尝试预算: 20
```

## 6. 输出契约

一次运行至少产生以下输出：

| 输出 | 说明 |
|---|---|
| 业务交付物 | 面向最终使用者的报告、代码、配置、结果或建议 |
| 证据包 | 支撑关键结论的原文、日志、测试、查询结果及定位信息 |
| 状态快照 | 最终状态、计划版本、已完成节点、未完成事项和恢复点 |
| 动作回执 | 实际调用了什么、影响了什么、返回了什么、是否核验 |
| 决策摘要 | 关键选择、替代方案、采用依据和影响范围 |
| 异常包 | 未解决问题、失败结果、已尝试方案和人工接管建议 |
| 验收记录 | 每项验收条件的通过、失败、豁免或待确认状态 |

不得仅返回“已完成”而不返回可验收结果。

## 7. 核心运行对象

| 对象 | 稳定标识 | 关键内容 |
|---|---|---|
| 任务 | task_id | 目标、边界、交付物、验收条件、风险 |
| 运行 | run_id | 一次端到端执行实例，可由同一任务产生多次运行 |
| 计划 | plan_id、plan_version | 节点、依赖、顺序、并行关系、修改原因 |
| 节点 | node_id | 输入、输出、责任、就绪条件、完成条件 |
| 分支 | branch_id | 并行或层级子任务的边界和回收状态 |
| 尝试 | attempt_id | 同一节点的一次执行或重试 |
| 证据 | evidence_id | 来源、位置、版本、时间、摘要、完整性 |
| 决策 | decision_id | 候选方案、采用结论、依据、影响 |
| 动作 | action_id | 工具、目标、参数、权限、前置条件、结果 |
| 评审 | review_id | 评审对象版本、标准、问题、结论和处理状态 |
| 审批 | approval_id | 被批准动作、对象、版本、范围、额度、有效期 |
| 交接 | handoff_id | 交付版本、接收者、剩余责任和恢复点 |
| 预算 | budget_id | 任务级、节点级、分支级和循环级额度 |

这些标识用于关联记录，不要求对应独立服务。

## 8. 状态机

### 8.1 任务状态

```text
待分析
  ↓
运行中
  ├─→ 等待资料 ─→ 运行中
  ├─→ 等待审批 ─→ 运行中
  ├─→ 需要重新规划 ─→ 运行中
  ├─→ 局部失败 ─→ 恢复或重新规划
  ├─→ 人工接管
  ├─→ 已终止
  └─→ 待验收 ─→ 已完成
```

### 8.2 状态规则

1. “等待审批”不是“执行失败”。
2. “工具返回成功”不是“业务完成”。
3. “局部失败”只有在仍有恢复路径和预算时才能回到运行中。
4. 计划、目标对象、权限范围或关键证据发生变化时，必须生成新版本。
5. 任何已产生外部效果的节点不得简单回到“未执行”；应记录补偿、撤销或保留状态。
6. 只有全部强制验收项通过，任务才能进入“已完成”。
7. 终止和人工接管必须输出当前状态、已产生效果、未完成事项和建议入口。

## 9. 通用执行流程

## 9.1 阶段一：建立任务边界

### 进入条件

收到业务目标或恢复请求。

### 执行动作

1. 识别目标、交付物、验收条件和禁止事项；
2. 区分事实缺失、方案不确定、动作风险和协作需求；
3. 明确可读、可写、可调用和可影响范围；
4. 标记必须由人作出的判断；
5. 建立任务标识、运行标识和初始状态版本。

### 退出条件

任务契约完整，且不存在会使后续设计失真的关键歧义。

### 失败回退

信息不足时进入“等待资料”，不得用默认假设替代关键边界。

---

## 9.2 阶段二：判断是否需要模式组合

按以下顺序判断：

1. 普通程序能否直接完成；
2. 单次模型调用能否在现有上下文中完成；
3. 是否存在独立分支，可以并行；
4. 是否需要根据新证据动态改变下一步；
5. 是否存在明确依赖，需要计划和调度；
6. 是否存在高风险写入，需要治理约束；
7. 是否存在角色、上下文或责任变化，需要交接。

### 最小化原则

只增加能够解决明确困难的模式。若删去某一层后，质量、可恢复性、安全性或成本没有明显变差，该层应被视为可撤销候选。

---

## 9.3 阶段三：绘制任务地形

将任务拆成四条线：

| 检查线 | 要回答的问题 |
|---|---|
| 任务线 | 要完成哪些交付物，哪些分支缺失会导致整体不完整 |
| 状态线 | 哪些步骤已经完成，哪些正在等待，失败后从哪里恢复 |
| 权限线 | 谁能读取、修改、批准、发布和撤销，范围是否发生变化 |
| 证据线 | 每个关键结论或动作依据来自哪里，是否能回到原始材料 |

同时标注：

- 可并行单元；
- 依赖关系；
- 动态探索区；
- 确定执行区；
- 风险边界；
- 验收位置；
- 回退位置；
- 共享状态。

---

## 9.4 阶段四：选择拓扑

### 链式

用于严格前后依赖。后一步必须声明使用前一步的哪个版本和哪项结果。

### 路由

用于根据证据、风险、任务类型或当前状态选择路径。路由必须保留：候选路径、选择依据、未选路径和重新路由条件。

### 并行

用于相互独立的调查、计算或评审。并行前必须定义：

- 分支边界；
- 每个分支的同构问题；
- 共用输入；
- 输出契约；
- 聚合条件；
- 缺失分支处理方式。

### 编排

用于存在依赖、状态、等待、恢复、重排和多工具调用的任务。调度器只推进已经满足依赖和权限的节点。

### 循环

用于调查、修订、测试或自愈。每个循环必须有：

- 新信息目标；
- 最大次数；
- 最大时间或费用；
- 成功条件；
- 无进展条件；
- 退出和接管条件。

### 层级

用于父任务向子任务委派可验收责任。父任务保留整体目标，子任务只承担边界清晰的局部责任。

---

## 9.5 阶段五：选择工程模式并定义组合关系

模式之间主要存在六类关系。

| 关系 | 定义 | 必须检查 |
|---|---|---|
| 前后供料 | 前一步为后一步提供材料 | 后一步是否拿到了真正需要的内容，而非仅格式合法 |
| 内部嵌套 | 一个模式运行在另一个模式内部 | 内层循环和分支是否受外层预算、目标和完成条件约束 |
| 执行约束 | 某些条件作用于真实动作 | 审批、范围和前后检查是否绑定到同一动作版本 |
| 共享能力 | 多个步骤读取或更新同一状态 | 是否存在单一可信来源，是否有版本冲突 |
| 责任交接 | 工作从一个角色或上下文转给另一个 | 交付版本、接收责任、依据和恢复点是否完整 |
| 反馈回路 | 后一步结果影响前面判断 | 回退位置是否正确，是否会沿错误假设无限修补 |

每条连接都应声明：

```yaml
连接标识: EDGE_0001
上游节点: NODE_A
下游节点: NODE_B
传递对象:
  - 证据包
  - 摘要
  - 计划版本
所需版本: 指定版本或最新已批准版本
完整性要求: 必填字段列表
失败处理: 补取材料或退回上游
权限影响: 是否需要重新批准
```

---

## 9.6 阶段六：建立计划与节点契约

每个节点至少包含：

```yaml
节点标识: NODE_0001
节点目标: 当前节点要解决的问题
责任角色: 执行者或接收者
输入引用: 上游输出、证据或状态版本
就绪条件:
  - 必需依赖已完成
  - 必需权限有效
执行方式: 固定程序、模型判断、工具调用或人工处理
输出契约: 必须返回的字段和工件
完成条件: 可核验条件
失败分类:
  - 可局部恢复
  - 需要重新调查
  - 需要重新规划
  - 需要人工接管
预算: 次数、时间、费用或影响上限
下一节点: 成功、失败、等待和回退路径
```

节点不能只写“处理数据”“检查结果”这类不可验收描述。

---

## 9.7 阶段七：调度和执行

执行器按以下顺序工作：

1. 读取最新任务状态和计划版本；
2. 找出依赖已经满足的候选节点；
3. 过滤权限、预算和风险条件不满足的节点；
4. 根据拓扑选择串行、并行、路由或委派；
5. 为每次执行建立尝试标识；
6. 获取材料或调用工具；
7. 保存原始结果和必要证据；
8. 形成决策摘要或业务输出；
9. 检查局部完成条件；
10. 更新共享状态；
11. 选择继续、等待、回退、重新规划或终止。

### 参考伪代码

```text
初始化任务状态

当任务未进入终态时：
    读取最新状态、计划、权限和预算
    候选节点 = 找出依赖已满足的节点
    可执行节点 = 过滤未授权、超预算和风险不满足的节点

    如果没有可执行节点：
        判断是等待、计划缺陷、状态冲突还是任务结束

    对可执行节点按拓扑调度：
        获取输入和证据
        执行判断或动作
        保存原始结果
        检查局部完成条件
        更新状态和预算

        如果局部失败：
            判断局部恢复、重新调查、重新规划或人工接管

    检查全局验收条件

输出业务结果、证据包、状态快照和验收记录
```

---

## 9.8 阶段八：处理循环、修订和重新规划

### 局部自愈

只有满足以下条件时才允许局部重试：

- 原目标和主要假设仍然成立；
- 失败属于局部实现错误；
- 新尝试会引入不同修改或不同检查；
- 仍有节点级和任务级预算；
- 不需要扩大权限或作用范围。

### 返回调查

出现以下情况时，应回到调查或假设验证：

- 新结果直接否定原假设；
- 继续修补只能掩盖症状；
- 同一错误在不同实现中重复出现；
- 测试通过但原业务行为被破坏；
- 关键证据之间发生冲突。

### 重新规划

出现以下情况时，应生成新计划版本：

- 节点新增、删除或依赖变化；
- 目标对象变化；
- 外部条件变化；
- 所需工具或角色变化；
- 计划无法满足验收条件；
- 任务范围发生变化。

计划变化涉及已批准对象、版本、额度或作用范围时，原审批不得自动沿用。

---

## 9.9 阶段九：治理真实动作

任何会写入、发布、付款、删除、授权、通知或改变外部系统状态的动作，都应经过动作契约。

### 动作契约

```yaml
动作标识: ACTION_0001
动作类型: 导入配置
目标对象: 企业甲的新部门薪资组
输入版本: CONFIG_V3
前置条件:
  - 备份成功
  - 差异已确认
  - 审批有效
允许范围:
  - 仅目标部门
  - 最多一套薪资组
禁止范围:
  - 不修改旧部门
  - 不覆盖其他模板
审批引用: APPROVAL_0001
调用后核验:
  - 查询目标薪资组
  - 比较关键字段
补偿方式: 删除新建对象或恢复备份
```

### 三层约束

1. **审批门**：决定这项具体动作能否开始。
2. **爆炸半径控制**：限制动作最多影响哪些对象、多少资源和多长时间。
3. **调用前后护栏**：调用前检查条件，调用后核对实际结果。

三者可以由同一业务入口实现，但不能互相替代。

---

## 9.10 阶段十：聚合与验收

### 聚合规则

并行或层级任务聚合时必须检查：

- 必需分支是否全部返回；
- 输出是否符合相同契约；
- 是否存在重复、冲突或缺失；
- 每个结论是否保留证据引用；
- 不同分支是否使用相同时间和版本口径；
- 缺失分支是否被明确标注，而不是静默忽略。

### 五道验收门

| 验收门 | 核心问题 |
|---|---|
| 任务验收 | 必需交付物是否齐全，任务是否走偏 |
| 证据验收 | 关键结论是否有有效出处，能否回到原文 |
| 状态验收 | 计划、节点和外部效果是否一致，能否恢复 |
| 权限验收 | 实际动作是否在批准对象、版本和范围内 |
| 结果验收 | 测试、查询或业务检查是否证明事情真正办成 |

只有全部强制验收项通过，才能宣告完成。

---

## 9.11 阶段十一：交接、归档和复用

### 交接条件

只有当执行角色、工具权限、责任或上下文发生变化时，才需要显式交接。普通函数调用不必包装成 Agent 交接。

### 交接包

```yaml
交接标识: HANDOFF_0001
任务标识: TASK_0001
交付版本: ARTIFACT_V4
当前状态: 等待财务核对
已完成:
  - 创建备份
  - 导入目标配置
未完成:
  - 核对补贴规则
关键证据:
  - 查询结果引用
  - 差异报告引用
接收责任: 核对并决定是否放行
恢复点: NODE_VERIFY_02
失败后返回: NODE_IMPORT_01 或人工接管
```

### 归档内容

- 最终交付物；
- 原始证据引用；
- 计划及版本变化；
- 关键决策摘要；
- 动作和结果；
- 评审、审批与验收记录；
- 有复用价值的失败案例；
- 可沉淀为 Skill 的稳定步骤。

## 10. 场景选型表

| 场景特征 | 推荐拓扑 | 主要模式组合 | 不宜增加的复杂度 |
|---|---|---|---|
| 短输入、规则明确、一次处理可完成 | 链式或普通程序 | 直接处理、简单验收 | 多 Agent、层级委派、复杂状态机 |
| 多个独立资料方向，需要统一比较 | 并行＋链式 | 扇出聚合、检索增强、渐进发现、生成评审 | 让多个分支共同写同一结果 |
| 调查方向取决于新证据 | 循环＋路由 | 迭代假设验证、渐进发现、进度追踪 | 预先固定全部排查步骤 |
| 原因明确后存在多项依赖改动 | 编排＋链式 | 规划执行、工具调度、测试、局部自愈 | 继续让模型随意跨步调用工具 |
| 模糊业务要求需要转成严格操作 | 路由＋编排 | 方案探索、规划执行、审批门、范围控制、前后护栏 | 把业务依赖仅写在提示词中 |
| 多角色、不同权限和责任分工 | 层级或并行 | 层级委派、交接链、对抗评审 | 把所有角色共享成同一无边界上下文 |
| 长任务可能暂停或恢复 | 编排＋记忆 | 进度追踪、失败日志、状态版本、恢复点 | 只保留聊天历史而不保留任务状态 |
| 高风险外部写入 | 链式＋治理约束 | 审批门、爆炸半径控制、前后护栏、渐进承诺 | 以模型自信或评审通过替代权限控制 |

## 11. 三类通用场景适配器

## 11.1 资料研究适配器

### 适用条件

- 材料分散；
- 多个独立方向可以并行；
- 需要比较；
- 结论必须有出处；
- 摘要可能遗漏例外或限定条件。

### 推荐结构

```text
定义统一调查问题
        ↓
按方向扇出调查
        ↓
各分支检索或渐进发现
        ↓
返回结论＋原文位置＋缺失项
        ↓
聚合和口径检查
        ↓
生成说明
        ↓
评审按需回取原文
        ↓
修订与验收
```

### 强制规则

1. 分支必须返回原始来源位置，不只返回摘要。
2. 语义压缩不能替代原文证据。
3. 评审必须拥有独立回取原文的路径。
4. 必需分支缺失时，聚合器不得静默完成。
5. 证据冲突先核对版本、日期、适用范围和生效条件，再决定是否需要多角色评审。

### 可选增强

当调查方向本身也需动态拆分时，可增加层级委派；当专业立场确实不同且证据已经齐全时，可增加对抗评审。

---

## 11.2 故障排查适配器

### 适用条件

- 初始原因不明确；
- 每次检查结果会改变下一步；
- 需要修改、测试和回归；
- 可能中断续做；
- 局部失败和原假设错误必须区分。

### 推荐结构

```text
收集症状与变更范围
        ↓
提出候选原因
        ↓
选择能区分候选原因的检查
        ↓
读取结果并更新假设
        ↺ 证据不足则继续调查
        ↓ 原因明确
形成修复计划与依赖
        ↓
执行修改和测试
        ↺ 局部错误则限次自愈
        ↖ 假设被推翻则返回调查
        ↓
代码或配置评审
        ↓
受保护动作审批
        ↓
回归与验收
```

### 强制规则

1. 每次检查应说明它要区分哪些候选原因。
2. 检查结果否定原假设时，不得继续沿原方向无限修补。
3. 修改前保存受影响范围和恢复点。
4. 测试通过不代表业务行为正确，仍需核对原要求和权限约束。
5. 超过预算后停止自动尝试，交付改动、失败结果和已排除原因。

---

## 11.3 业务办理适配器

### 适用条件

- 输入是模糊或自然语言业务要求；
- 需要选择模板、方案或参数；
- 实际执行步骤有严格依赖；
- 会改变业务系统；
- 需要审批、范围限制和结果核验。

### 推荐结构

```text
理解业务差异并寻找候选方案
        ↓
确认目标对象与方案版本
        ↓
生成有依赖的执行计划
        ↓
审批具体动作
        ↓
调度器检查依赖、权限和当前状态
        ↓
调用前护栏
        ↓
执行写入
        ↓
调用后查询与差异核验
        ↓
必要时补偿、重新规划或交接
        ↓
终态验收
```

### 强制规则

1. 计划轮到某一步，不代表该步已经获得权限。
2. 批准一个对象，不得扩展到其他对象。
3. 接口返回成功后必须查询真实业务状态。
4. 等待审批和执行失败使用不同状态。
5. 自愈循环不得通过反复改参数绕过人工审批。
6. 自动化范围只能依据稳定运行证据逐步扩大。

---

## 12. 预算与停止条件

## 12.1 分层预算

预算至少分为：

- 任务级总预算；
- 分支级预算；
- 节点级预算；
- 循环级预算；
- 工具级调用上限；
- 外部影响上限。

一次动作实际可用额度取以下最小值：

```text
实际可用额度 = 任务剩余额度、分支剩余额度、节点剩余额度、循环剩余额度中的最小值
```

不得因为外层允许三轮、内层允许五轮，就默认允许十五次无约束尝试。

## 12.2 必须停止的情况

出现以下任一条件时，自动流程应停止、等待或转人工：

- 连续多轮没有新增证据或信息增益；
- 重复调用相同工具和参数；
- 已超过时间、费用、次数或影响范围；
- 关键权限缺失或审批过期；
- 目标对象、版本或范围与批准内容不一致；
- 证据冲突无法消解；
- 状态版本冲突；
- 补偿路径不可用；
- 验收条件已不可能满足；
- 风险等级上升到当前自治级别之外。

---

## 13. 失败分类与恢复矩阵

| 失败类型 | 判定特征 | 处理方式 | 返回位置 |
|---|---|---|---|
| 材料缺失 | 必需事实不存在或不可访问 | 请求补充、扩大合法检索或明确缺失 | 感知节点 |
| 证据冲突 | 来源在版本、日期、范围上不一致 | 核对元数据，必要时增加专业评审 | 证据核对节点 |
| 压缩丢失 | 摘要遗漏例外、条件或否定信息 | 回取原文，重做摘要并标记差异 | 压缩节点 |
| 假设被否定 | 检查结果与原解释相反 | 更新候选原因，返回调查 | 假设节点 |
| 局部实现错误 | 原目标成立，仅实现或参数错误 | 限次自愈并重新测试 | 当前动作节点 |
| 计划失效 | 新发现导致节点或依赖不再合理 | 生成新计划版本 | 规划节点 |
| 等待审批 | 动作正确但尚未获准 | 保存状态并等待，不计为失败重试 | 审批节点 |
| 审批失配 | 对象、版本、范围或有效期不一致 | 停止动作并重新申请 | 治理节点 |
| 部分成功 | 外部系统只完成部分写入 | 查询实际状态，补偿或续做 | 动作核验节点 |
| 状态冲突 | 多方更新了不同版本 | 冻结写入，选择可信版本并合并 | 状态恢复节点 |
| 预算耗尽 | 次数、时间、费用或影响到上限 | 输出异常包并人工接管 | 当前安全点 |
| 验收失败 | 动作完成但结果未满足业务条件 | 判断修订、补偿或重新规划 | 验收相关节点 |

---

## 14. 共享状态和版本规则

1. 任务状态只能有一个权威来源。
2. 计划、工件、证据包、配置和评审对象必须带版本。
3. 任何节点读取状态时记录读取版本；写回时检查版本是否仍有效。
4. 并行分支不得直接覆盖共享结果，应提交局部工件，由聚合器合并。
5. 计划版本变化不自动改变已经批准的动作版本。
6. 证据更新后，应标记受影响的结论、评审和后续动作。
7. 删除或覆盖状态前，必须确认是否存在已产生外部效果的动作。

## 15. 与工作流可观测性探针的交互契约

## 15.1 最小关联字段

执行流程向探针提供以下稳定关联字段：

```yaml
trace_id: 一条端到端链路标识
run_id: 一次运行标识
task_id: 任务标识
plan_id: 计划标识
plan_version: 计划版本
node_id: 当前节点
parent_node_id: 父节点
branch_id: 分支标识
attempt_id: 尝试标识
actor_id: 执行主体
artifact_version: 当前工件版本
```

## 15.2 交互顺序

```text
执行流程发送状态、证据、决策、动作和验收事件
                ↓
探针重建链路并检测缺口
                ↓
探针发送数据补全请求或异常发现
                ↓
执行流程返回快照、证据引用或不可获取原因
                ↓
探针更新判断并生成报告
                ↓
若治理策略明确允许，异常发现可触发暂停、复核或重新审批
```

## 15.3 数据补全请求

执行流程收到探针的数据补全请求后：

1. 核对请求是否属于当前任务和允许范围；
2. 优先返回已有原始记录或引用；
3. 不得为满足完整率而编造缺失事实；
4. 无法补充时返回“不可获得”及原因；
5. 补充数据不得悄悄改变业务状态；
6. 补充结果应关联原请求标识。

## 15.4 控制边界

默认情况下，探针只能观察、计算、报告和请求补数，不能：

- 改写任务目标；
- 修改计划；
- 伪造证据；
- 执行业务动作；
- 自行批准；
- 直接扩大或缩小权限。

只有显式治理规则授权时，探针发现才能成为暂停或阻断条件。

## 16. 最小可用实现

一个不依赖特定平台的最小实现至少包含：

1. 任务契约解析器；
2. 计划与依赖表示；
3. 节点调度器；
4. 状态存储；
5. 证据台账；
6. 动作调用入口；
7. 治理检查器；
8. 验收检查器；
9. 失败分类和恢复路由；
10. 可选事件发送适配器。

这些能力可以在单个程序内实现，不要求拆成多个 Agent、服务或进程。

## 18. 评估用例

### 用例一：短任务不过度设计

输入只有三份短文件，单次模型调用即可完整比较。

预期：选择简单链式处理，不启动多分支和层级委派；仍保留关键原文引用。

### 用例二：并行研究缺少一个分支

三个地区只返回两个地区的结果。

预期：聚合器标记缺失分支，不能把任务标记为完成。

### 用例三：摘要遗漏例外

原文包含“定制商品除外”，摘要漏掉该信息。

预期：评审能够通过原文回取路径发现问题并触发修订。

### 用例四：故障排查假设被推翻

原先怀疑超时，日志显示请求快速返回但字段缺失。

预期：路由转向响应格式和调用方，不继续修改超时参数。

### 用例五：修复循环失控

外层调查三轮，内层修复五轮。

预期：总尝试数受任务级预算限制，不自动扩张为十五次。

### 用例六：审批范围不一致

审批只允许修改一个部门，执行计划新增了第二个部门。

预期：原审批失效，写入被停止并要求重新审批。

### 用例七：接口返回成功但业务未生效

导入接口返回成功，查询目标对象发现仍是旧配置。

预期：任务进入验收失败或部分成功，不得宣告完成。

### 用例八：中断后恢复

任务在等待审批时中断。

预期：恢复后读取同一计划版本、审批状态和已完成动作，不重复执行备份或导入。

## 19. 常见反模式

1. 按模式清单堆组件，却说不清每一层解决什么问题。
2. 把所有任务固定成“检索、生成、评审、执行”。
3. 将摘要作为评审的唯一材料，丢失原始证据路径。
4. 让多个并行执行者同时修改同一工件，却没有分区和冲突策略。
5. 把业务依赖只写进提示词，不由任务图或程序检查。
6. 让每个局部循环独立决定继续，缺少任务级总预算。
7. 将“等待审批”计为失败并自动重试。
8. 把审批、范围限制和结果核验当作同一件事。
9. 只保存聊天文本，不保存任务状态、计划版本和外部效果。
10. 评审对象没有版本，修订后仍沿用旧评审结论。
11. 工具成功即宣告完成，没有业务查询或验收。
12. 探针缺数时由执行流程补写推测值，而不是返回不可获得。

## 20. 完成定义

本流程的完成定义为：

```text
必需交付物齐全
且关键结论可追溯
且真实动作在授权范围内
且外部结果已经核验
且共享状态与实际效果一致
且未解决问题已显式说明
且后续责任已有归属
```

任何一项强制条件不满足，都不得用“流程已跑完”替代“任务已完成”。
